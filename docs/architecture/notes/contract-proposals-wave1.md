## A. До роста графа (номер узла > 63, контент MVP)

### A1. Формат `id` узла и раскладка файлов
- **Проблема.** [Факт: `common.schema.json` `nodeId` = `^s[0-9]+[.](fnd|…|app)[.][a-z0-9_]+$`; `NodeTable.Raw.cs` проверяет, что сегмент типа совпадает с полем `type`; поля `sector` нет, сектор живёт только в префиксе и ничем не проверяется.] Каталог секторов не зафиксирован (RR-0008: варианты первой ступени V1–V3, «число секторов»), каталог дисциплин (~34) — тоже. Сектор в `id` делает идентичность зависимой от классификации: смена каталога переименует узлы. А `id` — ключ ссылок модов (ADR-0010) и строковый ID сохранения (ADR-0005, ADR-0013 п. 7).
- **Варианты.** (а) Как сейчас: `<sector>.<type>.<name>`. Плюс — ничего не трогать; минус — переименования при смене каталога секторов. (б) Чистое имя + поля `type`, `sector`. Плюс — идентичность без классификации; минус — коллизии имён разных типов (`turbojet` как ENG и APP), в списках `requires` не виден тип. (в) **`<type>.<name>`**, сектор не хранится в узле, а выводится из каталога дисциплин (`discipline → sector`).
- **Решение [Предл., выбрано (в)].** Тип по грамматике RR-0008 устойчив: смена типа — это другое понятие, то есть новый узел. Сектор — производная каталога. Текст для RR-0008 §«Формат» и схемы:
  > `id` узла — `<type>.<name>`, `type` ∈ {`fnd`, `prn`, `eng`, `cmp`, `prc`, `app`} совпадает с полем `type` (громкая ошибка загрузки), `name` — `[a-z0-9_]+`, уникален в пределах типа. Сектор узла — `sector(discipline)` из каталога дисциплин; в `id` и в узле его нет. `id` после публикации не меняется; переименование — новый узел + `delete` старого (ADR-0010).
  Схема: `nodeId` = `^(fnd|prn|eng|cmp|prc|app)[.][a-z0-9_]+$`.
- **Файлы [Предл., принимаю позицию RR-0008].** `mods/core/knowledge/<discipline>.yaml`, один файл на дисциплину (~34 файла по ~60 узлов при 2000). В моде `core` у каждого `define` поле `discipline` равно имени файла — громкая ошибка загрузчика; файлы `override`/`patch` других модов не ограничены. Загрузчик собирает все `kind: node` в порядке манифеста; строки графа упорядочены по `number`, поэтому порядок файлов на результат не влияет. Прежнее предложение note «файл на макросектор» снято: дисциплина — обязательное поле узла и единица `K_d`, сектор — нет.
- **Алиасы.** Сейчас не нужны: сохранений игрока нет (ADR-0013), сторонних модов нет. В ADR-0010 механизма alias/deprecate нет [Факт: ADR-0010 «Операции … define, override, patch, delete»]. Когда появится первое сохранение игрока или внешний мод, переименование потребует `aliases: [old_id]` в узле (загрузчик разрешает ссылки, предупреждение) — это расширение ADR-0010, новый ADR (gate).
- **Детерминизм и хеши.** RNG и строки графа ключуются `number`, не `id`. `data_hash` меняется (другой текст данных); state-хеши и траектории — нет [Предп.: проверить, что нигде нет сортировки по строке `id`; тест — golden state-хеши до и после переименования равны]. Сохранения: нет.
- **Цена.** ~630 вхождений в 30 файлах (данные `mods/core`, тесты `Core.Tests/Data`, спека среза, CSV `docs/research/data/jet-slice`, пример §6 контракта). Механическая замена одним скриптом; контракт — erratum (пример §6 «`s6.prc.precision_blade_forging`»).
- **Проверка.** Схемный тест паттерна; тест загрузчика «тип в `id` ≠ `type`» и «`discipline` ≠ имя файла»; golden state-хеши без изменений.
- **Уровень:** light (формат внутри ADR-0010). **Исполнители:** developer (схема, загрузчик, данные), simulation-engineer (спека), research-scientist (RR-0008).

### A2. Ключ RNG знания
- **Проблема.** [Факт: `KnowledgeRng.MaxNodeNumber = 63`, `entity = actor·64 + node`; ещё одно место — `KnowledgeSchedule`: `Delta = new int[actorCount * 64]`, индекс `actor * 64 + graph.Number[r]`.] Номер узла > 63 не загрузится.
- **Текст** (спека среза §9.1, контракт не затрагивается): `entity = actor·2¹⁶ + number`, `1 ≤ number ≤ 65 535`, `0 ≤ actor ≤ 32 766` (`int`, `checked`). `number = 0` — за L_K. `KnowledgeSchedule.Delta` размером `actorCount·(maxNumber + 1)` по фактическому графу, а не `·2¹⁶` (иначе 30·65 536 `int` ≈ 7,9 МБ).
- **Детерминизм.** L1/L2 сохраняются: ключ — чистая функция стабильных номеров (ADR-0004). У актора 0 выборки те же, у прочих — другие → все golden-хеши со знанием и эталон EXP-0002 меняются один раз (причина «RNG key widening»). Сохранений нет → миграции нет.
- **Варианты срока (вопрос владельцу, RR-0008 Q6):** (1) **до финального прогона EXP-0002**: эталон снимается один раз на окончательном ключе; цена — переснять предварительные golden сейчас; (2) **сразу после EXP-0002** с переснятием эталона: выводы EXP-0002 статистически не меняются (то же распределение), но артефакты EXP-0002 побитно не воспроизводятся новой сборкой — нужна пометка в эталоне; (3) не менять до MVP — блокирует любой контент с `number > 63`. Рекомендация: (1), если финальный прогон EXP-0002 ещё не начат.
- **Альтернатива** «актор в счётчике `n`» отклонена: `n` занят выборками L_K.
- **Проверка.** Тест ADR-0004 «перестановка строк не меняет выборки» на новом ключе; тест загрузки номера 65 535 и отказа 65 536.
- **Уровень:** light; срок — владелец.

### A3. Плотный `number → row`
- **Проблема.** [Факт: note rr-0008 п. 6] `KnowledgeGraph.RowOf`, `IndustryLayout.RowOf` — линейный поиск в циклах `WhyNotAnalyzer` и адаптеров Session; при 2000 узлах O(n²) на вызов `why_not`, а `why_not` входит в тик (контракт §11).
- **Текст.** `int[] rowOfNumber` размером `maxNumber + 1` (−1 — нет узла), строится в `Create`. Поведение и хеши не меняются.
- **Проверка.** Архитектурный тест «нет линейного `RowOf` в compute»; бенчмарк `why_not` на синтетическом графе 2000.
- **Уровень:** light.

## B. До формата сохранения v1

### B1. Реестр кодов отказа команд
- **Проблема.** Контракт называет коды только для `cancel_design`, `retire_cohort`, `sell_cohort`, `take_licence`, `SERIES_GATE` и `DESIGN_CAPACITY` (§3.1, §4.4, §5). [Факт: `IProductsInputs.CommandRejection`] код уже различает `NoBureau`, `SlotUnavailable`, `PlatformThreshold`, `BadRequirement`, `BadDerive`, `LineTransferred`. Счётчик отказов по коду — колонки состояния (§3.1 r6), то есть набор кодов — часть раскладки сохранения.
- **Найденная дыра.** [Факт: `ProductsSystem.cs` ~1097: `_inputs.StartSeries(a, d, t)` опрашивается только для проектов в стадии О или В снимка] `start_series` для проекта в П, С или «снят» не отклоняется, а молча не читается: команда есть в журнале, отказа нет. Это расходится с инвариантом «каждая команда либо применена, либо отклонена с кодом».
- **Текст для §5** (новый блок «Коды отказа»):
  > `compose_design`: `DESIGN_CAPACITY` (нет свободной строки проекта), `NO_BUREAU` (нет свободного КБ; UI «КБ занято»), `SLOT_UNAVAILABLE` (альтернатива ∉ `avail`, слот вне диапазона, запрет `max_eng_gen`), `PLATFORM_THRESHOLD`, `BAD_REQUIREMENT`. `derive`: те же + `BAD_DERIVE`. `start_series`: `BAD_SERIES_STAGE` (стадия снимка не О и не В), `SERIES_GATE`, `LINE_TRANSFERRED`. `cancel_design`: `BAD_CANCEL`. Парк и лицензия — как в §4.4f, §5. Каждая команда журнала либо применяется, либо отклоняется ровно одним кодом; первый непройденный шаг валидатора задаёт код.
- **Детерминизм и хеши.** `BAD_SERIES_STAGE` — новая колонка счётчика → state-хеш и `save_format_version` +1 (по #117). Траектории не меняются (команда и раньше не действовала).
- **Проверка.** Свойство-тест «Σ применённых + Σ отказов = Σ команд журнала» по каждому типу команды; фикстура `start_series` в П.
- **Уровень:** light (коды существуют, смысл не меняется; новая колонка — erratum в духе F33 (а)).

### B2. `max_designs` и ёмкость КБ
- **Проблема.** [Факт: контракт §3.1, G4-8; спека §3.3 `max_designs` = 12 [Предп.]] строки проектов не переиспользуются, снятый проект слот не возвращает. За 1945–2100 актор с 12 строками упрётся в `DESIGN_CAPACITY` задолго до конца игры, и игрок не видит причины (RR-0007 §11.7). Одновременно RR-0012 §3.1, §3.4 вводит игровую ёмкость — число параллельных проектов по ступени института. Сейчас обе вещи смешаны: техническая ёмкость таблицы выглядит как игровое ограничение.
- **Предложение.** Разделить:
  1. **Хранение (light):** таблица проектов растёт, строки только добавляются, `design_id = (actor, seq)` никогда не переиспользуется; `max_designs` — начальная ёмкость буфера, а не предел. `DESIGN_CAPACITY` как игровой отказ исчезает. [Предп.] таблицы Kernel поддерживают рост строк — проверить (developer); если нет, ёмкость берётся с запасом по горизонту сценария (оценка: проектов на актора за 155 лет ≤ 256) с громкой ошибкой при переполнении.
  2. **Ёмкость КБ (gate, RR-0012):** `NO_BUREAU` обобщается в `BUREAU_CAPACITY`: у института ступени k не больше `tiers[k].projects` проектов в П/О. Срез — частный случай: 2 КБ, ёмкость 1, поведение и golden прежние.
- **Детерминизм и сохранение.** П. 1 меняет раскладку проектов (ADR-0013 п. 7) — это нужно сделать до save v1, иначе потребуется миграция раскладки. Golden среза не меняются, если ни один прогон не достигал `DESIGN_CAPACITY` [Предп.; проверить счётчик отказов на golden-прогонах].
- **Уровень:** п. 1 — light; п. 2 — gate (механика волны 2, civilization-systems-designer, владелец).

### B3. Отправитель команды и `Bureau.initiative`
- **Проблема.** RR-0012 §3.3: институт сам берёт ТТЗ по приоритету и ёмкости. Это не функция слоя изделия, а правило ИИ, которое подаёт ту же команду `compose_design` через тот же валидатор.
- **Текст для §5:** «Каждая команда журнала несёт `sender` ∈ {`player`, `actor_ai`, `institution(id)`}. Слои не различают отправителя, кроме инвариантов журнала (`force` — только `player`). `Bureau.initiative` — правило-источник команд, а не вход слоя.»
- **Сохранение.** Поле журнала команд; добавить до save v1 (в срезе пишется только `player`/`actor_ai`). Хеши состояния не меняются.
- **Уровень:** light (резерв); содержание правила инициативы — gate вместе с B2 п. 2.

### B4. `perf` — не состояние
- **Проблема.** RR-0007 ОВ-12: хранить `perf[]` вектором с весами свёртки из данных. [Факт: `DesignRules.Perf(layout, alts)`] `perf` уже чистая функция состава проекта и данных класса; в колонках его нет.
- **Текст для §3.1:** «`perf(d)` и будущий вектор `perf_k(d)` в состоянии не хранятся: это функции `alts(d)` и данных класса. Свёртка `perf(d) = Σ_k w_k·perf_k(d)`, веса `perf_fold_w[class][k]` — данные мода (`data_hash`), сумма в порядке `k` ↑, каждое `·` — одна операция `Fx6` (§4.0).»
- **Хеши.** Срез — одна ось, `w = 1`: без изменений. Вектор (RR-0016, бой) — новые данные → `data_hash`.
- **Уровень:** light (принцип записать сейчас, чтобы никто не добавил колонку `perf`); вектор — gate вместе с RR-0016.

### B5. Когорта: `wear`, `mothballed`
- **`wear`** [Предл.: не вводить]. Возраст когорты — функция `t` и года выпуска; износа от использования без боя и налёта нет (RR-0016 — FUTURE). Если понадобится старение — чистая функция возраста, не запас. Запас износа — только вместе с моделью использования (gate).
- **`active`/`mothballed`** [Предл.]: не флаг состояния когорты, а счётчик `reserve_count[cohort]` (`Fx6` ≥ 0, `count` — действующие), потому что `mothball_cohort(design, n)` действует на `n` единиц, как `retire_cohort`. Колонка добавляется вместе с механикой (FUTURE); ADR-0013 п. 7 (миграция — цепочка чистых функций) покрывает добавление колонки со значением 0, заранее резервировать её не нужно.
- **Уровень:** light (записать в §13 контракта как закрытое).

## C. Позже

### C1. Звено «форсаж → потери парка»
- **Проблема.** RR-0007 §11.7: путь «серия форсирована → `X > 0` → `loss_acc` → потери» — 4 шага; звена в `why_not` нет.
- **Текст для §6 п. 3:** «(PRODUCT) `FORCED_DEFECTS`: проект с `series_forced` и `X > 0` (§4.4c); `have = X`, `need = 0`, `eta_months` — месяцы до `X = 0` при текущем темпе выявления, `yield_if_fixed` — текущий. Рычаги: `reassign_workforce`, затем (ECONOMY) `retire_cohort`.»
- **Хеши.** ИИ `force` не подаёт (#94) → у проектов ИИ звена нет → траектории main без изменений; меняется выход `why_not` в фикстурах плеча `FORCE`. Требование: ни один предикат ИИ не читает `FORCED_DEFECTS`.
- **Уровень:** light; слова — game-designer.

### C2. Рычаг при дефиците сплава
- **Проблема.** `line_bind = ALLOY` (§3.1) не ведёт к рычагу; состав после создания не меняется (#82).
- **Текст для таблицы рычагов §6:** «`simplified_variant` — также PRODUCT «дефицит CMP» при `line_bind = ALLOY`, если в `avail` есть альтернатива слота `hot_section` с меньшим `alloy_kg`; `subject_id` = слот; исполнение — `derive(d, {hot_section → alt})` (#90).»
- **Хеши.** Без изменений, если предикаты ИИ этот рычаг не читают (как F33); `derive` у ИИ — только плечо `DERIV`.
- **Уровень:** light.

### C3. Причина снятия проекта

### C4. Атрибуция `D0` по слотам
- **Предложение.** Доли источников `share_s(d) ∝ novelty_s·complexity_s` (RR-0009 §4.5), интеграция — `compat.extra_D0` (второй срез). Это **чистая функция** `alts(d)` и данных: `D_hidden_s = D_hidden·share_s`. Нового запаса и колонки нет (правило §3 «один запас — один эффект» не нарушается). Звено `SERIES_GATE` получает UI-поле `top_slot` (только UI, вне ключей сортировки, как `cluster` у F33).
- **Уровень:** light; закрывает RR-0007 §11.7 (строка «Допуск закрыт») и RR-0009 §4.6 п. 4.

### C5. «Туман инженерии» против `SERIES_GATE`
- **Проблема.** `SERIES_GATE` показывает `have = D_hidden` — точное скрытое значение (§6 п. 3). Туман (RR-0007 ОВ-2) потребует скрыть его. `why_not` — вход решений ИИ (§6 r7), поэтому замена `have` меняет траектории.
- **Варианты.** (а) Как сейчас: точное значение (в срезе тумана нет, #28). (б) Разделить поля: `have` (точное, для ИИ и сортировки) и `have_ui` — детерминированная оценка из снимка (например, корзина по выявленным дефектам и часам испытаний); траектории не меняются. (в) ИИ тоже видит только оценку — меняет golden и баланс, нужен EXP.
- **Рекомендация.** (а) до решения о тумане; при тумане — (б). **Уровень:** gate (game-designer, владелец), FUTURE.

### C6. Пересмотр RR-0009 §4.6 под #61, #62, #71
Решение #61 требует правки контракта gate+research до спецификации второго среза. Пункты §4.6 в новой редакции:
1. **Склад и делёж (#61, #71).** Новое состояние `component_stock[site, design_c]` (`Fx6` ≥ 0, единицы; владелец — изделие компонентного класса). Приход — выпуск линии компонента месяца t (merge t); расход — в compute t+1 по снимку (лаг 1 мес., без порядка внутри тика). Делёж между потребителями {линии платформ, программы модернизации, замены}: запрос `req_i` ≤ мощности потребителя за месяц (без накопления запросов); доля `⌊stock·w_i·req_i / Σ w_j·req_j⌋` в `Fx6`, веса `w_i` задаёт игрок (по умолчанию ИИ); остаток раздаётся по одной единице по кругу, начиная с потребителя `t mod K` в каноническом порядке `(site_id, design_id)` — «по очереди», без колонки курсора. Склад — инвентарь, не накопление: в таблицу §3 не входит, в §3.1 — да. Защита от двойного счёта: `line_E` линии компонента действует только на `assembly_hours` компонента; платформа получает единицы по их `unit_cost`, своего обучения на компоненте нет.
2. **Замыкание `prc_set` (#62 решён, нужна форма).** `prc_set*(d) = prc_set(d) ∪ ⋃_{c ∈ comp(d)} prc_set*(c)`, глубина ≤ 2 (#65), граф классов ацикличен (валидатор). `mastered`/`fielded` для `tech_lead` (§9.1) — по `prc_set*`, освоенному актором самим; `production_profile` платформы — только по своему `prc_set` (компонент приходит со склада). Импортный компонент даёт `FV`, но не ключ `G`.
3. **`gen(d)` модернизации.** Новое правило не нужно: модернизированная когорта становится когортой проекта-потомка (RR-0009 §4.4), к нему применяется #70 `gen = min(g_p, eng_gen(engine) + 1)`, где `eng_gen` — поколение `Design` двигателя.
4. **Атрибуция `defects_hidden`** — C4.
5. **Порядок merge** — `(site_id, design_c)` для прихода; делёж — compute по снимку (п. 1), отдельного порядка merge не нужно.
- **Детерминизм и сохранение.** Новые колонки `component_stock`, веса дележа → `save_format_version` +1 (после save v1 — миграция с нулевым складом). Все суммы — в каноническом порядке, `Fx6` с floor; RNG нет.
- **Проверка.** Инварианты: сохранение единиц (приход − расход = Δstock), `Σ доли ≤ stock`, детерминизм остатка при перестановке потребителей; Lab: делёж не даёт доминирующей стратегии (плечо весов).
- **Уровень:** gate+research (#61); исполнители — systems-architect (правка контракта), economy-analyst (делёж), simulation-engineer (спека второго среза).
