## 4. Фазы и ADR-0001
[Предл.] Фазы брифа делятся на две части. Порядок внутри каждой — как в §21 брифа.

**Часть H (headless, сейчас, не трогает ADR-0001):** фаза 2 (детерминированное управление) → фаза 3 (сценарии и сохранения) → фаза 6 частично (определения тестов, отчёты, регрессия) → фаза 7 частично (производительность симуляции). **Часть G (Godot):** фаза 1 (test mode, сборка, запуск, подключение) → 4 (bridge и MCP) → 5 (реальный ввод) → 7 (визуальные проверки, рендер).

2. Godot-оболочка (`game/`) над Core;
3. экран производства по `docs/ui/UI_ART_DIRECTION.md` v0.2.

[Предп.] Это первые задачи M1. Ранее — только если владелец сдвинет срок Godot, а это меняет ADR-0001 («после M0») и требует нового ADR с `supersedes` или явного решения владельца. [Предл.] Срок не сдвигать. Сразу после закрытия M0 сделать спайк совместимости (Godot 4.8 stable + `net10.0` + `ProjectReference` на Core, `--headless --build-solutions` в CI) — это и есть проверка из «Последствий» ADR-0001. ## 5. Test API: один контракт для headless и Godot
```
Singularity.Kernel   ← tick, RNG, Fx6, Table, StateHash, (new) TableSnapshot I/O, EventBuffer
Singularity.Core     ← domain systems, (new) ICommand + validators, read views per domain
Singularity.Session  ← (new) World = mods + scenario → tables + TickRunner; command queue; Step; IReadOnlySession
Singularity.Testing  ← (new) ITestSession, TestGuard, scenario overlay loader, SaveFixtureManager, TestEventRecorder
   ↑ used by: tools/GameTest.Cli (headless, now) · game/ Testing harness (later) · Lab (optional, Session only)
```
- [Предл.] **Read и Mutate раздельно:** `IReadOnlySession` (tick, дата, хеш, доменные представления) и `ITestSession : IReadOnlySession` (Pause/Resume/Step/AdvanceTo, LoadScenario, LoadSave/CreateSave, Submit(command)). Godot UI получает только `IReadOnlySession` и отправляет команды игрока в ту же очередь.
- [Предл.] **Изменения только через команды.** Каждое изменение — `ICommand` с валидатором; применяется в начале тика (ADR-0006) в детерминированном порядке (tick, source, seq). Тестовые изменения, которые не являются командами игрока (например, «бюджет = X»), — тоже команды `TestPatch` поверх тех же patch-операций ADR-0010, но разрешены только в test mode. Все они попадают в журнал команд. Тогда прогон воспроизводится как seed + `scenario_hash` + журнал. Произвольного кода и прямой записи в колонки нет.
- [Предл.] **Детерминизм:** в Session и Core нет `double`. Числа отдаются как `Fx6.Raw`, в JSON — как точная десятичная строка (`MetricFormat.Fx6`). Время рендера и стены в тик не входит. `Step` выполняется на потоке симуляции, возвращается после post, ответ содержит tick и `StateHash`. Ожидание по таймеру запрещено.
- [Предл.] **Представления чтения — только для того, что есть.** Сначала tick, дата, хеш, знание (фронтир, известные узлы), промышленность (культура, оснастка, выпуск) из TASK-0014/0015. Политика, дипломатия и армия из §3.2 брифа не заглушаются; их представления появятся вместе с системами.
- [Предл.] **События:** generic `EventBuffer` в Kernel (tick, systemId, kind, entity, int payload), запись в merge/post в детерминированном порядке. `TestEventRecorder` его читает. Если события влияют на геймплей, они часть состояния и сохранения; иначе — наблюдение.
- [Предл.] Архитектурные тесты дополняются: Core не ссылается на Session/Testing; Session не ссылается на Testing; в Session и Testing нет `double` вне форматирования.
- Новые сборки фиксирует **ADR «Session и Test API»** (gate).

## 6. Сценарии
- [Предл.] Один канонический формат — YAML ADR-0010; второго языка сценариев нет. Тестовый сценарий — мод `test.<id>` с `depends: core` (или другой шаблон) и `scenario_test.yaml`: `id, name, description, version, requires_game, start_date, seed, active_country, hypotheses[]`. Изменения пишутся через `patch`/`override` по ID.
- [Предл.] Шаблоны: `test.1945_baseline` → `test.industrial_crisis` и т. п. только через зависимость. Глубина цепочки ≤ 3; циклы и конфликты дают громкую ошибку (уже правило ADR-0010).
- [Предл.] Тестовые моды лежат вне `mods/` и загружаются только при явно заданном пути поиска в test mode. В обычной игре их не видно.
- [Предл.] Валидация §8.3 брифа: каждая ошибка содержит `file:line` и JSON Pointer поля; неизвестное свойство — ошибка (`additionalProperties: false`). После загрузки сценарий сам себя проверяет: снимок представлений сравнивается с объявленными ожиданиями из `expect_initial`.

## 7. Сохранения (нужен ADR, gate+research)
| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Снимок колонок** (бинарный, little-endian; по таблице: имя, тип, длина, данные) + заголовок | точный, быстрый, общий для игры и тестов; хеш проверяется после загрузки | бинарные diff нечитаемы |
| B. Текстовый снимок (YAML/JSON, Fx6 как целые) | читаемые diff фикстур | большие файлы, медленно; второй путь сериализации |
| C. Replay: `scenario_hash` + seed + журнал команд | крошечный; отличен для воспроизведения дефектов | загрузка = пересчёт; ломается при любой смене кода; не годится как сохранение игрока |

[Предл.] **A как формат сохранения; C — как артефакт прогона и дефекта.** Рядом со снимком лежит JSON-сводка (`summary.json`) с ожидаемыми значениями для фикстур — её читает человек и с ней сравнивают тесты.
- Заголовок: `save_format_version`, `game_version`, `test_api_version` (для фикстур), моды и версии + хеш данных (ADR-0010), `scenario_id`, `seed`, `tick`, дата, `schema_version` таблиц, `state_hash`, `created`, `description`, `suite`.
- Состояние RNG: [Факт] `CounterRng` хранит только seed (`CounterRng.cs`), поэтому seed + tick восстанавливают его полностью. Проверка: `StateHash` после загрузки равен заголовку, **и** продолжение с загрузки даёт тот же хеш на тике N, что и прогон без перерыва (L1). Это главный тест формата.
- [Предл.] Миграции — цепочка чистых функций vN→vN+1 над колонками по стабильным строковым ID (ADR-0005), в Core. Исходная фикстура не меняется: копия мигрирует в `artifacts/`. Отрицательные фикстуры: усечённый файл, неверный хеш, неизвестная версия, отсутствующая колонка.
- [Предл.] Сериализация колонок общая и без домена — в Kernel (`TableSnapshot`), домен и миграции — в Core.
- Межплатформенность: формат переносим, но совпадение продолжения на разных ОС не заявляется (L3 отложен, ADR-0002).

## 8. Runner, отчёты, производительность (headless)
- [Предл.] `tools/GameTest.Cli` (команда `gametest`): `run <id>`, `run-suite <tag>`, `scenario validate|load`, `save validate|create|compare`, `report latest`. Коды выхода: 0 PASSED; 1 FAILED; 2 BLOCKED/INCONCLUSIVE; 3 ошибка определения или окружения.
- [Предл.] Определения тестов — YAML в `tests/definitions/` (поля §10.1 брифа), проверяются JSON Schema. PASSED ставится только по проверенным утверждениям.
- [Предл.] Без дублирования с xUnit: xUnit — тесты кода (уровень 1). Определения уровня 2 запускаются в CI одним параметризованным xUnit-тестом через ту же библиотеку `Singularity.Testing`. CI остаётся одним `dotnet test`, а `gametest` — удобный вход для Claude и человека.
- [Предл.] Прогон: `artifacts/runs/<run_id>/` (gitignore) — `report.json`, `report.md`, `junit.xml`, `commands.log` (replay), `events.jsonl`, снимки до и после. В git — только определения, сценарии, фикстуры и одобренные эталоны.
- [Предл.] Производительность: профили Small/Medium/Large/Extreme — параметры генератора сценария (число акторов, площадок, узлов). Замер ticks/s, мс на тик по системам, память — в хосте (`Stopwatch` вне логики симуляции разрешён). Бюджеты — только после базового замера (критерий M0 «бенчмарк тика»). Рендер и UI — в части G.

## 9. Часть G: harness, bridge, MCP, ввод ОС (эскиз, решается после спайка)
- [Предл.] **Harness:** автозагрузка `TestBootstrap` в `game/Testing/`, активна только при `-- --test-mode` **и** сборке с `Singularity.Testing`. Готовность объявляется после инициализации Session (строка `GAMETEST_READY {port, apiVersion, build}` в stdout). Сервер протокола работает в своём потоке и передаёт запросы в очередь, которую симуляция разбирает на границе тика.
- [Предл.] **Транспорт:** TCP на `127.0.0.1`, порт 0 (выбирает ОС), токен сессии 256 бит передаётся через переменную окружения (не через аргумент: его видно в `ps`), JSON с префиксом длины, максимум 1 MiB, envelope §5.2 брифа, `protocolVersion` проверяется рукопожатием. Альтернативы: WebSocket (лишний слой без браузера); named pipes / Unix sockets ([Предп.] в .NET есть на всех ОС, но различается поведение путей и прав); stdin/stdout (смешивается с логом Godot). TCP loopback — самый простой и одинаковый на трёх ОС.
- [Предл.] **Bridge — библиотека, а не отдельная служба:** `tools/GameTest.Client` (запуск и наблюдение процесса, протокол, таймауты, сбор улик). Её используют и `gametest`, и `tools/GameTest.Mcp`. Отдельная долгоживущая служба для маленького проекта избыточна. Это отступление от §5 брифа.
- [Предл.] **MCP:** `ModelContextProtocol` 2.3.x, STDIO, набор инструментов минимальный и типизированный (lifecycle, simulation, scenario, save, evidence; UI — с фазы 5). Без game instance сервер отвечает понятной ошибкой. Подключение через `.mcp.json` проекта — это изменение настроек Claude Code, его одобряет владелец.
- [Предл.] **Ввод через ОС (путь B):**
  - Linux: игра в отдельном X-сервере — Xvfb в CI, Xephyr для наблюдения на рабочем столе — плюс xdotool/XTEST для ввода и `xwd`/`import` для снимков. Тест не захватывает мышь владельца и не зависит от Wayland [S13, S16]. Wayland напрямую: ydotool (uinput, нужны права) или порталы (запрашивают согласие) — [Предп.] неудобно для автоматики.
  - Windows: FlaUI (UIA3) + SendInput [S17]. macOS: CGEvent + разрешение Accessibility; [Предп.] на macOS-раннерах CI его не выдать — реальный UI на macOS только локально.
  - Поиск элементов: [Предп.] AccessKit отдаёт Control-узлы в UIA и AT-SPI [S14, S15], и тогда можно кликать по имени, а не по координатам. Статус экспериментальный — проверить спайком; запасной путь — координаты элемента от harness.
- [Предл.] **Путь A (внутри):** GdUnit4Net — только для сцен и узлов, и только версия, совместимая с выбранным Godot (сейчас для 4.8 её нет [S9, S10]). Логика остаётся в xUnit без Godot.
- [Предл.] **Визуальная регрессия:** внутренний снимок viewport при фиксированном разрешении (1920×1080, 2560×1440 — #38) для эталонов; снимок ОС — для улик реального окна. Сравнение с допуском и масками; эталоны одобряет ui-art-director, автоматической замены нет. Библиотеку сравнения выбрать в фазе 7 с учётом ADR-0009 и лицензий кода.

## 10. Безопасность и исключение из release (§20)
- [Предл.] Двойной барьер. (1) Сборка: в конфигурации release-экспорта Godot проект `game/` не ссылается на `Singularity.Testing` (условный `ProjectReference` + `DefineConstants SINGULARITY_TEST`). [Предп.] Godot.NET.Sdk собирает экспорт в конфигурациях `ExportDebug`/`ExportRelease` — проверить в фазе 1. (2) Время выполнения: `TestGuard` отказывает без флага, вне loopback и без токена.
- [Предл.] Проверка: CI-тест экспортирует release-сборку и убеждается, что в ней нет `Singularity.Testing.dll`, а флаг `--test-mode` ни на что не влияет.
- [Предл.] Отдельный каталог данных теста (`--test-data-dir` после `--`); SaveManager отказывается писать вне него; пути пользовательских сохранений test mode не открывает. MCP не даёт доступа к файловой системе и shell; разрушительные операции — только внутри `artifacts/`. Каждое изменение пишется в журнал с `run_id`. Окно в test mode помечено плашкой.

## 11. Агенты и первая веха
**Агенты** [Предл.]: 7 ролей брифа ложатся на существующих агентов.
| Роль брифа | Агент |
|---|---|
| Test Architect, Simulation QA, Regression QA, Performance QA (headless) | test-engineer (зона `tests/**`; добавить `docs/testing/**`) |
| Test Infrastructure Developer | developer |
| Профили, гипотезы сценариев | simulation-engineer |
| Эталоны и визуальные проверки | ui-art-director |
| Functional QA / UI Automation | **сейчас никто**; при фазе 5 — один новый агент `qa-automation` (играет через MCP и реальный ввод, пишет только `artifacts/` и отчёты дефектов). Отдельный агент нужен, потому что у этой роли другие инструменты (MCP) и другая зона записи |

**Веха TG-0 «headless-фундамент тестов»** [Предл.], после TASK-0013..0015:
1. ADR-0013 «Формат сохранения v0» и ADR-0014 «Session и Test API, test mode» — gate, critic + advocate, одобрение владельца.
2. `Singularity.Session` и `Singularity.Testing` (headless), `TableSnapshot` в Kernel, `tools/GameTest.Cli`.
3. Сценарий `test.1945_slice_baseline` (оверлей на `core`) и `test.alloy_shortage` (дефицит жаропрочного сплава) — аналог второй демонстрации §22 без UI.

Критерии приёмки:
- `gametest scenario validate` на 5 отрицательных фикстурах даёт ошибку с путём поля; на корректной — 0 ошибок.
- `gametest run SLICE-SMOKE-001`: загрузка, проверка стартовых условий через `ITestSession`, `Step(12)`, утверждения по знанию и промышленности, отчёт JSON/MD/JUnit, код выхода. Повторный прогон даёт тот же `state_hash`.
- Save: create → load → хеш равен заголовку; продолжение до тика N совпадает с прогоном без перерыва (L1, L2 при 1 и N потоках). Повреждённая фикстура даёт громкую ошибку.
- Сценарий дефицита: после загрузки утверждение «сплава < потребности» PASSED; сохранение и повторная загрузка подтверждают то же.
- Те же определения зелёные в CI на 3 ОС через `dotnet test`; архитектурные тесты новых границ зелёные.
- В отчёте `target: core-headless`; нигде не заявлено «протестирована игра».

**Не входит в TG-0:** Godot, bridge, MCP, ввод ОС, визуальные проверки.

5. **Агенты.** (a) новых нет, `qa-automation` — при фазе 5; (b) создать сейчас; (c) никогда, роль у test-engineer. **Рекомендация: (a).**
6. **Объём первой вехи.** (a) TG-0 как в §11, после TASK-0015; (b) только ADR-0013/0014 сейчас, код — после HYP-0002; (c) отложить всё до Godot. **Рекомендация: (a)**, или (b), если приоритет — срез.
