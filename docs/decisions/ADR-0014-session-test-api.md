# ADR-0014 — Session и Test API: единая сборка мира, команды, test mode

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

## Контекст
- [Факт] Решения #57–#60: сейчас только ADR; спайк Godot идёт параллельно (TASK-0016); мост — библиотека с интерфейсом, допускающим вынос в службу; тик = 1 день.
- [Факт] Сейчас мир собирает Lab (`LabModel`), команд игрока в Core нет; ADR-0006 (ввод — только команды в начале тика) — PROPOSED.
- [Факт] Ревью critic (gate): риск второго пути сборки мира, недетерминированного порядка команд, разрастания Test API, утечки тестового кода в release.
- [Факт] Спайк TASK-0016 выполнен (`docs/architecture/spikes/godot-compat.md`, прогон 2026-11-03): Godot 4.7.2-stable mono + `net10.0` собирает и запускает Kernel/Core через `ProjectReference` в редакторе и в release-экспорте; хэш состояния после 1000 тиков побитно совпадает с чистым .NET-хостом. Пункты, ранее помеченные «уточнить по TASK-0016», ниже разрешены по фактам спайка (пп. 4а, 8, 11–13; «Проверка»).

## Решение (предложение)
**Сборки.** `Singularity.Kernel ← Core ← Session ← Testing`. Core не знает Session и Testing; Session не знает Testing.

1. **Session — единственный путь сборки мира.** `Singularity.Session` содержит: сборку мира (моды + сценарий через загрузчик ADR-0010 → таблицы + `TickRunner`), очередь команд, `Step(n)`, представления чтения (`IReadOnlySession`). Lab, `gametest`, xUnit-тесты уровня 2 и Godot-клиент **обязаны** собирать мир через Session; второго пути нет.
2. **Команды.** Любое изменение мира после старта — типизированная доменная `ICommand` с валидатором. Поток симуляции при получении назначает команде `apply_tick` (следующая граница тика) и `seq` (монотонный счётчик); порядок применения — `(apply_tick, seq)`. Журнал replay пишет **назначенный** тик, а не время отправки.
3. **Patch/override ADR-0010 — только до тика 0**, через загрузчик (оверлей-мод тестового сценария). После тика 0 — только типизированные доменные команды; общего `TestPatch` над колонками нет.
4. **Время** продвигается в тиках (днях, #60); календарные единицы не мельче дня; часов нет. `Step` синхронный, выполняется на потоке симуляции и возвращает tick, дату, `StateHash` после post. Ожидание по таймеру запрещено.
4а. **Модель потоков (по спайку §6).** Поток симуляции отдельный и единственный владелец таблиц и `TickRunner` (Compute внутри распараллеливается `Parallel.For`, в Godot работает без изменений). Главный поток Godot, UI и harness **не читают колонки `Table`** — это запрет контракта. Чтение — только через неизменяемые доменные снимки, которые поток симуляции собирает после post и публикует одной записью ссылки (`Volatile.Write`; читатель — `Volatile.Read`), без блокировок. Снимок узкий и доменный (read view), а не копия колонок: полная копия стоит O(строк) на тик [Факт, спайк §6]. Команды из главного потока — в очередь, которую поток симуляции разбирает на границе тика (п. 2).
5. **Поверхность Test API.** `ITestSession : IReadOnlySession` добавляет Pause/Resume/Step/AdvanceTo, LoadScenario, LoadSave/CreateSave (ADR-0013), Submit(command). Представления чтения — только для существующих систем, без заглушек. Владение: DoD каждой новой доменной системы включает её read view и тест на него; systems-architect ревьюирует изменения поверхности; любое изменение поднимает `test_api_version`. `active_country` не вводится, пока нет механики игрока.
6. **Транспорт (часть G, после клиента).** TCP loopback, только IPv4 `127.0.0.1`, порт 0 (выбирает ОС); `localhost` не используется, сокет не dual-stack (`AddressFamily.InterNetwork`), чтобы не слушать `::`. Токен 256 бит через переменную окружения, сравнение за постоянное время (`CryptographicOperations.FixedTimeEquals`). Один клиент; второе подключение отклоняется. JSON с префиксом длины, ≤ 1 MiB, рукопожатие с `protocolVersion`. Unix sockets / named pipes — позже, за интерфейсом транспорта.
7. **Мост (#59).** `GameTest.Client` — библиотека за интерфейсом (`IGameTestClient`), который можно реализовать отдельной службой без изменения вызывающих (`gametest`, `GameTest.Mcp`).
8. **Исключение из release.** (а) Сборка: release-конфигурация не ссылается на `Singularity.Testing` (условный `ProjectReference` / `Compile Remove`, код за `#if SINGULARITY_TEST`). (б) Автозагрузка harness регистрируется в рантайме, а не в `project.godot`. (в) `TestGuard` в рантайме: флаг `-- --test-mode`, loopback, токен. По спайку §7 [Факт]: Godot.NET.Sdk 4.7.2 знает конфигурации `Debug` (редактор), `ExportDebug`, `ExportRelease`; в `ExportRelease` задаёт `Optimize=true` и константу `EXPORTRELEASE`. Барьер (а) ставится условием `$(Configuration) != ExportRelease`: в нём `DefineConstants += SINGULARITY_TEST` и условный `ProjectReference` на `Singularity.Testing`; в `ExportRelease` — `Compile Remove` каталога тестовых хуков, файлы дополнительно под `#if SINGULARITY_TEST`. Барьер (б): тестовый узел добавляется под `/root` во время выполнения (`CallDeferred(AddChild)`) только при `--test-mode`; в списке autoload `project.godot` его нет, поэтому в release нет даже ссылки на скрипт. `ExportDebug` по этой схеме тестовый код **содержит** (это допустимо: распространяется только `ExportRelease`).
9. **CI части G** — только Linux; спайк показал, что всё работает в `--headless` без Xvfb (Xvfb нужен только для проверок реального окна, когда они появятся). Windows/macOS — вручную или ночью. Headless-часть ядра — на 3 ОС, как сейчас.
10. **Демонстрация брифа §22** (реальное окно, заказ через UI) **не считается выполненной**, пока нет Godot-клиента, команды игрока и экрана производства. Отчёты headless несут `target: core-headless`.
11. **Аргументы командной строки.** Флаги harness (`--test-mode` и др.) — только после `--`, читаются `OS.GetCmdlineUserArgs()` [Факт, спайк §4]. Godot молча игнорирует неизвестные флаги, поэтому harness сам проверяет свои флаги и завершает запуск с ошибкой при неизвестном. Пути экспорта в скриптах — только абсолютные (относительный путь считается от `--path`).
12. **Kernel/Core внутри Godot собираются как Release (P2, обязательно).** Godot передаёт `Configuration=ExportRelease` в `ProjectReference`; обычный SDK-проект не включает для неё `Optimize`, и тик ядра в release-игре в 2,5–3 раза медленнее [Факт, спайк §5, §8]. Требование: `ProjectReference` на Kernel/Core/Session из Godot-проекта вне `Debug` несёт `AdditionalProperties="Configuration=Release"`. [Предл.] Альтернатива — включать `Optimize` для `Export*` в `src/Directory.Build.props`; выбор — при создании клиента, требование к результату (оптимизированное ядро) не меняется. Godot-проекту нужен `.sln` рядом с `.csproj` (P1).
13. **Версия Godot (#57).** Целевая — первый stable с официальной поддержкой .NET 10 (4.8), когда выйдет; до этого — 4.7.2-stable mono с `net10.0`, выставленным вручную (работает, но официально не поддерживается, P5). При выходе 4.8 stable спайковые проверки повторяются на 4.8 до перехода. Окружение: редактор запускается с `DOTNET_ROOT` (иначе падает на `hostfxr`, P4); экспортированная игра self-contained и от системного .NET не зависит.

## Предусловия
- ADR-0004 (RNG без состояния) — ACCEPTED-предпосылка для replay и сохранений.
- ADR-0006 (команды в начале тика, тик = день) — должен быть принят до реализации пп. 2–4.
- ADR-0013 — формат LoadSave/CreateSave.

## Рассмотренные альтернативы
- **Test API прямо над Core, Lab строит мир сам.** Меньше сборок, но два пути сборки мира расходятся незаметно. Отклонено.
- **`TestPatch` (patch-операции ADR-0010 во время игры).** Гибко, но это запись в колонки в обход доменной логики и валидаторов. Отклонено: patch только до тика 0.
- **Тик команды задаёт клиент.** Проще, но гонка с потоком симуляции даёт недетерминированный журнал. Отклонено.
- **Транспорт:** WebSocket (лишний слой), stdin/stdout (смешивается с логом Godot), Unix sockets сейчас (различие путей и прав на ОС). Выбран TCP loopback.
- **Мост как долгоживущая служба (бриф §5).** Избыточно сейчас; интерфейс оставляет путь (#59).

## Последствия
- Плюсы: один контракт для headless, Lab и Godot; прогон воспроизводится как `scenario_hash + seed + журнал`; поверхность API растёт только вместе с системами.
- Минусы: Lab переводится на Session (работа при реализации); каждая новая система несёт read view и тест.
- Обязательно: без `double` в Session и Testing вне форматирования; числа — `Fx6.Raw`, в JSON — точная десятичная строка.

## Проверка
- Архитектурные тесты: Core не ссылается на Session/Testing; Session — на Testing; Lab не создаёт `TickRunner`/таблицы мира мимо Session; нет `double` в Session/Testing вне форматирования.
- Тест порядка команд: команды, отправленные из разных потоков, применяются в порядке `(apply_tick, seq)`; replay журнала даёт тот же `StateHash`.
- Тест: patch/override после тика 0 отклоняется.
- Тест версии: снимок публичной поверхности `ITestSession`/read views сравнивается с эталоном; изменение без повышения `test_api_version` валит CI.
- Транспорт (часть G): подключение с неверным токеном, второе подключение и подключение не с `127.0.0.1` отклоняются.
- Release (схема проверена спайком §7): CI-тест экспорта — в каталоге `data_*` нет `Singularity.Testing.dll`; строки-маркера тестового API нет ни в одном файле экспорта (включая `.pck`); инспекция метаданных игровой сборки (`System.Reflection.Metadata`) не находит тестовых типов и ссылки на `Singularity.Testing`; запуск release-экспорта с `-- --test-mode` не создаёт тестовый узел, а Debug с тем же флагом — создаёт.
- CI Godot-сборки проверяет **произведённые файлы, а не код возврата** (P3: экспорт без `.sln` завершается кодом 0 без сборок .NET): наличие `data_*` с игровыми сборками, хэш состояния, список типов.
- L1 между хостами: хэш состояния после N тиков в Godot-экспорте равен эталону headless-раннера.
- Производительность (P2): время тика ядра в Godot release-экспорте в пределах шума от чистого .NET-хоста Release (в спайке 0,56–0,67 мс против 0,56–0,66 мс на 100 000 строк); замедление ≥ 2× валит проверку.
