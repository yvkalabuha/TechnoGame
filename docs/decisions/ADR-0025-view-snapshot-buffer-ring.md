# ADR-0025 — Снимок вида: клиент получает блоки узлов только своих акторов

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Уровень: gate. Шаг 3.6 этапа 3 `development/PLAN.md` (стражи до кода #228); находка A7 `docs/reviews/project-review-2026-11-19.md`; DEBT-0057. Ревизия 2 после gate (critic, advocate, reviewer, DeepSeek: `docs/reviews/adr-0025-*.md`). Кольцо буферов ревизии 1 перенесено в альтернативы. Новых замеров нет (бенчмарки заморожены).

## Краткий вывод
- [Предл.] **Вид клиента с подпиской.** Сессия строит блоки узлов (`NodeBlock`) только для подписанных акторов: в клиенте — играемый и выбранный. У остальных `ActorView.Nodes` — пустая `NodeList` с признаком «не подписан». Остальная часть вида строится для всех, как сейчас.
- [Предл.] ADR-0014 п. 5 (неизменяемый вид, атомарная публикация ссылки) остаётся целиком: нет аренд, `StaleViewException`, `ViewsDropped`, кольца.
- [Предл.] Lab и тесты строят полный вид (все акторы), как сейчас. Переиспользование блоков в Lab не вводится.
- [Предп.] Эффект при 200 акторах (M1): ≈ 0,6 МиБ на снимок клиента вместо 6,94; после дневного тика ≈ 18 МиБ/мес. вместо ≈ 208. Цена ≈ 1–1,5 дня developer + тесты, `TestApiVersion` +1.
- [Предл.] Делается до кода #228, отдельной задачей; на M-play (5 акторов) выигрыш мал, решение нужно для масштаба M1.

## Контекст
- [Факт: ADR-0014 п. 5] Поток симуляции собирает неизменяемый вид после post непустого тика и публикует его одной атомарной записью ссылки (`Volatile.Write`, `SliceSession.cs`).
- [Факт: DEBT-0057, `docs/simulation/debt-0057-gen2.md`] Свежий снимок в точке A (200 акторов, 651 узел-процесс) — 6,94 МиБ, из них блоки узлов 6,42 МиБ (93 %). Внутри блоков массивы `ProcessView[]`: 651 × 200 × 40 Б = 4,97 МиБ; остальные ≈ 1,45 МиБ — маски `Known`/`ByLicence`, `KnownSince`, заголовки объектов. На актора ≈ 33 КиБ [Предп.: 6,42 / 200]. Живой снимок держат `SliceSession.View` и `NodeBlockCache`; сборки gen1 переводят его в gen2 — основной источник установившегося gen2.
- [Факт] Число 6,6 МиБ в A7 — более ранняя оценка ревью проекта; 6,94 — замер DEBT-0057. Ниже везде 6,94.
- [Факт: ADR-0023 п. 2.2, 2.6] Порог пути снимка (P8): ≤ X = 8 МиБ на снимок, 0 LOH, ни одного ссылочного объекта на узел. Сегодня 6,94 < 8 — запас 1,06 МиБ (13 %).
- [Факт: MS-M05] M-play — 5 акторов, 61 узел знаний. [Факт: MS-M1] M1 — ~200 акторов, 379 регионов, дневной режим #228.
- [Предп.] После #228 непустой каждый день: ≈ 30 × 6,94 ≈ 208 МиБ мусора в месяц при 200 акторах; при 30 тиках/с (`SimHost.TicksPerSecond`) — ≈ 200 МиБ/с реального времени.
- [Факт: код, advocate и reviewer] Вид идёт к клиенту так: `SimHost.Publish` на потоке симуляции берёт `session.View` и кладёт в `HostSnapshot`, тот уходит в поток Godot через `volatile _snap`. Потребители: `ActorPanel`, `TechTree`, `AudioDirector`, `SignalField`. `Nodes` читаются только для одного актора (`TechTree.cs:145` `View.Actors[_actor].Nodes`, `AudioDirector.cs:244`); остальное берётся из статических `_host.Data.Nodes`. Вид держится между кадрами (`ActorPanel._lastView`, `TechTree._lastView`, `SimHost._lastWhyView`, `HostSnapshot.View`).
- [Факт: код] Lab держит несколько видов: `JetSliceModel` — прошлый и текущий; `SliceObserver` — ещё `_initial` (весь прогон), всего 3.
- [Факт: код] Повторная публикация без новой сборки: путь F7a (`SliceSession.cs` ~243–247, `prev with { … }` с теми же `ActorView` и `NodeList`) и R2 (`NodeBlockCache` отдаёт блок прошлого снимка того же месяца).
- [Факт: `NodeList.cs:75`] `NodeList.Equals` возвращает true сразу при одной ссылке на блок.

## Решение

### 1. Подписка
1. Новый исполнительный параметр `SliceRunConfig.ViewScope`: `All` (по умолчанию; Lab, тесты, бенчмарки) или `Subscribed` (клиент). Не хешируется, не сохраняется, не влияет на `SchemaVersion`. `SliceViewMode` (`Full`/`Calibration`) не меняется — это другая ось.
2. В режиме `Subscribed` сессия хранит множество подписанных акторов (поле экземпляра, массив `bool[actors]`). Меняет его `session.SetViewSubscription(ReadOnlySpan<int> actors)` — только поток-владелец (тот, что вызывает `Step`; в клиенте это поток `SimHost`). UI передаёт выбор в `SimHost` так же, как команды.
3. **Граница тика.** Смена подписки действует с ближайшей публикации. Если сессия на паузе, `SimHost` после смены вызывает пересборку текущего вида без тика (полная сборка `ViewBuilder.Snapshot`, не путь F7a). Состояние, хеш и RNG не затрагиваются.
4. Клиент подписывает играемого актора и выбранного (≤ 2 блока, ≈ 66 КиБ на снимок). **Будущий экран соперников** подписывает нужных ему акторов: цена ≈ 33 КиБ на актора за снимок [Предп.]; подписка «все» равна режиму `All`. Ограничение числа подписанных — задача экрана, не этого ADR.

### 2. «Не подписан»
5. У неподписанного актора `ActorView.Nodes = default(NodeList)`: блока нет, `Count = 0`. Новое публичное свойство `NodeList.IsPresent` (сейчас `internal HasBlock`) отличает «не подписан» от данных. Индексатор пустого списка бросает `InvalidOperationException("actor not subscribed")`. Пустой граф у подписанного актора невозможен (`NodeShape` общий), так что `Count = 0` не двусмыслен.
6. Остальные поля `ActorView` (знания по дисциплинам, бюро, проекты, решения) строятся для всех акторов: их ≈ 0,52 МиБ на снимок при 200 акторах [Предп.: 6,94 − 6,42].
7. **Равенство.** `NodeList.Equals` с ранним true по ссылке верен, пока блоки неизменяемы после публикации — это сохраняется. Два «не подписан» равны; «не подписан» и блок — не равны (`Count` разный). Правило: любая будущая схема переиспользования блоков после публикации обязана убрать этот короткий путь или сравнивать поколение.

### 3. Повторная публикация и кэш
8. F7a переиспользует `ActorView` прошлого вида, включая отсутствие блоков; поэтому смена подписки всегда идёт полной сборкой (п. 3). R2: `NodeBlockCache` хранит блоки только подписанных акторов; новый подписанный актор получает свежий блок.

### 4. Lab и поток-владелец
9. Lab строит полный вид. Переиспользование блоков в Lab без аренд (только поток-владелец) **не вводится**: `SliceObserver` держит 3 вида, значит нужно N ≥ 4 и правило «не держать `_initial` дольше N − 1 публикаций»; gen2 в Lab влияет только на бенчмарки, их покрывает ADR-0024. Вернуться можно отдельным ADR, если замер Lab покажет нарушение P8.

### 5. Связи
10. **Детерминизм (ADR-0002).** Вид — наблюдение. Подписка — исполнительный параметр; хеш L1/L2 не зависит от `ViewScope`, подписки и `SkipViews`. Логика игры и ИИ внутри сессии не читают виды (запрет фиксируется тестом, п. 4 «Проверки»).
11. **Сохранение (ADR-0013, TASK-0124).** Подписка не сохраняется; после загрузки клиент подписывается заново до первого вида.
12. **Два мира (TASK-0125).** Подписка — поле экземпляра сессии; нет static, `[ThreadStatic]`, `ArrayPool.Shared`.
13. **Частота публикаций (ADR-0023 п. 2.6)** не меняется.

### Отношение к ADR-0014
- Дополняет ADR-0014 (поверхность вида, п. 6): состав `ActorView.Nodes` зависит от подписки. П. 5 не меняется, `supersedes` не нужен.

## Последствия
- **Плюсы:** снимок клиента ≈ ×11 меньше при 200 акторах; живой снимок перестаёт кормить gen2 в клиенте [Предп.]; запас по X сохраняется при росте вида в M1; модель потоков и п. 5 ADR-0014 не меняются.
- **Минусы:** клиент обязан подписываться; код, который читает `Nodes` чужого актора, получит исключение — экран соперников должен подписаться явно. Lab не выигрывает.
- **Обязательно:** `TestApiVersion` +1 (`ViewScope`, `SetViewSubscription`, `NodeList.IsPresent`); golden и `SchemaVersion` не меняются.
- **Стоимость [Предп., advocate]:** Session ≈ 0,5–1 день, `SimHost` (подписка, пересборка на паузе) ≈ 0,5 дня, тесты ≈ 0,5 дня.
- **Когда:** до кода #228 (этап 3). Сегодня 6,94 < X, но #228 умножает число снимков ≈ ×15–30 (1–2 → ~30 в месяц, ADR-0023 п. 2.6) и добавляет потребителей вида; сменить контракт «что клиент может читать» дешевле до них. Запас 1,06 МиБ съест любое расширение вида в M1 (экономика E1, провинции) [Предп.].

## Проверка
Пороги выводятся из P8 ADR-0023 (X = 8 МиБ, 0 LOH), без новых констант.
1. **Аллокации, режим `Subscribed`:** точка A (200 акторов), подписаны 2. Байты в блоках узлов = 2 × (байт одного блока, считается из `NodeShape`) ± заголовки; весь снимок ≤ X; 0 LOH. Мутация: строить блок для всех — тест падает.
2. **Не подписан:** у каждого неподписанного актора `Nodes.IsPresent == false`, `Count == 0`, индексатор бросает; `NodeBlockCache` не держит их блоков.
3. **Смена подписки на границе тика:** смена между тиками — следующий вид несёт блок нового актора и не несёт старого; смена на паузе через `SimHost` — пересобранный вид того же `Tick`, хеш не изменился; путь F7a после смены не отдаёт старые `ActorView`.
4. **L1/L2:** хеши каждого дня равны при `All`, `Subscribed` с разными подписками и `SkipViews`; L2 по матрице ADR-0019 «Проверка» п. 5. Архитектурный тест: системы `Singularity.Core` и ИИ не ссылаются на типы `Singularity.Session.Views`.
5. **Эквивалентность:** у подписанных акторов вид `Subscribed` равен виду `All` (JSON, дневной зонд, прогон с командами).
6. **Сохранение:** продолжение TASK-0124 — после загрузки на тике K и подписки вид тика K + m равен виду непрерывного прогона с той же подпиской.
7. **Два мира:** тест TASK-0125 с видами в режиме `Subscribed` и разными подписками; IL-тест static-полей покрывает новые поля.
8. **P8 в CI:** проба `alloc` пути снимка ADR-0023 (база + 5 %, ≤ X, 0 LOH) — в режиме `All`, как сейчас; добавляется вторая проба `Subscribed`.
