# RR-0012 — Личности, институты, национальные проекты

> Пометки: **[Факт]** — подтверждено источником (для истории — вторичным, см. §2); **[Предп.]** — предположение; **[Предл.]** — предложение. Ничего здесь не утверждено; в силе только решения владельца #19, #28, #192–#196, #205–#208.

## Вопрос исследования

Как сделать институты (НИИ, КБ, лаборатории), личности и национальные проекты **акторами симуляции**, чтобы игрок управлял условиями (ТТЗ, бюджет, приоритеты, запуск проектов, назначение руководителей), а не процессами (#19), и причину любого провала можно было назвать цепочкой ≤ 3 звеньев (`why_not`)?

### 3. Институты как акторы

**3.1 Данные.** `InstitutionType{ kind, tiers[k]{ projects, workforce[cat], upkeep }, spec_default[d] }`; `kind` — НИИ, КБ, лаборатория, испытательный центр, университет, корпорация (`corporate_lab`), `coordinator_agency`, `state_research_network`, `programme_lab`. `tiers[k].projects` — **игровая ёмкость КБ** (B2); срез — ёмкость 1. Тип — данные/мод.

**3.2 Состояние.** `institution_id` — **плоский и стабильный**; `region`, `owner` — атрибуты (не часть ключа). Смена владельца/региона допустима в v1 как событие без слияния (NACA 1958); влияние на ключи и сохранение — подтвердить systems-architect (OPEN). Поля: `tier`, `spec[d]` (Σ = 1), `bureau_exp[class]` (контракт), `funding_share`, `leader`, [позже] `school_H[d]`.

**3.3 Логика.** Ежемесячно (ADR-0006) институт по приоритету владельца и свободной ёмкости (`projects`) выбирает `Requirement`, **подаёт `compose_design` с `sender = institution(id)` (B3) через общий валидатор** и резервирует людей как исполнитель. Отмена (A40) — только у владельца, никогда у института, для проектов игрока (#19) и ИИ-владельца. `requester_id` институтов и проектов — **одно пространство id** (§4.6). Доктрина запуска (P1/P2/P3 по `k_P`, `COMPONENT_SELECTION.md`) выбирается из `risk_attitude` лидера — существующий параметр, не новый эффект.

**3.3a Кадры.** Только общий пул `reserve_workforce`; торг зарплатами — REJECTED (вторая валюта).

**3.4 Ступени.** `tier_up` и `tier_down` — национальные проекты. `tier_up`: цена `C_k` (выпуклая), срок `T_k`, исполнитель резервирует кадры. `tier_down` запускает владелец (игрок; ИИ — по правилу простоя). Автопауза «институт простаивает». Эффект ступени — только `projects` и потолок кадров.

**3.5 Специализация.** `spec` — вектор по дисциплинам (RR-0008). **Один эффект:** допуск к `Requirement` (класс/дисциплина совпадают) и скорость работ по совпавшим заказам. Не `out_d` (это `school_H`), не `bureau_exp`. Цена смены профиля — **только время и деньги**: пока `spec ≠ spec*`, бонус скорости отстаёт; смена стоит денег пропорционально |Δspec|. [Предл., опц.] `spec` дрейфует к фактически выполняемым заказам со скоростью `r_spec` (5–10 п.п./год [Предп.]); явный `spec*` — необязательная команда.

**Таблица эффектов (один запас — один эффект, контракт §3):**

### 4. Национальные проекты

- `NationalProject{ id, owner, goal, stages[], leader, institutions[], budget_cap, deadline }`. Для `programme` `deadline` и `budget_cap` **обязательны** (основа расчёта `support`).
- `Stage{ kind: research|build|test|deploy, cost, duration, materials, tech_req }`. **Своих людей у этапа нет**: заказ уходит исполнителю (институту/`site`), резервирует он. Этап — заказ существующим слоям: исследование → знание, стройка → способность, изделие → `DesignProject` (RR-0007).
- **Срыв — детерминированный** (#28): `slip = f(D_hidden, leader.admin)`, `overrun = g(…)`; случайных событий проекта нет.
- Политическая цена до RR-0015 (#208): деньги + кадры + `support`.
- Отмена: потраченное не возвращается (как #123). Каталог: `tier_up`, `tier_down`, `build_complex`, `programme` (ядерная/космическая — RR-0013); остальное FUTURE.

### 5. Личности

Выбран вариант **C** (#206): реальные личности по пути §5a, сгенерированные заполняют пустоты (нет реального человека, вне исторической роли, после смерти/ухода). Прежняя рекомендация автора (A, сначала сгенерированные) отклонена владельцем.

**Модель.** `Personality{ id, birth, death_date?, country, role, real, source[], traits{ admin, risk_attitude, spec_pref[d], class_pref }, branched }`. Черты `loyalty` и `drive` в v1 **убраны** (нет эффекта; `loyalty` — кандидат RR-0015). Появление, возрастной уход и смерть генерируемых людей — слой событий, именованный поток `EVT_PERS`, ключ расширенный (`actor·2¹⁶ + ordinal`, A2, срок решает владелец); слои способности/изделия читают лидера как данные.

**Кандидаты (#207): ≤ 3, без доминирования.** Для любой пары есть ось, где каждый лучше: (`admin`, `risk_attitude`, совпадение `spec_pref`). Цена назначения растёт с `admin` (лучший администратор дороже). Генератор отбирает антицепь; доминируемый кандидат допускается только если дешевле.

**Правовые и чувствительные риски** [Предп., не консультация] — ведёт RISK-0020: права на имя/образ умерших зависят от юрисдикции; репутация; тяжёлые контексты; портреты только PD/CC0/CC BY; факты не защищены, тексты — защищены.

### 5a. Реальные личности: исполнимые правила (RISK-0020, #206)

[Предл.]; юридическая проверка до релиза (не моя зона).
1. **Допуск (предикат).** `death_date` известна ∧ `birth < 1930` ∧ нет в `exclusions` ∧ есть `source` PD/CC0/CC BY. Валидатор данных отклоняет иное.
2. **Роли — только документированные;** негативные эпизоды в поведение не включаются никогда.
3. **Ветка по человеку.** Флаг `branched[person]` ставится в первый месяц, когда историческая роль отсутствует (нет института/страны/должности занята иначе) **или** игрок назначил/снял человека. До флага — историческая хронология (назначение, уход, смерть по датам). После — только черты и общая таблица смертности, без насильственных смертей и вымышленных эпизодов.
4. **Разрывы карьеры** (арест, эмиграция, отстранение) — нейтральная недоступность `unavailable(from,to)`; событие и текст не показываются.
5. **Черты — из таблицы «роль/достижение → черты»** с источником по каждой строке; частная жизнь и мнения не используются.
6. **Страна.** Реальный человек работает только на свою историческую страну.
7. **Список исключений** (`data/personality_exclusions`, в git, с причиной): живущие; известные преимущественно преступлениями/репрессиями; жертвы-фигуры; по запросам правообладателей/наследников/юристов.
8. **Типа «шарашка» в данных нет;** принудительный труд не моделируется.
9. **Читаемость:** `why_not` не называет реального человека причиной отказа — только черту или институт. Тест: ни одно отрицательное звено не ссылается на `Personality.real = true`.
10. **Прочее:** переключатель «исторические / вымышленные имена» (те же черты); портреты только PD/CC0/CC BY или значок; пометка «игровая интерпретация».
11. **Тесты:** валидатор (предикат, источник, исключения); нет негативных событий у `real = true`; нет реального человека вне своей страны; ветка не откатывается.

### 5b. Назначение и ротация (#207)

`appoint_leader(institution|project, candidate)`: ≤ 3 кандидата (§5); цена — деньги + провал `admin` на период вхождения `T_on` (6–12 мес. [Предп.]). **Неравенство для Lab:** потери от вхождения за `T_on` ≥ любого бонуса нового лидера за `T_on` — ротация «ради бонуса» не окупается. Частота — не чаще раза в `N_rot` лет на институт (параметр Lab). `why_not`: «нет кандидата» ← пул категории пуст ← образование.

### 5c. `support` и закрепление узла (#208, #205)

`support ∈ [0,1]`. **Трата пропорциональна отставанию от заявленного плана** (`deadline`, `budget_cap`): `spend = Σ cost_i · (rel_slip_i + rel_overrun_i)·k`, взвешенная по стоимости, поэтому дробление проекта сумму не меняет. Восстановление медленное. Низкий `support` замедляет **новые** проекты и удорожает ступени. Модель временная до RR-0015. Закрепление узла: вес на пути к узлу, без жёсткой очереди; ≤ 1–2 закрепления; цена переключения.

| Институт теряет опыт | недофинансирование → `δ_B` | поднять долю бюджета |
| Не берёт заказ | `spec` не совпадает → смена профиля идёт | `spec*` / другое КБ |
| Замедлен | `support` низкий ← проект X (отстаёт на N мес.) | отменить или сжать X |

Звено никогда не называет реального человека.

### 9. Автопауза и темп (#196)

Паузы: этап завершён, `tier` достигнут, руководитель ушёл, институт простаивает, отставание проекта. Приоритеты по типам, ≤ 1 пауза на границу тика, пакетная сводка. Ориентир [Предп.]: флагман — 5–15 мин реального времени (после T12, #177).

### 10. P21: Requirement с двумя исполнителями (флагманы)

Игрок поручает флагманский `Requirement` **двум** КБ (двойные деньги и кадры), затем выбирает прототип. История: конкурс бюро (КБ СССР, конкурсы заказчиков США) [Предп., не проверено источниками]. Польза: осмысленный косвенный рычаг. Риски: ×2 нагрузки на флагман; «спам конкурсов»; вопросы двойного счёта `bureau_exp` (проигравший копит опыт?) — RR-0007. [Предл.] Ограничения: только флагманы, ≤ 1–2 одновременно на страну, цена — оба бюджета. Рекомендация автора: **IMPORTANT, после MVP**; решение — владельца (новая механика, вопрос ниже).

## MVP

- [Предл.] Срез: **5 стран (США, Великобритания, СССР, Франция, Швеция, #41)**, КБ по данным среза (#25), ёмкость 1; 4 типа институтов, ступени 1–3. Реальные личности — пул 30–60 на 1945 для этих 5 стран; пустые слоты — сгенерированные. Мир целиком (E1) — ≈150–300 институтов, остальные лидеры сгенерированные.
- Проекты `tier_up`, `tier_down`, `build_complex`, каркас `programme`. Назначение руководителей, `support`, закрепление узла.
- Агрегация: институт — один актор; люди — агрегат `reserve_workforce`; ≈1 лидер на институт и проект.
- Бюджет тика [Предп.]: институты ≈300 × ~50 оп./мес ≈ 10⁴; проекты ≤ 100 × ~20; личности ≈ 10³/мес; пренебрежимо рядом с E1. Состояние института ≈ 20–30 чисел.
- Детерминизм: порядок по `institution_id`; команды с t+1 (ADR-0006); `EVT_PERS` — именованный поток; `school_H` при появлении меняет раскладку сохранения (ADR-0013 п. 7).
