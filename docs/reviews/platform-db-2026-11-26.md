## Вариант 1. SQLite как производный индекс (источник правды — файлы)
- Как: `tools/development/kb_db.py` при `registry.py index` (и хуком после коммита) собирает `.claude/.state/kb.sqlite` из frontmatter задач, таблиц DECISIONS/ORCH/TECH_DEBT/OPEN_QUESTIONS, errors.yaml, agents.jsonl. Таблицы: items, decisions (с superseded_by), debt, questions, errors, agent_runs, links. Запросы: `kb_db.py q "debt status=open area=Lab"`, `... decisions about=наука since=2026-11-20`.
- Плюсы: быстрые фильтры и связи (задача → решения → долг → ошибки → агенты); короткие ответы вместо больших выдержек; проверки целостности (ссылка на несуществующий DEBT — как ошибки kb_check) одним запросом; ничего не ломает: файл можно удалить и пересобрать.
- Минусы: ещё один инструмент; индекс устаревает, если не пересобран (лечится пересборкой при каждом запросе по mtime файлов); вся запись по-прежнему через файлы.
- Цикл записи: select + insert — да (insert = дописать файл + пересобрать). update/delete — только через файл; «мягкое удаление» и история уже даёт git (SUPERSEDED, история коммитов).
- Экономия токенов [Предп.]: на запросах-выборках 30–70 % меньше вывода, чем grep по таблицам с длинными строками; в целом по сессии — 2–5 %. Основная цена — контекст разговора и отчёты агентов, а не чтение этих файлов.

## Вариант 2. SQL как источник правды (записи только в БД)
- Плюсы: настоящие update/delete, soft delete (deleted_at), транзакции, многотабличность.
- Минусы: [Факт] бинарный файл в git не сливается между ветками-worktree (у нас 10–40 worktree и land.py); [Факт] владелец и агенты читают markdown — пришлось бы генерировать документы обратно; потеря обзора изменений в diff и в ревью Codex; хуки зон записи (guard_zone) перестают работать. PostgreSQL — ещё и сервер, резервные копии.
- Вывод: не подходит для решений, задач и документов. Подходит только для служебных журналов вне git (agents.jsonl, отказы хуков, сбои посадок).

## Вариант 3. Redis для обмена сообщениями между агентами
- [Факт] Агенты Claude Code не опрашивают внешние очереди во время работы: обмен идёт через SendMessage/оркестратор и файлы; подписку на канал агент держать не может.
- Плюсы: быстрые счётчики, блокировки (land, тесты — сейчас flock и файлы), TTL для разрешений (client_permit).
- Минусы: сервер-демон, установка, пароль/доступ, сохранность при перезапуске; выигрыша для агентов почти нет — нужные блокировки уже есть.
- Вывод: не нужен сейчас.
