## 2. Компонент = `Design` своего `ProductClass` (#61, #65)
- `ProductClass.kind ∈ {platform, component}` (данные, ADR-0010). Вид слота: `alt` (глобальные альтернативы, как в срезе 1) или `component_ref` (класс компонента, `qty ∈ 1..4`).
- **Глубина ≤ 2.** Валидатор данных запрещает слоты `component_ref` у классов `kind = component`. Поэтому BOM ацикличен по построению.
- `jet_engine` (второй срез): слоты `alt` — `compressor`, `hot_section`, `afterburner` (переезжают из `jet_fighter`) и база по ENG. Три характеристики (#65): `thrust`, `sfc`, `service_life_h` (§8). Интерфейсные параметры: `thrust`, `mass`, `airflow` (§7).
- Цикл компонента не отличается от цикла изделия RR-0007 (К§4.4): `Requirement(class, gen, …)` → КБ (`bureau_exp[bureau, class]` уже по классу, моторное КБ — то же КБ с другим классом) → ≥ 2 варианта с разными `prc_set` (#29) → испытания → **допуск** (§10) → `ProductionLine` на site → `line_E`.
- `Design` компонента получает свои `D0`, `defects_hidden` и `complexity` (сумма tier по своему `prc_own`) по К§4.4 и срезу §3.3 без изменений.
- Платформа может быть спроектирована под **ещё не допущенный** компонент. Выпуск начнётся только после его допуска и появления на складе, либо на «временном» компоненте с последующей модификацией (кейсы C1, C3, C4).
- Родословная: `design_lineage(design_id, parent_id, lineage_id)` (отдельная таблица, §14). Модификация по правилу RR-0009 §3 в. 6: изменено ≤ `k_mod` слотов, `compat ≤ redesign`. Тогда `novelty` считается только по изменённым слотам, `line_E_new = τ·line_E_old`.
- **Модернизация экземпляров компонента** (F100-220E, C5) — FUTURE, третий срез. Кейс C5 частично не воспроизводится (RR-0009, Разногласия п. 6).

## 3. Склад компонентов — материальный запас (#61)
| Состояние | Владелец | Растёт от | Убывает от | Влияет на (и только на) | Забывание |
|---|---|---|---|---|---|
| `component_stock[site,design]` (целое) | `Core.Products` | годный выпуск линии компонента (`report_component_output`) | выдача по `reserve_component` | `granted` | нет |
| `component_held[requester,design]` (целое) | `Core.Products` | `granted` | установка (`consume_component`); при закрытии запросившего — возврат на склад | число единиц, которые запросивший может установить в t+1 | нет |

- Это **не запас К§3**: он не учит и ничего не удешевляет. В К§3 добавляется примечание: «материальные запасы (`component_stock`, `component_held`) не входят в таблицу накоплений; их эффект — только наличие». Тест разреженности К§8.1 распространяется на них: сдвиг склада меняет только `granted` и выпуск запросившего, но не `yield`, `unit_cost`, `D`.
- Хранение в целых штуках, а не в `Fx6`: компонент неделим, как человек в `reserve_workforce`.
- **Инвариант сохранения (post):** `Σ produced + Σ delivered = stock + held + installed + scrapped` по каждому `design`, точно.
- Ключ — `site`. В CI-фикстуре «2 site» склады разных site не общие. Перевозка между site (`ship_component`) — FUTURE. Импорт (`deliver_component(site, design, n, source)`) по #62 даёт боевую силу, но не лидерство. Он входит в API v3, но в MVP второго среза отключён (вопрос спецификации).
- Брака на складе нет: `q` компонента уже учтён в его годном выпуске и готовности (К§4.2, A4).

## 4. `reserve_component` (#61)
```
reserve_component(site, design, n, requester_id) -> granted@t+1     # порядок merge (site_id, design_id, requester_id)
consume_component(requester_id, design, used)                        # used ≤ held из снимка
report_component_output(site, design, units)                         # порядок (site_id, design_id); units — годные
```
- Запросившие — линии платформ и программы модернизации. `requester_id` берётся из **общего** пространства id: КБ, программы качества, линии, программы модернизации. Тогда ключ merge однозначен.
- Запрос в compute t: `n = need(t+1) − held_snapshot` (не меньше 0). Делёж — дословно К§4.6:
  - если хватает, `granted = n`;
  - иначе `granted_i = floor(n_i·avail/Σn)`, остаток по 1 в порядке `requester_id`.
- `avail` — склад после `report_component_output` этого тика (§12, шаги 3–4). Двигатель, выпущенный в месяце t, может стоять на самолёте с t+1. Лаг ровно 1 месяц, явный.
- `granted` пишется в `component_held` и **виден в t+1**. В t запросивший его не знает.
- Ярлык `why_not`: `COMPONENTS`, если `granted/n < 0.9` (по аналогии с `ENGINEERS`).
- Новый выпуск и модернизация делят склад пропорционально, как `reserve_workforce`. Приоритет — через размер запроса, который задаёт ИИ или игрок. Альтернатива с классами приоритета — вопрос владельцу 2.

## 5. Без двойного счёта: `prc_own` против `prc_closure`
```
prc_own(d)     = объединение PRC альтернатив слотов alt проекта d
prc_closure(d) = prc_own(d) ∪ ⋃_{(c,qty) ∈ bom(d)} prc_closure(c)
```
| Потребитель | Набор |
|---|---|
| `production_profile`, `unit_cost_mult`, `q`, `bottleneck` линии d | `prc_own(d)` |
| `report_output` линии d (и её `proc_v`) | `prc_own(d)`, `labour_hours` — только своя работа |
| `complexity(d)` → `D0`, `W`, upkeep своей части | `prc_own(d)` |
| `fielded` / `mastered` (К§9.1), `tier_display` | `prc_closure(d)` |
| `why_not(design)` — обход звеньев | `prc_closure(d)`: у звена компонента `subject_id` = id компонента |

- Если один PRC встречается и в `prc_own` платформы, и в компоненте (например, точная механообработка), это **не** двойной счёт: это две физические единицы работы на двух линиях. Двойной счёт — одна единица, учтённая дважды. Отсутствие такого учёта проверяет тест разреженности: сдвиг `proc_X` PRC двигателя меняет цену линии двигателя, но не `unit_cost_mult` платформы.
- `material_availability` и лимит сплава среза 1 (`alloy_kg[gen]`) переходят на линию двигателя. Делёж лимита по линиям — по `design_id`, как в срезе §1.4.

## 6. Агрегаты изделия с BOM
| Величина | Правило | Почему |
|---|---|---|
| Денежный поток | каждая линия платит за свой выпуск в месяц выпуска; установка компонента денег не стоит | компонент оплачен один раз, когда сделан |
| `unit_cost_full(d, site)` (для ИИ, `fleet_value`, ECONOMY, UI) | `unit_cost_own(d, site) + Σ_bom (qty · unit_cost(c, site_c))`, где `unit_cost(c)` — **текущая** цена из снимка (цена замещения) | стоимость аддитивна (C1: материалы и трудоёмкость Jumo 004 учитывались отдельно). Историческую цену на складе не храним — меньше состояния |
| `complexity(d)` | только своя | `D0` и `W` платформы не должны зависеть от двигателя; иначе дефекты двигателя считались бы дважды |
| `D0`, `defects_hidden` | у компонента — в его `Design`; у платформы — своё `D0` + интеграционное `extra_D0` из `compat` | #63, RR-0009 §4.5; §11 |
| `upkeep(d)` | `upkeep_own(complexity_own) + Σ_bom qty·upkeep(c)`, где у компонента `upkeep(c) = upkeep_base_c·PowFrac(complexity_c, q10_αu)/maintainability + overhaul(c)` (§8) | `PowFrac` вогнутая: от суммарной `complexity` двухмоторный самолёт содержать дешевле суммы частей, а это неверно |
| `readiness` когорты | `min(1, оплачено/нужно) · q_own · (1 − ψ_D·D/D0)_own · Π_{(c,qty)} r_c^qty`, `r_c = q_c·(1 − ψ_D·D_c/D0_c)`; степень — повторным `·` в порядке `slot_id` | последовательная надёжность: самолёт не готов, если не готов любой двигатель. `min` недооценивает два слабых звена |
| `perf(d)` | `perf_platform(d) · f_class(характеристики c)`, функция класса в данных; для `jet_fighter` — от `thrust/mass` и `sfc` | ось двигателя входит в ось платформы, как «база двигателя» среза 1 |

Все `Σ` идут по возрастанию `slot_id`, `Π` — по `slot_id`, затем по повторению `qty` (К§4.0 п. 4–5). При **пустом BOM операции не выполняются вовсе** (а не «+0», «·1»). Так канонические формы среза 1 не меняются (§15).

## 7. Совместимость (#63, #65)
`compat(platform_design, slot, component_design) → { level, reasons[], cost_mult, extra_D0, margin_used[param] }` — чистая детерминированная функция данных в `Fx6`, без RNG и без физики (CG, вибрации и охлаждение исключены, RR-0009 §3 в. 5).
- **Параметры интерфейса** (данные класса, 2–3 на слот): для `engine` — `thrust`, `mass`, `airflow`. #63 допускает «диаметр/расход». Я выбираю `airflow`, потому что кейсы C2 (VK-1 41 → 45 кг/с) и C6 (воздухозаборники +20%) выражены через расход. Альтернатива `diameter` — данные, а не контракт.
- У платформы на каждый параметр есть номинал `p_nom` (параметры компонента, под который её проектировали) и `growth_margin[param]`. Запас выбирается **при проектировании за цену** (#65): `W·(1 + k_W·gm)`, `unit_cost_own·(1 + k_c·gm)`, `perf·(1 − k_p·gm)`, где `gm` в пределах `[0, gm_max]` по данным класса. Это кейс C9, F-16 с заделами. `margin_left = growth_margin − Σ margin_used` по родословной; запас не восстанавливается.
- Для каждого параметра: `excess = max(0, (p_comp − p_nom)/p_nom)`, деление — отдельная операция. Уровень определяется по худшему параметру (ничья — по id параметра):
  | Уровень | Условие | Последствие |
  |---|---|---|
  | `direct` | все `excess = 0`, крепление совпадает | `cost_mult = 1`, `extra_D0 = 0` |
  | `minor_mod` | `excess ≤ margin_left` (или только иное крепление) | малый `cost_mult`, `extra_D0 ∝ excess`; модификация |
  | `redesign` | `margin_left < excess ≤ margin_left + redesign_reserve` | потомок платформы (`parent_id`), `novelty` по затронутым слотам, `margin_left → 0` (C6, C7 Su-17M) |
  | `new_variant` | `excess ≤ hard_limit` | только новый проект платформы (C7 Su-22) |
  | `incompatible` | `excess > hard_limit` **или** не совпал жёсткий тег (`config`: число и размещение двигателей) | нельзя (C8: 4 вместо 8 на B-52) |
- **Крепление** (`mount_family`) — не уровень, а добавка к цене: `cost_mult += k_mount`, `extra_D0 += d_mount`. Уровень поднимается не выше `minor_mod`. Это #63 и аргумент advocate (F-4/Spey, Su-17/АЛ-21).
- `reasons[]` — пары `(param, excess, margin_left)` по убыванию `excess`. Они идут в `why_not` (`PRODUCT/COMPAT`) и в UI.
- Тесты (property): уровень монотонен по `excess` и не убывает при уменьшении `margin_left`; `direct ⇒ extra_D0 = 0 ∧ cost_mult = 1`; функция не зависит от порядка строк; таблица кейсов C6, C7, C8, C9 даёт ожидаемые уровни.

## 8. Ресурс `service_life_h(design, site)` (#65)
Это не запас, а производная функция снимка. Имя выбрано так, чтобы не путать её с `service_life` среза 1 (возраст списания когорты, 180 мес.).
```
dfrac   = D / D0                                   # отдельная операция; 0 при D0 = 0
y_b     = yield узкого процесса prc_own(c) на site из production_profile (снимок)
life_f  = PowFrac(1 − dfrac, q10_kD) · PowFrac(y_b, q10_ky)
service_life_h = L_min[class,gen] + (L_max[class,gen] − L_min[class,gen]) · life_f
overhaul(c)    = (hours_month / service_life_h) · overhaul_cost(c)      # единственный эффект ресурса
```
- **Эффект один — upkeep** (капремонты). Готовность ресурс не трогает: её уже несёт `(1 − ψ_D·D/D0)`. Иначе один `D` влиял бы на готовность дважды. Альтернатива «ресурс → и готовность» — вопрос владельцу 3.
- Ресурс растёт по двум существующим каналам: выявлению дефектов (испытания + `fleet_hours` **по всем** платформам, на которых стоит компонент; J47 стоял на F-86 и B-47) и `yield` узкого процесса (зрелость производства, C11). Нового канала обучения нет: «зрелость конструкции» не вводится (#65, Разногласия п. 4).
- **Калибровка (Lab, цели [Факт] по historical_cases):**
  | Цель | Источник | Коридор [Предп.] |
  |---|---|---|
  | J47: ~15 ч при допуске (1948) → ~625 ч через ~8 лет (1956), `L_max` ≈ 1 200 ч | C3, S10 | 625 ч ±25%; рост ≥ 25× |
  | WS-10 / AL-31F на одну дату ≈ 30/400 | C11, S32–S34 | отношение 0,05–0,15 |
  | VK-1 при допуске ~25 ч; Jumo 004B 10–25 ч | C1, C2 | допуск «сырого» двигателя даёт 10–40 ч |
- Ablation `q10_ky = 0`: ресурс зависит только от дефектов. Разложение роста ресурса J47 по двум каналам печатается в отчёте Lab, коридор задаёт спецификация среза.

## 9. Лидерство: замыкание и поколение (#62; К§9.1, К§13)
- `fielded(a, t)`: в строю ≥ `n_service_min` единиц d, **собранных на site актора**, и `mastered(a, p, t)` для всех `p ∈ prc_closure(d)`.
  - Импортный двигатель даёт `fleet_value`, но пока PRC двигателя не освоены своими site, d не попадает в `fielded` (#62).
  - Освоение PRC через **другой** свой двигатель засчитывается: #62 говорит о процессах.
- `gen(c)` компонента — поколение его ENG/APP-узла. `gen(d)` платформы с BOM = `min(gen_app(d), min_{c ∈ bom(d)} gen(c))`. Это продолжение правила среза 1 «APP g требует двигатель ≥ g».
  - Модернизированный вариант (старый планер + новый двигатель) не поднимает `G` выше планера.
  - Новый планер на «временном» двигателе (F-14/TF30, C4) получает `G` двигателя, пока его не перемоторизуют.
  - Альтернатива «`gen` только по планеру» — вопрос владельцу 1.
- Переоборудованная когорта переходит к проекту-потомку и сохраняет site сборки планера (§10).
- **Агрегация `G`, `P` по классам (закрывает К§13):** компонентные классы в `G` и `P` не входят напрямую. Они действуют через `prc_closure` (на `fielded`, `T`, `N`) и через `min` в `gen`. Платформенные классы перечисляет сценарий (`lead_classes`):
  - `G` = max `gen(d)` по `fielded` всех перечисленных классов (шкала G0–G4 RR-0008 общая);
  - `P` = `Σ_{class ∈ lead_classes, по id}` max `perf(d)/perf_ref[class]` по `fielded` класса.
  - Во втором срезе класс `jet_fighter` один, так что `P` совпадает с К§9.1, если `perf_ref = 1`.

## 10. Модернизация и допуск (#64)
```
ModernizationProgramme { id (общее пространство requester_id), actor, from_design, to_design,
  cohort_filter {build_year_min, build_year_max}, target_count, conversion_site, rate_cap,
  downtime_months, status }
```
- Условие: `to_design` — потомок `from_design` по `design_lineage`, `compat(from → to) ≤ redesign`. Подпарк — когорты `(design, год выпуска)` по фильтру. Роли — FUTURE (в срезе их нет).
- По умолчанию программы ведёт ИИ по правилу профиля. Игрок их меняет командой (ADR-0014). Решение ИИ — состояние в таблице, действует с t+1 (ADR-0006).
- Каждый месяц: `k = min(rate_cap, held/qty, бюджет/цена переоборудования, остаток)`. Переоборудуемые k единиц уходят из когорты в «вне строя» на `downtime_months`, затем становятся когортой `to_design` с **тем же годом выпуска и site сборки**. Списание — по возрасту планера. Снятые компоненты — `scrapped` (запчасти — FUTURE).
- Работа переоборудования — линия `kind = conversion` на `conversion_site` со своим `line_E`. Это канал сборки К§8.2, учитывается в бюджете (§13).
- **Допуск — решение**, а не порог: `admit(design, series)`, `admit(design, service)` — команда или решение ИИ.
  - Можно допустить «сырой» проект с высоким `D/D0`: ресурс будет низким (§8), готовность тоже (C2: VK-1 — 25 ч; C11).
  - Без `admit(series)` линия не запускается; без `admit(service)` программа не переоборудует.
  - `why_not`: `PRODUCT/NOT_ADMITTED`, рычаг `admit`, и рядом показаны `D/D0` и `service_life_h` при допуске сейчас.

## 11. Дефекты: компонент отдельно, на платформе — интеграция
- Дефекты компонента — в `defects_hidden[c]`, `D0[c]` компонента. Выявляются по К§4.4 по `test_hours(c) + k·fleet_hours(c)`, где `fleet_hours(c) = Σ` по когортам всех платформ с c в BOM `(count·qty·hours)`.
- У платформы `defects_hidden[d]` = свои дефекты (`novelty·complexity_own`) + интеграционные (`extra_D0` из `compat` при проектировании или модификации). Доля интеграционных хранится в отдельной таблице `defects_integration[design]`. Выявленные делятся пропорционально: floor, остаток — своим. Это разбиение одного запаса, а не новый запас (К§3 п. 4 цел).
- `why_not` и UI называют источник: «компонент X / интеграция / свой слот».

## 12. Порядок merge месячного шага (дополняет К§4.0, К§11)
1. `report_output` — `(site_id, prc_id)`. Без изменений, теперь сюда входят и линии компонентов.
2. `consume_component` — `(requester_id, design_id)`: `held −= used`, `installed += used`.
3. `report_component_output` — `(site_id, design_id)`: `stock += units`.
4. `reserve_component` — `(site_id, design_id, requester_id)`: делёж §4, `stock −= Σ granted`, `held += granted`.
5. Операции программ модернизации над когортами — `(programme_id, cohort_id)`. Новые строки когорт дописываются в конец в этом порядке (порядок строк важен, ADR-0013 п. 3).
6. `reserve_workforce` — `(site_id, cat, requester_id)`. Без изменений.

Шаги 2–5 при отсутствии сообщений не выполняются (§15).

## 13. Бюджет каналов §8.2 и абляции для изделия с BOM
- Коридоры К§8.2 применяются **к каждой линии отдельно** (платформа, компонент, переоборудование) по её собственному накопленному выпуску.
- Для `unit_cost_full` платформы `Δlog` на удвоение выпуска платформы раскладывается на 4 канала: выход и сборка платформы, выход и сборка компонента. Выпуск компонента удваивается быстрее (`qty` двигателей на самолёт, плюс модернизация), это учитывается по фактическому выпуску. Сумма должна попасть в тот же коридор (≤ 40% в освоении, 15–30% на зрелой линии); аддитивность — ±15%.
- **Абляция «`line_E` двигателя ≡ 0»** (`b = 0` только для линии компонента). Ожидания:
  - (а) `unit_cost_own` платформы не меняется (разреженность);
  - (б) падение `unit_cost_full` уменьшается ровно на вклад сборки двигателя × его долю в цене (±15%);
  - (в) ни один канал платформы не «подхватывает» обучение двигателя.
- Симметричные абляции: «`line_E` платформы ≡ 0», `q10_ky = 0` (§8).
- **Эквивалентность со срезом 1 (Lab, диагностика).** Сравнивается сценарий, где двигатель — слот, с BOM-сценарием, где линия двигателя на том же site и выпуск 1:1.
  - Падение цены на удвоение должно совпасть в пределах ±10% [Предп.] при данных с `h_first_platform + qty·h_first_engine = h_first_slice1`.
  - Разница допустима только от раздельного `line_E`. Больше — значит появился новый канал.
- Цена тика [Предп.]: ~1,5·10³ компонентных проектов в полной игре; склад, делёж и программы обходятся линейно. `compat` вызывается только при решениях (проект, модификация, программа, годовой перебор ИИ: ~60 стран × 25 пар). Итого < 0,5 мс на месячный тик против бюджета К§11 — несущественно.

## 14. Формат сохранения (ADR-0013 v0 → v1)
- **Новые таблицы**:
  - `design_bom(design_id, slot_id, component_design_id, qty)`;
  - `design_lineage(design_id, parent_id, lineage_id)`;
  - `design_margin(design_id, param_id, growth_margin, margin_used)`;
  - `defects_integration(design_id, value)`;
  - `component_stock(site_id, design_id, units)`, `component_held(requester_id, design_id, units)`;
  - `component_ledger(design_id, produced, installed, scrapped)` — для инварианта;
  - `modernization_programme(...)`, `cohort_conversion(cohort_id, source_cohort_id, programme_id, back_in_service_month)`;
  - `admission(design_id, series, service)`.
- **Схема таблиц среза 1 не меняется**: ни новых колонок, ни переименований. Всё новое — в боковых таблицах.
- Таблицы регистрируются, только если в данных сценария есть класс `kind = component` или включены программы модернизации. В остальных сценариях их нет в `Table` и в `StateHash`.
- `save_format_version` 0 → 1. Это надмножество, поэтому читатель v1 читает файлы v0: нет таблиц — функция выключена. Миграция не нужна: ни одного сохранения игрока ещё нет (ADR-0013 п. 7). Фикстуры второго среза создаются заново.
- Сообщения шагов 2–4 §12 — буферы `[Scratch]`, в снимок не входят. Запросы между тиками не переживают: всё переходящее — в `component_held`.
- Новых потоков RNG нет. Если спецификации понадобится случайность в решениях ИИ по модернизации, она получает новый `system_id` (ADR-0004, «один поток — один смысл»), а не `AI = 5`.

## 15. Срез 1 не меняется — CI-тест (ADR-0002 L1)
- **`Slice1HashUnchangedUnderV3`**. Код v3 с манифестом и данными среза 1 (`jet_fighter`, двигатель-слот `alt`, BOM пуст) прогоняется на seeds 1…20. Годовые и финальные хеши должны совпасть с golden-хешами, зафиксированными до v3 (Linux, ADR-0013 п. 10). Тот же тест — при 1/4/8 потоках (L2).
- Байтовый тест: снимок среза 1 под v1 совпадает со снимком v0, кроме поля `save_format_version` в заголовке.
- Механизм: при пустом BOM формулы §6 не выполняют лишних операций `Fx6`. Новые таблицы не регистрируются. Шаги 2–5 §12 не запускаются. Бюджет пустых тиков (ADR-0006) не меняется.
- Архитектурный тест: `Core.Products` (в том числе компоненты и модернизация) не получает `CounterRng` (срез §9.1).

## 16. `why_not` (дополнение К§6)
- Новые причины слоя `PRODUCT`: `COMPONENTS` (`granted/n < 0.9`), `COMPAT` (уровень ≥ `redesign`, `reasons[]`), `NOT_ADMITTED`.
- Новые рычаги (в реестр сборки): `expand_component_line`, `admit`, `modernization_programme`; `import_component` — только если включён импорт.
- Обход идёт по `prc_closure`: узкое место двигателя показывается как `CAPABILITY` с `subject_id` компонента. Порядок слоёв К§6 не меняется.

## 17. Открытые вопросы владельцу (критичные первыми)
1. **Поколение самолёта на «временном» двигателе.** Рекомендация: (а) `gen = min(планер, двигатель)` — перемоторизация не поднимает `G`, временный двигатель понижает. Альтернатива: (б) `gen` только по планеру — тогда F-14/TF30 сразу 4-е поколение, но `G` можно получить без своего двигателя, и это частично обходит #62.
2. **Делёж двигателей между новым выпуском и модернизацией.** Рекомендация: (а) пропорционально, как `reserve_workforce`, приоритет — через размер запроса. Альтернатива: (б) классы приоритета (новый выпуск раньше) — проще ИИ, но одна программа может голодать годами.
3. **На что влияет ресурс.** Рекомендация: (а) только на содержание (капремонты), готовность — через дефекты, как сейчас. Альтернатива: (б) ещё и на готовность — нагляднее (WS-10 «стоит на земле»), но один дефект считается дважды, и нужна новая абляция.
4. **Импорт двигателей во втором срезе.** Рекомендация: (а) API есть, в MVP выключен (кейс C11 «AL-31F как запасной» — диагностика). Альтернатива: (б) включить с одним поставщиком — проверяет #62 в игре, но добавляет торговлю, которой в срезе нет.
