# ADR-0017 — StateHash schedule and table copy in daily mode

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

Основа: `docs/architecture/notes/daily-hash-and-view.md` §3; профиль `docs/simulation/tick-profile-m0.md` (#283); решения владельца **#289** (расписание хеша) и **#290** (копия таблиц в этом же ADR, доля Kernel 50 мс остаётся).

## Контекст

- [Факт: профиль #283, `hash-copy.txt`] На полном масштабе (200 акторов, 2000 узлов; ≈ 8800 колонок × 200 строк ≈ 14 МБ):
  - `StateHash` (SHA-256) — 37,7 мс на вызов;
  - `Table.CopyCurrentToNext` — 1,88 мс на вызов.
- [Предп.] F8 (TASK-0068: хеш через `MemoryMarshal.AsBytes`, байты те же) снижает хеш до ~8–10 мс. Не замерено на i7.
- ADR-0016 §2 определяет дневной режим так: «каждый день — непустой тик: копия и swap, post, **хеш, снимок**». ADR-0016 §3 даёт Kernel + Session долю `K_d ≤ 50` мс/мес; §4 требует Kernel-ADR до кода #228, если `K_d > 150` мс.
- Ежедневный хеш и полная копия дают ≈ 30 × (9 + 1,9) ≈ 0,33 с/мес, без F8 — ≈ 1,2 с. Одна копия — ≈ 56 мс/мес, больше всей доли `K_d`.
- #228: месячные системы раскладываются по дням, поэтому в игре каждый день будет непустым тиком. Этот ADR — Kernel-ADR, которого требует ADR-0016 §4.
- [Факт] ADR-0002, «Последствия»: хеш считается «каждый тик **(или по расписанию)**». Расписание уровнем детерминизма допускается.
- [Факт] Golden-хеши состояния (SHA-256) лежат в ~15 тестовых файлах, в `SelfTest.cs`, `SliceChecks.cs` и манифестах EXP-0002 (опубликованные результаты).

## Решение

### A. Расписание `StateHash` (#289)

1. **Канонический хеш не меняется.** SHA-256 с байтовым форматом `StateHash.cs` и ADR-0013 п. 2: заголовок `schema_version`, `n_rows`, затем `Current` всех колонок в порядке регистрации, little-endian. F8 меняет способ подачи байтов, а не байты.
2. **`SliceSession.LastHash` — ленивый.** Между тиками таблицы и есть состояние после последнего post: пустые тики его не меняют (ADR-0006). Поэтому хеш, посчитанный по первому запросу и закэшированный до следующего непустого тика, побитно равен хешу, посчитанному сразу после post. `HashComputations` считает только реальные вычисления.
3. **Обязательные точки.** На них хеш считается сразу, даже без запроса:
   - тик месячного шага (при #228 — граница календарного месяца);
   - тик с применённой внешней командой (ADR-0006: такой тик выполняет post и хеш);
   - save (заголовок ADR-0013), load (проверка ADR-0013 п. 8), конец `Replay`.
4. **Ежедневный хеш — execution-only флаг** `SliceRunConfig.HashEveryTick`. Он не хешируется, колонок не добавляет и по умолчанию выключен. При флаге хеш считается на каждом непустом тике. Его включают тесты L1/L2, которые ищут первый расходящийся день, и аудиты Lab.
5. **`SliceView.StateHash` → `string?`.** Значение задано, если хеш этого тика посчитан (п. 3 или п. 4), иначе null. Это изменение поверхности ADR-0014 п. 6: `TestApiVersion` +1.
6. **XXH3/XXH128 и Merkle-хеш не вводятся.** XXH3 — зарезервированный вариант для проверки рассинхрона каждый тик в будущем lockstep-мультиплеере (L3). Там он вводится новым ADR как **второй**, некалибровочный хеш, а SHA-256 остаётся каноническим.

### B. Копия таблиц: только колонки, которые пишут (#290)

7. **Объявленный набор записи.** `ITickSystem` получает `IReadOnlyList<Column> Writes`: колонки, чей `Next` система пишет в `Compute` или `Merge`, включая чужие колонки-почтовые ящики, которые она применяет.
   - Реализация по умолчанию — «все колонки таблицы». Это поведение сегодня, поэтому системы переводятся по одной без изменения результата.
   - `DailyProbeSystem` объявляет пустой набор.
8. **Тик раннера.** Перед compute `TickRunner` последовательно:
   - строит объединение `Writes` активных систем — детерминированно, в порядке регистрации колонок;
   - вызывает `CopyCurrentToNext` и открывает на запись **только эти** колонки.
   После merge `Swap` делается только для открытых колонок, после чего они закрываются. Остальные колонки не копируются и не меняются местами: их `Current` остаётся верным, а устаревший `Next` никто не читает. При следующем открытии копия его обновит.
9. **Структурная защита.** Доступ к `Column<T>.Next` у неоткрытой колонки бросает `InvalidOperationException` во всех сборках. Проверка — чтение одного bool, его выставляет поток симуляции до `Parallel.For`. Необъявленная запись — громкая ошибка, а не тихо пропущенная копия.
10. **Параллельная копия разрешена дополнительно.** Копию открытых колонок можно разбить по диапазонам колонок на потоках раннера: каждая итерация пишет только свои колонки, контракт не меняется. Включать её или нет, решает замер R2.
11. Команды (`CommandState`, `Column.Load` по `Current` между тиками) и post (только чтение `Current`) не затрагиваются.

### Отношение к ADR в силе

- **ADR-0016 §2, частично заменяется.** В абзаце «Обязательный режим — дневной (#228)» слова «каждый день — непустой тик: копия и swap, post, хеш, снимок» заменяются на «каждый день — непустой тик: копия и swap **открытых колонок** (п. 8), post, снимок; хеш — **по расписанию п. 3**». В пункте T1a фраза «Session делает хеш и снимок на каждом непустом тике» читается так: снимок — на каждом непустом тике, хеш — по п. 3. В «Что входит в `T`» (§1) `StateHash` входит в объёме расписания п. 3. Остальное в ADR-0016 (бюджет, раздел, исходы, флаг 150 мс, протокол) остаётся в силе без изменений.
- **ADR-0002:** не меняется (расписание разрешено). L1/L2 проверяются тем же SHA-256.
- **ADR-0006:** фаза post по-прежнему отвечает за хеш состояния после post. Меняется только момент вычисления (по запросу или в обязательной точке), а не значение. Тест «дневной цикл = месячный» сравнивает те же точки.
- **ADR-0013:** формат сохранения и `state_hash` заголовка не меняются.
- **ADR-0014:** п. 4 («хеш после последнего post») соблюдается побитно через ленивый `LastHash`. Меняется поверхность п. 6 (п. 5 выше).

## Рассмотренные альтернативы

| Альтернатива | Причина отказа |
|---|---|
| SHA-256 каждый день (+ F8) | [Предп.] 30 × 8–10 мс ≈ 0,25–0,3 с/мес > 150 мс (флаг ADR-0016). |
| XXH3/XXH128 (`System.IO.Hashing`) каждый день + SHA-256 раз в месяц | Два хеша в API, неясно, какой сверять, новая зависимость. Отложено до lockstep (#289). |
| Merkle-хеш по колонкам или чанкам с грязными колонками | Новый корень ⇒ все golden и EXP-0002 недействительны. При #228 почти все колонки грязные каждый день. Необъявленная запись делает L1/L2 слепыми. Отклонено (#289). |
| Параллельный SHA-256 по колонкам + корень | Новый корень ⇒ все golden. Не нужен при расписании. |
| Двойная буферизация без копии: система обязана записать каждую ячейку своих колонок | Пропущенная ячейка получает значение двухтиковой давности. Это тихая ошибка состояния, которая проходит L1/L2. Отклонено в пользу п. 7–9: там ошибка громкая. |
| Копия по грязным строкам или чанкам | Нужен учёт записи на строку в горячем цикле. Сложность не оправдана, пока неизвестен профиль #228. |
| Только параллельная копия всей таблицы | [Предп.] Ограничена пропускной способностью памяти, ×2–3 ⇒ ~20–28 мс/мес. Сама по себе почти съедает долю. Оставлена как дополнение (п. 10). |
| Пересмотр доли `K_d` вместо оптимизации | Отклонено владельцем (#290: доля 50 мс остаётся). |

## Последствия

**Плюсы:**
- Golden, сохранения и манифесты EXP-0002 действительны, миграции данных нет.
- [Предп.] На зонде M0 `K_d` ≈ 1–2 хеша × 9 мс + копия ~0 + снимок + накладные — в пределах 50 мс, если снимок дешёвый (F7a).
- Необъявленная запись в `Next` становится громкой ошибкой.

**Минусы:**
- [Предп.] При #228 выигрыш копии зависит от наборов записи дневных срезов систем. Его нельзя оценить до ADR #228.
- Новый контракт `Writes` у каждой системы. Объявление «все колонки» по умолчанию прячет недоделанный перевод: см. «Проверка», п. 7.
- Ежедневное расхождение в игре без флага не локализуется до дня, только до месяца или тика команды. Для поиска дня прогон повторяют с `HashEveryTick`.

**Обязательно:**
- новая система объявляет `Writes` (в DoD);
- `TestApiVersion` +1;
- EXP-0007 перерегистрируется до прогона (ниже).

**Влияние:**
- **Тесты L1/L2.** Сравнение хешей на месячных точках и в конце — без изменений. Тесты, которые сравнивают хеш на немесячных днях (`ViewTests` с `v.StateHash == s.LastHash`, `DailyTickProbeTests.FlagOn_HashesAndSnapshotsEveryDay`), включают `HashEveryTick`. L2-матрица (threads 1/4/8/16 × ChunkSize 1/8/32) получает вариант с `HashEveryTick = true`.
- **Lab / EXP-0007.** `K_d` замеряется с `DailyTickProbe = true`, `HashEveryTick = false` (игровое расписание) — это исход ADR-0016 §4. Прогон с `HashEveryTick = true` записывается справочно. `k` на колонку (ADR-0016 §7) пишется отдельно для открытой и неоткрытой колонки. Поправку пре-регистрации вносит Orchestrator до прогона.
- **Golden:** без изменений (байты и алгоритм те же).
- **Формат сохранения:** без изменений.

## Research до ACCEPTED (i7-11800H, условия ADR-0016 §5)

- **R1. `StateHash` после F8.** Точки (200, 2000) и (200, 500): прогрев 100, затем 1000 вызовов; записываются медиана и p95. Ожидание [Предп.]: 8–10 мс. Если p95 > 15 мс, пересмотреть расписание п. 3 (например, только месячный шаг).
- **R2. Копия.** На той же таблице, 1000 повторов:
  - (а) полная `CopyCurrentToNext`;
  - (б) параллельная по диапазонам колонок при t8;
  - (в) копия открытых колонок по наборам записи текущих систем среза на месячном шаге;
  - (г) зонд — пустой набор.
  Записать `k` на колонку.
- **R3 (справка для будущего MP).** `XxHash3`/`XxHash128` той же таблицы — мс на вызов.
- **R4.** Повторный `K_d` по методу ADR-0016 §2 после F1–F8 и п. 1–10.

## Проверка

1. Ленивый хеш: на каждом дне прогона (24, 180) с командами `LastHash` без флага == `LastHash` с `HashEveryTick`. Счётчик `HashComputations` без флага и без чтений `LastHash` равен числу обязательных точек.
2. Golden: все существующие golden-хеши (`dotnet test`, `lab selftest`) проходят без изменения констант.
3. L2: `StateHash` в конце и на месячных точках равен при threads 1/4/8/16 × ChunkSize 1/8/32, с `HashEveryTick` и без него, и при полной копии против копии по `Writes`.
4. Эквивалентность копии: тот же прогон с `Writes` = «все колонки» у всех систем и с объявленными наборами даёт одинаковый хеш на каждом дне (`HashEveryTick`).
5. Защита `Next`: тестовая система, которая пишет необъявленную колонку, получает `InvalidOperationException` при t1 и t8.
6. Сохранение: save → load → продолжение даёт тот же хеш (ADR-0013). `state_hash` в заголовке посчитан в момент save.
7. Архитектурный тест:
   - в Session `StateHash.Compute*` вызывается только из кэша `LastHash` и обязательных точек;
   - список систем Core с `Writes` по умолчанию сверяется с эталоном и может только уменьшаться.
8. Поверхность: снимок API с `string? StateHash` и `TestApiVersion` +1.
9. Бюджет: `K_d` по R4 в EXP-0007.

## Вне ADR (light, отдельные задачи; записка §1–§2)

- **F4-A** — параллельные `ViewBuilder.Inputs` по акторам, слоты `rows[a]`. Условие для F2: кэши не заполняются лениво при чтении.
- **F7a** — переиспользование `Actors` на тиках только с зондом, с поправкой `Closes[].Reason = None`.
- **F7b** — перенос `Inputs`/`Step` до следующего шага (`TestApiVersion` +1, ADR-0014 п. 6). Если будет одобрен, объединить повышение версии с п. 5.
