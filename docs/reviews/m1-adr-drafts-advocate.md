# Gate: M1 ADR drafts — advocate

STATUS: done
SUMMARY: The three drafts are sound at their core, but two decisions taken since they were written break them. Owner decision #504 (M1 core code runs in parallel with the levers core) contradicts the ordering in the daily-tick draft, §4. ADR-0003 rev 3 (#377) already introduced the `Rate` type at scale 2⁵³, so the 10⁻¹² `DayRate` scale in that draft would be a third scale. Under #504, the alternatives the drafts reject — "#228 in parallel" and "tables before the levers" — become the better option.
FILES: none changed (review only)
FINDINGS:
— adr-draft-228-daily-tick.md —
1. (critical) §9 and §4 say #228 core code waits until the levers batch has landed, and owner question 2 asks about this order. Owner decision #504 chose the opposite: parallel work in separate branches, conflict risk accepted. The rejected alternative "#228 parallel to the levers" is now the decision. Fix: rewrite §9 as "start in parallel in separate branches". Keep only the landing order: levers land first, #228 rebases onto them, and §12 (tag of the owner's playtest build before #228 lands) stays. Move §10 and §11 into a "rules for parallel work" section. Remove owner question 2.
2. (high) §5 introduces `DayRate` at scale 10⁻¹². It ignores ADR-0003 rev 3 §54 (#377): the result type is `Rate` at 2⁵³ and inventory item R-3 is already closed. Fix: use the existing `Rate`. Remove "scale 10⁻¹²" from §5, §10 and check 3. Add ADR-0003 to related and to "Частично заменяет", because the ban on negative δ contradicts the golden vectors ADR-0003 proposes.
3. (high) The prototype threshold is day p99 ≤ 100 ms, but EXP-0007 already showed day p99 = 254 ms on M0. The draft gives a branch for K_d > 150 only (§2). Fix: pre-register what happens if day p99 is over 100. Either a separate allocation or GC task, or make the day threshold a warning flag rather than a gate. Otherwise the condition of #503 is likely to fail with no defined next step.
4. (medium) #503 has already accepted §1, so owner question 1 is redundant. Fill in `approval_ref: #503` and remove the question.
5. (medium) Under #504, the requirements of §11 (annual norms, the decay formula, one-off money going to the reserve) are written only as a review checklist for TASK-0150…0153. The checklist will not cover lever code already written. Fix: name the files or commits of TASK-0150 that must be checked against §11 now.
6. (keep as is) The decay and growth rule: λ = −ln(1−δ) with `FloorMul` and `DaySlice`. The alternative, `DayRate` on `Rate`, is weak: rounding down still pushes decay one way, up to 1 raw a day. Check 2 is measurable.
— adr-draft-province-budget.md —
7. (high) §7, the allocation task before the early K4, touches the Core tick path. Under #504 that makes a third branch in the same systems. 1.1 GB/month against a 1 MB limit is about 1000×, and one task is unlikely to close that gap. Fix: pre-register a fallback threshold, for example GC pauses under 10% of T, and put the task into the #228 branch rather than a separate one.
8. (medium, strong alternative) "Day budget instead of month" is rejected only by reference to #333. The owner plays at 3 days/s, so a smooth game needs one day ≤ 333 ms. K4 measures months and catches neither stutter nor the owner's actual speed. Fix: keep K4 unchanged and add a measurable diagnostic gate "day p99 ≤ 333 ms at 3 days/s" (#481). That also makes owner question 2 concrete.
9. (medium) The ≤ 300 ms share for systems rests on the assumption that GC will be removed, which nobody has measured. The p95 shares are added up as if p95 values were additive. Fix: label the split "diagnostic, not additive". Treat measured systems p95 over 300 after the allocation round as an expected WARN, not as "a reason for a round".
10. (low, moderate alternative) Keeping the price register in ARCHITECTURE.md means one more hand-maintained document. The alternative is a `budget_ms` field in the frontmatter of each M1 system task, checked by `registry.py check`, which makes the gate automatic. Proposal for systems-architect.
11. (keep as is) The measurement ladder: prototype, then early K4 at E1a, then final K4. The rejected "new EXP with regions" really is blocked by #419.
— adr-draft-entity-tables.md —
12. (high, strong alternative) The draft rejects "move before the levers" and has the lever code written in an interim layout, then moved a second time (§6). Under #504 a second golden re-record is already accepted. The Kernel `World` work plus child tables is small: the multi-table-api note estimates 1.5–2.5 days, plus `NextRange`. Fix: make the D2 branch of §6 the default plan. The Kernel step lands first, and `institutes` and `licences` are created as tables inside the levers batch. That avoids moving the lever code twice (§6, ≈ 1–2 days).
13. (medium) `institutes` are grouped by owner with fixed offsets. On a change of owner or a new polity (#312, #313, decolonisation), the grouping by parent breaks. Fix: either say explicitly that the owner is fixed for M1, or give `institutes` its own `ChunkTable` with an `owner` column and send sums to the actor through merge buffers.
14. (medium) §3 removes the `cmd.*` queues in #228, which changes when commands take effect. TASK-0150/0153 add `SetPriorityNode` and `FundProgramme` in parallel. Fix: require the levers batch to keep its new commands only in the command log (ADR-0014) and as columns of their own entity, never in `cmd.*`.
15. (low) The tick cost of `designs` (3–6 ms/month K_d) is an assumption. Fix: add `designs` and `institutes` to the measurement points of prototype 3.5.
— all three —
16. (low) The headers still say the drafts sit in `docs/architecture/drafts/`, but they are now in `docs/decisions/drafts/`.
