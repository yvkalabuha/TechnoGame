Независимый эталон для теста P0 (T8): решение #42, спецификация `docs/simulation/slice-jet-aviation.md` §6.4, §11 T9; формулы — `docs/architecture/LAYER_CONTRACT.md` v2.2.

## Краткий вывод
- Одна команда, только stdlib: `python3 lab/reference/jet_slice/jet_ref.py` (пишет `out/`), `python3 lab/reference/jet_slice/jet_ref.py --check` (код 1, если `out/` расходится со свежим прогоном или потеряно покрытие траектории).
- Арифметика повторяет Core по правилу ADR-0003 R1–R2 (#49): все величины — `Fx6` (целые raw = значение·10⁶), каждое `*` и `/` — floor, как `Fx6.FloorDiv`; проверка вероятности — `(NextU64 >> 11) < ⌊p_raw·2⁵³/10⁶⌋`; `CounterRng` портирован и сверяется с векторами `tests/Singularity.Kernel.Tests/CounterRngTests.cs` при каждом запуске. `double` нет нигде.
- `out/formulas.json`: 11 случаев `culture_H` (контракт §4.1), 8 случаев `production_profile` (§4.2), `c_eff`/прогресс и 7 случаев hazard (спец. §3.1), проверка вероятности, выборки `⌊3U⌋`/`j`/целое 6…18 (спец. §9.2), дележ `reserve_workforce` (контракт §4.6).
- `out/trajectory.json` (+ `trajectory.csv` для чтения): 1 актор, 6 узлов (FND, hazard-ENG, CMP, PRC, APP + стартовый PRC), 24 тика, состояние после каждого тика и журнал merge.
- **Не покрыто:** `q` (не определён в контракте, A4), изделие (`PowFrac`, `assembly_hours`, дефекты, когорты), `why_not`, события, лицензия в траектории (только в формулах), `world_lead` = 1 в траектории (один актор; есть в формулах).
- [Предл.] Порядок вычислений внутри формулы контрактом не задан; эталон считает «слева направо, как записано» (A1). Пока это не принято как правило, T8 должен либо повторить этот порядок, либо сверять с допуском (см. «Тесты для T8»).

## Соглашения формата
- Все числа `Fx6` в JSON — целые raw (`3500000` = 3,5). Целые без масштаба: тики, id, люди в `workforce_split`, `u`, `r`, `threshold`.
- Узел = индекс в ключе RNG (`entity = actor·64 + node`, спец. §9.1); актор траектории = 0 (A7).
- `formulas.json` — у каждого случая `input` и `output` с промежуточными величинами (`drive`, `maint`, `sat`, `g` по измерениям, `ramp`, `yc`…), чтобы T8 мог локализовать расхождение.
- `trajectory.json`: `setup` (решение ИИ тика 0, профиль из потока `AI`), затем `rows[t]`: `commands_applied` (решены на t−1), `knowledge` (вес, `alloc`, `c_eff`, `dprog`, `prog_new`, ключ/`u`/порог hazard), `merge_report_output` и `merge_discoveries` в каноническом порядке, `commands_issued` (применятся на t+1), `yield_used` (по снимку), `state_after`.

## Порядок тика в эталоне
1. Начало t: бюджет `budget(t) = budget(t−1)·(1 + g/12)` (`g/12` сначала, A12); применяются команды, решённые на t−1.
2. compute (только снимок): НИОКР `S = share_R·budget`, фронтир по снимку, `w_n = prio·j / Σ`, `alloc = S·w_n`, `prog += alloc/c_eff`; детерминированный узел открывается при `prog_new ≥ 1`, hazard — по `prog_new` (A3b); выпуск PRC по `yield` из снимка и действующему темпу; команды ИИ на t+1 (темп линий — каждый месяц, `j` года — при t mod 12 = 0, t > 0).
3. merge: `report_output` по `(site, prc)` → `proc_X`; открытия по `(actor, node)`; `K_d += μ_K·amount_d/S_ref + k_node·opened_d`; `culture_H` по `v_p` этого тика и `H` снимка (A3); износ `tooling_M`; забывание `proc_X` простаивающих PRC.
4. post: `K_ind` по `V_d` этого тика и уже обновлённому `K_d` (A10); инварианты.

Покрытие траектории (`coverage` в JSON, проверяется в `--check`): промах hazard до открытия (ENG: тики 9, 10 — промах, 11 — открытие), два `report_output` в одном тике (с 17), два открытия в одном тике (11: узлы 2 и 3), команда темпа `t → t+1` (решена 16, действует 17), годовая команда `j` (12 → 13), открытие APP (19). Seed 6 выбран перебором `--find-seed` как первый, дающий всё покрытие; это выбор фикстуры, а не результат модели.

## Инварианты и тесты детерминизма для T8
Эталон проверяет на себе в каждом тике (`assert`) I1, I2, I4, I5 и диапазон `yield` из I3.
- I1 `0 ≤ culture_H`; рост за месяц ≤ `ρ_max` + 1 raw (RR-0006 §4.14).
- I2 падение `culture_H` не опускает ниже `min(H_prev, H_floor)` (#30).
- I3 `0 ≤ yield ≤ 1`; `g` монотонна по `c_d`; `yield = 0` ⇒ нет `report_output`.
- I4 расходы НИОКР ≤ `S_R` ≤ бюджет; остаток сгорает (спец. §3.4).
- I5 hazard-`prog` ≤ `prog_cap`; известный узел имеет известные `requires` (для `alt_group` — хотя бы один).
- I6 `granted ≤ n`, `Σ granted ≤ avail`, остаток раздаётся по `requester_id` (контракт §4.6).
- I7 `Core.Industry`, `Core.Products` не получают `CounterRng`; в Core нет `double` (ADR-0003 R1, тест архитектуры).

Тесты T8 по эталону:
- D1 формулы: каждый случай `formulas.json` → C#-функция; сравнение raw **точно**. Если порядок A1 не принят, сравнение `|Δ| ≤ k` raw с явным `k` в тесте и пометкой — решение Orchestrator.
- D2 `CounterRng`: векторы `counter_rng` и `draws` (`⌊3U⌋`, `j`, 6…18) — точно.
- D3 проверка вероятности: `prob_check` (включая `p = 0`, `p = 1`, `u = 0`, `u = 2⁶⁴−1`) — точно.
- D4 траектория: C#-прогон той же фикстуры с seed 6 → `state_after` каждого тика и журналы merge совпадают с `trajectory.json`.
- D5 инъекция `u`: те же тики, но `NextU64` подменён значениями из `rows[].knowledge[].hazard.u` — проверяет логику hazard отдельно от порта RNG.
- D6 порядок обхода: перемешать порядок акторов/узлов/сообщений в compute — результат бит-в-бит тот же (значение RNG — функция ключа, merge сортирует).
- D7 L1: два прогона подряд — одинаковые хеши; L2: threads 1/4/8 (спец. §9.3).
- D8 t → t+1: команда, решённая на t, не влияет на compute тика t (тик 16 в траектории: `rate_in_force[4] = 0`, хотя PRC 4 известен).
