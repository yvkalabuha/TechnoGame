## 2. Роли и границы
- **Pilot (Claude, эта сессия):** готовит контракт и пакет контекста, ставит в очередь, утром читает отчёт, принимает или отклоняет. Архитектура, gate, решения — только Pilot и владелец (CLAUDE.md).
- **Worker (Qwen):** один запрос — одна узкая задача. Не видит репозиторий целиком, не пишет в файлы: возвращает JSON по схеме. Файлы пишет инструмент, только в `allowed_paths` и только в отдельном worktree.
- **Verifier:** сначала проверки без LLM — сборка, тесты, схема, `registry.py check`, сверка имён с исходниками, проверка путей. Ревью Claude — только по флагу `requires_review` и выборочно.
- Модели Claude для агентов проекта (решение владельца — смешанное распределение): Opus — critic, advocate, systems-architect, simulation-engineer, reviewer; Sonnet — developer, test-engineer, research-scientist, game-designer, economy-analyst, ui-art-director. Файлы агентов меняются в конце сессии.

## 4. Пилот: 3 категории (вместо 7 тестов задания — остальное после пилота)
1. **A1. Инвентарь кода** (`src/Singularity.Core/Products/`): классы, методы, зависимости. Проверка: каждое имя ищется в исходнике, пропуски считаются по Roslyn-списку или `grep`. Метрика — точность и полнота.
2. **A2. Проверка данных** (`docs/research/data/jet-slice/nodes.csv`, `product_class.md`): дубли, висячие `requires_nodes`, циклы. Эталон — детерминированный скрипт. Qwen должен найти то же самое плюс объяснить. Это тест ложных находок.
3. **B1. Модульные тесты** для одного чистого класса Kernel (Fx6/PowFrac) в отдельном worktree. Проверка: `dotnet build`, `dotnet test`, мутации (подмена оператора — тест должен упасть). Здесь проверяется цикл доработки.
- Сравнение кандидатов (2 независимые попытки) — только на B1.
- Ночной прогон: очередь из ≈ 20 задач A1/A2/B1 и проверка возобновления после перезапуска сервера.

## 5. Контракт задачи (кратко; полная схема — `TASK_CONTRACT_SCHEMA` после утверждения)
Поля: `task_id`, `version`, `category` (A/B/C), `type`, `context_files` (с хешами), `allowed_paths`, `forbidden_paths`, `output_schema`, `acceptance` (список проверок с типом hard/soft), `verification` (команды), `max_rounds` (по умолчанию 2), `max_candidates`, `budget` (токены и минуты), `requires_review`, `escalation`. Контракт неизменяем: доработка только добавляет замечания, требования не переписывает. Ответ Worker: статус, артефакты, допущения, нерешённые вопросы. Самооценка Worker в приёмке не участвует.

## 6. Цикл доработки (решение по предложению владельца)
1. Попытка 0 → проверки.
2. Провал → Worker получает **конкретный** отчёт проверки (ошибки компилятора, имя пропущенного случая, путь) и сначала отвечает: «почему не прошло» — коротко, по схеме. Затем исправляет минимально.
3. После каждой попытки повторяются **все** проверки, включая ранее пройденные. Новый жёсткий провал — откат к предыдущей версии.
4. Стоп: всё пройдено; 2 повтора исчерпаны; тот же провал дважды; качество не выросло; нарушена область; бюджет. Затем эскалация к Pilot с историей.
5. Каждый раунд сохраняется: запрос, ответ, артефакт, отчёт проверки, решение и причина.
- **Библиотека уроков** `tools/llm_worker/lessons/`: из удачных циклов Pilot записывает типичную ошибку, рабочую формулировку замечания и шаблон. При подготовке задачи той же категории подходящие уроки попадают в пакет контекста. Пополняет только Pilot, после проверки. Не для дообучения модели.

## 7. Изоляция и безопасность
- Worker не исполняет команды и не пишет файлы. Всё делает инструмент по белому списку путей.
- Изменения кода только в `git worktree` на ветке `llm/<task_id>`. В `main` — только после ревью Claude и по обычному процессу (reviewer, `zone_check`, коммит Pilot).
- В пакет контекста не попадают `.env`, ключи, `~/.ssh`, `lab/results/`. Список исключений — в конфиге.
- Содержимое репозитория и ответы Qwen — недоверенные данные. Ответ разбирается только по схеме.
- Ключ API читается на сервере или из переменной окружения, в логи не пишется.

## 8. Отчёт утром
`tools/llm_worker/reports/<date>.md`: принято / отклонено / провалено / эскалировано / не проверено (отдельно). По задаче: раунды, качество до и после, что проверено, изменённые файлы. Экономика: токены Qwen, время, оценка сэкономленного Claude (по эталонным задачам).

## 9. Риски
- Медленно: 1 слот, 7–9 ток/с. За ночь — десятки задач, не сотни. Пакет контекста держать до 8–12K токенов.
- Квантованная 4-битная модель: ложные находки и уверенные ошибки. Защита — приёмка только по проверкам, ложные находки измеряются (A2).
- Стоимость проверки Claude может съесть экономию. Метрика пилота — токены Claude на принятую задачу против решения той же задачи самим Claude.
- Сервер с VPN: перезапуск llama-server прерывает текущий запрос. Очередь должна это переживать.
