- [high] §5.18–19 replace ADR-0016's mandatory budget and outcome table without a partial-supersede clause: ADR-0016 §1 makes p95 ≤ 500 ms and median ≤ 400 ms mandatory; §3 fixes systems ≤ 100 ms, K_d ≤ 50 ms and a 350 ms reserve governed by the `19·P` rule requiring an ADR if `S + K_d + 19·P > 500`; §4 makes p95 > 500 a FAIL that triggers an optimisation round, not a speed cut. ADR-0020 §5.18–19 instead defines PASS by p95/median alone, WARN for 500–1500 with a speed reduction, FAIL > 1500, and moves provinces (100 ms) and E1/other (250 ms) out of the 350 ms reserve. It says it only 'уточняет диагностический раздел', keeps ADR-0016 ACCEPTED with empty `supersedes`, and never mentions the `19·P` rule or the S/K_d share checks. MS-M1 K4 already relies on the new thresholds, so the registry and gate criteria conflict.
- [high] ≤4 controllers / 4 `attr` slots conflicts with the expected Vienna '4 sectors + center': §1.4 defines `attr_polity_0..3` and §7 caps a region at 4 controllers; §12 expects Vienna in `mixed_regions` as '4 сектора + центр', and ADR-0011 §5 confirms the center is a joint polity with up to 4 members. The center is one additional controller polity, so a Vienna region containing all five has 5 controllers and one has no `attr` slot; if the center is made a separate region, Vienna is not a mixed region and the province-set rule changes. Berlin's 4 sectors fit; Vienna's do not.
- [high] `mixed` in generated/sealed `regions.yaml`; per-province `w_p` has no defined file, schema or hash: ADR-0011 §2.11 fixes `regions.yaml` output to `id`, `capital_province`, `isolated`; it is generated by `tools/map` and §4 seals `map/*` in v1. ADR-0020 §1.2 says weights are Core.Map arrays, while 'Влияние' adds a `mixed: {weights_source, as_of}` field to `regions.yaml`, but no file, lock, schema or hash rule holds the actual `w_p` values. Mixed status and weights are scenario/occupation-dependent (1945 controllers), not geography, so a scenario mod allowed by ADR-0011 §4 to change polities/owners could not change them. The present `regions.yaml` (sha b224…) has no such field and covers Europe only.
- [high] `econ_shares` in `polities.yaml` classified as DataHash, contradicting ADR-0011's scenario_hash: ADR-0011 §1 says `polities.yaml` enters `scenario_hash`; §4 defines `DataHash` for `map/*.yaml` including derived geometry. ADR-0020 'Влияние на ADR-0011' assigns `econ_shares` in `polities.yaml` to DataHash and the validator, contradicting an ACCEPTED ADR and the save/scenario binding. Scenario mods (ADR-0011 §4) change `polities.yaml`, so DataHash classification would misclassify the file and could interact incorrectly with ADR-0013 §8 checks.
- [high] Actor budget `share(r,a) × region output` with Fx6 shares cannot preserve raw output (K3): §1.4 stores `attr_share` as Fx6 summing to 1,000000; §17 defines the actor budget as Σ `share × output`. Multiplying an Fx6 share by an integer/Fx6 region output requires per-actor rounding; with 3–4 controllers and small outputs (e.g. F = 1 raw unit) the rounded parts need not sum to F, so the §2.10/K3 conservation invariant (money, energy, people) and property test #5 can fail. `Apportion` is defined for splitting a sum by weights, not for multiplying a pre-rounded share.
- [medium] K9 change journal and 'change not from the event table — error' lack a mechanism: §2.8 explicitly says there is no separate state flag; §2.10 asserts the invariant, but after swap there is no previous state to compare and no table/column holds a journal; ADR-0013 §4 forbids state outside tables. MS-M1 K9 requires a change journal in Lab output and StateHash, and ADR-0019 §3.12 lists a change journal in post. If the journal is state it must be a table and hashed; if output-only, 'in StateHash' is undefined and unauthorised changes cannot be detected.
- [medium] Alignment CI cannot be green on staged map/event data: §11 runs over t0 and every date of the whole 1.6a event table and fails on any unaligned event. MS-M1 runs map 1.1 and event table 1.6a in parallel, with the event core first and the wide list later; the current `regions.yaml` covers only ~80 European regions and lacks Berlin/Vienna provinces. Events referencing missing provinces cannot be checked, and any partial map/event set produces red CI. No coverage/waiver rule is defined, yet the ADR names CI as the enforcement mechanism and admits map 1.1 depends on 1.6a.
- [medium] Province/region CoW and StateHash are both in `K_d ≤ 50` and in the new province share ≤ 100: ADR-0016 §1 includes table copy/swap and `StateHash` in `K_d`; ADR-0017 puts CoW and `LastHash` in Kernel; the `provinces`/`regions` tables are Kernel state. ADR-0020 assigns a separate province share (≤ 100 ms) while keeping `K_d ≤ 50`, and its < 5 ms/month decomposition mentions province hash, CoW and the view without saying which bucket pays. Event-day CoW and hash points can be capped twice or not capped; the 100 ms share is not reconciled with `K_d`.
- [medium] Multi-table world hash omits table names and per-table column counts: §1.5 hashes `table_count`, per-table `schema_version`, `n_rows` and the columns, but not table names or column counts, unlike ADR-0013's save header which stores table names. ADR-0013 §8 checks only `StateHash`, which will match a consistently stale save. No build-time or load-time validator is defined; tests #3/#5 cover post-event but not t0/load.
