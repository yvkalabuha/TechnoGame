# ADR-0019 — Monthly systems split into daily slices (#228), revision of ADR-0006

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Уровень: gate+research (меняет все golden мира M1). Пункт 0.2 плана `development/milestones/MS-M1-economy-provinces-open-race.md`. Зависит от ADR-0003 (0.1).

## Краткий вывод
- [Предл.] Режим тика — **глобальный** параметр сценария: `TickModel = Daily228 | SliceLegacy`. Смешивать режимы в одном мире нельзя. Внутри `Daily228` у каждой системы явная **роль**: `Flow` (величины, режутся по дням) или `Decision` (дискретные решения, остаются на своей частоте и читают свежее состояние).
- [Предл.] Месячная величина `F` режется функцией Kernel `Fx6.DaySlice(F, k, D)` по **накопленной доле** (без колонок остатка): при постоянном `F` сумма за месяц равна `F` до бита. Деньги и ресурсы сохраняются двойной записью: каждый перевод — одно число, списанное и зачисленное.
- [Предл.] Порядок дня `D`: внешние команды → compute всех систем по `Current` (конец дня `D−1`) → merge в порядке списка (сценарные события пишут владение в merge, ADR-0011 §3) → swap → post. Событие с датой `D` есть в состоянии на конец `D` и действует на вычисления с `D+1`.
- [Предл.] `SliceLegacy` — нынешний путь M0 без изменений, эталон EXP-0002 (`183e47b9…` main, `824f4ded…` det). Живёт до закрытия M2 (K6), запись в TECH_DEBT.
- [Предл.] Хеш — по ADR-0017 без изменений. При `Daily228` каждый день непустой, поэтому `HashEveryTick` = 30 хешей в месяц (только тесты и Lab). Контрольная точка месяца — та же граница первого дня.

## Контекст
- [Факт: DECISIONS_LOG #228] Месячные системы раскладываются по дням и каждый день читают свежее состояние; это меняет все golden; срез M0 (EXP-0002) остаётся на прежней семантике.
- [Факт: ADR-0006] Тик = день; системы с `Cadence`; месячная система за один запуск обрабатывает весь месяц; compute читает `Current`, merge — в порядке списка систем; пустой тик ничего не делает.
- [Факт: код `TickRunner.cs`] Все системы тика читают одно состояние `Current`; merge идут в порядке списка; post — после swap. Ключ RNG — `(seed, tick, system, entity, n)` (ADR-0004).
- [Факт: код `SliceSession.StepOne`] Команды и `Policy.ApplyDeals` пишут `Current` до `RunTick`.
- [Факт: ADR-0017] CoW по колонкам, хеш по расписанию (`HashCheckpoints`, `HashEveryTick`); R2 (в) — кривая цены CoW при доле записываемых колонок 0–100 % — замеряется в EXP-0007.
- [Факт: ADR-0016 §2] `S` среза — нижняя граница: в #228 фиксированная цена вызова системы умножается на ~30.
- [Факт: ADR-0011 §3, «Обязательно»] Владение меняется только в merge; изменение видно в `t+1`.
- [Факт: план MS-M1, K5, K6, «Нужно от systems-architect» (а), (в), (е)] — вопросы этого ADR.

## Решение

### 1. Режим глобальный, роль — на системе
1. `TickModel` задаётся сценарием и входит в `scenario_hash` (меняет динамику, поэтому не execution-only флаг). Значения: `Daily228` (основной в M1), `SliceLegacy` (только мир среза M0).
2. В `Daily228` каждая система объявляет `SliceRole`:
   - `Flow` — пишет величины (выпуск, потребление, переводы, накопление прогресса). `Cadence = Daily`. Месячные параметры режутся по п. 2.
   - `Decision` — пишет дискретное решение (бюджетные доли ИИ, выбор, старт проекта). Частота — своя (обычно `Monthly`, день 1); читает `Current` на конец предыдущего дня, то есть свежее состояние. Решение действует со следующего тика (ADR-0006).
   - Роль без значения по умолчанию: список ролей — явная таблица в Core (`SliceRoles`); система без записи не регистрируется в `Daily228`.
3. Система с двумя ролями (например, Industry: распределение усилий — `Decision`, накопление прогресса — `Flow`) делится на две системы. Перевод слоя способности M0 — пункт 2.5 плана.
4. **Почему не по системам.** Смесь «одна система месячная целиком, соседняя дневная» даёт третью семантику, которую не проверяет ни golden M0, ни golden M1. Глобальный режим оставляет ровно два набора golden.

### 2. Нарезка величин и сохранение
5. Параметры потоков задаются **за календарный месяц** (`F`, Fx6). Срез дня `k` месяца длины `D` (`D` — из календаря Kernel):
   - `DaySlice(F, k, D) = q + (trunc(r·k/D) − trunc(r·(k−1)/D))`, где `q = F / D`, `r = F % D`; все деления — с усечением к нулю (как `/` и `%` в C#), `|r| < D ≤ 31`, переполнения нет;
   - знак симметричен: `DaySlice(−F) = −DaySlice(F)`;
   - при постоянном `F` за месяц `Σ_k DaySlice = F` точно; при меняющемся `F` каждый срез отличается от `F/D` не больше чем на 1 raw-единицу.
   - Состояния остатка нет: срез — чистая функция `(F, k, D)`; save/load и replay его не касаются.
6. **Раздел суммы между получателями** (доли, нормирование при нехватке): `Apportion(F, w[])` по накопленным весам `trunc(F·W_i/W) − trunc(F·W_{i−1}/W)`, `W_i` — сумма весов `w_0..w_i`, `w ≥ 0`, обход в порядке индекса получателя, промежуточное произведение 128-битное (`Int128`). Сумма частей равна `F` точно.
7. **Сохранение.** Перевод между строками — одна величина `x`: источник получает `−x`, приёмник `+x` в одном merge. Нормирование (спрос больше запаса) считается на **полной** сумме спроса дня, а не по мере поступления заявок. Инвариант post: `stock(t+1) = stock(t) + Σ in − Σ out` в raw-единицах для денег, энергии, людей (K3).
8. Пороговые события (достижение мощности, завершение проекта) проверяются по дневному накопленному состоянию; дата события — день пересечения порога.

### 3. Порядок внутри дня `D` (#325, #328)
9. Session до `RunTick`: внешние команды с `apply_tick = D` по ключу `(apply_tick, source_class, source_id, local_n)` (ADR-0014); затем действия начала месяца, если `D` — день 1 (как `ApplyDeals` сейчас).
10. compute всех систем, у которых `D` по частоте, — по `Current` (конец `D−1` плюс команды п. 9).
11. merge в порядке списка систем. `ScenarioEventSystem` (`Cadence = Daily`) — **первая** в списке: в merge дня `D` она пишет `owner`/`controller` провинций и производные колонки региона (ADR-0020) для всех событий с датой `D`, в порядке `(date, event_id)`. Остальные merge владения не читают.
12. swap, post (инварианты K3/K9, журнал смен), снимок view, хеш по расписанию ADR-0017.
13. Итог: событие с датой `D` есть в состоянии конца дня `D`, а потоки дня `D` посчитаны при старом владении. Решения дня 1 следующего месяца видят все события до последнего дня прошлого месяца включительно. Это следует из ADR-0011 §3 и не меняет его.

### 4. Слияние дневных вкладов при L2
14. По умолчанию — **pull**: строка-приёмник сама считает своё изменение, читая `Current` источников; пишет только свою строку. Буферы не нужны.
15. **Push** (вклад в чужую строку) — только через буфер чанка; merge применяет буферы в порядке чанков 0..N−1, внутри чанка — в порядке выпуска. Сложение — целое `long` с проверкой переполнения (`checked`), поэтому сумма от порядка не зависит.
16. Любая нелинейная операция над суммой (clamp, нормирование, порог) — после полного сложения вкладов дня, в merge владельца колонки или в compute следующего дня. Последовательные clamp по мере поступления вкладов запрещены: они зависят от порядка.
17. Агрегат актора из регионов (бюджет, #330) — pull по атрибуции ADR-0020, обход регионов по возрастанию индекса.

### 5. `SliceLegacy`
18. `SliceLegacy` выбирает нынешний набор систем среза с `Cadence.Monthly`, нынешний `SliceSession.StepOne` и ключи RNG месячного тика. Код M0, который меняется для `Daily228`, ветвится по режиму, а не переписывается.
19. Эталон: EXP-0002 det `golden_set_hash` `824f4ded07216828ee6354f95f6bd942dcefd6059f70fdff24fbf9f9ab91ea5b` и main `183e47b9fc81957ccd6a53f93f5d09f4d10a2ca094b0be119680bd1cf42ab02d` (`docs/simulation/exp0002-result.md` §1). Если ADR-0003 меняет golden среза, новый эталон принимает владелец с отчётом о расхождении (K6).
20. Срок жизни — до закрытия M2; запись в TECH_DEBT (Orchestrator). Снятие — решение владельца в DECISIONS_LOG; замороженные EXP не правятся.
21. Тест ADR-0006 «дневной цикл = месячный» остаётся тестом `SliceLegacy`.

### 6. Хеш, CoW и view (ADR-0017)
22. Байтовый формат и алгоритм хеша — без изменений. Контрольная точка (а) ADR-0017 п. 3 — тик первого дня месяца в обоих режимах. При `Daily228` каждый день непустой, поэтому `HashEveryTick` даёт хеш каждый день: [Предп.] ≈ 30 × 8–10 мс ≈ 0,25–0,3 с/мес — цена только тестов и Lab, в игре её нет (#291).
23. CoW: `Flow`-системы открывают свои колонки каждый день. Цена копии в `K_d` = доля открытых колонок × цена полной копии — кривая R2 (в) из EXP-0007. `Decision`-системы открывают колонки один раз в месяц.
24. **Публикация view (частично заменяет ADR-0014 п. 5).** Игровой хост может включить `ViewPublish = OnRequest`: снимок строится после непустого тика, только если хост с прошлой публикации запросил его (флаг кадра). Флаг execution-only, на состояние не влияет. Тесты и Lab — `EveryTick` по умолчанию.

### 7. Бюджет (ADR-0016)
25. `T` замеряется в `Daily228` (K4). Ожидание [Предп.]: цена `Flow`-систем растёт в ~30 раз по фиксированной части вызова; `Decision`-системы — без изменения.
26. Каждая `Flow`-система заявляет удельную цену на день (ADR-0016 «Обязательно»). Если `S_daily + K_d + заявленное > 500` мс — gate до кода системы; при WARN — пол скорости #331 (ADR-0020).

### Частично заменяет
- **ADR-0006:** «Месячная система за один запуск обрабатывает весь месяц» — только в `SliceLegacy`; в `Daily228` действует п. 1–2. Тест «дневной = месячный» — только `SliceLegacy`.
- **ADR-0014 п. 5:** публикация после каждого непустого тика — по умолчанию; `OnRequest` — п. 24.
- **ADR-0016 §2 «Составляющие»:** разложение `k_i = (T_i − M_i)/29` действует только в `SliceLegacy`; в `Daily228` месячного прогона с теми же состояниями нет, `S` и `K_d` берутся из профиля (inclusive по системам и Kernel).
- Не меняются: ADR-0002, ADR-0013, ADR-0017.

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| Режим на систему (часть систем месячные, часть дневные в одном мире) | Третья семантика без golden; K6 ломается незаметно |
| Нарезка «побитно равна месячному запуску» (рекомендация до #228) | Отклонена владельцем #228 |
| Все системы дневные, включая решения ИИ | [Предп.] ×30 цены ИИ без выигрыша в смысле: решение раз в день меняет доли бюджета 30 раз за месяц, «дрожание» бюджета. Вынесено на вопрос владельцу 1 |
| Параметры как физическая дневная норма (31-дневный месяц даёт больше) | Месячные итоги «пляшут» по длине месяца, февральский провал в метриках; калибровка E1 по месячным якорям сложнее. Вопрос 2 |
| Остаток деления в колонке на поток | Лишнее состояние и колонки в хеше; накопленная доля даёт ту же точность без состояния |
| События до compute (как команды), видимые в тот же день | Противоречит ADR-0011 §3 «владение — только в merge»; нужен пересмотр ACCEPTED ADR. Вопрос 3 |
| Clamp по мере поступления вкладов | Зависит от порядка, L2 ломается |
| Удалить `SliceLegacy` сразу | Нарушает K6 и #228 («срез M0 не меняется») |

## Последствия
- **Плюсы:** один набор golden на режим; сохранение денег и ресурсов точное и проверяемое; нарезка без нового состояния; порядок событий совместим с ADR-0011.
- **Минусы:** все golden M1 новые; слой способности M0 делится на `Decision`/`Flow` (пункт 2.5); код M0 ветвится по режиму до M2; `HashEveryTick` дорог в Lab (×30).
- **Обязательно:** `SliceRole` у каждой системы `Daily228`; `DaySlice`/`Apportion` только из Kernel; нормирование после суммы; `ScenarioEventSystem` первая в списке.

## Проверка
1. **Нарезка (property-тесты, Kernel):** для случайных `F` (включая отрицательные и около `long.MaxValue/31`) и `D ∈ {28, 29, 30, 31}`: `Σ_k DaySlice(F, k, D) = F`; `DaySlice(−F) = −DaySlice(F)`; `|DaySlice − F/D| ≤ 1` raw. `Apportion`: сумма равна `F`, порядок индексов фиксирован.
2. **Сохранение (post, каждый день):** инварианты K3 в raw-единицах на 100 % тиков, в том числе в дни событий.
3. **L2:** `Daily228`, threads 1/4/8/16 × ChunkSize 1/8/32, `HashEveryTick` — хеш каждого дня равен.
4. **Порядок дня:** тест с командой и событием в один день `D` и в день 1: потоки `D` — при старом владении, состояние конца `D` — с новым; решение дня 1 видит событие последнего дня прошлого месяца.
5. **Push-слияние:** тестовая система с push-вкладами из всех чанков в одну строку, t16, ChunkSize 1, 20 повторов — одинаковый хеш.
6. **Роли:** архитектурный тест — каждая система мира `Daily228` есть в `SliceRoles`; `Flow` имеет `Cadence.Daily`.
7. **`SliceLegacy`:** CI на каждый PR, меняющий `src/Singularity.{Kernel,Core,Session}`, — матрица `EXP-0002-det` даёт `824f4ded…`; main `183e47b9…` — на каждом gate M1 и при закрытии M1.
8. **Хеш:** тесты ADR-0017 (п. 4, 6, 8) в `Daily228`.
9. **View:** `OnRequest` без запросов не строит снимков; с запросом — снимок равен построенному в `EveryTick`.
10. **Бюджет:** K4 в EXP бенчмарка полного мира (пункт 2.8, ранняя версия на gate 2.10).

## Вопросы владельцу (критичные первыми)
1. **Решения ИИ.** [Предл.] Дневными становятся только потоки (выпуск, потребление, переводы, прогресс); решения ИИ и бюджетные доли остаются раз в месяц, но читают свежее состояние. Альтернатива — всё дневное, включая ИИ (дороже ×30, бюджет «дрожит»). Это соответствует смыслу #228?
2. **Единица нормы.** [Предл.] Норма потока — «за календарный месяц», делится на дни месяца; месяц любой длины даёт одинаковый итог. Альтернатива — дневная норма (31-дневный месяц даёт на 11 % больше февраля).
3. **Когда действует событие.** [Предл.] Событие с датой `D` видно в состоянии на конец `D` и влияет на расчёты с `D+1` (по ADR-0011). Альтернатива — с утра `D` (нужен пересмотр ADR-0011 §3).
