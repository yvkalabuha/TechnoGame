# ADR-0013 — Формат сохранения v0: бинарный снимок колонок SoA + заголовок

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

## Контекст
- [Факт] ADR для сохранений нет. ADR-0005 требует стабильных строковых ID в сохранениях, ADR-0010 — запись модов и их версий.
- [Факт] Всё состояние мира лежит в `Table` (SoA). Сейчас `StateHash` в Kernel (`src/Singularity.Kernel/StateHash.cs`) включает в хеш номер тика: `StateHash(Table, SchemaVersion, tick)`, вызовы в `RunExecutor.cs`, `ToyFunnelModel.cs`. `CounterRng` — чистая функция `(seed, tick, system, entity, n)` без состояния (ADR-0004, `CounterRng.cs`).
- [Факт] Решение #58: тестовой инфраструктуре сейчас нужны только ADR, реализация позже. Сохранение нужно и игре, и тестовым фикстурам (`TESTING_ARCHITECTURE_PROPOSAL.md` §7).
- [Факт] Ревью critic (gate) указал на скрытые зависимости от порядка строк, состояния систем, очередей команд и событий. Повторный gate-ревью (critic + advocate, 2026-11-03) учтён ниже.

## Решение (предложение)
1. **Формат.** Бинарный little-endian файл: заголовок + по каждой таблице `name, schema_version, row_count`, затем колонки `name, type, length, bytes`. Рядом — `summary.json` (читаемая сводка ожидаемых значений для фикстур; не источник состояния).
2. **Заголовок:** `save_format_version`, `game_version`, `test_api_version` (только фикстуры), список модов с версиями и хешем данных (ADR-0010), `scenario_id`, `scenario_hash`, `seed`, `tick`, календарная дата, `schema_version` таблиц, `state_hash`, `created`, `description`, `suite`. **`state_hash` покрывает только таблицы и их схему**; `tick` и дата в хеш не входят — это отдельные поля, которые сверяются отдельно (ADR-0006).
3. **Инвариант порядка.** Порядок строк сохраняется и восстанавливается **байт в байт**: загрузка не сортирует, не уплотняет и не переиндексирует таблицы. Причина — только порядок merge (LAYER_CONTRACT §4.0: merge применяет сообщения в фиксированном порядке). Ключ RNG от порядка строк не зависит: в нём стабильный id сущности из отдельной колонки, а не индекс строки (ADR-0004).
4. **Нет состояния вне таблиц.** Системы не держат изменяемого состояния в полях экземпляров или статических полях; всё, что влияет на следующий тик, — в `Table`. Исключение — рабочие буферы, помеченные `[Scratch]`: они сбрасываются в начале compute и между тиками ничего не переносят. RNG восстанавливается из `seed` и индекса срабатывания (ADR-0004).
5. **Очереди.** Решения систем (ИИ), ожидающие применения, — уже состояние в таблицах (ADR-0006) и входят в снимок как есть. Очередь ожидающих **внешних** команд (ADR-0014) сериализуется в снимок **тем же кодеком, что и журнал replay** (п. 9). Та часть `EventBuffer`, что влияет на геймплей, входит в снимок как таблица; наблюдательные события — нет. [Предл.] Ошибка `SaveNotQuiescent` (запрет сохранения при непустой очереди) не вводится. Она допустима только как временная мера, если кодек журнала ещё не реализован, и снимается вместе с появлением кодека.
6. **Слои.** Сериализация колонок без домена — `TableSnapshot` в Kernel. Домен, сопоставление ID и миграции — в Core.
7. **Версии и миграции.** `save_format_version` растёт при любом изменении раскладки. Неизвестная или более новая версия — громкая ошибка. **До первого сохранения игрока миграции не требуются**: тестовые фикстуры при смене раскладки пересоздаются из `scenario + seed + журнал команд`. С первого сохранения игрока миграция — цепочка чистых функций vN→vN+1 над колонками по стабильным строковым ID (ADR-0005); исходный файл не меняется, мигрирует копия в `artifacts/`. Формат остаётся бинарным снимком.
8. **Проверки при загрузке.** `StateHash` таблиц пересчитывается и сравнивается с `state_hash` заголовка; `tick` и дата сверяются отдельно с заголовком. Расхождение — ошибка загрузки. Набор модов (id, версии, хеш данных) или `scenario_hash`, отличающиеся от текущих, — **громкая ошибка**, если для этой пары нет явной миграции.
9. **Replay — артефакт, а не сохранение.** `scenario_hash + seed + журнал внешних команд` (ADR-0014; решения ИИ в журнал не пишутся — они воспроизводятся самой симуляцией) пишется в `artifacts/runs/<run_id>/commands.log` для воспроизведения дефектов.
10. **Межплатформенность.** Файл переносим между ОС, но равенство продолжения на разных ОС не заявляется (L3 отложен, ADR-0002). Проверки CI — относительные, на одной машине. Абсолютный golden-хеш фикстур проверяется только на одной ОС (Linux).

## Рассмотренные альтернативы
- **Текстовый снимок (YAML/JSON, Fx6 как целые).** Читаемые diff, но большие файлы, медленно и второй путь сериализации. Отклонено; читаемость даёт `summary.json`.
- **Только replay.** Крошечный, но загрузка = пересчёт, ломается при любой смене кода, не годится как сохранение игрока. Оставлен как артефакт прогона и источник пересоздания фикстур.
- **Сохранять состояние систем через отдельный интерфейс `ISaveable`.** Позволяет держать состояние в полях, но плодит второй путь состояния, мимо `StateHash`. Отклонено: запрет + архитектурный тест проще.
- **Уплотнять таблицы при сохранении.** Меньше файл, но меняет порядок merge. Отклонено (п. 3).
- **Тик в `StateHash`.** Тогда хеши дневного и месячного циклов и прогонов с пропуском пустых тиков несравнимы. Отклонено: тик — отдельное поле (п. 2).
- **Запрет сохранения при непустой очереди (`SaveNotQuiescent`).** Проще, но игрок не может сохраниться в любой момент. Отклонено в пользу сериализации очереди кодеком журнала (п. 5).

## Последствия
- Плюсы: один формат для игры и тестов; точность до бита; быстрая загрузка; хеш проверяет целостность.
- Минусы: бинарные diff нечитаемы; после первого сохранения игрока каждое изменение схемы требует миграции и повышения версии.
- Обязательно: всё изменяемое состояние — в таблицах; новые очереди или буферы с влиянием на геймплей — таблицы в снимке.
- Следующий шаг (задача для Orchestrator): изменить `StateHash.Compute` в Kernel — убрать тик из хеша, тик и дату сверять отдельно. Код этим ADR не меняется.
- Предусловия: ADR-0004 (RNG без состояния) и ADR-0006 (команды в начале тика) — ADR-0006 пока PROPOSED, его принятие нужно до реализации.

## Проверка
- Главный тест (L1, L2 при 1 и N потоках): прогон до тика K → save → load → продолжение до тика N даёт тот же `StateHash` таблиц и тот же тик/дату, что прогон без перерыва, **на той же машине**. Вариант теста: save при непустой очереди внешних команд.
- Байтовый тест: save → load → save даёт идентичный файл; порядок строк совпадает.
- Архитектурный тест (IL-сканер): у типов систем Core нет изменяемых полей экземпляра и статических полей; `readonly`-поля изменяемых ссылочных типов (массивы, списки, словари) запрещены, кроме помеченных `[Scratch]`.
- Тест «состояние вне таблиц»: прогон с двумя экземплярами каждой системы (по одному на половину прогона, пересоздание между тиками) и с одним экземпляром даёт одинаковый хеш.
- Отрицательные фикстуры: усечённый файл, неверный хеш, неверный тик/дата в заголовке, неизвестная версия, отсутствующая колонка, другой набор модов или `scenario_hash` без миграции → громкая ошибка.
- Тест миграции — с первого сохранения игрока: фикстура vN → vN+1 → хеш совпадает с эталоном мигрированной копии.
- CI: относительные проверки на всех ОС; абсолютный golden-хеш — только на Linux.
