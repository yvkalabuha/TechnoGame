# ADR-0019 — Monthly systems split into daily slices (#228), revision of ADR-0006

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Уровень: gate+research (меняет все golden мира M1). Пункт 0.2 плана `development/milestones/MS-M1-economy-provinces-open-race.md`. Зависит от ADR-0003 (0.1) и ADR-0020 (таблицы, хеш, атрибуция). Ревизия 3: gate (`docs/reviews/adr-0019-0020-{critic,advocate,reviewer}.md`, `docs/reviews/adr-0019-deepseek.md`) и ответы владельца #344–#347.

## Краткий вывод
- [Предл.] После #228 в дереве один режим — дневной. Срез M0 (EXP-0002) живёт в **git-теге** (#346); ядро далее проверяется инвариантами Kernel и новым golden M1.
- [Предл.] Роли систем: `Flow` (суммы, каждый день), `Decision` (решения ИИ **раз в 7 дней со сдвигом** по актору, #344), `Event` (сценарные события).
- [Предл.] Нормы потоков — **годовые суммы**, нарезанные по дню года 365/366 (#345); одно округление — floor; нелинейные правила — дневной параметр `Fx6.DayRate`.
- [Предл.] **Один писатель на колонку.** Переводы — журнал `(src, dst, x)`; применяет и нормирует владелец величины в merge по полному спросу дня.
- [Предл.] Событие с датой `D` применяется в merge тика `D−1` и действует с утра `D` (#347; ADR-0011 не меняется).

## Контекст
- [Факт: DECISIONS_LOG #228] Месячные системы раскладываются по дням и читают свежее состояние; все golden меняются.
- [Факт: #344–#347] Решения ИИ не реже раза в неделю, разные страны — в разные дни; нормы годовые по дню года; срез M0 — git-тег, после #228 проверка инвариантами Kernel и новым golden; событие действует с утра своей даты.
- [Факт: ADR-0006] Тик = день; `Cadence`; compute читает `Current`, merge — в порядке списка; решение действует со следующего тика.
- [Факт: код `TickRunner.cs`; `SliceSession.StepOne`] Все системы читают `Current`; команды и `Policy.ApplyDeals` пишут `Current` до `RunTick`.
- [Факт: reviewer, `KnowledgeRng.cs:8`, #60] Kernel ключует RNG `(seed, tick, system, entity, n)`, но Core передаёт индекс **месяца**.
- [Факт: reviewer, `IndustrySystem.CreateMailbox:194`; `CommandState`] Почтовые ящики требуют одинаковой частоты; команды привязаны к месяцу.
- [Факт: ADR-0011 §3] Владение меняется только в merge; видно в `t+1`. [Факт: ADR-0016 §2] `S` среза — нижняя граница.
- [Факт: #339–#343; `docs/game-design/scripted-events-conditions.md`] События с предусловиями: ежедневная перепроверка, отсрочка 6/12/36 мес., затем пропуск; без RNG; `event_status`, `effective_date` — в `StateHash`.

## Решение

### 1. Роли
1. Роли (явная таблица `SliceRoles` в Core; система без записи не регистрируется):
   - `Flow` — суммы (выпуск, потребление, переводы, прогресс). `Cadence = Daily`.
   - `Decision` — дискретные решения актора (доли бюджета, цели, старт проекта). Запускается каждый день, но обрабатывает только акторов своего слота (п. 3).
   - `Event` — `ScenarioEventSystem` (п. 16–19).
2. Система с двумя ролями делится. [Предп.] Набросок: `Industry` → `IndustryDecision` + `IndustryFlow`; `Products`, `Policy` — `Decision` (исполнение сделок — `Flow`); `Knowledge` — `Flow`. Точный список — R3.
3. **Сдвиг решений (#344).** Слот актора `slot(a) = ordinal(a) mod 7`; актор решает на тике `t` (индекс дня от старта сценария), если `t mod 7 = slot(a)`. Каждый актор решает ровно раз в 7 дней; в день решает ≈ 1/7 акторов. Актор, активированный событием, решает в ближайший свой слот. Детерминированно, без RNG.
4. **Один писатель на колонку** (во всех таблицах ADR-0020): у колонки ровно одна система-владелец. Архитектурный тест по регистрации.

### 2. Нарезка, округление, переводы
5. **Норма — годовая сумма** `F` (raw Fx6, `long`) (#345). Срез дня `k` года длины `Y ∈ {365, 366}` (календарь Kernel): `DaySlice(F, k, Y) = floor(F·k/Y) − floor(F·(k−1)/Y)`, произведение — `Int128`. При постоянном `F` сумма за год = `F` точно; сумма за отрезок дней `k1..k2` = `floor(F·k2/Y) − floor(F·(k1−1)/Y)`, от доли `F·n/Y` отличается < 1 raw. Смена `F` (решение, событие) добавляет ≤ 1 raw на смену. Состояния остатка нет.
6. Режутся только суммы. Ставка (доля, %/год) сначала даёт сумму `F = FloorMul(rate, stock)`, затем режется; деление ставки на `Y` запрещено. Суммы, зависящие от состояния (выпуск от мощности), пересчитываются каждый день как годовой эквивалент `F_d` и режутся `DaySlice(F_d, k, Y)`.
7. **Округление — floor везде** (как `Fx6` `*`/`/` через `FloorDiv`), в том числе при отрицательных `F` и `F = long.MinValue`.
8. **`Apportion(F, w[])`**: части `floor(F·W_i/W) − floor(F·W_{i−1}/W)`, `W_i` — накопленная сумма, `w_i ≥ 0`, сумма весов — `checked long`, произведение — `Int128`; сумма частей = `F` для любого знака. `W = 0` → все части 0, `F` остаётся у источника.
9. **Переводы — журнал.** Перевод сохраняемой величины `Q` (деньги, энергия, люди) — запись `(src, dst, x)` в буфер чанка системы-заявителя (compute). У `Q` одна система-владелец («книга `Q`»); в своём merge она читает журналы всех систем в порядке (список систем, чанк 0..N−1, порядок выпуска), видит **полный спрос дня** на источник, нормирует `Apportion` при нехватке и пишет обе стороны. Инвариант post: `stock(t+1) = stock(t) + Σin − Σout` в raw (K3).
10. Pull (строка считает своё изменение по `Current`) — только для своей строки, не для переводов.
11. Сложение — `checked long` в фиксированном порядке п. 9; детерминизм (в том числе момент переполнения) держится на порядке, а не на коммутативности.
12. **Нелинейные правила** (распад δ_H, рампа λ, культура, пороги I1–I3): дневной параметр `Fx6.DayRate(δ, Y) = 1 − (1−δ)^(1/Y)` из годовой ставки — целочисленный корень бисекцией в Kernel, считается при загрузке для `Y ∈ {365, 366}`. Пороги — по дневному состоянию, дата — день пересечения. Опись — R3.

### 3. Порядок дня `D`
13. Session: внешние команды с `apply_tick = D` в порядке `(apply_tick, source_class, source_id, local_n)` (ADR-0014) пишут `Current` и действуют в тике `D`.
14. Один проход: compute `Decision` (акторы слота `D`), `Flow`, `Event` по `Current` (конец `D−1` + команды); merge в порядке списка; swap; post (K3, K9); снимок view; хеш по расписанию ADR-0017. Решения действуют с `D+1` (ADR-0006 без изменений).
15. **RNG:** ключ `Flow` и `Decision` — индекс тика (дня), не месяца. Сценарные события RNG не используют (#342). **Связь `Decision` → `Flow`** — только через колонки; почтовые ящики — только внутри одной роли.

### 4. Сценарные события (#325, #328, #339–#343, #347)
16. **Дата.** Событие с датой `D` применяется в merge тика `D−1` (для `D = t0` — при сборке мира) и видно с утра `D`: потоки и решения дня `D` идут при новом владении. Это ADR-0011 §3 как есть.
17. **Ежедневная проверка.** В merge тика `D−1` `ScenarioEventSystem` обходит события `due` (дата `D`) и `deferred` в порядке `(nominal_date, event_id)`. Условия (закрытый словарь атомов, только структура в M1, #340) читают `Current` тика `D−1` плюс эффекты уже применённых в обходе событий. Атомарная группа — одно решение.
18. **Исход:** выполнено → эффект, `fired`, `effective_date = D`; транзитный провал → `deferred` до `AddMonths(nominal_date или effective предшественника, 6 | 12)`, не более 36 (#341); истёк срок или постоянный провал → `skipped` (или ручной `alt`). Oder–Neisse — 1950 и запасная 1970 с `excludes` (#343).
19. **Что пишет событие** (п. 4): `owner`/`controller` провинций и территорий, `actors.active`, `events.status`/`effective_tick` (ADR-0020). Колонки E1 не пишет: последствия для людей и мощности (2.9) считает владелец колонок E1 в тике `D`, маркер — `events.effective_tick = D`. Журнал событий (Lab, UI) — производный вывод, не хешируется.

### 5. Срез M0 — git-тег (#346)
20. До слияния кода #228 Orchestrator ставит аннотированный тег [Предл. имя `m0-slice-exp0002`] на коммит, где матрица EXP-0002 даёт det `824f4ded07216828ee6354f95f6bd942dcefd6059f70fdff24fbf9f9ab91ea5b` и main `183e47b9fc81957ccd6a53f93f5d09f4d10a2ca094b0be119680bd1cf42ab02d` (`docs/simulation/exp0002-result.md` §1); результат сверки — в DECISIONS_LOG.
21. После слияния: в дереве нет `TickModel`, `SliceLegacy`, месячного пути и ветвления по режиму. Golden EXP-0002 в CI не проверяется; ядро проверяют инварианты Kernel, L1/L2 и golden M1. Замороженные EXP-документы не правятся. Тест ADR-0006 «дневной = месячный» остаётся только в теге.
22. K6 плана MS-M1 («`slice_legacy` бит-в-бит до M2») меняется по #346 — правка Orchestrator.

### 6. Хеш и бюджет
23. Формат хеша мира — ADR-0020 §1 (там же частичная замена ADR-0017). Расписание ADR-0017 без изменений; `HashCheckpoints`/`HashEveryTick` по умолчанию `false`; `HashEveryTick` — только в тестах детерминизма.
24. CoW: `Flow` и `Decision` открывают свои колонки каждый день — точка на кривой R2 (в) EXP-0007.
25. **Флаги замера K4:** `HashCheckpoints = false`, `HashEveryTick = false`, view — игровой режим ADR-0014, команды включены; пишутся в манифест.
26. **p99 дня.** K4 дополнительно пишет p99 и максимум тика (дня). Сдвиг решений (п. 3) выравнивает нагрузку; [Предл.] флаг действия — p99 дня > 100 мс → профиль и раунд оптимизации.
27. Каждая система заявляет цену на день (ADR-0016 «Обязательно»); превышение — gate до кода.

### Частично заменяет
- **ADR-0006:** «месячная система обрабатывает месяц за запуск» и тест «дневной = месячный» — сняты (остаются в теге п. 20); роли и сдвиг решений — п. 1–3.
- **ADR-0016 §2 «Составляющие»:** `k_i = (T_i − M_i)/29` в M1 не применяется (месячного прогона нет); `S`, `K_d` — из inclusive-профиля.
- **ADR-0017:** через ADR-0020 §1 (формат, версия мира); здесь — только п. 23.
- Не меняются: ADR-0002, ADR-0011, ADR-0013, ADR-0014.

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| Нарезка «побитно = месячному запуску» | Отклонена #228 |
| Решения ИИ раз в месяц в день 1 (ревизия 2) | Заменено #344; пик нагрузки в день 1 |
| Решения ИИ каждый день | ×7 цены, «дрожание» бюджета |
| Месячная или дневная норма | Заменено #345: скачок февраль/март или зависимость от длины месяца |
| Pull для переводов | Две копии расчёта `x`; `Apportion` O(n²); нормирование не видит полный спрос |
| Событие действует с `D+1` (ревизия 1) | Заменено #347 |
| `SliceLegacy` в дереве (ветвление или заморозка классов) | Заменено #346 |
| Остаток деления в колонке | Лишнее состояние |
| Clamp по мере поступления вкладов | Зависит от порядка |

## Последствия
- **Плюсы:** годовые суммы точны, дневная норма ровная по месяцам; нагрузка решений равномерна; сохранение двойной записью в одном месте; события по дате; в дереве один режим.
- **Минусы:** все golden M1 новые; журнал переводов — новый механизм Kernel; Flow и Decision открывают колонки каждый день (CoW); воспроизведение EXP-0002 — только из тега.
- **Обязательно:** `SliceRoles`; один писатель на колонку; `DaySlice`/`Apportion`/`DayRate` только из Kernel; переводы только журналом; тег п. 20 до слияния #228.

## Проверка
1. **Kernel property:** `Σ_{k=1..Y} DaySlice(F, k, Y) = F` для `Y ∈ {365, 366}`, `F` случайные, `0`, `±1`, `long.MinValue`, `long.MaxValue`; високосный год из `TickCalendar`; сумма отрезка = формуле п. 5. `Apportion`: сумма = `F` при любом знаке; `W = 0` → нули; переполнение весов → исключение. `DayRate`: `(1−DayRate)^Y` отличается от `1−δ` ≤ `Y` raw.
2. **Сдвиг решений:** каждый актор решает ровно раз в 7 тиков; число решающих в день отличается не больше чем на 1 от `N/7`; новый актор — в свой слот.
3. **Сохранение (post, каждый день):** K3 в raw на 100 % тиков, в дни событий, при нормировании и смене `F`.
4. **Один писатель:** архитектурный тест по всем системам и таблицам.
5. **L2:** threads 1/4/8/16 × ChunkSize 1/8/32, `HashEveryTick` — хеш каждого дня равен. Журнал: все чанки шлют переводы одному `dst`, t16, ChunkSize 1, 20 повторов; граничный тест переполнения.
6. **Порядок дня:** событие с датой `D` — потоки и решения дня `D` при новом владении; команда дня `D` действует в `D`; replay с командами в произвольные дни даёт тот же хеш.
7. **События:** отсрочка с ежедневной проверкой; истечение 6/12/36 мес. → `skipped`; Oder–Neisse 1950/1970 `excludes`; базовый прогон — все `fired`, `lag_days = 0`.
8. **RNG:** ключи `Flow`/`Decision` уникальны по дням.
9. **Save/load** в произвольный день и между `D−1` и `D` события → тот же хеш.
10. **Тег:** при создании — матрица EXP-0002 det и main даёт эталоны п. 20 (один раз, R4). CI каждого PR в `src/` — инварианты Kernel, L1/L2, golden M1.
11. **Роли:** каждая система — в `SliceRoles`; `Flow` — `Cadence.Daily`.
12. **Бюджет:** K4 с флагами п. 25: p95/медиана месяца, p99 дня.
