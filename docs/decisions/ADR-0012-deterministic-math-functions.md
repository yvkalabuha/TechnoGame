# ADR-0012 — Детерминированные степенные функции: PowFrac вместо Pow/Exp/Log

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

## Контекст
- [Факт] ADR-0003 и `csharp-core.md` запрещают `Math.Pow/Exp/Log` в состоянии мира. Архитектурный тест (`tests/Singularity.Architecture.Tests/DeterminismRules.cs`) разрешает только `Sqrt, Floor, Abs, Min, Max, BigMul`.
- [Факт] В Kernel уже есть `DetMath.PowDyadic(x, eighths)`: показатель с шагом 1/8, вычисляется через повторный `sqrt` и умножения.
- [Факт] Модели волны 1 требуют степеней:
  - RR-0007: Wright `(1+E)^(−b)` при `LR ∈ [0,75; 0,92]`, Duane `h^β`, `complexity^α`;
  - HYP-0002 (RR-0006 §7): `(1+T/Tref)^γ·P^β·N^(1−β)`;
  - RR-0005: `exp(−t/τ)`.
- [Факт] Шага 1/8 мало. В диапазоне LR 0,75–0,92 он даёт всего три значения `b` (0,125 / 0,25 / 0,375, то есть LR ≈ 0,917 / 0,841 / 0,771). Различия между классами изделий таким шагом не выразить.
- Контекст сводки: `docs/architecture/LAYER_CONTRACT.md` §4.5.

## Решение
1. В `Singularity.Kernel.DetMath` добавить `PowFrac(double x, int q10)`: `x^(q10/1024)` для конечного `x ≥ 0`.
   - Целая часть показателя `q10 >> 10` считается возведением в квадрат.
   - Дробная часть: цепочка `r_i = sqrt(r_{i−1})`, `r_0 = x`, i = 1..10. Корень `r_i` берётся в произведение, если установлен бит `2^(10−i)`.
   - **Порядок умножений фиксирован** (для совпадения бит в бит): аккумулятор `acc = 1.0`, затем `acc *= r_i` по возрастанию i, затем `acc *= x^int`. Числа `double` не ассоциативны, поэтому порядок — часть контракта функции. Golden-векторы его фиксируют.
   - Отрицательный показатель: `1.0 / PowFrac(x, −q10)`. Это одно деление IEEE, оно корректно округляется.
   - **Ранний выход:** цепочка `sqrt` останавливается на младшем установленном бите. Порядок оставшихся умножений не меняется, поэтому результат бит в бит равен полному циклу (тест). При `q10`, кратном 128, считаются только 3 корня.
   - `PowDyadic(x, e8)` становится частным случаем `PowFrac(x, e8·128)`, если `PowDyadic` перевести на тот же порядок умножений.
   - Ошибки и исключения такие же, как у `PowDyadic`.
2. Показатели в тике — только целые `q10` из скомпилированных данных. Скомпилированные данные покрыты хешем контента. `Math.Log` и `Math.Pow` нет ни в рантайме, ни в компиляторе. Способ получения `q10` зависит от вида данных:
   - **Показатель задан десятичным числом** (`β`, `α`, `γ`): `q10 = round_half_even(y·1024)`. Считается в `System.Decimal`: десятичная строка в нём точна, так что результат не зависит от платформы.
   - **Задан LR** (`b = −log2(LR)`): целочисленный поиск. Ищем `q`, при котором `PowFrac(2, −q)` ближе всего к `LR` по значению. `PowFrac(2, −q)` монотонно убывает по `q`, поэтому хватает двоичного поиска (~11 вызовов). При равном расстоянии берётся чётный `q` (half-even).
   - Почему не `Math.Log` в компиляторе: для детерминизма мира это было бы допустимо (результат всё равно идёт под хеш), но у значений около границы округления `q10` мог бы различаться между машинами разработчиков. Хеш данных тогда «плавает», и CI шумит. Поиск через ту же `PowFrac` гарантирует, что эффективный LR в тике — именно ближайший к заданному.
   - Пример: `LR = 0,8` → `q10 = 330`, эффективный LR = `2^(−330/1024)` ≈ 0,79983. Для `q = 329` было бы ≈ 0,80037, это дальше от 0,8.
   - **Дополнительные показатели** хранятся как `q10(1−β) = 1024 − q10(β)`, а не квантуются отдельно. Так `β + (1−β) = 1` точно, и `P^β·N^(1−β)` сохраняет постоянную отдачу от масштаба.
3. Экспоненциальное убывание в состоянии мира задаётся множителем за месячный шаг `(1 − δ_month)`, а не через `exp`. Все δ в данных хранятся в единицах «за месяц». Насыщения и кривые освоения в рациональной форме (`x/(x+h)`) там, где форма кривой не важна.
4. `Exp`, `Log` и `Pow` с произвольным вещественным показателем в рантайме остаются запрещены. Если когда-нибудь понадобится показатель, который **вычисляется из состояния** и не квантуется, нужен новый ADR (см. альтернативу C).

## Рассмотренные альтернативы
| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| A | Только `PowDyadic` (шаг 1/8) | уже есть, проверен | шаг грубый, LR классов не различить |
| **B** | **`PowFrac` с шагом 1/1024 (выбран)** | ~20 строк кода. Только `sqrt`, `×` и одно деление, без выражений `a*b+c`, поэтому сама функция не зависит от вопроса FMA из ADR-0003. ~50 нс | показатель только двоично-рациональный; 10 `sqrt` на вызов |
| C | Целочисленные `Log2`/`Exp2` на `Int128` (побитовый log2, таблица констант `2^(2^−i)`), общий `FxPow(x,y)` | произвольный показатель, полностью целочисленный | ~150 строк, таблица констант требует генератора и проверки, ~30 умножений Int128 на вызов. Сейчас не нужен |
| D | Таблицы кривых (Wright по числу удвоений с линейной интерполяцией) | очень быстро | отдельная таблица на каждую кривую и каждый LR; ошибки интерполяции; трудно моддить |
| E | Везде рациональные заменители (как `ramp` в RR-0006) | нет новой математики | меняется форма закона Райта и Duane, теряется связь с литературой и калибровкой |
| F | Разрешить `Math.Pow` | проще всего | нарушает ADR-0003; на разных платформах и runtime результат может отличаться |

## Последствия
- Плюсы:
  - Кривые RR-0007 и HYP-0002 выражаются без нарушения ADR-0003;
  - Lab и Core используют одну функцию;
  - стоимость в бюджете (LAYER_CONTRACT §11: ~4·10⁴ вызовов в месяц ≈ 2 мс).
- Минусы:
  - Параметры квантуются. Авторы данных видят эффективное значение (компилятор печатает LR после квантования).
  - Ошибка квантования показателя: `|Δy| ≤ 1/2048` при округлении к ближайшему. Относительная ошибка **значения** `x^y` ≈ `|ln x|·|Δy|`. Это до `ln(x)/2048` при округлении и до `ln(x)/1024` в худшем случае для любого шага 1/1024. При `x` ~ 1e4–1e6 (накопленный выпуск) это ≈ 0,45–0,7% и до ≈ 1% соответственно. Ошибка детерминирована и одинакова для всех акторов. Калибруется эффективное значение, а не «истинное».
  - Формулы, которые используют результат `PowFrac` (`a*b+c` в LAYER_CONTRACT), по-прежнему зависят от открытого ADR-0003 (FMA).
  - Вызов в ~5 раз дороже, чем `PowDyadic`.
- Обязательно:
  - модели не вызывают `PowFrac` в плотных внутренних циклах без кеша;
  - кривые линий пересчитываются раз в месяц.

## Проверка
- Kernel-тесты:
  - golden-векторы: фиксированные пары `(x, q10)` → ожидаемые биты `double`, одинаковые на CI x64 и ARM64;
  - совпадение `PowFrac(x, 128·e) == PowDyadic(x, e)` бит в бит;
  - ранний выход совпадает с полным циклом из 10 корней бит в бит для всех `q10` ∈ [−4096, 4096];
  - относительная ошибка против `Math.Pow` ≤ 1e-13 на сетке (в тестах `Math.Pow` разрешён, это не состояние мира);
  - монотонность по `x` при фиксированном `q10 > 0`;
  - исключения для `x < 0`, NaN, ∞, `0^(<0)`, переполнения.
- Архитектурный тест: список `AllowedMath` не меняется. `Math.Pow/Exp/Log` в Kernel и Core по-прежнему падают.
- Тесты компилятора данных:
  - `LR = 0,8` даёт `q10 = 330` и печатает эффективный LR ≈ 0,7998;
  - `β = 0,3` → `q10 = 307` (307,2 → 307); `q10(1−β) = 717`, сумма ровно 1024;
  - случай half-even: `y·1024 = 0,5 + k` округляется к чётному;
  - в компиляторе и рантайме нет `Math.Log/Pow/Exp` (архитектурный тест распространяется на компилятор данных);
  - хеш скомпилированных данных одинаков на x64 и ARM64.
