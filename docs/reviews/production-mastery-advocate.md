# Gate review: docs/game-design/notes/production-mastery.md — advocate

> 2026-11-24, owner decision #439. Report copied verbatim from the agent.

STATUS: done
SUMMARY: The draft's AI foresight solves fault (В), but its separate "mastery programme" with slots repeats an input the code already has. The probe's evidence does not show that fault (Б) blocks G5 from entering service in M-play. A smaller version is better: the newest-generation project in the "Prototype" stage is itself the mastery programme, the series start is gated, and the working line stays on the old generation. I checked the code against `ProductsSystem.cs`, `CbCultureRule.cs`, `PolicySystem.Products.cs` and `IndustryInputsAdapter.cs`. I did not run any simulation.
FILES: none (I made no edits)
FINDINGS:
1. **high, §2 p.2(б) and §8 q.2.** [Факт] The "nominal output" `V_OC` already exists. `ProductsSystem.cs:840` `GrowthNominal` returns `RRef·N·Labour` for every project in stage Prototype or Series whose `prc_set` holds the process. `Planned` already covers stages П/О (`IIndustryInputs.cs:70`), so the programme slot adds nothing to the input. The draft's `x_prog`=0.3 is even weaker than the existing channel. So the real cause of (Б) for 43/73 is not "no input". The likely cause is that the process is in no live `prc_set`, or that `isHome`/`max`-lead takes the growth. [Предп.] Fix: before any design, simulation-engineer explains (Б) with this channel taken into account (the 1-seed harness is enough).
2. **high, alternative "Prototype stage = programme", strong.** [Предл.] Keep `Requirement` on the newest generation, so design work and the bureau keep moving. Keep the project in Prototype (the existing `GrowthNominal`/`Planned` inputs) until `y_min ≥ y_start`, and do not launch the series earlier. The working line of the old generation stays. The player's lever is the existing "Наладка" (#112, up to 3 priority processes) plus a "hold / force the series" button. This needs no new columns or schema-train change, no `T_hand` and no slots. It meets #439, because the AI does not start an unmasterable series and the country still learns. It also does not make the "fall back to an old generation" option, which the owner rejected, into a rule: the new project stays alive.
3. **high, §3 "Requirement on the last masterable generation".** This is the very "fall back" option the owner did not choose in #439. Fix: as in item 2, gate the series start (`:411–418`), not the `Requirement` (`:270, :299`).
4. **medium, §3 `Masterable` via `DHForecast` over 60 months.** This is a forecast inside a forecast. It costs actors × projects × processes × 60 steps per year, and if it diverges from the real dynamics the AI either never starts or starts with a delay. The stronger alternative is the probe's fix 2 (§7.6): a static check (`Hcap(t+T_look) > r_d`, tooling reachable, `why_not` without `Saturation`) plus feedback: the candidate line closes after `y_min < y_prod` lasting longer than `T_Ab`. It is cheap, needs no forecast tuning, and directly removes the 77 % of line-months USA spent on a G6 candidate line.
5. **medium, P1 invariant.** "Never starts a series it cannot master" depends on the forecast and cannot be checked. Replace it with: (a) no launch with `y_min < y_start`; (b) no candidate line below `y_prod` longer than `T_Ab`. Both are checked on the old code and fail there, as the fail-without-the-fix rule requires.
6. **medium, §7 measurement plan.** Add the baseline branch "#438 + fix 2 only" with no new mechanic. CF-1 already gave G5 in service in 3 countries (9/10 seeds) through `hot_sc_cmc`, bypassing 43/73. The decision rule should be: keep the programme only if it improves P3/P4 over this baseline. P2 should exclude 73, since CF-2 gave yield 0.00 and the criterion would fail for a reason other than the mechanic.
7. **medium, #127 and #30.** The conflict is weaker than §8 q.1 says: the "test batch" input (I-OC) is already in the contract and the code. The new element is only holding a project at the prototype stage, while #127 was about starting data. Write it into the owner question like that, without asking whether to "override #127". "Штучные опытные образцы при отставании" (#30, marked FUTURE) is a different case: the `Hcap > r_d` admission check excludes it, and that should be stated.
8. **low-medium, education as the lever.** The spec already says `Hcap` "grows with education" (§1.1). Letting "Наладка" or an education budget speed up growth under #438 is a moderate alternative. It is the only lever against fault (А) for SUN/FRA and keeps #24 if growth is capped. Do not put it into M-play; put it on the record as a parameter of the #438 calibration probe.
9. **low, changing the culture rule (`ℓ`, `ΔL`).** Weak: #127 forbids it directly, and CF-2 showed that lowering the step does not help. Keep as is (rejected).
10. **low, licence as an accelerator.** Keep as is: no new mechanic, and #102/#104 hold.
11. **low, UI §4.** The progress bar `(H−H₀)/(r_d−H₀)` covers one dimension, while a process has up to 3. Show the minimum over the active dimensions and name the limiting one ("кадры точности").
12. **low, "2 slots", `T_hand` 24 months, `T_max` 120 months.** With the item 2 approach they are not needed: the limit comes from money (D) and from the bureaus. That means three fewer calibration parameters.
13. **calibration risk.** Programme plus forecast adds 5 parameters (`x_prog`, `T_look`, `T_hand`, `B_prog`, slots). The item 2 version keeps only `y_start` and `T_Ab`, and both already exist.
