## 4. Динамика (формулы контракта)
### 4.0 Арифметика и фазы тика (v2.3; v2.4 — новые строки)
**Арифметика `Fx6` (A1).** Бит-точность между Core и эталоном требует одного порядка операций. Правила:
1. Все величины формул §4 — `Fx6`. Числовые константы (`0.25`, `1`) — литералы `Fx6`. Целые счётчики (`opened_d`) переводятся в `Fx6` точно. `double` нет (ADR-0003 R1).
2. Каждое `·` и `/` — **одна** операция `Fx6` с floor к −∞ (`Fx6.operator *`, `/`, `FloorDiv` по `Int128`). `+`, `−`, `min`, `max`, сравнения точны. Переполнение — исключение (`checked`), а не насыщение.
3. Порядок — **слева направо, как записано**, скобки обязательны к исполнению. `a·b/c` = `(a·b)/c`; `a·b·c` = `(a·b)·c`. Деление внутри дроби не раскрывается: `s_p = v_p/V_c` считается отдельно, затем умножается (не `Σ v_p·x / V_c`).
4. Суммы `Σ` идут по возрастанию id (процесса, кластера). Сложение точное, порядок фиксирован для воспроизводимости при переполнении и для журналов. v2.4: `max_p`, `argmax` — ничья по меньшему `prc_id`; `alt_id` в ничьих — ordinal (побайтно, COMPONENT_SELECTION G-8).
5. Произведение по измерениям `Π_d` — в каноническом порядке измерений (в срезе: `precision`, `purity`, `quality_control`), начиная с `1`; множитель `ramp` — последним.
6. Забывание записывается как `x − δ·x` (вычитается floor декремента), а не `x·(1 − δ)`. Математически это та же форма §3, в `Fx6` запас округляется вверх. Когда `δ·x` < 1 raw, забывание останавливается — допустимо.
7. Формулы спецификации среза (`ramp`, hazard, `c_eff`, бюджет) подчиняются тем же правилам. Порядок в них задаёт спецификация (владелец — simulation-engineer). Пример: `h = (h_max·y)/(y + y_half)`.
8. Формулы §4.1–4.4 ниже записаны в канонической форме: при реализации их нельзя переупорядочивать и «упрощать».
9. (v2.4) Деление с возможным нулём в знаменателе записывается веткой `(den = 0) ? 0 : …` до деления. Циклы с перераспределением (налив §4.1b) ограничены числом кандидатов.

**Фазы тика (ADR-0006; A3, A10).** Compute читает только снимок (состояние после тика t−1) и пишет свои колонки или буферы. Merge применяет сообщения в фиксированном порядке. Post — только инварианты, метрики, хеш: в состояние, которое читает симуляция, post не пишет. Здесь «тик t» — месячный шаг t месячных систем (ADR-0006: тик = день, месячные системы — в первый день месяца).
| Шаг | Фаза тика t | Читает | Пишет |
|---|---|---|---|

- Итог: выпуск и деньги наладки месяца t влияют на `culture_H`, `K_ind` и `world_lead` с шагом compute тика t+1 и становятся видимыми с t+2. Внутри своего compute система может использовать свои только что вычисленные значения (например, hazard узла считается по `prog` после прироста и `prog_cap` этого тика, A3b; остаток наладки идёт в оснастку того же compute); чужие — только из снимка.
- `proc_v`, `proc_yield`, `proc_E` — служебные колонки «прошлый месяц», не запасы §3: ни забывания, ни своего эффекта.
- (v2.4) **Распределение наладки — правило системы, а не решение ИИ.** Решения — это доли (`share_D`, раз в год у ИИ, команда у игрока) и фокус игрока. Они применяются с t+1 (ADR-0006). Само распределение — детерминированное правило бюджета месяца t по снимку, как вложения в оснастку. Поэтому `proc_E` месяца t пишется в merge t, а культура читает его в t+1 — та же фаза, что у `proc_v` (PD §2.1, `culture-round2.md` §1.3 п. 5). Формулировка PD §5 «деньги тратятся в t+1» с этим не совпадает — см. §13, противоречие П-4.
- (v2.4) Типы сообщений пишут разные колонки, поэтому порядок между типами на результат не влияет. Для журналов он фиксирован: `report_output` → `effort_spend` → `reserve_workforce` → `write_off`.

### 4.1 Культура `culture_H` (v2.4 черновик: временное правило C-B, #99, #111; RISK-0016)
Каноническая форма (§4.0). Ячейка `(site, c, d)`. `H`, `M`, `Hcap`, `H_floor`, `act`, `w` — из снимка. Для процесса p: `v_p = proc_v[site,p]`, `E_p = proc_E[site,p]` месяца t−1, `lic_p = licensed(owner, p)` ∈ {0, 1}. Источник формул — `culture-round2.md` r3 §1.1, §1.1.2.
**Процессы ячейки** `P(c,d)` = процессы кластера c с **активным** измерением d (`r_d(p) > 0`) и с `v_p > 0` или `E_p > 0`. Перебор — по возрастанию `prc_id`.
```
# параметры процесса (единицы — culture-rule-selection.md §7.5)
v_cap(p)  = r_cap  · labour_p          # r_cap  = r_ref / 2,5 = 10 шт. процесса в месяц
v_keep(p) = r_keep · labour_p          # r_keep = r_ref / 4   = 6,25 шт. процесса в месяц
# канал лицензии (#104 — рост, #107 — поддержание)
ṽ_p    = (1 + k_tr · lic_p) · v_p      # k_tr = 1; lic_p ∈ {0,1}, произведение точное
# потолок пользы денег от выпуска (M1), форма SMOOTH
x_V    = (v_cap = 0) ? 0 : min(1, ṽ_p / v_cap)
c_p    = (x_V · x_V) · (3 − 2·x_V)
x_E    = (E_full = 0) ? 0 : min(1, E_p / E_full)
e_V    = min(x_E, c_p)                 # = min(E, E_useful)/E_full
e_L    = (ℓ = 0) ? 0 : min(x_E, ℓ)      # лабораторная часть; при ℓ = 0 всегда 0
gap_p  = max(0, r_d + 0.25 − H)
gapL_p = max(0, (r_d − ΔL) − H)
t_p    = max(e_V · gap_p, e_L · gapL_p)
# поддержание — только от выпуска (G-5: пол встроен)
a_r     = min(1, act[c] / act_norm)
m_p     = (v_keep = 0) ? 0 : min(1, ṽ_p / v_keep)
maint_p = H_floor + (max(r_d · a_r, H_floor) − H_floor) · m_p
# агрегация по ячейке: максимум, а не доля объёма
drive  = max_{p ∈ P(c,d)} t_p                       # пусто → 0
catch  = max_{p ∈ P(c,d), world_lead(p, owner)} t_p  # пусто → 0
maint  = max(H_floor, max_{p ∈ P(c,d)} maint_p)      # пусто → H_floor
spill    = Σ_c' R[c,c'] · max(0, H[c',d] − H[c,d])   # без изменений v2.3
H_floor  = φ_floor · Hcap[site,d]
sat      = max(0, 1 − H / Hcap[site,d])
α_eff[d] = α · (1 + k_qp)  или  α
ΔH⁺      = sat · ( ((α_eff[d] · act[c]) · w[c]) · drive + k_catch · catch + σ · spill )
ΔH⁻      = δ_H · max(0, H − max(maint, H_floor))
H'       = H + min(ΔH⁺, ρ_max) − ΔH⁻
```
| Параметр | Значение | Статус |
|---|---|---|
| форма `c` | SMOOTH | #111 |
| `r_cap`, `r_keep` | 10 и 6,25 шт. процесса в месяц; записываются как `r_ref/2,5` и `r_ref/4` и меняются вместе с `r_ref` | #111; связь с `r_ref` — [Предл.] по образцу G-6 |
| `k_tr` | 1 | #104, #107; [Предп.] «З» |
| `E_full` | **константа манифеста**: `(0,4 · 0,25 · budget_index_GBR(1945)) / 13` → `Fx6` 0,001838 индекса бюджета в месяц | R2-7; [Предп.] «З» |
| `ℓ`, `ΔL` | `ℓ` = 0 [Предл.: #111 его не называет; при `ℓ` 0 и 0,1 бумажные числа одинаковы, правило выбора §1.8 п. 3(4) берёт 0]; `ΔL` = 0,5 (при `ℓ` = 0 не действует) | П-2, §13 |
| `α`, `δ_H`, `k_catch`, `σ`, `ρ_max`, `φ_floor`, `act_norm` | калибровка; `α` ∈ [0,02; 0,15] | #96 |

- **Единица `r_cap`, `r_keep`** — «шт. процесса в месяц», то есть число исполнений p, а не изделий: `proc_v = Σ_линий r_line·n_p·labour_p` (`culture-rule-selection.md` §7.5). При `labour_p = 0` `v_cap = v_keep = 0`, ветки дают `x_V = m_p = 0`; валидатор данных такой PRC не пропускает.
- **Свойства, которые проверяет CI (`culture-round2.md` §1.5, I1–I10).** `ΔH⁺` не убывает по `E_p` и по `v_p`. При `E ≡ 0` `ΔH⁺ = sat·σ·spill`, а `maint` тот же, что при `E > 0` (деньги не держат культуру). При `v_p = 0` у всех p ячейки и `ℓ = 0` рост от усилия равен 0. `lic` 0 → 1 не уменьшает ни рост, ни `maint`. Деление по site не создаёт усилия (P4).
- **Что изменилось против v2.3 (текст v2.3 — Приложение А):**
  - `V_c`, `s_p` (доля объёма, F2) заменены на `max` по процессам ячейки. Одна линия ведёт ячейку и не разбавляется (K3, #80).
  - Процессы с `r_d = 0` в ячейку не входят (A2 v2.3 снят). Базовая тяга к 0,25 у таких процессов пропадает — П-3.
  - Прямой канал лицензии в культуру — новый (#104, #107). Канал `X½·(1 − l_lic)` остаётся.
- **#79, #85, #101 в этом правиле.** #85 (R1c) не принят: hold-out провален, #95. От #79 остаётся слабая зависимость от темпа с насыщением: она задаётся `c_p` (SMOOTH по `ṽ`). По #101 «тлеющий цех» может учиться, но дороже и дольше. **[Факт: `culture-round2.md` §1.9, бумажная оценка, не стенд] Временное правило эти требования выполняет не везде:** K2a — 29 сбоев из 295 при `α` 0,07, HK8 — 33/10 из 57, цена K2b′ в режиме AI — 9. Это и есть RISK-0016. Пороги не подбираются, правило на стенде больше не правится (#111).
- **Заменяемость (RISK-0016).** Правило живёт за интерфейсом §4.1a (`E_useful`, `limiter`, `limiter₀`, `lead`, `dH_forecast`) и одним шагом compute ячейки. ИИ, `why_not` и UI читают только функции §4.1a. Тогда замена правила по итогам полной модели меняет один модуль Core, а не три слоя. Тест: абляция «правило C-B → R0 v2.3» собирается без правок ИИ и `why_not` [Предл.].
- [Предл.] **#30.** Ниже `H_floor` культура не падает. Пол растёт с образованием, поэтому возобновить производство дешевле, чем освоить с нуля. Если `H < H_floor` (уровень никогда не был достигнут), падения нет, но и автоматического подъёма до пола нет. `proc_X` и `line_E` пола не имеют [Предл.]. Тест (Lab): после 10 лет простоя путь к `yield ≥ 0.7` короче, чем у новичка с теми же кадрами.
- `world_lead(p, a)` = 1, если в прошлом месяце **другой актор** `a' ≠ a` вёл p с `yield ≥ 0.7`: на его site `proc_v > 0` и `proc_yield ≥ 0.7` в снимке (§4.0). Свои site актора не считаются. Значение — чистая функция снимка (v2.3: не post-фаза). По #102 `catch` переносом знания не считается.
- `α_eff[d] = α·(1 + k_qp)` для `d = quality_control` на site с активной программой качества (§7), иначе `α`. В C-B программа качества умножает отдачу усилия на `qc`: две ручки на одно измерение — П-6.

### 4.1a Функции правила культуры (интерфейс, v2.4 черновик)
Все функции чистые, читают только снимок t−1. Источник — `culture-round2.md` §1.2, `PROCESS_DEVELOPMENT.md` v0.2 §2.3. Ячейка процесса — `cell(p) = (site, c(p), d*(p))`.
- `t̂_p` — `t_p` при полном усилии: `t̂_p = max(c_p·gap_p, ℓ·gapL_p)`; при `v_p = 0` `c_p = 0`.
- `lead(site, c, d)` → `prc_id` или «нет». Процесс кластера c с активным d и наибольшим `t̂_p`; ничья — меньший `prc_id`; все `t̂_p = 0` → нет. От `E` не зависит.
- `d*(p)` — измерение с наибольшим `r_d − H` среди ячеек, которые ведёт p. Если p не ведёт ни одной — среди всех активных измерений p. Ничья — канонический порядок.
- `limiter(site, p)` — первое совпадение, порядок фиксирован. Если p не ведёт ни одной ячейки, его `limiter` равен `limiter` процесса `lead(cell(p))`. Значения:
  1. `NONE` — `gap_p(d*) = 0`;
  2. `TOOLING` — `M[s,c,d*] < H[s,c,d*]` (A5);
  3. `SATURATION` — `Hcap[s,d*] ≤ r_d*`;
  4. `LAB_CEILING` — `v_p = 0` и (`ℓ = 0` или `H ≥ r_d* − ΔL`);
  5. `VOLUME` — `v_p > 0`, `E_p ≥ E_useful` и `k* < 1`;
  6. `EFFORT` — во всех остальных случаях.
- `limiter₀(site, p)` — `limiter` при `E_p = 0`. От `E` не зависит, поэтому выбор ИИ не мерцает.
- `E_useful(site, p)` = 0, если `lead(cell(p)) ≠ p` или `limiter₀ ∈ {NONE, TOOLING, SATURATION, LAB_CEILING}`. Иначе `E_useful = E_full · k*`, где `k* = ℓ`, если `ℓ·gapL_p > c_p·gap_p`, иначе `k* = c_p`. Это точка излома `t_p` по `E`.
- `dH_forecast(site, p, E, v)` = `min(ΔH⁺, ρ_max)` ячейки `cell(p)` по §4.1, где вместо `E_p` подставлено `E`, а вместо `v_p` — `v` (в `ṽ_p`, `x_V`, `m_p`). Остальное — из снимка. Функция не убывает по `E` и по `v`. При `E = E_p`, `v = v_p` она побитно равна фактическому приросту. Если `lead ≠ p`, вклад `E` равен 0. Нужна только UI и `why_not`, в тик не входит.
- **Деление `E` актора по site** (PD §1.2): `E_{s,p} = (E_{a,p} · v_{s,p}) / Σ_s v_{s,p}`, floor. Остаток floor получает site с наибольшим `v`, при ничьей — меньший `site_id`. Если `Σ v = 0`, всё получает меньший `site_id`. `Σ_s E_{s,p} = E_{a,p}` точно (инвариант).

### 4.1b Распределение наладки производства (v2.4 черновик, #99, #112)
Детерминированно, без RNG, по актору, в compute месяца t (§4.0). Полное правило ИИ — `PROCESS_DEVELOPMENT.md` v0.2 §5, стендовое — `culture-round2.md` §1.3. Контракт фиксирует порядок и инварианты.
```
D_a      = share_D[a] · budget_a(t)                      # доля — из снимка
шаг 0 (только игрок, #112): для p в effort_focus[a] по порядку:
           E_p = min(D_left, E_useful(p));  D_left −= E_p
шаг 1 кандидаты K = { p ∈ known_processes(a) : limiter₀(p) = EFFORT ∧ E_useful(p) > 0 ∧ E_p < E_useful(p) }
шаг 2 вес  w_p = (v_exp(p) / (r_ref · labour_p)) · gap_H(p)    # нормировано (R2-10), Fx6 без переполнения
шаг 3 налив: alloc_p = (D_left · w_p) / Σ_K w,  floor, Σ по возрастанию prc_id
           E_p += min(alloc_p, E_useful(p) − E_p); упёршиеся выходят из K;
           повтор, пока D_left > 0 и K не пусто; итераций ≤ |K|
шаг 4 остаток D_left (вместе с копейками floor) → бюджет invest_tooling_M того же compute
```
- Ключ — `(actor, p)`. В срезе один site на страну, и `E_useful(p) = E_useful(site, p)`. При нескольких site деньги актора делятся по §4.1a, а налив по сумме `Σ_s E_useful(s,p)` может дать site больше его `E_useful` — П-14.
- `gap_H(p)` — наибольшее `max(0, r_d(p) − H)` по активным измерениям. `v_exp(p)` — PD §5 п. 1. Множители доктрин P1/P2/P3 — PD §5 п. 3 (×2 / ×2 / ×1, [Предп.], заморожены до калибровки). `Σ_K w = 0` → шаг 3 пропускается.
- Фокус сверх `E_useful` не даёт ничего. Процесс с `lead ≠ p` фокус принимает, но получает 0 (`E_useful = 0`). Пустой фокус = «как у ИИ». У ИИ фокуса нет.
- Инварианты (test-engineer): `Σ_p E_p + остаток = D_a(t)` точно; `0 ≤ E_p ≤ E_useful(p)`; ИИ не даёт денег процессу с `limiter₀ ≠ EFFORT` или с `lead ≠ p`; распределение — чистая функция снимка и решений (два прогона — один хеш); оно не зависит от `proc_E` прошлого месяца; при фокусе игрока шаги 1–4 те же, что у ИИ.
- Доля `D` у ИИ берётся из статьи способности: `share_D = 0,4·share_cap_v010`, `share_cap = 0,6·share_cap_v010` (PD §1.1, [Предп.], не калибруется).

### 4.2 Выход и цена (C1)
Каноническая форма (§4.0); все величины из снимка.
```
c_d     = min(culture_H[site,c,d], tooling_M[site,c,d])           # c = cluster(p)
g(gap)  = 0 (gap < −1);  (1 + gap)·(1 + gap) (−1 ≤ gap < 0);  1 (gap ≥ 0)
yield_p = ((1 · g_d1) · g_d2 · …) · ramp(proc_X)       # только d с r_d > 0, канонический порядок измерений, ramp последним
yc_p    = max(yield_p, ε)                              # общий ε контракта для всех делений на yield
q_p     = g(c_qc − r_qc(p)), если r_qc(p) > 0; иначе 1    # qc = quality_control (A4)
production_profile(site, prc_set) =
  admitted        = ∀p: yield_p > 0 ∧ p ∈ known_processes(owner)
  unit_cost_mult  = (Σ_p (n_p · base_cost_p) / yc_p)  /  (Σ_p (n_p · base_cost_p))
  q               = min_p q_p
  bottleneck      = argmin_p yield_p → (dim, H|M); ничьи по prc_id
```
По #26 «фактически невозможно» = `g = 0`.
- **A4, `q`.** [Предл.] `q_p` — множитель измерения `quality_control` из того же `yield_p` (новых параметров нет): доля годных по контролю качества. Его читают `readiness` когорт и правило ИИ «программа качества» (спецификация среза §4–5). Брак `q` и `defects_hidden` по-прежнему разные причины (§3 п. 4). `quality_control` действует и на цену (через `yield`), и на готовность (через `q`) — это два разных выхода, а не двойной счёт по цене; Lab проверяет вклад абляцией `k_qp = 0`. Если в `prc_set` нет процесса с `r_qc > 0`, `q = 1`.
- **A5, A6, `bottleneck`.** Узкий процесс — минимальный `yield_p`, ничья по `prc_id`. В нём узкое измерение — минимальный `g_d`, ничья по каноническому порядку измерений; источник `H`, если `culture_H ≤ tooling_M` (при равенстве — `H`), иначе `M`. Если у узкого процесса все `g_d = 1` (ограничивает только `ramp`), то `dim = null`, источник `ramp`. v2.4: при источнике `H` в звене добавляется `limiter(site, prc)` (§4.1a, §6).

### 4.3 Промышленность → наука (C8)
Каноническая форма (§4.0). Шаг compute знания тика t по снимку: `v_p = proc_v`, `yield_p = proc_yield` месяца t−1 (по всем site актора), `K_d`, `K_ind` — из снимка (A10).
```
V_d    = Σ_{p: discipline(p)=d, yield_p ≥ 0.3} v_p
если V_d = 0:  K_ind' = K_ind − δ_ind · K_ind
иначе:         ΔK_ind = ((η · V_d) / (V_d + V_ref)) · max(0, 1 − K_ind / (θ_ind · K_d))      θ_ind ≈ 0.25
```

#### 4.4c Досрочный запуск серии (#94, #97)

- **Доработка построенных** (#97): `retro_pool = X` в месяц запуска. Каждый дефект, исправленный бригадой (A32), пока `retro_pool > 0`, расходует единицу пула и стоит `c_retro · units_in_service`, где `c_retro = (unit_cost_floor · ρ_retro) / D_ref`. - **Готовность** — §4.4b без новой формулы: у досрочного парка `D ≈ D0`.
- Проверка — плечо `FORCE` с критерием S-F, зафиксированным до прогона: досрочный запуск выгоден (`ΔFV > 0`) в 20–80% случаев (#97). `a_acc`, `ρ_retro` по результату не подбираются.

## 6. `why_not(actor, target)` (F6)
`target` ∈ {`app_id`, `design_id`, `requirement_id`}. Это чистая функция снимка. Возвращает **полный отсортированный** `List<Link>`: UI показывает первые 3, Lab использует весь список.
`Link { layer, cause, subject_id, have, need, lever, yield_if_fixed, eta_months }`
- `layer` ∈ `KNOWLEDGE` < `CAPABILITY` < `PRODUCT` < `ECONOMY`.
- `yield_if_fixed` — `yield` узкого процесса изделия, если закрыть только это звено (`have := need`), а остальное не трогать.
- `eta_months` — когда `have` дойдёт до `need` при **текущих** скоростях из снимка: `ceil((need − have)/rate)`. Если `rate ≤ 0`, значение `null` («само не дойдёт»). Функция детерминирована.
- Сортировка: `layer`, затем `yield_if_fixed` по убыванию, `eta_months` по возрастанию (`null` в конце), `subject_id`.

Причины по слоям:
1. **KNOWLEDGE:** нет узлов на пути к APP. Звено — ближайший недостающий узел по цене. v2.4: недоступная альтернатива слота (`avail = false`) — то же звено.
2. **CAPABILITY:** `admitted = false` или `yield < 0.7` у узкого процесса. Звено — `(prc, dim, H|M, have, need)`. v2.4: при источнике `H` звено несёт `limiter(site, prc)`. При `lead ≠ prc` `subject_id` указывает на ведущий процесс. `rate` для `eta` — `dH_forecast` при текущих `E` и `v`.
3. **PRODUCT:** нет проекта, `granted/n < 0.9`, открыты `defects_hidden`, дефицит CMP. v2.4: `SERIES_GATE` — «серия не допущена: скрыто N при допуске M»; `have = D_hidden`, `need = k_gate·D_ref`, `eta_months` — месяцы до допуска при текущем `test_rate`, `yield_if_fixed` — текущий `yield` узкого процесса.
4. **ECONOMY:** «допущено, но не по карману»: `admitted`, но `unit_cost·n_plan + upkeep` больше бюджета программы.

**v2.4: звено культуры по `limiter` (новые причины CAPABILITY, источник `H`)** [Предл.; PD §10.4, #93, #112]:

## 8. Абляции и проверка двойного счёта (C3)
1. **Тест разреженности (CI).** Сдвигаем один запас на Δ, проводим один месячный compute и сверяем изменившиеся выходы с §3. Если меняется чужой выход, тест падает.
2. **Бюджет падения цены на удвоение (Lab, срез).** На эталонной линии `Δlog unit_cost` за удвоение накопленного выпуска раскладывается на два канала:
   - **канал выхода:** `proc_X`/`ramp` + `culture_H`/`g` → `1/yc`;
   - **канал сборки:** `line_E` → `assembly_hours`.

   Вклад канала = симметричная оценка `½[(полная − без канала) + (только канал − ни одного)]` в `log`.
   | Фаза | Суммарное падение на удвоение | Доля канала выхода | Доля канала сборки |
   |---|---|---|---|
   | освоение (первые 3 удвоения) | ≤ 40% | 50–80% | 20–50% |
   | зрелая линия (`yield ≥ 0.9`) | 15–30% (Wright 70–85%) | ≤ 20% | ≥ 80% |

   Значения [Предп.], их калибрует Lab по RR-0007. Выход за коридор = двойной счёт или пропуск. Аддитивность: сумма вкладов совпадает с полным эффектом в пределах ±15%. v2.4: в C-B культура растёт от денег, а не от объёма. ## 9. Старт 1945 (#23), асимметрия (#24), лидер (#27), разброс (#28)
### 9.1 Метрики лидерства
Определения (все величины — из снимка месяца t, post-фаза):
- `mastered(a, p, t)` — процесс p **освоен** актором a: на каком-то site актора `yield_p ≥ 0.7` (§4.2) и `v_p ≥ v_min` (§4.1) в каждом из месяцев t−5…t (без «показательных» единиц).
- `fielded(a, t)` — проекты d, которые у актора **на вооружении и освоены**: в строю ≥ `n_service_min` единиц когорт d, выпущенных на site актора, и `mastered(a, p, t)` для всех `p ∈ prc_set(d)`. `n_service_min` — параметр данных. Отсюда #62/#70: двигатель должен быть освоен самой страной.
- (v2.4, #70) `gen(d) = min(g_p(d), rank(engine(d)) + 1)` (§4.4a). Двигатель, отстающий от платформы на одно поколение, `gen` не снижает; на два и больше — снижает. Двигатель новее платформы `gen` не повышает. (v2.3: «поколение APP-узла класса изделия» — Приложение А.)

- [Предл.] `tech_lead(t)` среди великих держав (#44, без объёма и цены). Ключ актора `K(a, t)` сравнивается лексикографически:
  1. `G` = max `gen(d)` по `d ∈ fielded(a, t)`; 0, если пусто;
  2. `T` = max `complexity_tier(p)` по p с `mastered(a, p, t)`; затем `N` = число таких p с tier = `T`;
  3. `P` = max `perf(d)` по `d ∈ fielded(a, t)` (только `perf`, линейно, сравнение в `Fx6`; 0, если пусто).

  Итого `K = (G, T, N, P)`. `unit_cost`, `line_E`, объём выпуска и `perf/unit_cost` в ключ не входят ни на каком уровне.
- [Предл.] **Ничьи.** `best(t)` = акторы с максимальным `K`. Если `best(t)` = {a} — кандидат a. Иначе (ничья по всем полям) кандидата нет и `tech_lead(t) = tech_lead(t−1)`. Действующий лидер, который входит в `best(t)`, остаётся лидером. `actor_id` и «кто раньше» ничьи не разрешают: исход не зависит от нумерации акторов. `tech_lead(t0)` задаёт сценарий (#23).
- **Смена лидера** засчитывается, если новый `tech_lead` держится ≥ 24 месяца (без дребезга).
- Если в сборке несколько классов изделий, `G` и `P` считаются по классу, заданному метрикой (в срезе он один). Агрегация по классам — §13.
- `volume_lead` = Σ выпуска по tier ≥ 4 при `yield ≥ 0.7`. Отдельная метрика, считается и показывается, ориентира нет, в `tech_lead` не входит (#27, #44).
- `fleet_value` (v2.4 черновик; #91, COMPONENT_SELECTION G-5). Считается против соперника **при равном бюджете** B (горизонт 15 лет, #34), upkeep учтён явно:
  ```
  FV_a = max_v n_v · readiness_v · PowFrac(perf_rel_v, q10_γ)        # γ = 0,5, q10_γ = 512 («З»)
  n_v  = min(n_budget_v, ⌊(supply_a / alloy_kg_v) · H_build⌋), шаг 10 вниз    # H_build = T_field = 24 мес.
  ```
  `n_budget_v` — наибольшее n (шаг 10), при котором `Σ_{k=1..n} unit_cost_v(E + k) + n·upkeep_v·H ≤ B` (спека §5.5). Lab печатает отношение `FV(A)/FV(B)`. Обоснование `γ` — квадратичный закон Ланчестера (COMPONENT_SELECTION §6), а не подбор (#91). Поле `P` ключа остаётся линейным. Форма v2.3 «Σ по когортам» против «max по проектам» — П-11.
- Критерий совместной гипотезы (#25):
  - смена `tech_lead` за 1945–1975 — в 30–40% seeds (Wilson CI);
  - малая держава становится `tech_lead` против великой не чаще чем в 5% seeds.

## Приложение А. Текст v2.3, который v2.4 заменяет (действует до утверждения v2.4)
**§4.1 v2.3 (правка RR-0006 §4.5; F2, F3, #30).** Каноническая форма (§4.0). Ячейка `(site, c, d)`; `H` — из снимка; `v_p = proc_v[site,p]` месяца t−1.
```
V_c      = Σ_{p∈c} v_p                     # все p кластера с v_p > 0, включая r_d(p) = 0 (A2)
если V_c = 0:  drive = catch = maint = 0    # без деления на ноль
иначе:   s_p = v_p / V_c                    # отдельная операция
  drive  = Σ_p s_p · max(0, r_d(p) + 0.25 − H)
  catch  = Σ_{p: world_lead(p, owner)} s_p · max(0, r_d(p) + 0.25 − H)   # world_lead — выбор, не множитель
  maint  = Σ_p (s_p · r_d(p)) · a_r,   a_r = min(1, act[c] / act_norm)
spill    = Σ_c' R[c,c'] · max(0, H[c',d] − H[c,d])   # H[c',d] — из снимка
H_floor  = φ_floor · Hcap[site,d]           # Hcap — от образования кадров; φ_floor из данных
sat      = max(0, 1 − H / Hcap[site,d])
α_eff[d] = α · (1 + k_qp)  или  α
ΔH⁺      = sat · ( ((α_eff[d] · act[c]) · w[c]) · drive + k_catch · catch + σ · spill )
ΔH⁻      = δ_H · max(0, H − max(maint, H_floor))
H'       = H + min(ΔH⁺, ρ_max) − ΔH⁻
```
- **A2.** Процессы кластера с `r_d(p) = 0` входят в `V_c` и `s_p`, как записано (`Σ_{p∈c}`, F2: доля объёма кластера). Они разбавляют тягу трудных процессов, в `maint` дают 0, а в `drive` — `max(0, 0.25 − H)`, то есть держат культуру не ниже базового уровня 0,25.
- [Предл.] **F2.** Линия с 1% объёма кластера даёт 1% тяги. Освоение требует массового трудного выпуска, убыточного при низком выходе.

**§4.4 v2.3, варианты (#29).** [Предл.] Требование (`Requirement`) порождает у КБ не меньше 2 вариантов с **разными** `prc_set`: «превосходящий» — выше `perf`, трудный `prc_set`; «технологичный» — ниже `perf`, `prc_set` в пределах текущей способности. Тест: эталонное требование среза даёт оба варианта, `prc_set` различаются. Процессная часть цены: `Σ_p n_p·base_cost_p / yc_p`.

**§9.1 v2.3.** `gen(d)` — поколение APP-узла класса изделия, который реализует проект d (данные знания, RR-0008). `fleet_value(A) = Σ_cohort count·readiness·perf_rel` при равном бюджете B, где `Σ unit_cost·count + Σ upkeep·months ≤ B`.

**§6 v2.3, рычаг `training_series`:** CAPABILITY, узкое место `H` (любое).
