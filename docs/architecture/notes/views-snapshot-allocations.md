# Снимок видов: аллокации (DEBT-0051, TASK-0103 F6)

> Автор: systems-architect, 2026-11-18. Статус: записка (design note), не ADR.
> Основа: TASK-0103 («Отчёт профиля аллокаций», F2/F6, ревью шага 1), ADR-0006, ADR-0014 п. 5–6, ADR-0016 §1 и §6, ADR-0017 п. 5–7 и 16, `docs/architecture/notes/daily-hash-and-view.md` §2 (F7a/F7b).
> Код: `src/Singularity.Session/Views/ViewBuilder.cs`, `SliceViews.cs`, `SliceSession.cs:195-230`, `src/Singularity.Kernel/Column.cs`.

## Краткий вывод

- [Факт: TASK-0103, строка 3 таблицы и F6] Один полный снимок в точке A (200 акторов × 2000 узлов) стоит ≈ 49 МиБ: `NodeView` ≈ 34 МиБ и массивы ≈ 14 МиБ. В месяц строится 2 снимка: тик команд и месячный тик. После F1–F5 останется ≈ 85–100 МиБ/мес. против порога P8 ≤ 1 МБ.
- [Предп.] Даже без узлов остаток снимка (`DesignView`, `BureauView`, `KD`, `Decisions` у 200 акторов) стоит ≈ 0,5–1 МБ на снимок. Значит, порог 1 МБ/мес. для пути снимка не выполним ни одним вариантом, кроме переиспользуемых буферов. Это число нужно замерить отдельной пробой (см. «Проверка»).
- [Факт: `Column.cs:42-53, 119-126`] Kernel держит у каждой колонки два массива и меняет их местами. Ленивый вид поверх живых колонок через два тика читал бы чужие данные, а с потока клиента это ещё и нарушение ADR-0014 п. 5. Поэтому «лениво» здесь значит только «поверх компактных массивов, которыми владеет снимок».
- [Факт: ADR-0017 строка 198; записка daily-hash-and-view §2] В игре снимок строится на каждом непустом тике. После #228 это каждый день, то есть ×15 к числам ниже. Вариант «раз в месяц» как правило контракта не годится. Годится его механическая часть: переиспользование неизменившихся блоков.
- **[Предл.] Рекомендация.** До TASK-0102:
  - R1 — компактные блоки узлов по актору без объекта на узел;
  - R2 — переиспользование блоков на тиках, которые не писали их колонки;
  - R3 — решение владельца о разделённом пороге P8: путь тика и путь снимка.

  Пул с арендой (B) и узлы только для наблюдаемых акторов (A2) переходят в ADR #228. Дельта (C) отклонена.

## 1. Что стоит снимок сейчас

- `NodeView` — record class. [Предп.] Объект ≈ 88 Б: заголовок 16, `Number`, два `bool`, `ProcessView?` 48, `long?` 16. 400 тыс. объектов ≈ 34 МиБ, что сходится с профилем.
- `ProcessView` есть у 651 из 2000 узлов. Остальные 1349 узлов на актора несут пустой `ProcessView?` на 48 Б.
- Объекты со ссылками живут столько, сколько их держит потребитель:
  - клиент держит `HostSnapshot.View` до следующей публикации, на медленной скорости это секунды;
  - Lab `JetSliceModel.cs:196-199` держит два снимка (`snapshot` и `s.View`).

  Поэтому они переживают gen0. 400 тыс. ссылочных объектов дорого размечать в gen1/gen2. Важны и байты, и форма.
- **Ловушка LOH.** Если просто сделать `NodeView` структурой (≈ 72 Б), блок актора займёт 2000 × 72 = 144 КБ > 85 КБ. Это 200 аллокаций LOH на снимок, и они снова запустят gen2, которые убрал F1. Любой вариант обязан держать каждый массив снимка < 85 КБ.

## 2. Варианты

Числа — точка A, 2 снимка/мес., после F1–F5, только путь снимка [Предп., расчёт по размерам типов; не замер].

### A. Компактные блоки узлов и ленивый доступ (R1)

- `ActorView.Nodes` становится `NodeList` — `readonly struct`, реализует `IReadOnlyList<NodeView>`. `NodeView` — `readonly record struct` с теми же членами.
- Блок актора хранит:
  - `Known` и `ByLicence` — битовые маски по 250 Б;
  - `ProcessView[651]` ≈ 26 КБ, индекс по `IndustryLayout.RowOf`, его карта строк берётся из `Layout` и не копируется;
  - `long[2000]` `KnownSince` (16 КБ) — только при `TracksKnownSince`.
- Индексатор собирает `NodeView` на лету, без аллокаций и без чтения таблиц.
- **Аллокации:** ≈ 27–43 КБ на актора, ≈ 5,5–8,5 МБ на снимок, **≈ 11–17 МБ/мес.** Нет LOH, нет ссылок на узел.
- **API:** почти совместим по исходникам. `av.Nodes[r]`, `foreach (NodeView n in av.Nodes)`, `.Length`/`.Count`, `n.Process is ProcessView p`, `new NodeView(...)` в `SliceChecks.cs:129` работают. Нужны правки:
  - `TechTree.cs:146-147` и `AudioDirector.cs:244` — только при несовпадении `Length`/`Count`;
  - `ApiSurfaceTests` — `TestApiVersion` +1 (ADR-0014 п. 6);
  - `DailyTickProbeTests` сравнивает JSON. Форма JSON та же, если `NodeList` сериализуется как массив; это нужно проверить.
- **Детерминизм:** риска для хеша нет, вид не входит в состояние. Риск только в неверных данных вида, его закрывает тест эквивалентности.
- **Трудозатраты:** ≈ 1–2 дня developer + тесты.
- **ADR:** не нужен. Это light внутри ADR-0014 п. 6, ревью поверхности за systems-architect.

### A2. Узлы только для наблюдаемых акторов

- Узлы строятся для подписанного набора акторов: execution-only опция, не хешируется. Клиенту нужны игрок и выбранная держава. Lab ставит «все».
- **Аллокации:** при K = 2 ≈ 0,1 МБ/мес. на узлы. Плюс остаток снимка ≈ 1–2 МБ/мес. [Предп.].
- **API:** смена выбранной державы требует нового снимка (задержка до тика) или запроса через очередь.
- **Детерминизм:** тест «хеш с ObserveAll = хеш с ObserveNone».
- **Трудозатраты:** ≈ 2–3 дня.
- **ADR:** нужен. Меняется смысл «полного `ViewMode`» в ADR-0016 §1/§6, и это решение владельца.

### B. Переиспользуемые буферы с протоколом владения

- Блоки берутся из пула. Потребитель получает аренду: `using ViewLease l = session.AcquireView()`. Счётчик ссылок `Interlocked`, у буфера номер поколения. Поток симуляции строит снимок в свободный буфер; если свободного нет, выделяет новый, и пул растёт до установившегося размера.
- Кто и сколько может держать снимок:
  - клиент — один кадр или до следующего `Publish`;
  - Lab-наблюдатель — два снимка на время `observer.Month`;
  - копии (как `TechTree._nv`) — без ограничений, потому что это копии значений.
- **Аллокации:** ≈ 0 в установившемся режиме для всех 200 акторов, и после #228 тоже.
- **API:** ломает ADR-0014 п. 5 («неизменяемый снимок, одна атомарная запись ссылки, без блокировок»). Затронуты все потребители: `SimHost`, `ActorPanel`/`SignalField` (`ReferenceEquals` как признак изменения), `JetSliceModel`, тесты.
- **Детерминизм:** хеш не затронут. Главный риск — чтение после возврата в пул: тихая порча вида и, через `SliceObserver`, свидетельств EXP. Нужна проверка поколения на каждом доступе (в Debug — бросать) и стресс-тест.
- **Трудозатраты:** ≈ 4–6 дней + gate.
- **ADR:** нужен (gate+research: модель потоков). Новый ADR с `supersedes` по ADR-0014 п. 5.

### C. Дельта-снимок

- Публикуются только изменившиеся узлы с номером версии.
- **Аллокации:**
  - `Known`/`ByLicence` меняются редко, это КБ;
  - `ProcessView` (`Yield`, `V`, `UnitCostMult`) меняется каждый месяц у большинства из 130 тыс. процессов, ≈ 5 МБ/мес. Дельта бьёт не туда.
- **API:** потребитель сворачивает дельты в своё состояние. Клиент, который опрашивает `View` раз в кадр, пропускает промежуточные публикации, поэтому нужна цепочка дельт или пересинхронизация. Lab нужен полный вид.
- **Детерминизм:** хеш не затронут. Риск пропущенной дельты, то есть рассинхронизации вида.
- **Трудозатраты:** ≈ 5–8 дней.
- **ADR:** нужен.
- **[Предл.] Отклонить:** сложность без выигрыша на главной части.

### D. Раз в месяц, а не дважды (R2 — механическая часть)

- Не публиковать вид после тика команд нельзя: ADR-0014 п. 5 публикует после каждого непустого тика, игрок должен видеть принятую команду.
- Можно переиспользовать. На тике команд `_month` ещё прошлый, поэтому `next` тот же, что у предыдущего месячного снимка. Если с той сборки не писалась ни одна колонка из набора чтения блока узлов (или всего `ActorView`), блок берётся из прошлого вида как есть. Это обобщение F7a.
- Нужен счётчик версий у колонки в Kernel: +1 в `SwapIfOpen` и `Load`. Это не доменная логика. Ещё нужен объявленный набор чтения блока; какие колонки читает `LicenceShare`/`Profile`, должен подтвердить тест.
- **Аллокации:** 1 сборка в месяц. С A — **≈ 6–9 МБ/мес.**, без A ≈ 49 МиБ.
- **API:** нет.
- **Детерминизм:** хеш не затронут. Риск — устаревший блок, если набор чтения объявлен неполно.
- **Трудозатраты:** ≈ 1–2 дня.
- **ADR:** не нужен. Это light: ADR-0017 п. 6 уже вводит версию таблицы, здесь она дробится по колонкам.
- После #228 выигрыш зависит от того, какие колонки пишут дневные системы [Предп.].

### E. Пересмотр порога P8 для пути снимка (R3)

- ADR-0016 §6 задаёт «≤ 1 МБ/мес., снимок видов включён» с пометкой [Предл.]. Порог защищает от пауз GC и gen2.
- [Предл.] Разделить порог:
  - **путь тика** (системы, команды, хеш, `Inputs`, `Step`) — ≤ 1 МБ/мес.;
  - **путь снимка** — ≤ 8 МБ на снимок в точке A, 0 аллокаций LOH в `ViewBuilder`, ни одного объекта со ссылками на узел;
  - общее — 0 gen2 за 120 мес. и доля пауз GC ≤ 2 % времени прогона.
- **Аллокации:** кода нет.
- **API:** нет.
- **Детерминизм:** нет.
- **Трудозатраты:** правка пре-регистрации EXP-0008.
- **ADR:** ADR-0016 — ACCEPTED, поэтому нужен новый ADR с `supersedes` §6 (или запись в DECISIONS_LOG по образцу поправки ADR-0022) и решение владельца.

## 4. Рекомендация и очередность [Предл.]

1. **До TASK-0102:** R1 + R2, light, developer. Без них P8 предсказуемо проваливается, и серия тратится впустую. Их цель — 0 LOH и 0 gen2 и ≈ 6–9 МБ/мес.
2. **До пре-регистрации EXP-0008 (TASK-0102):** R3, решение владельца. P8 пре-регистрируется, поэтому определение порога должно быть зафиксировано до прогона. Иначе P8 либо FAIL по определению, либо меняется после факта.
3. **В ADR #228 (дневные системы, ×15 снимков):** выбрать между A2 и B, либо ограничить частоту публикации частотой кадра клиента (записка daily-hash-and-view §2, F7a). До #228 это не нужно.
4. Не делать:
   - C (дельта);
   - ленивый вид поверх живых колонок (`Column.cs` меняет массивы местами; ADR-0014 п. 5);
   - ленивые кэши при чтении вида (условие F4-A в ADR-0017).

## 5. Проверка

- **Проба `alloc`:** разделить на «Snapshot без узлов» и «узлы». Первая проверяет [Предп.] об остатке ≈ 0,5–1 МБ на снимок — именно она решает, какое число ставить в R3.
- **Эквивалентность:** на (24, 180) с командами и дневным зондом JSON каждого опубликованного вида после R1/R2 равен JSON эталонной полной пересборки (по образцу теста F7a). Плюс тест «тик, писавший колонку набора чтения, пересобирает блок».
- **Golden:** golden-хеши и `bench --mode validity` (t1/4/8/16 × c1/8/32) без изменений.
- **LOH:** архитектурный или юнит-тест, что каждый массив снимка в точке A < 85 000 Б. GC-событий `AllocLarge` из `ViewBuilder` в трассе 0.
- **CI (ADR-0016 «Проверка»):** порог байт/мес. — раздельно для пути тика и пути снимка, если R3 принят.
