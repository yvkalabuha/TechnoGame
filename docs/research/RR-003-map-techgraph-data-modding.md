## 1. Вопрос исследования

1. Как представить провинции Земли (~1910) так, чтобы это работало и для headless-симуляции (смежность, логистика), и для будущего рендера; какие открытые геоданные можно легально положить в публичный репозиторий.
2. Какие исторические наборы данных (население, ВВП, промышленность, образование) подходят для стартового состояния 1910 и совместимы по лицензии.
3. Какая модель данных подходит для нелинейного «пространства исследований» (не линейное дерево), и какой нужен инструментарий валидации.
4. Какой формат данных и какая модель модов (load order, overrides, конфликты, сейвы) нужны с ранней стадии без переусложнения.
5. Насколько глубоко моделировать модульные инженерные проекты.

- Данные/моды: **JSON-подобные данные с JSON Schema (2020-12)**, авторинг в YAML или TOML допустим; база игры = мод `core`; моды — декларативные патчи с явным load order по зависимостям (модель Factorio/RimWorld), без скриптинга до появления ядра. Lua/WASM — отложить.
- Инженерия: **уровень HoI4/Terra Invicta (слоты + компоненты + агрегирование статов)**, не Aurora/From the Depths.

## 3. Тема 1 — Глобальная карта

### 3.1 Способы представления провинций

| Подход | Как устроено | Смежность для симуляции | Рендер | Моддинг | Оценка для проекта |
|---|---|---|---|---|---|
| Paradox color-map | `provinces.bmp` (каждый цвет = провинция) + `definition.csv` (id;R;G;B;name) + `adjacencies.csv` для проливов/исключений [M] | Вычисляется по соседству пикселей при загрузке; проливы — вручную | Прямой (шейдеры, borders через lookup) | Очень удобен в графическом редакторе, плохо диффится в git (бинарь) | Хорош для рендера, плох как источник истины в git |
| Векторные полигоны | GeoJSON/TopoJSON/GeoPackage, полигон на провинцию | Вычисляется по общим рёбрам (топология) один раз, кэшируется | Триангуляция или растеризация в color-map/SDF | Текстовый, диффится, но громоздкий | **Лучший канонический источник** |
| Hex/Goldberg polyhedron | Сфера из ~12 пентагонов + гексов (геодезическая сетка), либо H3 (Uber) | Тривиальная, равномерная | Простой, но «игровой» вид, плохо ложится на исторические границы | Простой | Хорош как вторичная сетка (климат, ресурсы), не как провинции |
| Voronoi от городов/точек | Разбиение по сидам (города), обрезка по побережью | Тривиальная (Delaunay) | Нужен clipping | Генерируемый, воспроизводимый | Хорош для автогенерации провинций там, где нет исторических данных |
| Чистый граф (без геометрии) | Узлы + рёбра + атрибуты | Явная | Нет (нужна геометрия позже) | Очень простой | **Достаточно для M0** |

Факты/выводы:
- [A] Для симуляции важны только: список провинций, смежность (сухопутная/морская/пролив), площадь, центроид, принадлежность (страна/регион), терраин/климат, ресурсы. Геометрия нужна лишь для их вычисления и для рендера.
- [A] Сферичность: проекции (Equirectangular) искажают площадь на высоких широтах; площадь и расстояния считать по геодезии (на эллипсоиде/сфере) при компиляции, а не из пикселей.
- [M] H3 — иерархическая гексагональная сетка, лицензия Apache-2.0, есть биндинги для C#, Rust, C++ (исходная библиотека на C).

### 3.2 Конвейер (pipeline) карты — концепция

```
источники (NE, исторические контуры, ручные правки)  ->  provinces.geojson (канон, текстовый)
      -> map-compiler (offline tool) -> provinces.json: id, neighbors[], area_km2, centroid, coastal, terrain
      -> (позже) provinces.png color-map + borders mesh для рендера
```
- [R] Смежности генерировать инструментом, а ручные исключения (проливы, каналы — Суэц, Панама с 1914, Босфор) хранить отдельным текстовым файлом `adjacency_overrides`.
- [R] Стабильные строковые ID провинций (`prov.fr.paris`), а не цвета/числа — это ключ для модов и сейвов. Числовые индексы — только runtime.

### 3.4 Рендеринг (высокоуровнево, на потом)
- Color-map + shader (Paradox-подобно): провинции в текстуре, цвет страны через lookup-texture, границы через edge detection/SDF. Масштабируется до десятков тысяч провинций.
- Векторный рендер (триангулированные полигоны, Mapbox-like): чище при зуме, сложнее с эффектами.
- Глобус: кубосфера или equirectangular-текстура на сфере.
- [R] Решение по рендеру отложить; требование к данным сейчас — только «геометрия хранится в виде, из которого можно сгенерировать оба варианта».

### 5.2 Академические модели (основа для механик)

- **Knowledge production function** (Romer 1990; Jones 1995): `dA/dt = δ · L_A^λ · A^φ` — прирост знания зависит от числа исследователей и накопленного знания (φ > 0 — «стоять на плечах», φ < 0 — «рыба выловлена»). [M] → прямо переносится на дисциплины.
- **Recombinant growth** (Weitzman 1998): новые идеи = комбинации существующих; число потенциальных комбинаций растёт сверхэкспоненциально, ограничение — ресурс на их «обработку». [M]
- **W. Brian Arthur, «The Nature of Technology» (2009)** и Arthur & Polak (2006): технология = комбинация компонентов-технологий, использующая природный феномен; модель на логических схемах показала возникновение сложных технологий из простых через комбинацию. [M] → основа для «инженерного знания» как композиций.
- **Fleming (2001), recombinant uncertainty**: комбинации знакомых компонентов надёжнее, новых — с большей дисперсией результата. [M] → стохастичность исхода исследований.
- [A] Диффузия знаний (публикации, эмиграция учёных, шпионаж, лицензии) и «школы» (кластер учёных/институтов с бонусами к направлению) естественно ложатся на модель «знание как запас, распределённый по акторам».

### 5.3 Кандидатные модели данных

**Модель A — Взвешенный граф узлов (PoE/Stellaris-гибрид)**
- Узлы: `discovery`, `applied`, `engineering`, `paradigm` (keystone). Рёбра: `requires` (жёсткое), `boosts` (мягкое, вес 0..1), `excludes` (альтернативы), `enables_application`.
- Прогресс: очки исследования на узел; стоимость снижается от `boosts`.
- + Просто, наглядно, легко моддить, легко валидировать. − Знание дискретно, трудно выразить «общий уровень химии»; большой граф = много ручного контента.

**Модель B — Пространство дисциплин (непрерывные запасы знаний)**
- Нет дискретных техов: N дисциплин (физика, химия, металлургия, аэродинамика…) со значениями знания `K_d` на актора; «технологии» — пороговые условия над вектором K (напр. jet_engine: thermo ≥ 40, metallurgy ≥ 55, aero ≥ 35).
- + Естественная диффузия, школы, функции производства; мало контента для старта. − Слабый «вау-момент» открытия, сложнее объяснить игроку, трудно балансировать пороги.

**Модель C (рекомендуемая) — Гибрид трёх слоёв**
1. **Disciplines** — непрерывные запасы `K_d` (растут от бюджета × персонала × институтов по knowledge production function; диффундируют между странами).
2. **Discoveries / Concepts** — дискретные узлы с мягкими prerequisites: `p(прорыва)/тик = f(K релевантных дисциплин, вес рёбер, финансирование проекта, качество лабораторий)`. Есть `historical_window` (мягкая привязка к году) и тег `tier: historical | prospective | speculative`.
3. **Applications / Industrialization** — отдельные узлы «внедрения»: требуют открытие + инженерное знание + производственные мощности/материалы/энергию; дают технологии для проектов (компоненты).
- Рёбра (типизированные): `requires` (hard, только для явной логики), `informs` (soft weight → вероятность/стоимость), `uses_material`, `uses_energy`, `alternative_to` (группа альтернативных путей), `paradigm_shift` (keystone меняет веса).
- + Отражает все требования проекта (дисциплины, школы, «открытие ≠ внедрение», альтернативы, будущее по уровням достоверности). − Больше механик, нужна хорошая визуализация; балансировка требует инструментов (симуляционные прогоны).

Пример узла (иллюстрация формата, не финальная схема):
```yaml
id: disc.nuclear_fission
type: discovery
tier: historical
historical_window: { earliest: 1934, typical: 1938 }
disciplines: { physics.nuclear: 0.7, chemistry.radio: 0.3 }
informs: [ { from: disc.neutron, weight: 0.8 }, { from: disc.radioactivity, weight: 0.5 } ]
requires: [ disc.neutron ]
unlocks_applications: [ app.nuclear_reactor, app.fission_weapon ]
```

### 5.4 Размер графа и валидация

- [A] Ориентир: M1 — 50–150 узлов (1910–1950, 2–3 ветви); полный контент — 800–2000 узлов + 30–60 дисциплин. Victoria 3 ≈ 175 техов [F], PoE ≈ 1300+ узлов [M].
- Обязательные проверки валидатора (CI, `tools/validate`):
  - схема (типы, обязательные поля, enum `tier`);
  - ссылочная целостность (все id существуют; ссылки на дисциплины/материалы);
  - **циклы только по жёстким рёбрам `requires`** (Tarjan/DFS; мягкие `informs` могут быть циклическими — это нормально);
  - **достижимость** каждого узла из стартового состояния 1910 (BFS по `requires` с учётом порогов);
  - **сироты** (узлы без входящих и исходящих рёбер, приложения без потребителей);
  - анахронизмы: `typical` годы потомков ≥ предков; `speculative` не может быть hard-предком `historical`;
  - дубликаты id между модами (с явной политикой override).
- [R] Инструмент экспорта графа в DOT/GraphML/JSON для просмотра (Graphviz, Gephi, Cytoscape) — дешёвый способ визуального ревью без игровой графики.

## 6. Тема 4 — Форматы данных и моддинг

### 6.1 Форматы

| Формат | Плюсы | Минусы | Схемы/валидация |
|---|---|---|---|
| JSON | Повсеместно, строгий, быстрые парсеры во всех кандидатах (C#, Rust, C++) | Нет комментариев, шумный для ручного авторинга | **JSON Schema 2020-12** — текущая версия [F] |
| YAML | Читаемый, комментарии, якоря | Неоднозначности (Norway problem, implicit types), медленнее, сложная спецификация | JSON Schema применима к YAML-данным |
| TOML (v1.1.0 — актуальная [F]) | Простой, комментарии, хорош для конфигов/манифестов | Неудобен для глубокой вложенности и больших списков объектов | JSON Schema через конвертацию |
| Paradox script (Jomini/Clausewitz) | Компактен, удобен моддерам Paradox, поддерживает операторы/условия | Нестандартный, нужен свой парсер и тулинг, нет схем | Собственные инструменты (CWTools — community) [M] |
| XML (RimWorld) | XPath-патчи, XSD | Многословен | XSD |
| Lua (Factorio data stage) | Максимальная гибкость модов | Код вместо данных: сложнее валидировать, нужен sandbox | Валидация после выполнения |

[R] Канон: **YAML или JSON как формат авторинга + JSON Schema**, компиляция в бинарный/единый JSON-кэш при загрузке. Манифест мода — TOML или JSON. Свой скриптовый язык — нет.

### 6.2 Как устроен моддинг в референсных играх

| Игра | Данные | Load order | Overrides/конфликты | Код-моды |
|---|---|---|---|---|
| Paradox (HoI4/Stellaris/V3) | Plain-text script в папках | Порядок в playset/launcher [M] | Файл с тем же путём заменяет ванильный; `replace_path` в descriptor исключает папку [M]; одноимённый объект в другом файле часто **дублируется**, а не заменяется, зависит от типа объекта — отсюда full-file overrides и конфликты [F]; приёмы FIOS/LIOS через имена файлов [F] | Нет |
| RimWorld | XML Defs | `About.xml`: `modDependencies`, `loadAfter`, `loadBefore` по `packageId` [F]; `LoadFolders.xml` с `IfModActive` [F] | PatchOperation (Add/Replace/Remove…) по XPath к распарсенному дереву [F]; несработавший патч молча ничего не делает [F] | C# + Harmony (патчинг методов) |
| Factorio | Lua data stage: `data.lua` → `data-updates.lua` → `data-final-fixes.lua` (+ аналоги для settings) [F] | Зависимости в `info.json`; зависимый мод грузится после зависимости [F] | Последовательная мутация общей таблицы `data.raw` | `control.lua` runtime, sandbox |
| Factorio dependency syntax | `"? mod >= 1.2"`: без префикса — обязательная, `!` несовместимость, `?` опциональная, `(?)` скрытая опциональная, `+` рекомендуемая, `~` не влияет на порядок; операторы `< <= = >= >`; неявная зависимость от `base` [F] | | | |

Выводы [A]:
- Лучшие практики: **база = мод** (Factorio `base`, RimWorld Core), **явные зависимости вместо ручного порядка**, **гранулярные патчи объектов** вместо замены файлов (урок Paradox), **громкие ошибки** вместо тихих (урок RimWorld), **фазы загрузки** (урок Factorio).

### 6.3 Предлагаемая модель модов (концепция, PROPOSED)

- Мод = папка/архив с `mod.toml`: `id`, `version` (SemVer), `game_version`, `dependencies` (синтаксис по образцу Factorio), `license`, `data_format_version`.
- Базовая игра = мод `core` (+ отдельные data-пакеты, напр. `core.map1910`, лицензия может отличаться — важно для GPL-изоляции).
- Резолвер: топологическая сортировка по зависимостям, стабильный tie-break по id; цикл зависимостей = ошибка.
- Операции над объектами (по id): `define` (новый; конфликт, если уже есть), `override` (полная замена), `patch` (merge/append/remove полей; JSON Merge Patch RFC 7396 или подмножество JSON Patch RFC 6902), `delete`. Пустой результат патча = предупреждение.
- Отчёт о конфликтах: какие моды трогали какой объект (provenance), в каком порядке.
- Сейвы: сохраняют список модов+версий и хеш скомпилированных данных; ссылки только по строковым id; при загрузке — миграции по `data_format_version`; отсутствующие id → «tombstone» + предупреждение, а не краш.
- Unsafe-моды (код): **не в M0/M1**. Позже — Lua (MoonSharp/NLua для C#, mlua для Rust) с ограниченной stdlib, либо WASM (wasmtime/wasmer) с capability-API и детерминизмом. Нативные DLL-моды (Harmony-стиль) — только как явно «unsafe» уровень.

## 7. Тема 5 — Модульное инженерное проектирование

| Игра | Модель | Глубина |
|---|---|---|
| HoI4 (танки/корабли/самолёты) | Шасси + слоты модулей; статы = сумма/модификаторы; стоимость и производственные ресурсы из модулей [M] | Средняя — **ориентир** |
| Terra Invicta | Корпус + двигатель/реактор/радиаторы/броня/оружие; Δv и масса рассчитываются из реальной формулы ракеты [M] | Средняя+, одна «физическая» формула |
| Aurora 4X | Компоненты проектируются из технологий (двигатель = тип × мощность × размер), затем корабль из компонентов [M] | Высокая, микроменеджмент |
| From the Depths | Блочное строительство с физикой | Очень высокая (не наш случай) |

[R] Модель проекта: `design = platform(тип) + slots{engine, structure, materials, electronics, payload…}`; компонент = узел-«application» из графа (с поколением/качеством); статы — агрегирование (сумма, min/max, произведение коэффициентов) + 1–2 ключевых упрощённых соотношения на платформу (напр. thrust/weight → скорость). Проект имеет стадии: concept → prototype → series; стоимость разработки зависит от новизны компонентов (Fleming: новые комбинации — выше дисперсия/риск). Без геометрии и физсима.

## 9. Решения для ранних ADR

1. **ADR: Каноническое представление карты** — векторный источник → компилируемый граф провинций; color-map производна.
2. **ADR: Стабильные строковые идентификаторы** для всех игровых сущностей (провинции, техи, дисциплины, компоненты) — основа модов и сейвов.
3. **ADR: Политика лицензий данных** — допустимые лицензии в `core` (PD, CC0, CC BY 4.0), изоляция copyleft-пакетов (GPL/ODbL/CC BY-SA) в отдельные data-пакеты, запрет NC и «no redistribution»; обязательный `license` + `source` в метаданных каждого датасета.
4. **ADR: Формат данных и схемы** — выбор YAML vs JSON для авторинга, JSON Schema 2020-12 как контракт.
5. **ADR: Модель технологий** — модель C (или иная) и типы рёбер.
6. **ADR: Модель модов v0** — `core` как мод, манифест, зависимости, порядок, операции define/override/patch/delete, без кода.
7. **ADR: Лицензия кода и лицензия контента** репозитория (напр. MIT/Apache-2.0 для кода + CC BY 4.0 для данных) — до первого импорта данных.

## 10. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Попадание NC/no-redistribution данных (GADM, CShapes) в публичный репо | Средняя | Высокое (удаление истории git, юридически) | ADR лицензий, реестр источников, ревью PR с данными |
| Copyleft-«заражение» (GPL historical-basemaps, ODbL OSM) | Средняя | Среднее | Отдельные data-пакеты, или только референс |
| Отрисовка исторических границ вручную — большой объём работы | Высокая | Среднее | Грубая детализация в M0–M1, Voronoi-генерация, постепенное уточнение |
| Граф технологий разрастается без баланса | Высокая | Высокое | Малый вертикальный срез, валидатор, автопрогоны симуляции «1910→1950» с метриками |
| Модель C слишком сложна для игрока | Средняя | Среднее | Выводить в UI агрегаты и «вероятные ближайшие прорывы» |
| Ранний over-engineering моддинга | Средняя | Среднее | v0 = «core как мод + патчи», без Mod API/скриптов |
| Сейвы ломаются при изменении данных | Высокая | Среднее | Строковые id, версия формата, миграции, tombstones |
| Неверные исторические числа (Maddison в современных границах) | Высокая | Низкое–среднее | Пометка `estimated`, документировать пересчёт |

## 11. Открытые вопросы для владельца

1. Допускается ли в будущем коммерческая публикация (Steam)? Это определяет запрет NC-данных и выбор лицензии кода/контента.
2. Какую лицензию дать репозиторию: код (MIT/Apache-2.0/GPL?) и данные (CC0/CC BY 4.0/CC BY-SA)?
3. Приемлемо ли держать отдельный GPL-пакет данных (historical-basemaps) или всё рисуем сами?
4. Желаемая гранулярность провинций в итоге: ~1 000 (HoI4-масштаб страны), ~3 000–10 000 (EU/Victoria), или регионы + города?
5. Насколько стохастичны открытия: допускается ли, что ядерное деление откроют в 1925 или в 1955?
6. Авторинг данных: YAML (удобнее руками) или JSON (строже, проще для AI-генерации и валидации)?
7. Нужен ли игроку прямой выбор узлов (Civ) или только распределение бюджета/персонала по направлениям (Alpha Centauri/Terra Invicta)?
8. Нужен ли мультиплеер когда-либо (влияет на детерминизм и sandbox модов)?
