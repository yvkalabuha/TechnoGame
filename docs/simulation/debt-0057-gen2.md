# DEBT-0057: источник gen2 на пути снимка

Автор: simulation-engineer, 2026-11-19. Код замера: `lab bench --mode alloc` (формат 3) + флаги диагностики `--full-first`, `--gc-trace` (этот коммит, только Lab). Сырые данные: `lab/results/DEBT-0057/` (не коммитится). Точка A (200 акторов, 2000 узлов, cross), seed 1, прогрев 2 мес.

## Краткий вывод

- [Факт: 12 прогонов × 36 мес. + 13 прогонов × 130 мес.] **gen2 воспроизводится.** Это не разовое событие месяца 6, а два механизма:
  1. **Пусковой gen2** — 1–2 сборки в первые 0–11 месяцев первого прогона процесса: мир сессии (~27 МиБ SOH) проходит gen0 → gen1 → gen2 и съедает начальный бюджет gen2. Месяц зависит от порядка прогонов: полный прогон первым (как в формате 2) — месяцы 0 и 2–3, на t1 одинаково в 3 из 3 повторов; прогон тика первым (формат 3) — месяцы 0–1 полного прогона (в прогреве) и 4–11 прогона тика. Поэтому прямой замер a768c30 «не повторил» долг: gen2 ушёл в прогрев.
  2. **Установившийся gen2** — раз в 30–80 месяцев: в окне месяцев 24–129 полного прогона 0–3 сборки, медиана 2 (8 прогонов). У прогона без видов тоже бывает gen2: 1 за 106 месяцев в 5 из 8 прогонов. Значит, «без видов 0» верно только для окна 12–26 месяцев.
- [Факт] **Причина — бюджет gen2 при обычных мелких аллокациях**: `GCStart.Reason` = 0 (AllocSmall); `CondemnReasons0` = 0x28 (gen_alloc_budget → gen2) во всех 5 gen2 с записью `GCPerHeapHistory`; у 4 блокирующих ещё `CondemnReasons1` = 0x80 (gen_max_high_frag_p: gen2 сильно фрагментирован). Сборок AllocLarge нет, вызванных вручную в окне нет, нехватки памяти нет (MemoryPressure 44–55 %). Тип сборки: фоновая (BGC) или блокирующая с уплотнением.
- [Факт] **Чем кормится gen2.** Живой снимок примерно месяц держат `SliceSession.View` и `NodeBlockCache`. Это 9–11 МиБ, и каждая сборка gen1 переводит их из gen0 в gen1. Раз в 2 сборки (≈ 3 месяца) сборка gen1 идёт без уплотнения (`GlobalMechanisms` = 0x14). Тогда регион gen1 (12 МиБ, из них живо ~2 МиБ) целиком переходит в gen2. gen2 растёт на 8,5–9 МиБ мёртвого снимка за раз (55 → 123 МиБ за 33 месяца при живых ~30–37 МиБ). Когда бюджет кончается, идёт gen2.
- [Факт] **Что делает путь снимка в момент сборки.** 615 из 722 сборок внутри шагов и 33 из 42 сборок gen2 приходятся на тик с месячным шагом и свежим снимком: ключ месяца сменился, `NodeBlockCache.Begin` отбросил блоки, `ViewBuilder.Nodes` строит новые. Последний сэмпл аллокации (`GCAllocationTick`) перед сборкой чаще всего `ProcessView[]`: 397 сборок, далее `ActorView` 50 и `DesignView` 39. Перед gen2 — 21 из 33. Блоки узлов — 6,42 из 6,94 МиБ свежего снимка (93 %): 651 процесс × 200 акторов × `ProcessView` (40 Б).
- [Факт: 4 из 4 прогонов по 130 мес., t1 и t8] `DOTNET_GCgen0size=0x4000000` (64 МиБ): gen2 только в месяцах 3 и 19–20 (пуск). В месяцах 21–129 полного прогона и во всех 130 месяцах прогона тика — 0. Доля пауз 0,10–0,29 % против 0,35–0,76 %. Сегментный GC (`libclrgc.so`) не помогает: 3 gen2.
- **Итог по строке долга:** воспроизводится; источник — путь снимка (основной поток в gen2) плюс пусковой gen2 после постройки мира. Путь тика сам по себе тоже даёт редкий gen2. Значит, «0 gen2 за 120 месяцев» (ADR-0023 п. 2.4) при окне EXP-0008 (24 + 120 мес.) на текущем коде вероятно нарушается [Предп.: по 8 прогонам × 106 мес.].

## Предложения для developer (код Session/Core не менялся)

1. [Предл., дёшево, смягчает] **Конфигурация GC в хосте замера и клиенте:** `System.GC.Gen0Size` / `DOTNET_GCgen0size` = 64 МиБ. Снимок живёт меньше интервала сборок gen0 (~7 месяцев), до gen2 почти ничего не доходит. Остаётся пусковой gen2 (месяцы 3 и 19–20). При прогреве EXP-0008 в 24 месяца он попадает в прогрев. [Предп.] Это знание платформы, а не исправление: клиент на Godot может не дать настроить GC. Нужен прогон EXP-0008-подобного окна (24 + 120) ≥ 3 раз.
2. [Предл., исправление источника, gate: меняется контракт видов] **Переиспользовать память блоков узлов.** Хранить в `NodeBlockCache` два набора `NodeBlock` (`ProcessView[]`, `Known`, `ByLicence`, `KnownSince`) и писать новый снимок в набор, который не держит текущий опубликованный вид. Тогда 93 % снимка больше не мусор среднего возраста: массивы постоянно лежат в gen2, мусора нет. Условие: потребитель не держит вид старше предыдущего опубликованного. Это изменение контракта `SliceView` («вид — копия»), нужно решение systems-architect (ADR). Проверка устаревшего доступа — номер поколения в `NodeList` с исключением; детерминизм не затронут (виды — чистое чтение).
3. [Предл.] **Пусковой gen2:** в хосте после `SliceSession.Create` делать `GC.Collect(2, Forced, blocking, compacting)` до первого месяца, вне окна. Мир сразу ложится в gen2, не расходуя бюджет. Проверить тем же замером.
4. [Предл., решение владельца] **Критерий ADR-0023 п. 2.4.** Путь тика без видов тоже даёт ~1 gen2 за 106 месяцев (5 из 8 прогонов). Строгий «0 gen2 за 120 месяцев» на месячном снимке недостижим без п. 2 или п. 1. Варианты: считать только блокирующие gen2; или считать gen2 с подтверждённой фрагментацией; или оставить 0, приняв п. 1 + п. 3 как условие замера.

## Как воспроизвести

```
L=src/Singularity.Lab/bin/Release/net10.0/Singularity.Lab.dll
dotnet $L bench --mode alloc --threads 1 --months 36 --warmup 2 --full-first true --gc-trace true --out lab/results/DEBT-0057/x.json
```
Рядом пишутся `x.json.gc.jsonl` (все события GC: GCStart, GCHeapStats, GCGlobalHeapHistory, GCPerHeapHistory, GCAllocationTick с типом) и `x.json.steps.jsonl` (окно каждого `Step(1)` и вид снимка: none, plain, stepped).
