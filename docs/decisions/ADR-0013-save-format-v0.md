# ADR-0013 — Формат сохранения v0: бинарный снимок колонок SoA + заголовок

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

## Контекст
- [Факт] ADR для сохранений нет. ADR-0005 требует стабильных строковых ID в сохранениях, ADR-0010 — запись модов и их версий.
- [Факт] Всё состояние мира лежит в `Table` (SoA); `StateHash(Table, SchemaVersion, tick)` уже есть (`LabModel.cs`). `CounterRng` — чистая функция `(seed, tick, system, entity, n)` без состояния (ADR-0004, `CounterRng.cs`).
- [Факт] Решение #58: тестовой инфраструктуре сейчас нужны только ADR, реализация позже. Сохранение нужно и игре, и тестовым фикстурам (`TESTING_ARCHITECTURE_PROPOSAL.md` §7).
- [Факт] Ревью critic (gate) указал на скрытые зависимости от порядка строк, состояния систем, очередей команд и событий.

## Решение (предложение)
1. **Формат.** Бинарный little-endian файл: заголовок + по каждой таблице `name, schema_version, row_count`, затем колонки `name, type, length, bytes`. Рядом — `summary.json` (читаемая сводка ожидаемых значений для фикстур; не источник состояния).
2. **Заголовок:** `save_format_version`, `game_version`, `test_api_version` (только фикстуры), список модов с версиями и хешем данных (ADR-0010), `scenario_id`, `seed`, `tick`, календарная дата, `schema_version` таблиц, `state_hash`, `created`, `description`, `suite`.
3. **Инвариант порядка.** Порядок строк и индексы сущностей сохраняются и восстанавливаются **байт в байт**: загрузка не сортирует, не уплотняет и не переиндексирует таблицы. Причина: ключ RNG использует индекс сущности (ADR-0004), а merge идёт в порядке строк.
4. **Нет состояния вне таблиц.** Системы не держат изменяемого состояния в полях экземпляров или статических полях; всё, что влияет на следующий тик, — в `Table`. RNG восстанавливается из `seed + tick`.
5. **Очереди.** Очередь ожидающих команд (ADR-0006, ADR-0014) и та часть `EventBuffer`, что влияет на геймплей, входят в снимок как таблицы. [Предл.] До реализации их сериализации сохранение при непустой очереди или буфере запрещено (громкая ошибка `SaveNotQuiescent`). Наблюдательные события в снимок не входят.
6. **Слои.** Сериализация колонок без домена — `TableSnapshot` в Kernel. Домен, сопоставление ID и миграции — в Core.
7. **Версии и миграции.** `save_format_version` растёт при любом изменении раскладки. Миграция — цепочка чистых функций vN→vN+1 над колонками по стабильным строковым ID (ADR-0005). Неизвестная или более новая версия — громкая ошибка. Исходная фикстура не меняется: мигрирует копия в `artifacts/`.
8. **Хеш.** После загрузки `StateHash` пересчитывается и сравнивается с `state_hash` заголовка; расхождение — ошибка загрузки.
9. **Replay — артефакт, а не сохранение.** `scenario_hash + seed + журнал команд с назначенными тиками` (ADR-0014) пишется в `artifacts/runs/<run_id>/commands.log` для воспроизведения дефектов.
10. **Межплатформенность.** Файл переносим между ОС, но равенство продолжения на разных ОС не заявляется (L3 отложен, ADR-0002). Проверки CI — относительные, на одной машине. Абсолютный golden-хеш фикстур проверяется только на одной ОС (Linux).

## Рассмотренные альтернативы
- **Текстовый снимок (YAML/JSON, Fx6 как целые).** Читаемые diff, но большие файлы, медленно и второй путь сериализации. Отклонено; читаемость даёт `summary.json`.
- **Только replay.** Крошечный, но загрузка = пересчёт, ломается при любой смене кода, не годится как сохранение игрока. Оставлен как артефакт прогона.
- **Сохранять состояние систем через отдельный интерфейс `ISaveable`.** Позволяет держать состояние в полях, но плодит второй путь состояния, мимо `StateHash`. Отклонено: запрет + архитектурный тест проще.
- **Уплотнять таблицы при сохранении.** Меньше файл, но меняет индексы → меняет RNG и порядок merge. Отклонено (п. 3).

## Последствия
- Плюсы: один формат для игры и тестов; точность до бита; быстрая загрузка; хеш проверяет целостность.
- Минусы: бинарные diff нечитаемы; каждое изменение схемы требует миграции и повышения версии.
- Обязательно: всё изменяемое состояние — в таблицах; новые очереди или буферы с влиянием на геймплей — таблицы в снимке.
- Предусловия: ADR-0004 (RNG без состояния) и ADR-0006 (команды в начале тика) — ADR-0006 пока PROPOSED, его принятие нужно до реализации.

## Проверка
- Главный тест (L1, L2 при 1 и N потоках): прогон до тика K → save → load → продолжение до тика N даёт тот же `StateHash`, что прогон без перерыва, **на той же машине**.
- Байтовый тест: save → load → save даёт идентичный файл; порядок строк и индексы совпадают.
- Архитектурный тест (IL-сканер): у типов систем Core нет изменяемых полей экземпляра и статических полей, кроме `readonly` конфигурации.
- Отрицательные фикстуры: усечённый файл, неверный хеш, неизвестная версия, отсутствующая колонка, непустая очередь при сохранении → громкая ошибка.
- Тест миграции: фикстура vN → vN+1 → хеш совпадает с эталоном мигрированной копии.
- CI: относительные проверки на всех ОС; абсолютный golden-хеш — только на Linux.
