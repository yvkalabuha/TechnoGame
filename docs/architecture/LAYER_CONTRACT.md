## 4. Динамика (формулы контракта)
### 4.0 Арифметика и фазы тика (v2.3; v2.4 — новые строки)
**Арифметика `Fx6` (A1).** Бит-точность между Core и эталоном требует одного порядка операций. Правила:
1. Все величины формул §4 — `Fx6`. Числовые константы (`0.25`, `1`) — литералы `Fx6`. Целые счётчики (`opened_d`) переводятся в `Fx6` точно. `double` нет (ADR-0003 R1).
2. Каждое `·` и `/` — **одна** операция `Fx6` с floor к −∞ (`Fx6.operator *`, `/`, `FloorDiv` по `Int128`). `+`, `−`, `min`, `max`, сравнения точны. Переполнение — исключение (`checked`), а не насыщение. (v2.4, G4-3, G4-4) Исключения — именованные помощники Kernel с **одним** округлением, они считаются одной операцией:
   - `SmoothStep01(x)` = `floor(X²·(3S − 2X) / S²)` raw, где `X` = `x.Raw`, `S` = 10⁶, всё в `Int128`; вход `0 ≤ x ≤ 1`, иначе исключение. [Предл.] Место — `Singularity.Kernel.DetMath` (общая математика, не доменная логика);
   - `MulCeil(a, b)` = `ceil(a.Raw·b.Raw / S)` raw в `Int128` (потолок к +∞), для `a, b ≥ 0`. [Факт: в `Fx6.cs` сейчас только floor-операции, `FloorDiv` закрытый] — помощник добавляется в `Fx6` или `DetMath`.
3. Порядок — **слева направо, как записано**, скобки обязательны к исполнению. `a·b/c` = `(a·b)/c`; `a·b·c` = `(a·b)·c`. Деление внутри дроби не раскрывается: `s_p = v_p/V_c` считается отдельно, затем умножается (не `Σ v_p·x / V_c`).
4. Суммы `Σ` идут по возрастанию id (процесса, кластера). Сложение точное, порядок фиксирован для воспроизводимости при переполнении и для журналов. v2.4: `max_p`, `argmax` — ничья по меньшему `prc_id` (= `ProcessNumber`, §1); `alt_id` в ничьих — ordinal (побайтно, COMPONENT_SELECTION G-8).
5. Произведение по измерениям `Π_d` — в каноническом порядке измерений (в срезе: `precision`, `purity`, `quality_control`), начиная с `1`; множитель `ramp` — последним.
6. Забывание записывается как `x − δ·x` (вычитается floor декремента), а не `x·(1 − δ)`. Математически это та же форма §3, в `Fx6` запас округляется вверх. Когда `δ·x` < 1 raw, забывание останавливается — допустимо.
7. Формулы спецификации среза (`ramp`, hazard, `c_eff`, бюджет) подчиняются тем же правилам. Порядок в них задаёт спецификация (владелец — simulation-engineer). Пример: `h = (h_max·y)/(y + y_half)`.
8. Формулы §4.1–4.4 ниже записаны в канонической форме: при реализации их нельзя переупорядочивать и «упрощать».
9. (v2.4) Деление с возможным нулём в знаменателе записывается веткой `(den = 0) ? 0 : …` до деления. Циклы с перераспределением (налив §4.1b) ограничены числом кандидатов.

### 4.1 Культура `culture_H` (v2.4 черновик: временное правило C-B, #99, #111, #115; RISK-0016)
Каноническая форма (§4.0). Ячейка `(site, c, d)`. `H`, `M`, `Hcap`, `H_floor`, `act`, `w` — из снимка. Для процесса p: `v_p = proc_v[site,p]`, `E_p = proc_E[site,p]` месяца t−1, `lic_p = licensed(site, p)` ∈ {0, 1} (§3.1). Источник формул — `culture-round2.md` r3 §1.1, §1.1.2.
**Процессы ячейки** `P(c,d)` = процессы кластера c с **активным** измерением d (`r_d(p) > 0`) и с `v_p > 0` или `E_p > 0`. Перебор — по возрастанию `prc_id`.
**#117 (G4-1): одно `E_p` действует во всех активных измерениях p.** Деньги процесс получает за одну ячейку (ту, которую ведёт, §4.1a), но `t_p` считается в каждой ячейке `(site, c(p), d)` с `r_d(p) > 0` с тем же `E_p` — это формула стенда. Поэтому в ячейке, где p не ведущий или ведущего нет, рост от денег p тоже возможен.
```
# параметры процесса (единицы — culture-rule-selection.md §7.5)
v_cap(p)  = r_cap  · labour_p          # r_cap  = r_ref / 2,5 = 10 шт. процесса в месяц
v_keep(p) = r_keep · labour_p          # r_keep = r_ref / 4   = 6,25 шт. процесса в месяц
# канал лицензии (#104 — рост, #107 — поддержание)
ṽ_p    = (1 + k_tr · lic_p) · v_p      # k_tr = 1; lic_p ∈ {0,1}, произведение точное
# потолок пользы денег от выпуска (M1), форма SMOOTH
x_V    = (v_cap = 0) ? 0 : min(1, ṽ_p / v_cap)
c_p    = SmoothStep01(x_V)             # одно округление: floor(X²·(3S − 2X)/S²), §4.0 п. 2 (G4-3)
x_E    = (E_full = 0) ? 0 : min(1, E_p / E_full)
e_V    = min(x_E, c_p)                 # = min(E, E_useful)/E_full
e_L    = (ℓ = 0) ? 0 : min(x_E, ℓ)      # лабораторная часть; ℓ = 0,1 (#115); ветка ℓ = 0 — для абляции
gap_p  = max(0, r_d + 0.25 − H)
gapL_p = max(0, (r_d − ΔL) − H)
t_p    = max(e_V · gap_p, e_L · gapL_p)
# поддержание — только от выпуска (G-5: пол встроен)
a_r     = min(1, act[c] / act_norm)
m_p     = (v_keep = 0) ? 0 : min(1, ṽ_p / v_keep)
maint_p = H_floor + (max(r_d · a_r, H_floor) − H_floor) · m_p
# агрегация по ячейке: максимум, а не доля объёма (#115)
drive  = max_{p ∈ P(c,d)} t_p                       # пусто → 0; t_p ≠ 0 у любого p с E_p > 0, не только у lead (#117)
catch  = max_{p ∈ P(c,d), world_lead(p, owner)} t_p  # пусто → 0
maint  = max(H_floor, max_{p ∈ P(c,d)} maint_p)      # пусто → H_floor
spill    = Σ_c' R[c,c'] · max(0, H[c',d] − H[c,d])   # без изменений v2.3
H_floor  = φ_floor · Hcap[site,d]
sat      = max(0, 1 − H / Hcap[site,d])
α_eff[d] = α · (1 + k_qp)  или  α
ΔH⁺      = sat · ( ((α_eff[d] · act[c]) · w[c]) · drive + k_catch · catch + σ · spill )
ΔH⁻      = δ_H · max(0, H − max(maint, H_floor))
H'       = H + min(ΔH⁺, ρ_max) − ΔH⁻
```
| Параметр | Значение | Статус |
|---|---|---|
| форма `c` | SMOOTH | #111 |
| `r_cap`, `r_keep` | 10 и 6,25 шт. процесса в месяц; записываются как `r_ref/2,5` и `r_ref/4` и меняются вместе с `r_ref` | #111; связь с `r_ref` — [Предл.] по образцу G-6 |
| `k_tr` | 1 | #104, #107; [Предп.] «З» |
| `E_full` | **raw-литерал манифеста** `E_full_raw` = 1838 (`Fx6` 0,001838 индекса бюджета в месяц). Происхождение: `(0,4 · 0,25 · budget_index_GBR(1945)) / 13`; во время прогона не пересчитывается (G4-4) | R2-7; [Предп.] «З» |

- **Единица `r_cap`, `r_keep`** — «шт. процесса в месяц», то есть число исполнений p, а не изделий: `proc_v = Σ_линий r_line·n_p·labour_p` (`culture-rule-selection.md` §7.5). При `labour_p = 0` `v_cap = v_keep = 0`, ветки дают `x_V = m_p = 0`; валидатор данных такой PRC не пропускает.
- **Свойства, которые проверяет CI (`culture-round2.md` §1.5, I1–I10).** `ΔH⁺` не убывает по `E_p` и по `v_p`. При `E ≡ 0` `ΔH⁺ = sat·σ·spill`, а `maint` тот же, что при `E > 0` (деньги не держат культуру). При `v_p = 0` у всех p ячейки рост от усилия не больше `ℓ·gapL_p` и равен 0 при `H ≥ r_d − ΔL` (при абляции `ℓ = 0` — всегда 0). Рост от усилия в ячейке есть, только если у какого-то `p ∈ P(c,d)` `E_p > 0`; есть ли у ячейки `lead`, на это не влияет (#117, G4-1). `lic` 0 → 1 не уменьшает ни рост, ни `maint`. Деление по site не создаёт усилия (P4). Новое (G4-1): при `E_p > 0` и `gap_p(d) > 0` в любом активном d процесса p `t_p(d) > 0`, если `c_p > 0` или `ℓ·gapL_p(d) > 0` (до floor: при значениях в единицы raw произведение может дать 0) — деньги p не «пропадают» в его неведомых ячейках. Утверждение v2.4 r0 «нет `lead` → рост 0» снято.

  - Прямой канал лицензии в культуру — новый (#104, #107). Канал `X½·(1 − l_lic)` остаётся.

### 4.1a Функции правила культуры (интерфейс, v2.4 черновик)
Все функции чистые, читают только снимок t−1. Источник — `culture-round2.md` §1.2, `PROCESS_DEVELOPMENT.md` v0.2 §2.3. Ячейка процесса — `cell(p) = (site, c(p), d*(p))`. Внешние (§5): `E_useful`, `limiter`, `dH_forecast`. Внутренние (только модуль правила и §4.1b): `t̂_p`, `limiter₀`, `lead`, `d*`.
- `t̂_p` — `t_p` при полном усилии: `t̂_p = max(c_p·gap_p, ℓ·gapL_p)`; при `v_p = 0` `c_p = 0`.
- **`eligible(site, p)` (G4-2, critic H1)** — p может вести ячейку: `p ∈ known_processes(owner)` и (`v_p > 0` или `planned(site, p)`). `planned(site, p)` = p входит в `prc_set` хотя бы одного своего проекта актора в стадии П или О (чистая функция снимка изделия, §5). Причина: без этого условия известный, но никем не выпускаемый и не планируемый процесс с бо́льшим `r_d` получает `t̂_p = ℓ·gapL_p` и может перехватить ячейку у процесса с малым выпуском; деньги тогда идут в «стенд без серии».
- `limiter₀(site, p, d)` — собственный предел p в ячейке `(site, c(p), d)` при `E_p = 0`: шаги 1–4 списка `limiter` ниже с d вместо `d*`; если ни один не сработал и `t̂_p(d) > 0` — `EFFORT`, иначе `VOLUME`. Не читает `lead`, `d*`, `E` — поэтому цикла «`lead` ↔ `limiter₀`» нет. (Шаги 5–6 при `E = 0` сводятся к этому: при `t̂_p > 0` `E_useful > 0 = E_p`.)
- `lead(site, c, d)` → `prc_id` или «нет» (#115, G4-2). Кандидаты — процессы кластера c с активным d, `eligible(site, p)` и `limiter₀(site, p, d) = EFFORT`. Из них — с наибольшим `t̂_p`; ничья — меньший `prc_id`; кандидатов нет → нет `lead`: за эту ячейку деньги никому не выделяются (у процессов с `cell(p)` = эта ячейка `E_useful = 0`). Рост от денег других процессов, которые ведут другие ячейки, в ней всё равно возможен (#117). От `E` не зависит. Причина правки [Факт: стенд, `culture-round2.md` §10.2 п. 6(i), §10.5]: в v2.4 r0 ячейку вёл сосед с пределом `SATURATION`, ИИ ему денег не давал, и цель как ведомая не осваивалась никогда (FRA×40, SUN×40).
- `d*(p)` — измерение с наибольшим `r_d − H` среди ячеек, которые ведёт p. Если p не ведёт ни одной — среди всех активных измерений p. Ничья — канонический порядок.
- `limiter(site, p)` → `(value, subject_prc)` — первое совпадение, порядок фиксирован. `subject_prc` — процесс, чей предел показан (нужен `why_not` вместо внутреннего `lead`). Если p не ведёт ни одной ячейки и у `cell(p)` есть `lead`, результат — `limiter` процесса `lead(cell(p))` с `subject_prc = lead`. Если `lead(cell(p))` нет — `(limiter₀(site, p, d*), p)` [Предл.]: по построению это не `EFFORT` или p не `eligible`; во втором случае значение — `LAB_CEILING` при `v_p = 0` [Предл.]. Иначе `subject_prc = p`. Значения:
  1. `NONE` — `gap_p(d*) = 0`;
  2. `TOOLING` — `M[s,c,d*] < H[s,c,d*]` (A5);
  3. `SATURATION` — `Hcap[s,d*] ≤ r_d*`;
  4. `LAB_CEILING` — `v_p = 0` и (`ℓ = 0` или `H ≥ r_d* − ΔL`);
  5. `VOLUME` — `v_p > 0`, `E_p ≥ E_useful` и `k* < 1`;
  6. `EFFORT` — во всех остальных случаях.
- `limiter₀(site, p)` = `limiter₀(site, p, d*(p))`. От `E` не зависит, поэтому выбор ИИ не мерцает. Если p — `lead` ячейки `cell(p)`, то `limiter₀(site, p) = EFFORT` (инвариант).
- `E_useful(site, p)` = 0, если `lead(cell(p))` нет, или `lead(cell(p)) ≠ p`, или `limiter₀ ≠ EFFORT`. Иначе `E_useful = MulCeil(k*, E_full)` (G4-4, critic M7), где `k* = ℓ`, если `ℓ·gapL_p > c_p·gap_p`, иначе `k* = c_p`; все величины — в ячейке `cell(p)`. Это точка излома `t_p` по `E`. Почему потолок: при `E_p = E_useful` должно быть `x_E ≥ k*`, иначе `e_V` не доходит до `c_p` на 1 raw и предел `VOLUME` не наступает никогда. С потолком `E_useful·S ≥ k*·E_full`, поэтому `floor(E_useful·S / E_full) ≥ k*`; и `E_useful ≤ E_full`, так как `k* ≤ 1`. Тест: для случайных `k*` ∈ [0; 1] и `E_full_raw` при `E_p = E_useful` `e_V = min(x_E, c_p) = c_p` (или `e_L = ℓ`).
- Излом `E_useful` считается только по `cell(p)`. В других активных d процесса (#117) излом может лежать в другой точке; там деньги сверх `E_useful` не выделяются [Предл.: простота — деньги выделяются за одну ячейку].
- `dH_forecast(site, p, d, E, v)` = `min(ΔH⁺, ρ_max)` ячейки `(site, c(p), d)` по §4.1, `d` — активное измерение p (по умолчанию `d*`). Вместо `E_p` подставлено `E`, вместо `v_p` — `v` (в `ṽ_p`, `x_V`, `m_p`). Остальное — из снимка. Функция не убывает по `E` и по `v`. При `E = E_p`, `v = v_p` она побитно равна фактическому приросту ячейки. `E` действует через `t_p` процесса p **независимо** от того, ведёт ли p эту ячейку (#117, G4-1; утверждение r0 «при `lead ≠ p` вклад 0» снято). `why_not` передаёт `d` узкого места. Нужна только UI и `why_not`, в тик не входит.
- **Деление `E` актора по site** (PD §1.2; G4-6, П-14):
  1. `share_s = (E_{a,p} · v_{s,p}) / Σ_s v_{s,p}`, floor. Остаток floor получает site с наибольшим `v`, при ничьей — меньший `site_id`. Если `Σ v = 0`, всё получает меньший `site_id`;
  2. `E_{s,p} = min(share_s, E_useful(s,p))`; излишек `Σ_s (share_s − E_{s,p})` идёт в остаток наладки актора `rest_a` (в оснастку), между site не перераспределяется.
  Инвариант: `Σ_s E_{s,p} + излишек_p = E_{a,p}` точно; `E_{s,p} ≤ E_useful(s,p)`. В срезе один site, `E_{s,p} = E_{a,p}` (налив §4.1b уже ограничен `E_useful`).

### 4.2 Выход и цена (C1)
Каноническая форма (§4.0); все величины из снимка.
```
c_d     = min(culture_H[site,c,d], tooling_M[site,c,d])           # c = cluster(p)
g(gap)  = 0 (gap < −1);  (1 + gap)·(1 + gap) (−1 ≤ gap < 0);  1 (gap ≥ 0)
yield_p = ((1 · g_d1) · g_d2 · …) · ramp(proc_X)       # только d с r_d > 0, канонический порядок измерений, ramp последним
yc_p    = max(yield_p, ε)                              # общий ε контракта для всех делений на yield
q_p     = g(c_qc − r_qc(p)), если r_qc(p) > 0; иначе 1    # qc = quality_control (A4)
production_profile(site, prc_set) =
  admitted        = ∀p: yield_p > 0 ∧ p ∈ known_processes(owner)
  unit_cost_mult  = (Σ_p (n_p · base_cost_p) / yc_p)  /  (Σ_p (n_p · base_cost_p))
  q               = min_p q_p
  bottleneck      = argmin_p yield_p → (dim, H|M); ничьи по prc_id
```

По #26 «фактически невозможно» = `g = 0`.
- **A4, `q`.** [Предл.] `q_p` — множитель измерения `quality_control` из того же `yield_p` (новых параметров нет): доля годных по контролю качества. Брак `q` и `defects_hidden` по-прежнему разные причины (§3 п. 4). `quality_control` действует и на цену (через `yield`), и на готовность (через `q`) — это два разных выхода, а не двойной счёт по цене; Lab проверяет вклад абляцией `k_qp = 0`. Если в `prc_set` нет процесса с `r_qc > 0`, `q = 1`.
- **A5, A6, `bottleneck`.** Узкий процесс — минимальный `yield_p`, ничья по `prc_id`. В нём узкое измерение — минимальный `g_d`, ничья по каноническому порядку измерений; источник `H`, если `culture_H ≤ tooling_M` (при равенстве — `H`), иначе `M`. Если родитель уже в В, его `line_E = 0` (закрытие линии, §3), и производная начинает с 0. `τ_der` = 1 [Предп.: планер тот же] — частный случай «наследовать полностью» COMPONENT_SELECTION §7. Копия без закрытия родителя дала бы двойной счёт канала сборки (§8.2), поэтому отклонена. Две одновременные линии одной платформы — FUTURE.

#### 4.4c Досрочный запуск серии (#94, #97)
- **Команда** `start_series(design_id, rate, force)`. Валидатор: стадия О (работа `W` выполнена). Если `gate_open = false`: при `force = false` — отказ со звеном `why_not` `SERIES_GATE` (§6); при `force = true` — принято, `series_forced = true`. Решение необратимо. **ИИ никогда не подаёт `force = true`** (инвариант журнала решений ИИ).
- **Уровень допуска `d_gate` (G4-7, critic M4)** — в два шага:
  1. при входе в стадию О — предварительный: `d_gate = min(k_gate · D_ref, D0 − detected(t_test_min · test_rate))` (ожидаемый `D_hidden` после минимальных испытаний); `stage_o_month = t`;
  2. в первый месяц, когда `gate_open` (по снимку) истинно, — окончательный: `d_gate := D_hidden` снимка, `gate_opened = true`. Он не больше предварительного: к этому месяцу испытаний ≥ `t_test_min`, а выявление монотонно по часам.
- **Избыток** `X(t) = max(0, D_hidden(t) − d_gate)`. Скрытые дефекты только убывают. Без форсажа серия начинается только после открытия допуска, а с этого месяца `X = 0`. **Инвариант (test-engineer): `series_forced = false` ⇒ `X ≡ 0` во всех месяцах стадий С и В**, и вся плата ниже равна 0. Формулы общие, отдельного флага в них нет, main не меняется. Форсаж до `t_test_min` без избытка дефектов тоже не бесплатен: предварительный `d_gate` учитывает дефекты, которые нашли бы минимальные испытания.
- **Аварии** (compute Products, свои колонки, G4-7): `loss_acc += (((units_in_service · fleet_hours) · a_acc) · X(t−1)) / D_ref`, где `units_in_service` и `X(t−1)` — из снимка, `fleet_hours` — **часы налёта на одну машину в месяц** (параметр класса; в TASK-0018 `FleetHoursPerUnit`). `n = min(⌊loss_acc⌋, ⌊units_in_service⌋)`; `loss_acc −= n`. Списание — прямо в когортах проекта, без сообщения `write_off`: n раз снимается `min(1, count)` с когорты с наибольшим `count` (ничья — более ранний год выпуска). `count ≥ 0`, строки когорт не удаляются (ADR-0013 п. 3). `a_acc` = 10⁻³ 1/ч — [Предп.] «З». Инвариант: `Σ` списанного за месяц ≤ `units_in_service` снимка.
- **Доработка построенных** (#97): `retro_pool = X` в месяц запуска. Каждый дефект, исправленный бригадой (A32), пока `retro_pool > 0`, расходует единицу пула и стоит `c_u = c_retro · units_in_service`, где `c_retro = (unit_cost_floor · ρ_retro) / D_ref`. Платится из бюджета закупок после содержания и до закупок (§4.4d). Если денег не хватает, исправляется оплаченное число, остальные дефекты остаются открытыми и бьют по `readiness`. `ρ_retro` = 0,5 — [Предп.] «З».
- **Готовность** — §4.4b без новой формулы: у досрочного парка `D ≈ D0`.
- Проверка — плечо `FORCE` с критерием S-F, зафиксированным до прогона: досрочный запуск выгоден (`ΔFV > 0`) в 20–80% случаев (#97). `a_acc`, `ρ_retro` по результату не подбираются.
- `force_forecast(design_id, rate)` — чистая функция снимка: прогонка A31, A32 и §4.4c вперёд на ≤ 60 мес., только для UI.

## 6. `why_not(actor, target)` (F6)
`target` ∈ {`app_id`, `design_id`, `requirement_id`}. Это чистая функция снимка. Возвращает **полный отсортированный** `List<Link>`: UI показывает первые 3, Lab использует весь список.
`Link { layer, cause, subject_id, have, need, lever, yield_if_fixed, eta_months }`
- `layer` ∈ `KNOWLEDGE` < `CAPABILITY` < `PRODUCT` < `ECONOMY`.
- `yield_if_fixed` — `yield` узкого процесса изделия, если закрыть только это звено (`have := need`), а остальное не трогать.
- `eta_months` — когда `have` дойдёт до `need` при **текущих** скоростях из снимка: `ceil((need − have)/rate)`. Если `rate ≤ 0`, значение `null` («само не дойдёт»). Функция детерминирована.
- Сортировка: `layer`, затем `yield_if_fixed` по убыванию, `eta_months` по возрастанию (`null` в конце), `subject_id`.

Причины по слоям:
1. **KNOWLEDGE:** нет узлов на пути к APP. Звено — ближайший недостающий узел по цене. v2.4: недоступная альтернатива слота (`avail = false`) — то же звено.
2. **CAPABILITY:** `admitted = false` или `yield < 0.7` у узкого процесса. Звено — `(prc, dim, H|M, have, need)`. v2.4: при источнике `H` звено несёт `limiter(site, prc)`; `subject_id` = его `subject_prc` (ведущий процесс, если prc не ведёт ячейку; сам prc, если ведущего нет, §4.1a). `rate` для `eta` — `dH_forecast(site, prc, dim, E, v)` при текущих `E` и `v` и `dim` узкого места.
3. **PRODUCT:** нет проекта, `granted/n < 0.9`, открыты `defects_hidden`, дефицит CMP. v2.4: `SERIES_GATE` — «серия не допущена: скрыто N при допуске M»; `have = D_hidden`, `need = k_gate·D_ref`, `eta_months` — месяцы до допуска при текущем `test_rate`, `yield_if_fixed` — текущий `yield` узкого процесса.
4. **ECONOMY:** «допущено, но не по карману»: `admitted`, но `unit_cost·n_plan + upkeep` больше бюджета программы.

**v2.4: звено культуры по `limiter` (новые причины CAPABILITY, источник `H`)** [Предл.; PD §10.4, #93, #112]:

## 8. Абляции и проверка двойного счёта (C3)
1. **Тест разреженности (CI).** Сдвигаем один запас на Δ, проводим один месячный compute и сверяем изменившиеся выходы с §3. Если меняется чужой выход, тест падает.
2. **Бюджет падения цены на удвоение (Lab, срез).** На эталонной линии `Δlog unit_cost` за удвоение накопленного выпуска раскладывается на два канала:
   - **канал выхода:** `proc_X`/`ramp` + `culture_H`/`g` → `1/yc`;
   - **канал сборки:** `line_E` → `assembly_hours`.

   Вклад канала = симметричная оценка `½[(полная − без канала) + (только канал − ни одного)]` в `log`.
   | Фаза | Суммарное падение на удвоение | Доля канала выхода | Доля канала сборки |
   |---|---|---|---|
   | освоение (первые 3 удвоения) | ≤ 40% | 50–80% | 20–50% |
   | зрелая линия (`yield ≥ 0.9`) | 15–30% (Wright 70–85%) | ≤ 20% | ≥ 80% |

### 9.1 Метрики лидерства
Определения (все величины — из снимка месяца t, post-фаза):
- `mastered(a, p, t)` — процесс p **освоен** актором a: на каком-то site актора `yield_p ≥ 0.7` (§4.2) и `v_p ≥ v_min` (§4.1) в каждом из месяцев t−5…t (без «показательных» единиц).
- `fielded(a, t)` — проекты d, которые у актора **на вооружении и освоены**: в строю ≥ `n_service_min` единиц когорт d, выпущенных на site актора, и `mastered(a, p, t)` для всех `p ∈ prc_set(d)`. `n_service_min` — параметр данных. Отсюда #62/#70: двигатель должен быть освоен самой страной.
- (v2.4, #70) `gen(d) = min(g_p(d), rank(engine(d)) + 1)` (§4.4a). Двигатель, отстающий от платформы на одно поколение, `gen` не снижает; на два и больше — снижает. Двигатель новее платформы `gen` не повышает. (v2.3: «поколение APP-узла класса изделия» — Приложение А.)

- [Предл.] `tech_lead(t)` среди великих держав (#44, без объёма и цены). Ключ актора `K(a, t)` сравнивается лексикографически:
  1. `G` = max `gen(d)` по `d ∈ fielded(a, t)`; 0, если пусто;
  2. `T` = max `complexity_tier(p)` по p с `mastered(a, p, t)`; затем `N` = число таких p с tier = `T`;
  3. `P` = max `perf(d)` по `d ∈ fielded(a, t)` (только `perf`, линейно, сравнение в `Fx6`; 0, если пусто).

  Итого `K = (G, T, N, P)`. `unit_cost`, `line_E`, объём выпуска и `perf/unit_cost` в ключ не входят ни на каком уровне.
- [Предл.] **Ничьи.** `best(t)` = акторы с максимальным `K`. Если `best(t)` = {a} — кандидат a. Иначе (ничья по всем полям) кандидата нет и `tech_lead(t) = tech_lead(t−1)`. Действующий лидер, который входит в `best(t)`, остаётся лидером. `actor_id` и «кто раньше» ничьи не разрешают: исход не зависит от нумерации акторов. `tech_lead(t0)` задаёт сценарий (#23).

- Если в сборке несколько классов изделий, `G` и `P` считаются по классу, заданному метрикой (в срезе он один). Агрегация по классам — §13.

## Приложение А. Текст v2.3, который v2.4 заменяет (действует до утверждения v2.4)
**§4.1 v2.3 (правка RR-0006 §4.5; F2, F3, #30).** Каноническая форма (§4.0). Ячейка `(site, c, d)`; `H` — из снимка; `v_p = proc_v[site,p]` месяца t−1.
```
V_c      = Σ_{p∈c} v_p                     # все p кластера с v_p > 0, включая r_d(p) = 0 (A2)
если V_c = 0:  drive = catch = maint = 0    # без деления на ноль
иначе:   s_p = v_p / V_c                    # отдельная операция
  drive  = Σ_p s_p · max(0, r_d(p) + 0.25 − H)
  catch  = Σ_{p: world_lead(p, owner)} s_p · max(0, r_d(p) + 0.25 − H)   # world_lead — выбор, не множитель
  maint  = Σ_p (s_p · r_d(p)) · a_r,   a_r = min(1, act[c] / act_norm)
spill    = Σ_c' R[c,c'] · max(0, H[c',d] − H[c,d])   # H[c',d] — из снимка
H_floor  = φ_floor · Hcap[site,d]           # Hcap — от образования кадров; φ_floor из данных
sat      = max(0, 1 − H / Hcap[site,d])
α_eff[d] = α · (1 + k_qp)  или  α
ΔH⁺      = sat · ( ((α_eff[d] · act[c]) · w[c]) · drive + k_catch · catch + σ · spill )
ΔH⁻      = δ_H · max(0, H − max(maint, H_floor))
H'       = H + min(ΔH⁺, ρ_max) − ΔH⁻
```
- **A2.** Процессы кластера с `r_d(p) = 0` входят в `V_c` и `s_p`, как записано (`Σ_{p∈c}`, F2: доля объёма кластера). Они разбавляют тягу трудных процессов, в `maint` дают 0, а в `drive` — `max(0, 0.25 − H)`, то есть держат культуру не ниже базового уровня 0,25.
- [Предл.] **F2.** Линия с 1% объёма кластера даёт 1% тяги. Освоение требует массового трудного выпуска, убыточного при низком выходе.
