  1. `Requirement(class, gen, …)`;

  - Путь C2 записан так: поставка по графику (40 Nene → SUN) → событие лицензии на этот `Design` → свой проект-копия.

## 3. Склад и журнал движения компонентов — материальный запас (#61, #69)
| Колонка (таблица) | Ключ | Смысл |
|---|---|---|
| `units`, `life_h` (`component_stock`) | `site, design` | свободные единицы и их средний зафиксированный ресурс (§8) |
| `units`, `life_h` (`component_held`) | `requester, design` | выдано, но ещё не установлено |
| `produced, delivered, granted, used, returned, retired, scrapped` (`component_ledger`) | `site, design` | накопительные целые счётчики потоков |
| `installed` (`component_ledger`) | `site, design` | сейчас стоит на когортах, базирующихся на site |

**Инвариант (post, точно, по каждому `(site, design)`):**
```
produced + delivered = stock + held + installed + retired + scrapped
stock     = produced + delivered + returned − granted
held      = granted − used − returned
installed = used − retired − scrapped
```
Смысл потоков:
- `retired` — снятые с выработанным ресурсом (§8);
- `scrapped` — снятые при переоборудовании и при списании когорты;
- `returned` — удержанное, возвращённое на склад при закрытии запросившего.

Свойства:
- Это **не** запас К§3: обучения, забывания и влияния на `yield`, цену и `D` нет. В К§3 добавляется примечание о материальных запасах. Тест разреженности К§8.1 распространяется на них: сдвиг склада меняет только `granted`, выпуск, замены и число самолётов на земле у запросивших.
- Счёт в целых единицах: компонент неделим.
- **Только свой site** (инвариант, проверяется в post): запросивший берёт со склада site своей линии, программы или базирования когорт. В фикстуре «2 site» склады не общие. Перевозка между site — FUTURE.
- **Импорт** (#72): `deliver_component(site, design, n, schedule_id)` — только поставки по графику из данных сценария (пример: 40 Nene → SUN, 1946–47; кейс C2, решение #52). Рынка и цены поставщика нет. Поставка учитывается в `delivered`.

## 4. `reserve_component` (#61, #71)
```
reserve_component(site, design, n, requester_id) -> granted@t+1   # site — свой site запросившего
consume_component(requester_id, design, used)                      # used ≤ held из снимка
report_component_output(site, design, units, life_h)                # все выпущенные единицы (брак — в q_c, §6)
deliver_component(site, design, n, schedule_id)                     # только график сценария
```
- **Виды потребителей:** `new_production` (линии платформ), `modernization` (программы), `sustainment` (замены; один на `(site, component design)`). Пространство `requester_id` общее для КБ, программ, линий и `sustainment`.
- **Запрос (без накопления).** Compute тика t:
  - `n = max(0, min(need(t+1), cap(t+1)) − (held_snapshot − used_t))`;
  - для линии `cap = line_capacity·qty`, для программы `rate_cap·qty`, для `sustainment` — накопленная потребность в заменах (§8).
  - Property-тест: при постоянном спросе и достаточном складе `granted = n` каждый месяц, а `held` не растёт.
- **Делёж при нехватке** (`Σn > avail`), merge, всё в целых (`Int128`):
  1. Веса `w_kind ∈ 0..100` задаёт игрок для актора, по умолчанию — ИИ (таблица `component_priority(actor, kind, w)`).
  2. Доля вида `share_k = floor(avail·w_k / Σ_{k' со спросом} w_k')`, но не больше `Σ n_i` этого вида.
  3. Излишек перераспределяется между видами с неудовлетворённым спросом той же формулой. Видов три, поэтому повторов не больше трёх.
  4. Если у всех видов со спросом `w = 0`, веса считаются равными.
  5. Внутри вида: `granted_i = floor(n_i·share_k / Σ n_i)`.
  6. **Остаток** (`avail − Σ granted`) раздаётся по 1 единице по кругу среди запросивших с `granted_i < n_i`. Круг идёт в порядке `requester_id`, начиная с позиции `month_index mod R`, где `R` — число таких запросивших. Остаток не уходит всегда наименьшему id.
- `avail` — склад после поставок и выпуска этого тика (§12). Двигатель, выпущенный в месяце t, ставится с t+1.
- `granted` пишется в `component_held` и виден в t+1.
- **`granted/n` при `n = 0` = 1** (нехватки нет). Ярлык `COMPONENTS` ставится при `granted/n < 0.9`.

## 5. Без двойного счёта: `prc_own` против `prc_closure`
```
prc_own(d)     = объединение PRC альтернатив слотов alt проекта d
prc_closure(d) = prc_own(d) ∪ ⋃_{(c,qty) ∈ bom(d)} prc_closure(c)
```
| Потребитель | Набор |
|---|---|
| `production_profile`, `unit_cost_mult`, `q`, `bottleneck` линии d | `prc_own(d)` |
| `report_output` линии d (`labour_hours` — только своя работа) | `prc_own(d)` |
| `complexity(d)` → `D0`, `W`, upkeep своей части | `prc_own(d)` |
| `fielded` / `mastered` (К§9.1), `tier_display` | `prc_closure(d)` |
| обход звеньев `why_not(design)` | `prc_closure(d)` |

- Общий PRC в платформе и в компоненте — это две единицы работы на двух линиях, а не двойной счёт.
- Тест разреженности: сдвиг `proc_X` по PRC двигателя не меняет `unit_cost_mult` платформы.
- Лимит сплава среза 1 (`alloy_kg[gen]`) переходит на линию двигателя. Делёж — по `design_id` (срез §1.4).

## 6. Агрегаты изделия с BOM
| Величина | Правило | Почему |
|---|---|---|
| Денежный поток | каждая линия платит за свой выпуск; установка компонента денег не стоит | компонент оплачен один раз |
| `unit_cost_full(d, site)` (ИИ, `fleet_value`, ECONOMY, UI) | `unit_cost_own + Σ_slot qty·unit_cost(c)`; цена компонента — текущая из снимка | стоимость аддитивна (C1) |
| `complexity(d)` | только своя | иначе дефекты двигателя считались бы дважды |
| `D0`, `defects_hidden` | у компонента — в его `Design`; у платформы — своё `D0` плюс `extra_D0` из `compat`, **в том же** `defects_hidden` (#72, без разбиения) | #63, #72 |
| `upkeep(d)` | `upkeep_own + Σ_slot qty·upkeep_base_c·PowFrac(complexity_c, q10_αu)/maintainability`; слагаемого за ресурс нет | замены двигателей оплачиваются как выпуск линии двигателя (§8), иначе цена ресурса учтётся дважды |
| `readiness` когорты | `min(1, оплачено/нужно) · q_own · (1 − ψ_D·D/D0)_own · Π_slot r_c · (1 − grounded/count)`; `r_c = q_c·(1 − ψ_D·D_c/D0_c)` **один раз на слот**, без степени `qty` | решение Orchestrator. Нехватка двигателей учтена отдельно — через `grounded` |
| `perf(d)` | `perf_platform(d) · f_class(характеристики c)` (данные) | как «база двигателя» среза 1 |

- **Брак компонента — в одном месте:** в `report_component_output` идут **все** выпущенные единицы, а `q_c` входит в `r_c`. Этот вариант выбран против «склад = годные единицы, `r_c` без `q_c`» по трём причинам:
  - так в срезе 1 уже устроены `q` и `readiness` (К§4.2, A4); у `q` не появляется нового эффекта на количество;
  - не нужно округлять `units·q_c` до целого;
  - склад и журнал остаются точными счётчиками физических единиц.
- Порядок вычислений: `Σ` и `Π` — по возрастанию `slot_id` (К§4.0 п. 4–5).
- **При пустом BOM** новые операции не выполняются вообще (не «+0» и не «·1»), и `grounded` не умножается.

## 7. Совместимость (#63, #65)
`compat(platform_design, slot, component_design) → { level, reasons[], cost_mult, extra_D0, margin_used[param] }` — чистая функция данных в `Fx6`, без RNG и физики.

**Параметры и запас.**
- Параметры двигателя: `thrust`, `mass`, `airflow`. Выбран `airflow`, а не диаметр: по кейсам C2 и C6 его проще проверить. Диаметр остаётся вариантом данных.
- У платформы на каждый параметр есть `p_nom` и `growth_margin[param]`. Запас выбирается при проектировании за цену (#65): `W·(1 + k_W·gm)`, `unit_cost_own·(1 + k_c·gm)`, `perf·(1 − k_p·gm)`, `gm ∈ [0, gm_max]` (кейс C9).
- **`margin_left` по пути родословной** (решение Orchestrator). Для `d`: `growth_margin` ближайшего предка-«нового проекта» (корня ветки) минус `Σ margin_used` по всем проектам на пути от этого корня до `d` включительно.
  - Боковые ветки запас друг у друга не отнимают (C7: Su-22 — ветка от общей базы).
  - Запас не восстанавливается.

**Уровни.** Для каждого параметра `excess = max(0, (p_comp − p_nom)/p_nom)`. Уровень — по худшему параметру, ничья — по id параметра.

| Уровень | Условие | Последствие |
|---|---|---|
| `direct` | все `excess = 0` | `cost_mult = 1`, `extra_D0 = 0` |
| `minor_mod` | `excess ≤ margin_left` или отличается только крепление | малый `cost_mult`; `extra_D0 ∝ excess`; модификация |
| `redesign` | `margin_left < excess ≤ margin_left + redesign_reserve` | потомок платформы, `novelty` по затронутым слотам (C6, C7) |
| `new_variant` | `excess ≤ hard_limit` | новый проект платформы (C7, Su-22) |
| `incompatible` | `excess > hard_limit` или не совпал жёсткий тег `config` | нельзя (C8: 4 двигателя вместо 8) |

- Крепление (`mount_family`) — это добавка к цене (`k_mount`, `d_mount`), а не повод сразу поднять уровень. Уровень от него не выше `minor_mod` (#63).
- Тесты:
  - уровень монотонен по `excess` и по `margin_left`;
  - `direct ⇒ extra_D0 = 0`;
  - результат не зависит от порядка строк;
  - таблица кейсов C6–C9 даёт ожидаемые уровни.

## 8. Ресурс и замены (#65, #69)
**Ресурс фиксируется при выпуске.** В compute месяца выпуска по снимку:
```
dfrac          = D / D0                                         # отдельная операция; 0 при D0 = 0
y_b            = yield узкого процесса prc_own(c) на site выпуска
life_f         = PowFrac(1 − dfrac, q10_kD) · PowFrac(y_b, q10_ky)
service_life_h = L_min[class,gen] + (L_max[class,gen] − L_min[class,gen]) · life_f
```
- Значение уходит с партией в `report_component_output(…, life_h)`. Дальше оно **не пересчитывается**, в том числе от текущего `yield` (#69).
- На складе, в удержании и на когортах хранится **средневзвешенный** ресурс единиц: `life' = (life·N + life_new·n)/(N + n)`, floor. Состав партий не хранится (§«Разногласия» 2).
- Имя `service_life_h` выбрано, чтобы не путать с `service_life` среза 1 (возраст списания когорты, 180 мес.).

**Замены** (`cohort_engine(cohort_id, slot_id, design_id, life_h)` и `sustain(site, design, due, backlog)`):
1. Compute: `due += Σ_когорт (count·qty·hours_month)/life_h` (Fx6, по `cohort_id`). Запрос `sustainment` равен `floor(due) + backlog` с учётом §4.
2. Merge, по `cohort_id`: установленные единицы вычитаются из `due`, снятые идут в `retired`, `life_h` когорты обновляется средневзвешенно. Неудовлетворённое остаётся в `backlog`.
3. `grounded[cohort] = ceil(backlog_cohort/qty)`, но не больше `count`. Backlog делится по когортам floor-пропорционально `due`, остаток — по кругу (§4). Самолёты на земле не готовы (§6), но содержание за них платится.
4. `why_not`: `PRODUCT/COMPONENTS`, рычаги `expand_component_line` и веса приоритета.

Следствия:
- Низкий ресурс (WS-10) загружает линию двигателей заменами и оставляет самолёты на земле при нехватке (C11). Это **единственный** путь, которым ресурс действует на игру. Отдельного эффекта на upkeep и на `readiness` через `D` у него нет, и канал «`yield` → upkeep» закрыт.
- Ресурс растёт по двум существующим каналам (выявление дефектов и `yield`) только у **новых** партий. «Зрелости конструкции» как отдельной сущности нет (#65).

## 9. Лидерство: замыкание и поколение (#62, #70; К§9.1, К§13)
- `fielded(a, t)` = в строю ≥ `n_service_min` единиц d, собранных на site актора, и `mastered(a, p, t)` для всех `p ∈ prc_closure(d)`.
  - Двигатели по поставкам дают `fleet_value`, но не `fielded`, пока страна не освоила их PRC.
  - Освоение через другой свой двигатель засчитывается: #62 говорит о процессах.
- **`gen(d)` (#70):** `gen_eng(d) = min_{c ∈ bom(d)} gen(c)`; `gen(d) = gen_app(d)`, если `gen_eng(d) ≥ gen_app(d) − 1`, иначе `gen(d) = gen_eng(d) + 1`.
  - F-14/TF30 (отставание на одно поколение) получает поколение планера.
  - Перемоторизация не поднимает `gen` выше планера.
  - При пустом BOM `gen(d) = gen_app(d)`, как в срезе 1.
- **Агрегация `G`, `P` по классам (закрывает К§13).** Компонентные классы в `G` и `P` напрямую не входят. Сценарий задаёт `lead_classes`:
  - `G` = max `gen(d)` по `fielded` всех этих классов;
  - `P = Σ_{class по id} max perf(d)/perf_ref[class]`;
  - при одном классе и `perf_ref = 1` это совпадает с К§9.1.

## 10. Модернизация и допуск (#64, #72)
```
ModernizationProgramme { id, actor, from_design, to_design, cohort_filter {build_year_min, build_year_max},
  target_count, conversion_site, rate_cap, labour_h_per_unit, downtime_months, status }
```
- Условия: `to_design` — потомок `from_design`, `compat ≤ redesign`, `conversion_site` — site базирования когорт.
- Программы ведёт ИИ, игрок может изменить их командой (ADR-0014). Решения применяются с t+1 (ADR-0006).
- **Переоборудование (#72): фиксированная трудоёмкость** `labour_h_per_unit` (данные класса), без `line_E` и без канала §8.2.
  - Кадры — `reserve_workforce` под `requester_id` программы; цена — `labour_h·wage`.
  - Темп в месяц: `k = min(rate_cap, held/qty, granted_skilled/labour_h_per_unit, бюджет/цена, остаток)`.
- Переоборудуемые единицы стоят `downtime_months`. Затем они переходят в когорту `to_design` с тем же годом выпуска и site. Их ресурс — средневзвешенный ресурс установленных двигателей. Снятые двигатели идут в `scrapped`.
- **Допуск — решение** (`admit(design, series|service)`: команда или ИИ), а не порог.
  - «Сырой» допуск даёт низкий ресурс партий (§8) и низкую готовность.
  - `why_not`: `PRODUCT/NOT_ADMITTED`, рычаг `admit`, показывается `service_life_h` при допуске сейчас.

## 12. Порядок merge месячного шага (дополняет К§4.0 и К§11)
1. `report_output` — `(site_id, prc_id)`, без изменений; сюда входят и линии компонентов.
2. `consume_component` — `(requester_id, design_id)`: `held −= used`, `installed += used`; ресурс когорт пересчитывается.
3. Замены и снятия — `(cohort_id)`: `retired`, `scrapped`, `backlog`.
4. `deliver_component` — `(site_id, design_id, schedule_id)`.
5. `report_component_output` — `(site_id, design_id)`.
6. `reserve_component` — `(site_id, design_id)`, делёж по §4: `stock −= Σ granted`, `held += granted`.
7. Операции программ над когортами — `(programme_id, cohort_id)`; новые строки когорт дописываются в конец.
8. `reserve_workforce` — `(site_id, cat, requester_id)`, без изменений.

Если сообщений нет, шаги 2–7 не выполняются.

## 13. Бюджет каналов К§8.2 и абляции
- Коридоры К§8.2 применяются к каждой линии (платформа, компонент) по её собственному накопленному выпуску. Переоборудование каналом не является (#72).
- `unit_cost_full` раскладывается на 4 канала: выход и сборка платформы, выход и сборка компонента. Сумма должна попасть в коридор, аддитивность ±15%.
- **Абляция «`line_E` двигателя ≡ 0».** Ожидается:
  - `unit_cost_own` платформы не меняется;
  - падение `unit_cost_full` уменьшается на вклад сборки двигателя (±15%);
  - ни один канал платформы не перенимает обучение двигателя.
- Симметричные абляции: «`line_E` платформы ≡ 0»; `q10_ky = 0`.
- **Эквивалентность со срезом 1 (диагностика Lab).** Двигатель-слот сравнивается с BOM при линии двигателя на том же site и при `h_first_platform + qty·h_first_engine = h_first_slice1`. Падение цены на удвоение должно совпасть в пределах ±10% [Предп.]. Расхождение больше означает, что появился новый канал.
- **Округление забывания** (дополняет К§4.0 п. 6). Форма `x − floor(δ·x)` останавливается, когда `δ·x < 1` raw. Запас застревает в остатке `1 … ⌈1/δ⌉ − 1` raw: при `δ = 0.004` это 1–249 raw `Fx6`, то есть ≤ 0,00025 единицы, и до нуля не доходит. Это касается `proc_X`, `line_E` (в том числе линий компонентов) и `culture_H` над полом. Остаток допустим. Тесты не ждут точного 0; явный ноль бывает только по правилу (закрытие линии → `line_E = 0`).
- Цена тика [Предп.]: склад, делёж, замены и программы обходятся линейно. `compat` вызывается только при решениях. Итого < 0,5 мс на месячный тик.
