# ADR-0017 — StateHash schedule and table copy in daily mode

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

**Ревизия 2** (2026-11-17), по итогам gate:
- ревью: `docs/reviews/adr-0017-critic.md`, `adr-0017-advocate.md`, `adr-0017-deepseek.md`;
- решения владельца: #289, #290, #291;
- выбор Orchestrator: копирование при записи (CoW) по колонкам вместо объявленных `Writes`.

Основа: `docs/architecture/notes/daily-hash-and-view.md` §3, профиль `docs/simulation/tick-profile-m0.md` (#283).

## Контекст

- [Факт: профиль #283, `hash-copy.txt`] Цена на полном масштабе (200 акторов, 2000 узлов; ≈ 8800 колонок × 200 строк ≈ 14 МБ):
  - `StateHash` (SHA-256) — 37,7 мс на вызов;
  - `Table.CopyCurrentToNext` — 1,88 мс на вызов.
- [Предп.] F8 (TASK-0068: те же байты, но без поэлементной сериализации) снижает хеш до ~8–10 мс. Не замерено на i7.
- ADR-0016:
  - §2 определяет дневной режим как «копия и swap, post, хеш, снимок» каждый день;
  - §3 даёт Kernel + Session долю `K_d ≤ 50` мс/мес;
  - §4 требует Kernel-ADR до кода #228 при `K_d > 150` мс.
- Ежедневный хеш и полная копия стоят ≈ 30 × (9 + 1,9) ≈ 0,33 с/мес. Одна копия — ≈ 56 мс/мес, то есть больше всей доли.
- #228: месячные системы раскладываются по дням, поэтому в игре каждый день — непустой тик. Этот ADR — Kernel-ADR по ADR-0016 §4.
- [Факт] ADR-0002, «Последствия»: хеш считается «каждый тик **(или по расписанию)**».
- Решения владельца:
  - #289 — SHA-256 и golden не меняются; хеш считается по расписанию; XXH3 и Merkle отклонены, XXH3 оставлен как вариант для мультиплеера;
  - #290 — копию оптимизировать в этом ADR, доля 50 мс остаётся;
  - #291 — в игре обязательны только точки «старт, save, load, конец replay»; месячная и командная точки — под execution-only флагом.

## Решение

### A. Расписание `StateHash` (#289, #291)

1. **Канонический хеш не меняется.** SHA-256 с байтовым форматом `StateHash.cs` и ADR-0013 п. 2:
   - заголовок `schema_version`, `n_rows`;
   - затем `Current` всех колонок в порядке регистрации, little-endian.

   F8 меняет способ подачи байтов, а не сами байты.
2. **Обязательные точки в игре** (#291) — хеш считается всегда:
   - начальное состояние (тик 0, в `Create`);
   - save (заголовок ADR-0013);
   - load (проверка ADR-0013 п. 8);
   - конец `Replay`.
3. **Контрольные точки** — execution-only флаг `SliceRunConfig.HashCheckpoints`. Он не хешируется и колонок не добавляет. При флаге хеш считается сразу после post:
   - (а) на **тике месячного шага** — тик `t`, для которого `Calendar.IsDue(Cadence.Monthly, t)`, то есть тик первого дня календарного месяца. При #228 это та же граница, сколько бы дневных срезов систем ни работало, поэтому номера точек совпадают с сегодняшними;
   - (б) на тике с применённой внешней командой.
4. **Ежедневный хеш** — execution-only флаг `SliceRunConfig.HashEveryTick`: хеш на каждом непустом тике. Флаг включает п. 3. Нужен, чтобы найти первый расходящийся день.
5. **Значения по умолчанию.** `HashCheckpoints = true`, `HashEveryTick = false`. Игровой хост (клиент) явно ставит `HashCheckpoints = false`. Причина: флаг, забытый в тесте, тихо ослабил бы проверки, а флаг, забытый в игре, стоит только миллисекунд. Тесты и Lab получают нынешнюю строгость без правок (#291: «проверки детерминизма в тестах не слабее прежних»).
6. **Ленивый `LastHash` и версия таблицы.**
   - `Table.Version` (`long`) растёт:
     - в `Swap`, если поменяна хотя бы одна колонка;
     - в каждом `Column.Load` (колонка знает свою таблицу);
     - при загрузке сохранения (через `Load`).
   - Кэш сессии — пара `(version, hash)`. `LastHash` возвращает кэш, если `version == Table.Version`, иначе синхронно считает SHA-256 и обновляет кэш.
   - Между тиками таблицы — это состояние после последнего post, а версия ловит любую запись в `Current` вне тика. Поэтому значение побитно равно хешу, посчитанному сразу после post.
   - `HashComputations` считает только реальные вычисления.
7. **Поток.** `LastHash` и пути save/load вычисляют хеш только на **потоке-владельце сессии** (ADR-0014 п. 5).
   - Владелец — поток, вызвавший `Create`. Вызов с другого потока бросает `InvalidOperationException`.
   - `SliceView.StateHash` (`string?`) несёт только **уже посчитанный** хеш этого тика (п. 2–4) или null; view никогда не вычисляет хеш.
8. **Контракт `Step` (ADR-0014 п. 4).** Выбран **отдельный ленивый аксессор**, а не `string?` в результате `Step`:
   - `Step` возвращает только продвижение тика (сейчас `void`, тик и дата — свойства);
   - хеш после последнего post отдаёт `LastHash`: синхронно, на потоке-владельце, всегда не null.

   Почему не `string?` в `Step`: null там означал бы «не посчитано», и каждый вызывающий решал бы, пересчитывать ли хеш, — две семантики одной величины. Аксессор даёт одно значение и цену только тому, кто спросил. Будущий транспорт (часть G) кладёт хеш в ответ `Step` только по флагу запроса.

   `TestApiVersion` +1 — одно повышение на п. 7–8 и `string?` во view.
9. **XXH3/XXH128 и Merkle не вводятся** (#289). XXH3 — зарезервированный второй, неканонический хеш для проверки рассинхрона каждый тик в будущем lockstep (L3), вводится отдельным ADR.

### B. Копия таблиц: CoW по колонкам (#290)

10. **Открытие при первом касании.** Внутри тика первое обращение к `Column<T>.Next` открывает колонку:
    - быстрый путь — `Volatile.Read(ref _open)`;
    - медленный — `lock` на объекте колонки, повторная проверка, `_current.CopyTo(_next)`, затем `Volatile.Write(ref _open, true)`.

    Копия идемпотентна: содержимое `Next` до первой записи равно `Current`, какой бы поток ни открыл колонку. Писать поток может только после возврата из `Next`, то есть после завершения копии (release/acquire). Поэтому результат не зависит от расписания потоков (L2).
11. **Swap.** `Table.Swap` проходит все колонки **в порядке регистрации**, меняет местами только открытые и закрывает их. Общего списка открытых колонок нет, порядок открытия ни на что не влияет. Неоткрытые колонки не копируются и не меняются местами: их `Current` верен, а устаревший `Next` до следующего открытия никто не читает.
12. **Границы тика.**
    - `TickRunner` перед compute помечает таблицу «в тике» и закрывает все флаги (на случай тика, прерванного исключением).
    - `Next` вне тика бросает `InvalidOperationException`. Запись в состояние вне тика — только `Load`, он поднимает версию.
    - Пустой тик (ADR-0006) по-прежнему ничего не копирует.
13. **`Next` не сохраняется** (ADR-0013: в файл идёт только `Current`). После load `Next` устарел, но первое открытие в следующем тике копирует `Current`, поэтому устаревший буфер никогда не читается.
14. **Цена проверки.** Каждое обращение к `Next` — одно volatile-чтение bool. Горячие циклы берут span один раз на чанк (`Span<T> next = col.Next;` до цикла). Цену замеряет R2 (г).
15. **Параллельная копия** открытых колонок не вводится: при CoW копия идёт на первом касании внутри compute и уже распределена по потокам.
16. **Исключение в `.claude/rules/csharp-core.md`** (follow-up Orchestrator, не этот ADR). Текст: «Kernel `Column<T>.Next`: идемпотентное открытие под `lock` с двойной проверкой — единственная разрешённая общая запись в compute; результат не зависит от того, какой поток открыл колонку».

### Частично заменяет

`supersedes:` во frontmatter пуст намеренно: заменяемые ADR остаются ACCEPTED, а заменяются только перечисленные места.

**ADR-0016:**
- §1 «Что входит в `T`», пункт «`StateHash`» → `StateHash` по расписанию п. 2–3. `T` замеряется в игровой конфигурации (`HashCheckpoints = false`); прогон с `true` записывается справочно.
- §1, пункт «копия и swap таблиц» → CoW и swap открытых колонок (п. 10–11).
- §2 «Обязательный режим — дневной (#228)»: «каждый день — непустой тик: копия и swap, post, хеш, снимок» → «каждый день — непустой тик: CoW и swap открытых колонок, post, снимок; хеш — по п. 2–4».
- §2 T1a: «при флаге Session делает хеш и снимок на каждом непустом тике» → снимок — на каждом непустом тике, хеш — по п. 2–4.
- §2 «Запасной путь»: no-op-команда больше не даёт ежедневного хеша (п. 3б — только под флагом). `k_copy` — цена CoW, а не полной копии: при пустой дневной системе она ≈ 0.
- §2 «Проверка формулы» и «Составляющие»: `k` = CoW-копия + swap + снимок (+ хеш только под флагом). `M + 29·k`, `k_i = (T_i − M_i)/29` и `K_d,i = 30·k_i` в силе, если `M` и `T` замерены с одинаковыми флагами п. 3–4.
- §4 «Флаг действия `K_d > 150`»: этот ADR и есть требуемый Kernel-ADR.
- §7 «`k` на колонку» → `k` на **открытую** колонку.

**ADR-0006:**
- «Фазы тика: … post (инварианты, метрики, хеш)» → хеш после post только в точках п. 2–4.
- «Тик, на котором применена хотя бы одна команда, … на нём выполняются post и хеш» → post — всегда; хеш — при `HashCheckpoints`.
- «Пустой тик … не копирует таблицы» — в силе. Непустой тик копирует только открытые колонки.
- Проверка: «тик с применённой внешней командой … выполняет post и хеш» → проверяется при `HashCheckpoints = true`.

**ADR-0014:**
- п. 4: «`Step` … возвращает … `StateHash` таблиц после последнего выполненного post» → хеш возвращает синхронный ленивый `LastHash` на потоке-владельце (п. 8). Значение то же.
- п. 5: `SliceView` несёт посчитанный хеш или null (п. 7).

**Не меняются:**
- ADR-0002 — расписание разрешено, L1/L2 проверяются тем же SHA-256;
- ADR-0013 — формат и `state_hash` заголовка.

## Рассмотренные альтернативы

| Альтернатива | Причина отказа |
|---|---|
| SHA-256 каждый день (+ F8) | [Предп.] 30 × 8–10 мс ≈ 0,25–0,3 с/мес > 150 мс. |
| Месячная и командная точки обязательны в игре (рев. 1) | В игре у них нет потребителя. Отклонено #291. |
| XXH3/XXH128 каждый день + SHA-256 раз в месяц | Два хеша в API. Отложено до lockstep (#289). |
| Merkle по колонкам или чанкам; параллельный SHA-256 с корнем | Новый корень ⇒ golden и EXP-0002 недействительны (#289). |
| Объявленные `Writes` с проверкой (рев. 1, п. 7–9) | Объявления по умолчанию «все колонки» оставляют долг и отключают проверку на время миграции. Исключение в редкой ветке в игре. Проверка по объединению наборов, а не по системе (critic 3). CoW даёт ту же экономию без объявлений. |
| Двойная буферизация без копии (система пишет каждую ячейку) | Пропущенная ячейка получает значение двухтиковой давности. Тихая ошибка, которую L1/L2 не ловят. |
| Грязные строки или чанки | Учёт на строку в горячем цикле. Не оправдан до профиля #228. |
| Slab: одна непрерывная память на тип, копия одним memcpy | Несовместим с CoW по колонкам. **Запасной путь R2**: берётся, только если CoW не проходит порог R2. |
| Параллельная копия всей таблицы | [Предп.] ×2–3 при ограничении памяти ⇒ ~20–28 мс/мес. Не нужна при CoW. |
| `Step` возвращает `string?` | См. п. 8. |

## Последствия

**Плюсы:**
- Golden, сохранения и манифесты EXP-0002 действительны, миграции данных нет.
- Тесты и Lab по умолчанию сохраняют нынешнюю строгость.
- Копия подстраивается под то, что тик реально пишет. На дне только с зондом копии нет.

**Минусы:**
- [Предп.] При #228 выигрыш CoW зависит от того, сколько колонок пишет дневной срез. До ADR #228 оценка — кривая R2 (в).
- Расхождение в игре локализуется только при повторе с флагами п. 3–4.
- `Next` вне тика теперь бросает исключение. Код, который пишет `Next` при сборке мира, переводится на `Load`. При реализации проверить 14 файлов, обращающихся к `.Next`.
- Поверхность: `TestApiVersion` +1.

**Влияние:**
- **Тесты L1/L2.**
  - Сравнения на месячных точках и в конце — без изменений (флаг п. 3 по умолчанию включён).
  - Тесты, которые сравнивают хеш на немесячных днях (`ViewTests`, `DailyTickProbeTests.FlagOn_HashesAndSnapshotsEveryDay`), включают `HashEveryTick`.
  - Все сравнения хешей идут через помощник `HashAssert.Equal(string? expected, string? actual)`: он падает, если хоть один аргумент null. Так исключается пустое сравнение `null == null`.
- **Lab / EXP-0007.**
  - Исход ADR-0016 §4 замеряется в игровой конфигурации: `DailyTickProbe = true`, `HashCheckpoints = false`, CoW.
  - Справочно записываются прогон с `HashCheckpoints = true` и вариант «команда каждый день» (R4).
  - `K_d` с зондом — **нижняя граница**: зонд ничего не пишет, и CoW на нём не работает. Это пишется в EXP рядом с кривой R2 (в).
  - Поправку пре-регистрации вносит Orchestrator до прогона.
- **Golden:** без изменений.
- **Формат сохранения:** без изменений.

## Research до ACCEPTED (i7-11800H, условия ADR-0016 §5)

- **R1. `StateHash` после F8.** Точки (200, 2000) и (200, 500): прогрев 100, затем 1000 вызовов; медиана и p95.
  - Порог: p95 ≤ 15 мс.
  - Выше — это дефект F8, а не повод менять ADR: в игре хеш только в точках п. 2, но от этой цены зависит пропускная способность Lab.
- **R2. Копия** на (200, 2000), 1000 повторов каждого варианта:
  - (а) полная `CopyCurrentToNext`;
  - (б) CoW на месячном шаге среза (реальные системы) — открытые колонки, цена копии, swap;
  - (в) синтетическая дневная система, которая пишет 0 / 10 / 50 / 100 % колонок, — кривая цены CoW;
  - (г) цена проверки `Next`: месяц `M` (системы) с CoW против полной копии при t1 и t8;
  - (д) запасной slab — одно memcpy той же таблицы.

  **Пороги:**
  - (б): CoW ≤ полной копии + 5 %;
  - (в) при 100 %: ≤ (а) + 10 %;
  - (г): рост `S` ≤ 2 %.

  Если (г) выше порога — сначала span один раз на чанк в горячих системах, затем повтор. Если пороги не выполнены и после этого — в ревизию ADR идёт slab (д) или полная копия.
- **R3 (справка для MP).** `XxHash3`/`XxHash128` той же таблицы — мс на вызов.
- **R4. `K_d`** по методу ADR-0016 §2 после F1–F8 и этого ADR, в двух вариантах:
  - (а) зонд;
  - (б) зонд + no-op-команда каждый день.

  Оба варианта — в игровой конфигурации (`HashCheckpoints = false`) и справочно с `true`.

  **Пороги** (игровая конфигурация, p95):
  - `K_d ≤ 50` мс — цель ADR выполнена;
  - 50–150 мс — WARN по ADR-0016, следующий шаг решает владелец;
  - > 150 мс — ADR пересматривается до кода #228.

  В варианте (б) с `true` [Предп.] ≈ 30 × 9 мс ≈ 0,27 с — это цена только тестов и Lab, в игре её нет (#291). В игре ежедневная команда стоит применение команды, CoW колонок `cmd.*` и полный снимок view (F7a на тике с командой не работает): это и есть (б) в игровой конфигурации.

## Проверка

1. **Ленивый хеш против пересчёта.** Прогон (24, 180) с командами. `LastHash` читается в нерегулярные дни (детерминированная псевдослучайная выборка дней), вперемешку с `Column.Load` между тиками и командами. Каждое чтение сверяется с некэшированным `StateHash.Compute`.
2. **Версия.** `Load` между тиками → `Table.Version` вырос, и `LastHash` равен свежему `Compute`. Пустой тик версию не меняет. Тик только с зондом (ни одной открытой колонки) версию не меняет.
3. **Поток.** `LastHash` с чужого потока бросает исключение. `SliceView.StateHash` равен null на тиках без точки п. 2–4 и посчитанному хешу на тиках с точкой.
4. **Golden.** Все существующие golden-хеши (`dotnet test`, `lab selftest`) проходят без изменения констант при флагах по умолчанию.
5. **Счётчик.** При `HashCheckpoints = false` и без чтений `LastHash` `HashComputations` за прогон равен числу точек п. 2.
6. **CoW против полной копии.** Режим полной копии остаётся тестовым переключателем Kernel. На (24, 180) с командами и `HashEveryTick` хеш **на каждом дне** равен.
7. **Гонка CoW.** t16, ChunkSize 1, 20 повторов. Тестовая система, у которой все чанки первыми касаются одной колонки, даёт одинаковый хеш во всех повторах и равный полной копии.
8. **L2.** Хеш в конце и на месячных точках равен при threads 1/4/8/16 × ChunkSize 1/8/32, с `HashEveryTick` и без него.
9. **Границы.** `Next` вне тика бросает исключение. Тик, прерванный исключением, не оставляет открытых флагов для следующего тика.
10. **Сохранение.** save → load → продолжение даёт тот же хеш (ADR-0013); `state_hash` заголовка посчитан в момент save.
11. **Пустое сравнение.** Тестовый проект сканирует исходники тестов: сравнения со `StateHash`/`LastHash` идут только через `HashAssert`.
12. **Поверхность.** Снимок API с `string? StateHash` и `TestApiVersion` +1.
13. **Бюджет.** R4 — в EXP-0007.

## Вне ADR (light, отдельные задачи; записка §1–§2)

- **F4-A** — параллельные `ViewBuilder.Inputs` по акторам, слоты `rows[a]`. Условие для F2: кэши не заполняются лениво при чтении.
- **F7a** — переиспользование `Actors` на тиках только с зондом, с поправкой `Closes[].Reason = None`.
- **F7b** — перенос `Inputs`/`Step` до следующего шага. Если будет одобрен вместе с этим ADR, повышение `TestApiVersion` объединить.
- **Правило** `csharp-core.md` — п. 16.

## Разногласия

- **DeepSeek low 2** (заполнить `supersedes:`). Не принято: поле в реестре означает полную замену, и ADR-0016 был бы помечен SUPERSEDED целиком. Вместо этого — раздел «Частично заменяет» с перечнем мест (решение Orchestrator).
- **DeepSeek high** (контракт `Step`). Из двух предложенных вариантов выбран отдельный аксессор, а не `string?` в `Step` (п. 8). Остаточный риск: вызывающий, которому нужен хеш каждого дня, платит за него сам или включает `HashEveryTick`.
- **Critic 3, вторая часть** (архитектурный тест «один писатель на колонку или почтовый ящик»). В этот ADR не включено. CoW снимает проверку по объединению, а запрет двух писателей одних строк в compute — общее правило ADR-0006 / `csharp-core.md`, не связанное с копией. Если нужен отдельный тест, он идёт отдельной задачей test-engineer.
- **Critic 4, вариант решения** (сливать команды одного дня в одну точку хеша). Не нужен: по #291 командная точка в игре выключена. Вариант R4 (б) остаётся для записи цены.
- **Значение флага по умолчанию** (п. 5: `HashCheckpoints = true`). Формулировка #291 — «включён в тестах и Lab, выключен в игре». Выбрано «включён по умолчанию, игра выключает явно», чтобы пропущенный флаг не ослаблял тесты. Если владелец хочет обратное умолчание, нужен явный флаг во всех тестах и Lab-хостах и тест на это.
