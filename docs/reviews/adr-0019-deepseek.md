- [high] p. 14 pull model contradicts p. 7 double-entry and scarcity normalization: p. 14 says the default is pull: the receiving row computes its own change by reading Current sources and writes only its own row, with no buffers. For a transfer this cannot satisfy p. 7, which requires one amount debited from the source and credited to the recipient. If the recipient writes only its row, the source stock is not reduced and the post invariant stock(t+1)=stock(t)+sum(in)-sum(out) fails. The same gap affects p. 7 scarcity normalization: computing allocation on the full daily demand requires aggregating demand and available stock, but the pull description gives no aggregation step and no rule for pairing the source debit with recipient credits.
- [high] Mid-month changes of F and partial-month slicing are undefined: p. 5 calls F a monthly parameter and proves exact monthly conservation only for constant F. p. 13 allows an event on day D to change ownership and affect calculations from D+1, and p. 8 allows threshold/project-completion events mid-month. If a Flow system recomputes F after such an event, using DaySlice(F, k, D) with the calendar day k of the new F does not preserve the intended monthly total or remaining-month amount. The ADR does not say whether F is frozen at month start, recomputed daily, or prorated from the event day. This affects K3 conservation, calibration, and every M1 golden.
- [medium] TickModel in scenario_hash may break SliceLegacy/EXP-0002 compatibility: p. 1 adds TickModel to scenario_hash. EXP-0002 records scenario_hash 2ccb4adb..., and ADR-0019 claims SliceLegacy is the current M0 path without changes. Adding a hashed field changes scenario_hash for a SliceLegacy world unless it is explicitly excluded or the frozen provenance is updated. p. 19 only references golden_set_hash and does not authorize this change; no verification item checks scenario_hash for SliceLegacy.
- [medium] CI-every-PR requirement conflicts with R4: Verification item 7 requires CI on every PR that changes src/Singularity.{Kernel,Core,Session} to run the EXP-0002-det matrix and produce 824f4ded..., while R4 says the det matrix timing will be measured to decide whether to run it every PR or at night. Both cannot be true before R4 is resolved.
- [medium] ADR-0020 is an undeclared dependency: p. 11 relies on ADR-0020 for derived region columns, p. 17 relies on ADR-0020 attribution, and p. 26 relies on ADR-0020 for the speed floor. ADR-0020 is absent from the related list and from the linked files. If ADR-0020 is not accepted, the merge order and StateHash columns in p. 11, the actor aggregation in p. 17, and the WARN rule in p. 26 are undefined.
- [medium] K4 measurement flags are not pinned: ADR-0016 includes snapshot and StateHash in T, and ADR-0017 makes hash checkpoints execution-only with game defaults HashCheckpoints=false. ADR-0019 p. 24 introduces ViewPublish=OnRequest, while p. 25 only says T is measured in Daily228 (K4) without specifying HashCheckpoints, HashEveryTick, or ViewPublish settings. A K4 run with different flags can materially change p95 and therefore PASS/WARN/FAIL.
- [medium] Apportion has no defined behavior for zero total weight: p. 6 defines Apportion using W=sum(w) and divides by W. It allows w>=0 but does not say what happens when W=0 or all weights are zero. Depending on implementation this can divide by zero, drop F, or create/destroy value, violating the stated exact-sum property. The weight sum overflow bound before the Int128 product is also unstated.
- [low] Push-buffer 'issue order' is not proven deterministic: p. 15 says merge applies buffers in chunk order 0..N-1 and inside a chunk in order of issue. If issue order can depend on thread scheduling or system scheduling, the merge order is not deterministic and L2 can fail. The statement that checked long addition makes the sum order-independent is also too strong when intermediate overflow can occur in different orders.
