# ADR-0019 — Monthly systems split into daily slices (#228), revision of ADR-0006

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Уровень: gate+research (меняет все golden мира M1). Пункт 0.2 плана `development/milestones/MS-M1-economy-provinces-open-race.md`. Зависит от ADR-0003 (0.1) и ADR-0020 (таблицы, хеш, атрибуция). Ревизия 2 после gate: `docs/reviews/adr-0019-0020-{critic,advocate,reviewer}.md`, `docs/reviews/adr-0019-deepseek.md`.

## Краткий вывод
- [Предл.] Режим тика — параметр сценария `TickModel = Daily228 | SliceLegacy`; **по умолчанию (поле отсутствует) — `SliceLegacy`**, и тогда в хеш и колонки ничего не добавляется. Внутри `Daily228` у системы роль: `Flow` (суммы, режутся по дням), `Decision` (раз в месяц, отдельный проход в начале дня 1), `Event` (сценарные события).
- [Предл.] **Один писатель на колонку** (архитектурный тест). Переводы сохраняемых величин — журнал `(src, dst, x)` в буферах чанков; применяет и нормирует его владелец величины в merge, видя полный спрос дня.
- [Предл.] Режутся только **суммы за месяц** (raw Fx6), не ставки. Одно правило округления — floor (как `Fx6`). Нелинейные месячные правила получают дневные параметры (`Fx6.DayRate`).
- [Предл.] Событие с датой `D` применяется в merge тика `D−1` и действует **с утра `D`** (ADR-0011 §3 не меняется). Решения дня 1 видят события, датированные 1-м числом.
- [Предл.] `SliceLegacy` — нынешние классы M0, **замороженные**; `Daily228` — новые классы Flow/Decision. Пин-тест EXP-0002 (`824f4ded…`, `scenario_hash 2ccb4adb…`).

## Контекст
- [Факт: DECISIONS_LOG #228] Месячные системы раскладываются по дням и читают свежее состояние; все golden меняются; срез M0 (EXP-0002) — на прежней семантике.
- [Факт: ADR-0006] Тик = день; `Cadence`; месячная система обрабатывает месяц за запуск; compute читает `Current`, merge — в порядке списка.
- [Факт: код `TickRunner.cs`; `SliceSession.StepOne`] Все системы читают `Current`; команды и `Policy.ApplyDeals` пишут `Current` до `RunTick`.
- [Факт: reviewer, `KnowledgeRng.cs:8`, #60] Kernel ключует RNG `(seed, tick, system, entity, n)`, но Core передаёт индекс **месяца**; дневная система получила бы один бросок 30 раз.
- [Факт: reviewer, `IndustrySystem.CreateMailbox:194`; `CommandState`] Почтовые ящики бросают исключение при разной частоте отправителя и получателя; команды привязаны к месяцу (штамп = месяц + 1).
- [Факт: reviewer, `SliceWorld.RegisterRunColumns:484`] `run.scenario` = первые 8 байт `Scenario.Hash`: любое поле в хеше сценария среза меняет `824f4ded…`.
- [Факт: ADR-0011 §3] Владение меняется только в merge; видно в `t+1`. [Факт: ADR-0016 §2] `S` среза — нижняя граница, цена вызова ×30.
- [Факт: #337, #339–#343; `docs/game-design/scripted-events-conditions.md`] События с предусловиями: ежедневная перепроверка, отсрочка 6/12/36 мес., затем пропуск; без RNG; `event_status` и `effective_date` — в `StateHash`.

## Решение

### 1. Режим и роли
1. `TickModel` — поле сценария. Отсутствует → `SliceLegacy`: `scenario_hash`, `run.*` колонки и файлы среза не меняются. `tick_model: daily228` пишется только в сценарии M1 и входит в его `scenario_hash`.
2. Роли в `Daily228` (явная таблица `SliceRoles` в Core; система без записи не регистрируется):
   - `Flow` — суммы (выпуск, потребление, переводы, прогресс). `Cadence = Daily`.
   - `Decision` — дискретные решения (доли бюджета ИИ, выбор, старт проекта, применение отложенных команд). Раз в месяц, в **проходе решений** (п. 9).
   - `Event` — `ScenarioEventSystem` (п. 11–12): по дате, без нарезки.
3. Система с двумя ролями делится (Industry: распределение — `Decision`, накопление — `Flow`). [Предп.] Набросок: `Industry`→`IndustryDecision`+`IndustryFlow`; `Products`, `Policy` — `Decision` (покупки по сделкам — `Flow`); `Knowledge` — `Flow` (прогресс). Точный список — R3.
4. Почему режим глобальный: в одном мире не допускаются месячные **пакетные потоки** рядом с дневными — это третья семантика без golden. Решения раз в месяц — не пакетный поток.
5. **Один писатель на колонку** (во всех таблицах ADR-0020): у каждой колонки ровно одна система-владелец. Архитектурный тест по регистрации.

### 2. Нарезка, округление, переводы
6. Режется только **сумма за календарный месяц** `F` (raw Fx6, `long`). Ставки (доли, %/мес.) сначала превращаются в сумму: `F = FloorMul(rate, stock)`, затем режутся. Деление ставки на `D` запрещено (обнуляет малые ставки).
7. **Округление — floor везде** (как `Fx6` `*`/`/` через `FloorDiv`). `DaySlice(F, k, D) = q + floor(r·k/D) − floor(r·(k−1)/D)`, `q = floor(F/D)`, `r = F − q·D ∈ [0, D)`; `Σ_k = F` точно при постоянном `F`; срез отличается от `F/D` < 1 raw. Работает при `F = long.MinValue`. Состояния остатка нет.
8. **`Apportion(F, w[])`**: части `floor(F·W_i/W) − floor(F·W_{i−1}/W)`, `W_i` — накопленная сумма, `w_i ≥ 0`, сумма весов — `checked long`, произведение — `Int128`; сумма частей = `F` точно для любого знака `F`. `W = 0` → все части 0, `F` остаётся у источника (вызывающий обязан это обработать).
9. **Когда `F` меняется.** Месячные суммы из решений фиксируются в проходе решений дня 1 и постоянны весь месяц → `Σ` месяца = `F` этого месяца. Суммы, зависящие от состояния (выпуск от мощности), пересчитываются каждый день как месячный эквивалент `F_d` и режутся `DaySlice(F_d, k, D)`; для них свойство «`Σ = F`» не заявляется, сохранение держится двойной записью (п. 10).
10. **Переводы — журнал.** Перевод сохраняемой величины `Q` (деньги, энергия, люди) — запись `(src, dst, x)` в буфер чанка системы-заявителя (compute). У `Q` одна система-владелец («книга `Q`»); она в своём merge читает журналы всех систем в порядке (список систем, чанк 0..N−1, порядок выпуска в чанке), видит **полный спрос дня** на каждый источник, нормирует по `Apportion` при нехватке и пишет обе стороны. Инвариант post: `stock(t+1) = stock(t) + Σin − Σout` в raw (K3).
11. Pull (строка сама считает своё изменение по `Current`) — только для изменений своей строки, не для переводов.
12. Сложение — `checked long` в фиксированном порядке п. 10. Детерминизм (в том числе момент переполнения) держится на фиксированном порядке, а не на коммутативности.
13. **Нелинейные месячные правила** (распад δ_H, рампа λ, культура, пороги I1–I3): дневной параметр `Fx6.DayRate(δ, D) = 1 − (1−δ)^(1/D)` — целочисленный корень бисекцией в Kernel, считается при загрузке для `D ∈ {28..31}`; погрешность ≤ 1 raw/день (property-тест). Пороги проверяются по дневному состоянию; дата события порога — день пересечения. Опись — R3.

### 3. Порядок дня `D`
14. Session: внешние команды с `apply_tick = D` в порядке `(apply_tick, source_class, source_id, local_n)` (ADR-0014). Команды, меняющие месячные параметры, пишутся в слоты отложенных команд (колонки, в хеше) и применяются проходом решений ближайшего дня 1 — нынешняя семантика `CommandState` («месяц + 1»).
15. **Проход решений** (только день 1): отдельный проход runner'а с `Decision`-системами на том же индексе тика — compute по `Current` (начало дня 1, с событиями 1-го числа), merge, swap, post. Его результат читает проход потоков того же дня. RNG `Decision`-систем — ключ месяца (как сейчас).
16. **Проход потоков** (каждый день): compute `Flow` и `Event` по `Current`; merge в порядке списка; `ScenarioEventSystem` — **последняя** в списке merge (пишет только свои колонки, порядок с другими не важен, п. 5); swap; post (K3, K9, журнал); снимок view; хеш по расписанию ADR-0017.
17. **RNG `Flow`-систем:** ключ — индекс тика (дня), не месяца: `(seed, tick, system, entity, n)`. Сценарные события RNG не используют (#342).
18. **Связь `Decision` → `Flow`** — только через колонки (`Flow` читает `Current`). Почтовые ящики — только между системами одной роли и частоты.

### 4. Сценарные события (#325, #328, #339–#343)
19. **Дата.** Событие с датой `D` применяется в merge тика `D−1` (для `D = t0` — при сборке мира) и видно с утра `D`. Это ADR-0011 §3 как есть: смена в merge, видна в `t+1`. Потоки дня `D` идут при новом владении; проход решений дня 1 видит события 1-го числа.
20. **Ежедневная проверка.** В merge тика `D−1` `ScenarioEventSystem` обходит события со статусом `due` (дата = `D`) и `deferred`, в порядке `(nominal_date, event_id)`. Условия (закрытый словарь атомов, только структура в M1, #340) читают `Current` тика `D−1` плюс эффекты уже применённых в этом обходе событий. Атомарная группа — одно решение.
21. **Исход:** выполнено → эффект, `status = fired`, `effective_date = D`; транзитный провал → `deferred` до `AddMonths(nominal_date или effective предшественника, 6 | 12)`, максимум 36 (#341); истёк срок или постоянный провал → `skipped` (или `alt`, если написан вручную). Oder–Neisse — две записи, 1950 и запасная 1970 с `excludes` (#343).
22. **Что пишет событие** (п. 5): `owner`/`controller` провинций и территорий, `actors.active` (новые государства), `events.status`/`effective_tick` (ADR-0020). **Не пишет** колонки E1. Последствия для людей и мощности (2.9) считает система-владелец E1 в тике `D`: она видит смену по `controller` в `Current` и по `events.effective_tick = D` как маркеру.
23. Журнал событий (Lab, UI) — производный вывод, не хешируется; состояние `status`/`effective_tick` — в `StateHash` и сейве.

### 5. `SliceLegacy`
24. `SliceLegacy` = нынешние классы M0 (`IndustrySystem`, `ProductsSystem`, `PolicySystem`, `KnowledgeSystem`, `SliceSession`), **замороженные**: правки только багфиксов с повторным пин-тестом. `Daily228` получает новые классы; общий код — Kernel и `Fx6`, его изменения обязаны держать байты одной таблицы (ADR-0020 §1).
25. Эталон: EXP-0002 det `824f4ded07216828ee6354f95f6bd942dcefd6059f70fdff24fbf9f9ab91ea5b`, main `183e47b9fc81957ccd6a53f93f5d09f4d10a2ca094b0be119680bd1cf42ab02d`, `scenario_hash 2ccb4adb…` (`docs/simulation/exp0002-result.md` §1). Изменение эталона — только владельцем с отчётом (K6).
26. Срок — до закрытия M2 (TECH_DEBT). Тест ADR-0006 «дневной = месячный» — только `SliceLegacy`.

### 6. Хеш и бюджет
27. Формат хеша мира — ADR-0020 §1 (там же частичная замена ADR-0017). Расписание ADR-0017 без изменений: `HashCheckpoints`/`HashEveryTick` по умолчанию `false`; `HashEveryTick` (30 хешей/мес.) — только в тестах детерминизма, не в Lab по умолчанию. Точка месяца — после дня 1 (оба прохода).
28. CoW: `Flow` открывает свои колонки каждый день — точка на кривой R2 (в) EXP-0007; `Decision` — раз в месяц.
29. **Флаги замера K4:** `HashCheckpoints = false`, `HashEveryTick = false`, view — игровой режим ADR-0014, команды включены. Пишутся в манифест замера.
30. **p99 дня.** K4 дополнительно записывает p99 и максимум времени одного тика (дня); день 1 включает проход решений. [Предл.] Флаг действия: p99 дня > 100 мс → разнести решения акторов по дням (вопрос 1, вариант в).
31. Каждая `Flow`-система заявляет цену на день (ADR-0016 «Обязательно»); превышение — gate до кода.
32. `ViewPublish = OnRequest` из ревизии 1 **снят** с этого ADR (не следует из #228, не замерен; см. «Разногласия»).

### Частично заменяет
- **ADR-0006:** «месячная система обрабатывает месяц за запуск» и «решение действует со следующего тика» — только в `SliceLegacy`; в `Daily228` — п. 2, 15–16 (решение дня 1 действует в том же дне, во втором проходе).
- **ADR-0016 §2 «Составляющие»:** `k_i = (T_i − M_i)/29` — только `SliceLegacy`; в `Daily228` `S`, `K_d` — из inclusive-профиля.
- **ADR-0017:** через ADR-0020 §1 (формат заголовка, версия мира); здесь — только п. 27.
- Не меняются: ADR-0002, ADR-0011, ADR-0013, ADR-0014.

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| Режим на систему (месячные пакетные потоки рядом с дневными) | Третья семантика без golden |
| Нарезка «побитно = месячному запуску» | Отклонена владельцем #228 |
| Решения на последнем дне месяца (critic) | Не видят событий 1-го числа (1945-10-01, договоры) |
| Решение в compute дня 1, действует с дня 2 | `Σ` месяца не равна ни одному `F` (critic) |
| Pull для переводов | Две копии расчёта `x`; `Apportion` O(n²); нормирование не видит полный спрос |
| Событие в merge дня `D`, действует с `D+1` (ревизия 1) | Потоки дня события при старом владении; решения дня 1 пропускают месяц |
| Ветвление классов M0 по режиму | Тяжело при `IndustryMode`/`ProductsMode`/Layer; риск задеть эталон |
| Остаток деления в колонке | Лишнее состояние; накопленная доля точна без него |
| Clamp по мере поступления вкладов | Зависит от порядка |

## Последствия
- **Плюсы:** месячные суммы точны; сохранение — двойной записью в одном месте; нормирование на полном спросе дня; события по дате (#328); эталон M0 защищён заморозкой и пин-тестом.
- **Минусы:** все golden M1 новые; два прохода в день 1; журналы переводов — новый механизм Kernel; копии классов M0 до M2.
- **Обязательно:** `SliceRoles`; один писатель на колонку; `DaySlice`/`Apportion`/`DayRate` только из Kernel; переводы только журналом; `TickModel` по умолчанию `SliceLegacy`.

## Проверка
1. **Kernel property:** `Σ_k DaySlice = F` для `D ∈ {28,29,30,31}`, `F` случайные, `0`, `±1`, `long.MinValue`, `long.MaxValue`; февраль високосного года из `TickCalendar`. `Apportion`: сумма = `F` при любом знаке; `W = 0` → нули; переполнение суммы весов → исключение. `DayRate`: `(1−DayRate)^D` отличается от `1−δ` ≤ `D` raw.
2. **Месяц:** `Σ` дневных сумм решения = `F` решения месяца (тест на проход решений).
3. **Сохранение (post, каждый день):** K3 в raw на 100 % тиков, в дни событий и при нормировании; изменяющийся `F_d`.
4. **Один писатель:** архитектурный тест по всем системам и таблицам.
5. **L2:** `Daily228`, threads 1/4/8/16 × ChunkSize 1/8/32, `HashEveryTick` — хеш каждого дня равен. Журнал: все чанки шлют переводы одному `dst`, t16, ChunkSize 1, 20 повторов; граничный тест переполнения в фиксированном порядке.
6. **Порядок дня:** событие с датой `D` и команда в день `D` — потоки `D` при новом владении; событие 1-го числа видно проходу решений дня 1; команда дня 15 действует с 1-го следующего месяца; replay с командой не в день 1 даёт тот же хеш.
7. **События:** отсрочка с ежедневной проверкой, истечение 6/12/36 мес. → `skipped`; Oder–Neisse 1950/1970 `excludes`; базовый прогон — все `fired`, `lag_days = 0`.
8. **RNG:** ключи `Flow` уникальны по дням (30 дней × системы × сущности, без повторов).
9. **Save/load** в день 15 и в день между `D−1` и `D` события → продолжение даёт тот же хеш.
10. **Пин `SliceLegacy`:** без поля `tick_model` — `scenario_hash 2ccb4adb…`, det `824f4ded…`. CI на каждый PR в `src/Singularity.{Kernel,Core,Session}`, пока R4 не покажет > 10 мин; тогда — ночью и на каждом gate (решение Orchestrator по R4). Main `183e47b9…` — на каждом gate M1.
11. **Роли:** каждая система `Daily228` — в `SliceRoles`; `Flow` — `Cadence.Daily`; `LastTickRan` всегда `true` в `Daily228`.
12. **Бюджет:** K4 с флагами п. 29, p95/медиана месяца, p99 дня.
