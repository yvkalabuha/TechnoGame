# ADR-0014 — Session и Test API: единая сборка мира, команды, test mode

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

## Контекст
- [Факт] Решения #57–#60: сейчас только ADR; спайк Godot идёт параллельно (TASK-0016); мост — библиотека с интерфейсом, допускающим вынос в службу; тик = 1 день.
- [Факт] Сейчас мир собирает Lab (`LabModel`), команд игрока в Core нет; ADR-0006 (ввод — только команды в начале тика) — PROPOSED.
- [Факт] Ревью critic (gate): риск второго пути сборки мира, недетерминированного порядка команд, разрастания Test API, утечки тестового кода в release.
- [Факт] Спайк TASK-0016 выполнен (`docs/architecture/spikes/godot-compat.md`, прогон 2026-11-03): ядро работает внутри Godot в редакторе и в release-экспорте; хеш после 1000 тиков побитно совпадает с чистым .NET-хостом; модель «поток симуляции + неизменяемые снимки» и исключение тестового кода из release проверены. Версия Godot, флаги MSBuild и детали CLI — в отчёте спайка; закрепляются в будущем ADR клиента. Этот ADR задаёт только требования к результату.
- [Факт] Повторный gate-ревью (critic + advocate, 2026-11-03) учтён ниже.

## Решение (предложение)
**Сборки.** `Singularity.Kernel ← Core ← Session ← Testing`. Core не знает Session и Testing; Session не знает Testing.

1. **Session — единственный путь сборки мира из систем Core.** `Singularity.Session` содержит: сборку мира (моды + сценарий через загрузчик ADR-0010 → таблицы + `TickRunner` → фаза инициализации перед тиком 0, ADR-0006), очередь внешних команд, `Step(n)`, представления чтения (`IReadOnlySession`). Мир, собранный из систем Core (`gametest`, xUnit-тесты уровня 2, Godot-клиент, прогоны Lab над Core), строится **только** через Session. Прототипы Lab могут строить собственные таблицы, но их результаты **никогда не считаются свидетельством** поведения Core.
2. **Команды.** Любое изменение мира после старта — типизированная доменная `ICommand` с валидатором.
   - Внешние команды (игрок, harness) поток симуляции при получении относит к ближайшей границе тика (`apply_tick`). Решения систем (ИИ) — состояние в таблицах, а не элементы очереди; они применяются в начале следующего активного тика своей системы (ADR-0006).
   - Порядок применения — `(apply_tick, source_class, source_id, local_n)`: `source_class` — фиксированный порядок классов источников, `source_id` — стабильный id источника, `local_n` — номер команды у этого источника, хранится в самой команде (для внешних) или в таблицах (для систем). Глобального счётчика `seq` вне таблиц нет.
   - Журнал replay пишет **только внешние** команды с назначенным `apply_tick`, а не время отправки. Решения ИИ воспроизводит симуляция.
3. **Patch/override ADR-0010 — только до тика 0**, через загрузчик (оверлей-мод тестового сценария). После тика 0 — только типизированные доменные команды; общего `TestPatch` над колонками нет.
4. **Время** продвигается в тиках (днях, #60); календарные единицы не мельче дня; часов нет. `Step` синхронный, выполняется на потоке симуляции и возвращает **текущие тик и дату** и **`StateHash` таблиц после последнего выполненного post** (пустые тики post не выполняют, ADR-0006). Ожидание по таймеру запрещено.
5. **Модель потоков.** Поток симуляции — единственный владелец таблиц и `TickRunner`. Главный поток клиента, UI и harness колонки `Table` не читают (запрет контракта). Чтение — только через неизменяемые узкие доменные снимки (read views). Поток симуляции собирает их после post **непустого** тика и публикует одной атомарной записью ссылки, без блокировок. Внешние команды — через очередь, которую поток симуляции разбирает на границе тика.
6. **Поверхность Test API.** `ITestSession : IReadOnlySession` добавляет Pause/Resume/Step/AdvanceTo, LoadScenario, LoadSave/CreateSave (ADR-0013), Submit(command). Представления чтения — только для существующих систем, без заглушек. Владение: DoD каждой новой доменной системы включает её read view и тест на него; systems-architect ревьюирует изменения поверхности; любое изменение поднимает `test_api_version`. `active_country` не вводится, пока нет механики игрока.
7. **Транспорт (часть G, после клиента).** TCP loopback, только IPv4 `127.0.0.1`, порт 0 (выбирает ОС); `localhost` не используется, сокет не dual-stack (`AddressFamily.InterNetwork`), чтобы не слушать `::`. Токен 256 бит через переменную окружения, сравнение за постоянное время (`CryptographicOperations.FixedTimeEquals`). Один клиент; второе подключение отклоняется. JSON с префиксом длины, ≤ 1 MiB, рукопожатие с `protocolVersion` и таймаутом [Предл.: 5 с]. Unix sockets / named pipes — позже, за интерфейсом транспорта.
8. **Мост (#59).** `GameTest.Client` — библиотека за интерфейсом (`IGameTestClient`), который можно реализовать отдельной службой без изменения вызывающих (`gametest`, `GameTest.Mcp`).
9. **Требования к клиенту (результат, а не способ).** Способы, проверенные спайком, — в его отчёте §4–§8; выбор закрепляет будущий ADR клиента.
   - (а) В распространяемой (release) сборке клиента нет `Singularity.Testing` и его типов; тестовый режим в ней не включается никаким флагом.
   - (б) Kernel/Core/Session внутри клиента собраны с оптимизацией: время тика не хуже чистого .NET-хоста Release (порог — в «Проверке»).
   - (в) L1 между хостами: хеш таблиц после N тиков в клиенте равен эталону headless-раннера.
   - (г) Версия Godot — по решению #57.
10. **CI части G** — только Linux; Windows/macOS — вручную или ночью. Headless-часть ядра — на 3 ОС, как сейчас. CI проверяет **произведённые файлы** (сборки, хеш, список типов), а не код возврата инструментов: спайк показал, что экспорт Godot может завершиться с кодом 0 без сборок .NET (P3).
11. **Демонстрация брифа §22** (реальное окно, заказ через UI) **не считается выполненной**, пока нет Godot-клиента, команды игрока и экрана производства. Отчёты headless несут `target: core-headless`.

## Предусловия
- ADR-0004 (RNG без состояния) — ACCEPTED-предпосылка для replay и сохранений.
- ADR-0006 (команды в начале тика, тик = день, фаза инициализации) — должен быть принят до реализации пп. 1–5.
- ADR-0013 — формат LoadSave/CreateSave.

## Рассмотренные альтернативы
- **Test API прямо над Core, Lab строит мир сам.** Меньше сборок, но два пути сборки мира расходятся незаметно. Отклонено для мира из систем Core; прототипы Lab — вне этого правила (п. 1).
- **`TestPatch` (patch-операции ADR-0010 во время игры).** Гибко, но это запись в колонки в обход доменной логики и валидаторов. Отклонено: patch только до тика 0.
- **Тик команды задаёт клиент.** Проще, но гонка с потоком симуляции даёт недетерминированный журнал. Отклонено.
- **Глобальный счётчик `seq` у потока симуляции.** Прост, но это состояние вне таблиц: его надо сохранять и восстанавливать, а решения ИИ попадают в журнал. Отклонено в пользу ключа `(apply_tick, source_class, source_id, local_n)`.
- **Транспорт:** WebSocket (лишний слой); stdin/stdout (смешивается с логом Godot); Unix sockets сейчас — путь сокета ограничен по длине (`sun_path` ≈ 104–108 байт, во временных каталогах CI легко превысить), а на Windows поддержка `UnixDomainSocketEndPoint` в .NET зависит от версии ОС [Предп., проверить при части G]. Выбран TCP loopback.
- **Мост как долгоживущая служба (бриф §5).** Избыточно сейчас; интерфейс оставляет путь (#59).
- **Закрепить в этом ADR версию Godot, флаги MSBuild и синтаксис CLI.** Отклонено: это детали клиента, они меняются с версией Godot; здесь — только требования к результату (п. 9).

## Последствия
- Плюсы: один контракт для headless, Lab над Core и Godot; прогон воспроизводится как `scenario_hash + seed + журнал внешних команд`; поверхность API растёт только вместе с системами.
- Минусы: прогоны Lab над Core переводятся на Session (работа при реализации); каждая новая система несёт read view и тест.
- Обязательно: без `double` в Session и Testing вне форматирования; числа — `Fx6.Raw`, в JSON — точная десятичная строка.

## Проверка
- Архитектурные тесты: Core не ссылается на Session/Testing; Session — на Testing; код Lab, использующий системы Core, не создаёт `TickRunner`/таблицы мира мимо Session; нет `double` в Session/Testing вне форматирования.
- Тест порядка команд: команды, отправленные из разных потоков, применяются в порядке `(apply_tick, source_class, source_id, local_n)`; replay журнала внешних команд даёт тот же `StateHash`, тик и дату.
- Тест `Step`: после пустых тиков возвращается хеш последнего post и текущие тик/дата; read view после пустого тика не публикуется заново.
- Тест: patch/override после тика 0 отклоняется.
- Тест версии: снимок публичной поверхности `ITestSession`/read views сравнивается с эталоном; изменение без повышения `test_api_version` валит CI.
- Транспорт (часть G): `LocalEndPoint` слушающего сокета — `127.0.0.1` (не `::`, не `0.0.0.0`); подключение с неверным токеном, второе подключение и рукопожатие, не завершённое за таймаут, отклоняются.
- Release (п. 9а): CI-тест экспорта — среди произведённых файлов нет `Singularity.Testing.dll`; инспекция метаданных игровой сборки не находит тестовых типов и ссылки на `Singularity.Testing`; release-экспорт с флагом тестового режима не включает его, Debug — включает.
- L1 (п. 9в): хеш таблиц после N тиков в Godot-экспорте равен эталону headless-раннера.
- Производительность (п. 9б): медиана времени тика ядра в release-экспорте клиента **≤ 1,3×** медианы чистого .NET-хоста Release на той же машине и том же мире (в спайке без исправления было 2,5–3×, с исправлением — в пределах шума).

## Разногласия
- critic (первый gate-ревью) требовал единственного пути сборки мира без исключений, включая Lab. advocate (п. 9 повторного ревью) — смягчить: прототипы Lab строят свои таблицы. Orchestrator принял позицию advocate: правило действует для мира из систем Core, а прототипы Lab не считаются свидетельством поведения Core (п. 1). Остаточный риск: прототип Lab разойдётся с Core, и его результат по ошибке примут за свойство Core. Защита — архитектурный тест и маркировка отчётов Lab.
