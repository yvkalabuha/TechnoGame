# ADR-0023 — DeepSeek third voice (2026-11-18)

Record: tools/llm_worker/runs/gate-ADR-0023-adr-0016-benchmark-rules-amendment-e15a8bdd-third.json

STATUS changes_requested: 3 high, 4 medium, 2 low
  [high] Rust-port comparison protocol (ADR-0023 §1.10): ADR-0016 §4 requires exactly 10 processes per version and a median of 10 process medians. ADR-0023 §1.10 applies the repeat/exclusion gate of §1.3–1.5 to each of those 10 processes. If a process is excluded after three flagged attempts, fewer than 10 remain; the ADR does not say whether to replace it, accept fewer processes, or abandon the comparison. That can silently invalidate the language trigger.
  [high] X=10 MiB margin calculation (§2.3): The stated upper estimate is 8.5 MiB of nodes plus 1 MiB remaining snapshot = 9.5 MiB. Adding the stated ~5% for array headers and alignment gives about 9.975 MiB. The table nevertheless claims a ~5% margin for X=10 MiB; the actual margin against 10 MiB is only about 0.25%. The main arithmetic justification for choosing 10 MiB over 8 or 16 MiB is therefore wrong.
  [high] Noise and outcome after excluding flagged processes (§1.5–1.7): Noise and the outcome are computed only on accepted processes, while up to 20% of point A may be excluded. EXP-0007 shows the failure mode: 3 of 15 processes carried the noise; without them noise fell from 11.8% to 4.2% and the median moved only slightly. Under ADR-0023 those 3 processes can be excluded (exactly 20%, not more than 20%), so the main noise gate can pass on a machine that was not quiet. Sensitivity is only a label for PASS, not a condition on the outcome.
  [medium] TASK-0106 scope does not explicitly own the split `--mode alloc` probe: ADR-0023 §2.3 and its consequences assign the split `--mode alloc` probe (tick path vs snapshot path; Snapshot without nodes vs nodes) to TASK-0106. The linked TASK-0106 description covers EXP-0008 P10 and the TASK-0103 review findings (alloc JSON provenance, re-hash, lab-cli row, smoke test), but not the split probe needed to confirm X. The ADR notes a fallback to TASK-0103 step 2, but no linked task currently states that scope.
  [medium] CI gen2 check after the allocation-threshold split: ADR-0016 'Проверка' CI allocation job includes '0 сборок gen2 за окно'. ADR-0023 replaces the CI allocation description with two byte thresholds and 0 LOH, but does not state whether the CI gen2 check remains, is split by path, or is dropped. That leaves a regression risk exactly where the P8 change is being made.
  [medium] TASK-0103 acceptance allows an explained allocation gap: TASK-0103 acceptance says steady-state allocations must be at or below the P8 limit 'or the gap is explained with a follow-up item'. ADR-0023 says the TASK-0103 P8 criterion is read per §2 (tick path ≤1 MiB/month, snapshot ≤X, 0 LOH, 0 reference objects per node, 0 gen2). These are not the same gate. EXP-0008 P0 can therefore start after TASK-0103 is closed while P8 is still unmet.
  [medium] 5% foreign_cpu threshold is not justified against EXP-0007 load: On a 16-logical-CPU machine, one fully busy foreign core is 6.25% of total CPU. A 5% foreign_cpu threshold is therefore near one fully busy core, while EXP-0007 attributes noise to bdsecd, IDE and browser. The ADR says the number is EXP-level calibration but provides no calculation showing that 5% catches the load that produced the 11.8% noise.
  [low] ADR-level number list is incomplete: The summary and §1.9 say only 10%, 20%, 2 repeats and the seed-majority rule are ADR-level, but the ADR also fixes X=10 MiB, 0 LOH/85,000 B, 0 reference objects per node, 0 gen2, GC pause ≤2%, and specific test expectations. This makes change control ambiguous: it is unclear which numbers require a new ADR and which may move with a new EXP pre-registration.
  [low] P8 violation is called a criterion but has no outcome effect: §2.4 calls GC pause ≤2% and the other P8 limits criteria, while §2.5 says violating P8 does not change the ADR-0016 §4 outcome and only creates a follow-up task. This is a different status from an outcome-affecting criterion and should be labelled consistently.
