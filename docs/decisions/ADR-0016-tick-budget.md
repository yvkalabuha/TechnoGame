# ADR-0016 — Бюджет тика

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

Ревизия 4 (2026-11-17), по итогам gate:
- раунд 1: `docs/reviews/adr-0016-critic.md`, `adr-0016-advocate.md`, `adr-0016-deepseek.md`;
- раунд 2: `docs/reviews/adr-0016-round2.md` (раздел «Orchestrator resolution»);
- решения владельца #269–#272.

Вывод чисел и метод — `docs/architecture/notes/tick-benchmark-m0.md`.

## Контекст

- MS-M0 закрывается замером тика (#267).
- Замер питает триггер языка RR-0001 §5. ADR-0001 пересматривается при нехватке производительности, но бюджета не было.
- Решения владельца:
  - #269: максимальная скорость — 1 игровой месяц/с; ядру — половина, ≈ 500 мс на месяц; полный масштаб — ~200 стран и ~200 регионов; железо — i7-11800H (8C/16T, 31 ГБ);
  - #270 — триггер языка;
  - #271 — статистика бюджета;
  - #272 — любой валидный исход закрывает M0.

## Решение

### 1. Бюджет (обязательный)

[Факт #269, #271] Время ядра на игровой месяц `T`:
- **p95 ≤ 500 мс и медиана ≤ 400 мс**;
- при threads = 8, на i7-11800H, в условиях п. 5.

Другие точки:
- **t1 — обязательная записываемая точка**: она нужна для диагностики и пропускной способности Lab, но исход не определяет;
- t4 и прогон под синтетической фоновой нагрузкой клиента (2 потока) — справочные точки «слабая машина» (#271);
- [Предп.] уложатся ли в бюджет более слабые машины, этот ADR не утверждает.

**Полный масштаб.** ~200 акторов (стран), ~200 регионов, ~2000 узлов знания. **Провинции (#195, волна 3) не входят**: для них бюджет пересматривается новым ADR.

**Что входит в `T`.** Всё, что ядро делает за месяц в полном `ViewMode`:
- `Compute`/`Merge`/`Post` систем, включая инварианты и метрики фазы post (ADR-0006);
- копия и swap таблиц;
- планировщик;
- `StateHash`;
- снимок видов;
- применение команд.

**Что не входит.** Загрузка данных, сборка мира и метрические CSV-синки Lab.

### 2. Как получается `T`

**Обязательный режим — дневной (#228).** В нём каждый день — непустой тик: копия и swap, post, хеш, снимок.

**Основной путь — прямой замер.** Нужно light-изменение Session (задача T1a в записке):
- execution-only флаг в `SliceRunConfig`; он не хешируется и колонок не добавляет;
- флаг регистрирует пустую дневную систему;
- при флаге Session делает хеш и снимок на каждом непустом тике runner.

`T_i` замеряется прямо на реальных таблицах сессии в точке (N = 200, узлы 2000, t8, полный `ViewMode`).

**Запасной путь — без изменения Session.** Используется, только если T1a отклонят. Ежедневная no-op-команда (неизменные `set_budget_shares`) делает тик непустым для Session: хеш, снимок и команды идут каждый день. Но runner без системы к сроку таблицы не копирует. Тогда:
- `T_i = M_i^cmd + 29·k_copy,p95`;
- `k_copy` — копия и swap Kernel-`Table` той же формы (200 строк, те же число и типы колонок);
- `k_copy` замеряется в том же процессе после замера месяцев: прогрев 100, затем 1000 повторов, берётся p95.

**Проверка формулы.** При прямом пути записываются месячный режим `M_i` и `k` (копия + хеш + снимок). Расхождение `T` и `M + 29·k_p95` записывается и диагностирует метод, но исход не определяет.

**Составляющие.** Месячный и дневной прогоны с одним seed детерминированно проходят одни и те же состояния. Поэтому месяцы `i` спариваются:
- `k_i = (T_i − M_i) / 29`;
- `K_d,i = 30·k_i` — Kernel + Session за месяц в дневном режиме;
- `S_i = M_i − k_i` — системы.

Inclusive-профиль систем записывается для сверки. На запасном пути: `k_i = k_copy,p95 + (M_i^cmd − M_i) / 29`.

[Предп.] в #228 сами системы выполняются по дням, а в срезе они месячные. Поэтому `S` — нижняя граница: фиксированная цена вызова умножится на 30.

### 3. Раздел бюджета (диагностический) [Предл.]

| Часть | Доля |
|---|---|
| Системы типа среза | ≤ 100 мс |
| Kernel + Session (`K_d`) | ≤ 50 мс |
| Резерв | 350 мс |

- Доля резерва на классы изделий 2…20 — `19·P`, где `P` — цена Products на один класс по профилю.
- **Правило (critic M4).** Если `S + K_d + 19·P > 500` мс, до кода E1 обязателен ADR пересмотра раздела.
- Раздел предварительный до E1. Превышение доли — повод оптимизировать или пересмотреть раздел, но не язык (#270).

### 4. Исходы

`S` читается по p95 месяцев, `K_d` — по медиане.

| Исход | Условие | M0 (#272) | Действие |
|---|---|---|---|
| INVALID | Для одного seed `StateHash` в конце прогона различается между threads 1/4/8/16 или между `ChunkSize` 1/8/32 (ADR-0002); или нарушены условия п. 5 | блокирует | Исправить, повторить |
| INCONCLUSIVE | Шум > 10% на прогоне без троттлинга (п. 5) | блокирует | Исправить харнесс или условия |
| PASS | Бюджет п. 1 выполнен; `S ≤ 100` и `K_d ≤ 50` | закрывает | ADR-0001 в силе |
| WARN | Бюджет п. 1 выполнен; `S > 100` или `K_d > 50` | закрывает | Раунд оптимизации в следующей вехе; выход — ниже |
| FAIL | Бюджет п. 1 нарушен: p95 > 500 или медиана > 400 | закрывает | Первая задача следующей вехи — раунд оптимизации; затем ADR переделки по профилю; триггер #270 оценивается там |

**Флаг действия `K_d > 150` мс** (при любом из исходов PASS, WARN, FAIL; не отдельный исход). До кода #228 обязателен Kernel-ADR: инкрементальный хеш, копирование только изменённых колонок, хеш не каждый день.

**Ожидаемый риск.** [Предп.] По прогнозу записки PASS при `S ≤ 100` маловероятен. Ожидаемый исход — WARN или FAIL.

**Записываемая диагностика** (без цепочки причин):
- доля пауз GC (`GC.GetTotalPauseDuration()`) от времени замера;
- наклоны log-log для `T` и `S` по N и по узлам;
- `S(t1)/S(t8)`;
- `K_d`;
- top-10 методов по exclusive CPU.

**Раунд оптимизации** (первая задача следующей вехи при WARN или FAIL):
- одна TASK (developer) на top-3 горячих места по **exclusive CPU**;
- timebox [Предл.] 3 рабочие сессии;
- golden-хеши не меняются;
- потом повторный замер по тому же манифесту и протоколу; исход переклассифицируется по той же таблице;
- если timebox кончился, замеряется то, что смёрджено.

**Выход из WARN.** После раунда p95 сравнивается с 500, медиана — с 400, каждая отдельно; доли — с 100 и 50.
- Всё выполнено — исход PASS.
- Иначе до кода E1 обязателен ADR пересмотра раздела с оценками систем резерва по удельным ценам.
- Каждая новая система заявляет удельную цену. Если измеренные `S + K_d` плюс заявленное превышают 500 мс, назначается gate.

**Маршрут языка — только тест Rust-порта (#270, critic M3)**, пре-регистрируется сейчас. Оценивается в следующей вехе после раунда оптимизации, если `T` всё ещё нарушает бюджет п. 1.
- Выбор кода: top-1 метод (с телом ≤ 200 строк) по exclusive CPU внутри `S` на повторном замере. Его доля в `T` должна быть ≥ 20%, иначе порт не делается и маршрут — ADR переделки.
- Порт сравнивается с **оптимизированной** C#-версией: тот же вход (дамп входа метода из прогона), Release / `--release`, одна машина, медиана ≥ 10 прогонов каждой версии.
- Если порт быстрее в ≥ 2 раза, открывается пересмотр RR-0001 (gate+research, решает владелец). Иначе — ADR переделки.

### 5. Условия замера и шум

**Сборка и среда:**
- Release;
- одна точная версия .NET 10, runtime и SDK записываются;
- workstation concurrent GC (`DOTNET_gcServer=0`);
- TieredPGO по умолчанию;
- ОС — как на i7, записывается.

**Машина:**
- питание от сети, профиль «производительность»;
- один процесс на машине;
- `ChunkSize = 8` (25 чанков при N = 200).

**Объём:**
- прогрев 24 месяца, замер 120 месяцев;
- 5 процессов × 3 seed, точки перемешаны;
- медиана — медиана 15 медиан процессов; p95 — по всем 1800 месяцам.

**Шум** = (p90 − p10) / медиана по 15 медианам процессов, порог ≤ 10%.

**Троттлинг (critic m1).** Прогон троттлит, если медиана частоты CPU за окно замера ниже 90% базовой частоты i7-11800H. Такой прогон повторяется. Записываются оба прогона, исход определяет первый валидный.

**Оговорка.** [Предп.] Числа .NET 10 для работы внутри Godot (`net8.0`) оптимистичны; точка `net8.0` снимается в Godot-spike после M0.

### 6. Аллокации

- В установившемся режиме (после прогрева) на полном масштабе: **≤ 1 МБ на месяц**, снимок видов включён [Предл.].
- **0 сборок gen2 за 120 месяцев.**
- 0 Б в `Compute` каждой системы — цель для BDN `MemoryDiagnoser` (single-thread), если BDN появится. Правило переносится в `.claude/rules/csharp-core.md` отдельно.

### 7. Запись и вторичные ограничения

- Результат — EXP `kind: benchmark`. Пункты 2, 4 и 5 пре-регистрируются до прогона.
- Provenance — по `Provenance.cs` плюс условия п. 5.
- Записываются:
  - удельные цены: мкс на актор-месяц и на узел по каждой системе, `k` на колонку, `P`;
  - пиковая память;
  - дневной тик p99 (справка).
- **Пропускная способность Lab.** Если кампания 1945–2100 (1860 месяцев) при t1 длится больше 10 мин [Предл.]:
  - массовые эксперименты Lab по умолчанию идут на уменьшенном масштабе (N ≤ 24);
  - прогонов полного масштаба — не больше 100 на эксперимент.

## Рассмотренные альтернативы

- **40 мс при «год/с».** Отклонено решением #269.
- **Только 500 мс, без раздела.** Отклонено: не видно места под систему резерва. Раздел оставлен диагностическим (#270).
- **FAIL по доле среза включает Rust.** Отклонено решением #270.
- **FAIL-pending: раунд оптимизации до закрытия M0.** Отклонено: противоречит #272.
- **Цепочка причин, определяющая маршрут FAIL.** Отклонено: см. «Разногласия».
- **`T = M + 29·k` как основной путь.** Отклонено (critic M1): ошибка `k` умножается на 29. Формула оставлена проверкой и запасным путём с `k_p95`.
- **Обязательные t4 или фоновая нагрузка.** Отклонено решением #271; это справка.
- **Отложить бюджет до E1.** Отклонено решением #267.

## Последствия

**Плюсы:**
- 5 однозначных исходов;
- M0 не ждёт оптимизации;
- смена языка требует замеренного выигрыша Rust-порта на заранее выбранном коде.

**Минусы:**
- [Предп.] замер среза — нижняя граница полной игры: нет систем резерва, парных O(N²) взаимодействий, `net8.0`, а клоны подграфа занижают ветвление;
- прямой замер дневного режима требует light-изменения Session.

**Обязательно:**
- новые системы заявляют удельную цену;
- правило `19·P` до E1;
- флаг `K_d > 150` перед кодом #228;
- пропускная способность Lab записывается в каждом EXP полного масштаба.

## Проверка

- `lab bench` (Stopwatch в хосте, ADR-0008):
  - прямой замер в точке (200, 2000, t8) и обязательная точка t1;
  - сетка N 6/24/200 × узлы 180/2000 для наклонов, вариант со случайными перекрёстными рёбрами;
  - потоки 1/4/8/16;
  - проверка хеша между потоками и `ChunkSize`.
  Результат — EXP `kind: benchmark`.
- Проект BenchmarkDotNet создаётся, только если по Stopwatch `K_d > 5` мс (10% доли).
- CI:
  - на каждый PR — аллокации на тик при N = 24 и отсутствие gen2;
  - base/head на одном раннере в одном job, порог [Предл.] +25%, при превышении — повтор;
  - абсолютный бюджет — только на i7, вручную на каждой вехе, записью EXP.
- Бюджет пустых тиков ADR-0006 в силе.

## Разногласия

Отклонено или изменено (раунды 1–2), с причинами.

**Раунд 2:**
- **Critic M2, m3, m6** — фиксированный протокол цепочки причин, Kernel первым при `K_d ≥ S`, Rust-порт только на маршруте «вычисления». Цепочка снята по advocate. Защита от необоснованной смены языка держится на пре-регистрированном тесте Rust-порта (critic M3), а не на классификации причины. Вместо цепочки диагностика записывается, и ADR переделки пишется по профилю. Критик считал цепочку нужной для однозначности маршрута. Разногласие сохранено (решение Orchestrator, `adr-0016-round2.md`).

**Раунд 1:**
- **Critic 2** (язык по `S(t1)` против 8 × 100 мс) и **Critic 5** (триггер по доле среза) — сняты решением #270.
- **Critic 6** (ось классов изделий 1/5/20): класс зашит в `SliceWorld.ProductClass`, ось требует правки Session. Вместо оси — `19·P` и правило п. 3.
- **Critic 10, Advocate 4** (обязательные t4 или фон) — справка по #271. t1 записывается обязательно, но исход не определяет.
- **Critic 13** (точка `net8.0` в M0): нужен multi-target. Вместо неё оговорка и замер в Godot-spike.
- **Critic 9** («0 Б на систему» как правило ADR): цель BDN, правило — в `csharp-core.md`.
- **Advocate 2** (обязательный дневной тик p99 ≤ 25 мс): #271 задаёт только статистики месяца; p99 записывается.
- **Advocate 10** (порог памяти): отложен до волны провинций, пока только запись.
- **DeepSeek:** бюджет кадра клиента — вне рамок ADR; доверительный интервал не нужен, так как замер прямой.
