## Краткий вывод
- [Предл.] Игрок (по умолчанию ИИ) собирает проект из 5 слотов. Ограничений два: (1) альтернатива доступна, если известны её узлы и PRC; (2) у планера есть **порог платформы** по поколению. Двигатель и прочие слоты не ограничены поколением (#81): пример — МиГ-21-2000.
- [Предл.] **Поколение выводится из состава.** `g_p` — поколение платформы: наибольшее известное APP g, порог планера которого выполнен. `gen(d) = min(g_p, rank(engine) + 1)` (#70). Новый двигатель на старой платформе поднимает `perf` (поле P ключа), но не `G`.
- [Предл.] **Цена — по фактическим компонентам.** Процессная часть делится на два блока: силовая установка (двигатель, горячая часть, компрессор, форсаж) с множителем по рангу двигателя и планер с множителем по `g_p` (правило R-PS2). Сплав считается по рангу двигателя. `W`, штат КБ, часы сборки и покупное — по `g_p`. `complexity`, `D0`, `upkeep` — по фактическому `prc_set`.
- **Главная находка (высокая):** в v0.10 размер `D0` почти не влияет на игру: выявление и штраф готовности нормированы на `D0` (A31, `readiness`). Поэтому ось «надёжность» из #82 сводится к работе на исправление. [Предл.] Правка A35: штраф готовности от `D/D_ref`, `D_ref = d0·complexity`. Нужен gate.
- **Риск доминирующей сборки (высокий):** при зрелом производстве максимальная сборка выигрывает по `perf`/стоимости жизненного цикла (пример §5: 0,170 против 0,111). Выбор живёт только в окне освоения и при дефиците сплава. Это допустимо («новое со временем вытесняет старое»), если окно длинное. Проверяют это диагностики §8.
- [Предл.] ИИ: три пресета («превосходящий», «технологичный» с учётом сплава, «адаптивный» = больший `FV`). Политика детерминирована, без RNG, все числа заморожены до калибровки. В HYP-0002 нет «освежения» проекта той же платформы, поэтому сборки типа МиГ-21-2000 у ИИ редки (§7).

## 1. Слоты, доступность, совместимость (срез 1)
Данные слотов — `product_class.md` §1 (без изменений, кроме поля порога платформы).
- **Доступность** `avail(a, s)`: альтернатива слота s доступна актору a, если известны все её `requires_nodes` (для группы `|` достаточно одного члена) и все PRC её `prc_set`. Неизвестная альтернатива видна на карточке серой с причиной из `why_not` (слой KNOWLEDGE, рычаг `research_priority`). Выбрать её нельзя.
- **Порог платформы** [Предл., данные]: `platform_min_rank[g]` — минимальный ранг планера для APP g: G1 → `af_straight` (1), G2 → `af_swept` (2), G3 → `af_milled` (3), G4 → `af_titanium` (4). Порог G4 стоит на титане потому, что альтернативы под ENG 29 `mach2_airframe_g4` в данных нет (F-PI2). Это решение данных для research-scientist и simulation-engineer.
- **Совместимости между слотами в срезе 1 нет:** любые доступные альтернативы сочетаются. Физически странные сочетания (ТРДД g4 с кованой NiCr горячей частью) разрешены и наказываются только малым `perf`. Совместимость по интерфейсу (#63), модернизация (#64) и двигатель как отдельный класс изделия (#61) появятся во втором срезе.
- **Когда выбирается состав.** Состав задаётся при создании проекта (стадия П) и потом не меняется. Чтобы сменить состав, нужен новый проект (работа `W` с нуля). Команда — `compose_design(requirement_id, {slot → alt_id})`, её проверяет валидатор: доступность и порог платформы. ИИ подаёт ту же команду (детерминизм: выбор — это команда, а не скрытое правило).

## 2. Поколение проекта (#70)
[Предл.]
- `g_p(d) = max{ g : APP_g известно актору на момент создания ∧ rank(airframe) ≥ platform_min_rank[g] }`. Значение фиксируется при создании проекта. APP G1 известно всем, у кого есть проекты, поэтому `g_p ≥ 1`.
- `gen(d) = min(g_p, rank(engine) + 1)`. Если двигатель отстаёт на одно поколение, поколение не падает; если на два и больше, `gen = rank + 1`. Двигатель новее платформы `gen` не повышает.
- Поле `gen(d)` в контракте §9.1 сейчас определено как «поколение APP-узла». Его нужно заменить этой формулой (контракт v2.4, systems-architect). Условие #62 («освоено самим») уже входит в `fielded`: там нужно `mastered` для всего `prc_set`. Оговорка: PRC двигателя (54, 44) одинаковы у всех рангов. Поэтому «освоение двигателя» в срезе 1 означает освоение 54/44 и PRC горячей части и компрессора. Это ограничение среза 1, а не новая проблема.
- Следствие для метрик: дешёвая сборка с двигателем на поколение ниже даёт тот же `G`. Тогда смены лидера чаще решаются полями `T`, `N`, `P`. Это нужно проверить разложением по полям (§5.1 спеки) при старом и новом правиле.

**Почему каждая сборка разумна:**
- **A** — для богатого актора, у которого охлаждаемые лопатки (43, 52) уже идут или скоро пойдут. Сборка даёт наибольшие P и T без знания G4-платформы и при зрелом производстве лучше всех по `FV`. Плата: самый долгий проект, наибольшие `D0` и работа исправления, сплав в 4,4 раза дороже, чем у C, процессы tier 5 сразу после открытия — «на грани» или «не можем». Если они не допущены, серии нет.

## 6. Пресеты и политика ИИ (HYP-0002)
[Предл.] Функция `compose(preset, a, snapshot t−1)` детерминирована, RNG не использует, ничья решается рангом, затем `alt_id`. Цель ИИ — `g*` = новейшее известное APP (правило выдачи `Requirement` §4 без изменений). Планер — не ниже `platform_min_rank[g*]`.
1. **`superior`** («превосходящий», P1): в каждом слоте — наибольший ранг из `avail` (сплав и `yield` не учитываются: это доктрина «качество»).
2. **`producible`** («технологичный», P2): в каждом слоте — наибольший ранг из `avail`, у которого узкий PRC на своём site даёт `yield ≥ y_prod` (0,5). Для двигателя дополнительно `alloy_ok(r)`: `supply_a / alloy_kg[r] ≥ n_service_min / T_field`, где `T_field` = 24 мес. (З, новое, замораживается до калибровки). Если подходящих нет, берётся самая лёгкая альтернатива (для планера — порог платформы). Правило совпадения §1.4 сохраняется: при сборке, равной `superior`, облегчается слот с наибольшим tier в порядке F-PC2; если облегчать нечего — вариант один (F-PC3).
3. **`adaptive`** (P3): из `superior` и `producible` берётся сборка с бо́льшим `FV` (§5.5), как сейчас.
- **Сколько проектов.** Не больше одного проекта на пару (`g_p`, пресет), как в нынешних слотах `(g, вариант)`. **Освежения нет:** если после создания проекта стал известен двигатель лучше, ИИ проект той же платформы не пересобирает. Это сохраняет простоту и сравнимость с v0.10 (вариант с освежением — §7, «не проверяет»).
- **Не под результат.** Входы — `y_prod`, `n_service_min` (уже заморожены) и `T_field`. Все они фиксируются в манифесте до калибровки и, по правилу §4, меняются только новым EXP.
