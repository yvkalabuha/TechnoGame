## 2. Неопределённые требования

1. **Ресурсы проекта.** Кто, кроме AI, пишет код, делает графику, звук, UI. Опыт владельца в программировании и геймдеве. Бюджет и горизонт.
2. **Цель проекта.** Коммерческий релиз (Steam и т. п.), хобби или исследовательский прототип. Влияет на лицензии движков и данных.
3. **Первый проверяемый результат.** Что считается первым «работающим» состоянием: headless-симуляция, визуальный прототип, вертикальный срез.
4. **Модель времени.** Real-time с паузой (тики) или пошаговая. Длина тика (день/неделя/месяц).
5. **Масштаб мира.** Число государств, провинций; модель населения (агрегаты, «pops», агенты).
6. **Победа и поражение.** Есть ли цели, условия конца игры, может ли игрок потерять власть.
7. **Воплощение игрока.** Игрок = «государство как абстракция» или конкретная власть/правитель с ограниченным сроком.
8. **Историческая точность и чувствительные темы.** Реальные страны, идеологии, войны, геноциды, колониализм — как подавать.
9. **Минимальные системные требования.** На каком железе должна идти симуляция.
10. **Визуальный стиль и UI.** Нет требований вообще.
11. **Язык документации.** Русский, английский или смешанный (см. вопрос 4 ниже).
12. **Глубина ИИ государств.** Требование «собственная логика» не формализовано.

## 3. Противоречия и напряжения

| # | Противоречие | Суть | Предлагаемое разрешение [Предл.] |
|---|---|---|---|
| C1 | Объём процесса vs запрет на «иллюзию прогресса» | 16 агентов, 14-шаговый протокол, 13 обязательных документов, 9 шаблонов — до первой строки кода. Риск бесконечного планирования, который сам промт запрещает. | Создать каркас минимально: документы появляются, когда в них есть содержание. Полный протокол — только для фундаментальных решений. |
| C2 | Orchestrator как subagent | В Claude Code subagent не может запускать другие subagents [Предп., проверить в Phase B]. Orchestrator-subagent не сможет делегировать. | Orchestrator = основная сессия + `CLAUDE.md`, не файл в `.claude/agents/`. |
| C3 | Многопоточность + детерминизм + кроссплатформенность | Float-арифметика может давать разные результаты на разных CPU/компиляторах. Это ломает regression-тесты, сравнение экспериментов и lockstep-multiplayer. | Исследовать в Phase B: fixed-point для ключевых величин, детерминированный порядок редукций, фиксированный порядок обработки сущностей. Рано зафиксировать как ADR. |
| C4 | Свобода мира vs ощущение агентности | «Мир живёт сам», «игрок не всемогущ», «правительство может не исполнить политику» — без читаемой обратной связи это воспринимается как случайность и фрустрация. | Ввести принцип проектирования «легибельность причин»: игрок всегда видит, почему решение не сработало. Зарегистрировать как гипотезу. |
| C5 | Симуляционная глубина vs игра | Глубокая модель может дать «таблицу», а не игру. Промт ставит корректность модели первым приоритетом, «интерес» в списке приоритетов отсутствует. | Добавить критерий «игровой ценности» в проверку гипотез, рядом с корректностью. Требует решения владельца. |
| C6 | Два жизненных цикла | Статусы гипотез (7) и задач (12) плюс 14 шагов протокола идей частично пересекаются. | Свести в одну схему: гипотеза → эксперимент → задачи. Явная таблица соответствия статусов. |
| C7 | Моддинг «рано» vs «не усложнять» | Требования совместимы, если разделить слои. | Data-driven формат с первого дня; базовая игра сама загружается как «core mod». Скриптовый API и песочница — позже. |
| C8 | Структура папок до выбора архитектуры | `game/` разбит на 15 доменов до выбора языка и движка. Структура зависит от языка (C# solution, Cargo workspace, CMake). | Утверждать структуру `game/` только после ADR по стеку. Сейчас создавать только процессные папки. |
| C9 | Экономия токенов vs Critic+Advocate на каждой идее | Каждый цикл критики — отдельные контексты агентов. | Critic/Advocate — только для решений уровня ADR и гипотез статуса HYPOTHESIS+. |

## 5. Требуют исследования (вход в PHASE B)

1. **Стек:** Godot / Unity / Unreal / свой движок / гибрид (ядро отдельно + движок только для визуализации). Языки C#, C++, Rust. Лицензии.
2. **Архитектура симуляции:** ECS vs data-oriented таблицы, job system, фазы тика, double-buffered state, детерминизм, fixed-point.
3. **Глобальная карта:** форматы провинций, источники гео-данных, рендер.
4. **Граф технологий:** модели в существующих играх (Stellaris — случайные карты технологий, Paradox, PoE passive tree), формат данных, валидация.
5. **Данные и моддинг:** форматы (JSON/TOML/YAML/собственный), схемы, порядок загрузки, конфликты, опыт Paradox и RimWorld.
6. **Simulation Lab:** хранение результатов (Parquet/SQLite/CSV), анализ (Python + pandas/polars), воспроизводимость.
7. **Тестирование:** property-based тесты, golden-тесты симуляции.
8. **Механизмы Claude Code (актуальная документация):** subagents, skills, `.claude/rules/`, hooks, ограничения вложенности агентов.

## 7. Критические вопросы

1. **Ресурсы и цель.** Кто будет работать над проектом кроме AI? Какой у вас опыт программирования (по окружению похоже на PHP)? Цель — коммерческий релиз или прототип/хобби?
   *Почему критично:* определяет выбор языка и движка (C# проще в поддержке, Rust/C++ — производительнее, но тяжелее для ревью человеком) и лицензии.
2. **Первый milestone.** Предлагаю: **M0 — headless-прототип симуляции** (несколько государств, упрощённые наука/экономика, Simulation Lab с batch-запусками, без графики). Согласны?
3. **Масштаб фреймворка.** Предлагаю **поэтапный запуск**: сейчас — Orchestrator в `CLAUDE.md` + ~8 агентов (Game Designer, Research Scientist, Systems Architect, Simulation Engineer, Developer, Critic, Advocate, Reviewer). Остальные — по мере появления их предметной области (Economy, Geopolitics, Civilization, Modding, QA, Balance). Release Manager и Handoff — как skills, не агенты. Или нужно создать все 16 сразу?
4. **Язык документации.** Предлагаю: документы для вас (vision, GDD, отчёты, ADR) — на русском; файлы агентов, skills, rules — на английском (экономия токенов: кириллица дороже в токенах, и модель точнее следует английским инструкциям). Согласны?
5. **Git.** Разрешаете `git init` в `/var/www/gameDev` (локально, обратимо)? Нужен ли удалённый репозиторий (GitHub) — он нужен для CI-сборок под Windows/macOS?

**Следствия для PHASE B [Предп.]:**
- Код ревьюит не специалист по системному программированию. Читаемость и безопасность языка весят больше, чем пиковая производительность. Это аргумент в пользу C#; Rust и C++ должны доказать необходимость.
- Нет дедлайна. Можно позволить себе правильное ядро (детерминизм, данные) вместо быстрого прототипа.
- Репозиторий публичный. Все исторические и гео-данные должны иметь совместимую лицензию. Нужно выбрать лицензию кода (открытый вопрос, не блокирует).
- Публичный репозиторий даёт бесплатный CI под Windows/Linux/macOS (GitHub Actions).
