- [high] §4 R1 «double в Core запрещён полностью / нельзя вызывать ParamSet.GetDouble» vs §7 R4 и вопрос 2 владельцу: R4 keeps `Singularity.Core.Simulation` — the namespace that contains `ParamSet.GetDouble` — as an allowed exception, and owner question 2 plans to replace `ParamSet.GetDouble` with `GetFx6Raw` "у всех моделей", which means Core models call this double-returning method today. §4 states the opposite ("в Core нельзя вызывать … ParamSet.GetDouble"), and §Последствия asserts "срез M0 уже живёт по нему". Both claims cannot hold. In addition, the ADR never defines whether a call from Core into an exempt double-returning member is flagged by `Core_OutsideR4Exceptions_HasNoDouble`: a `double` return stored in a local is banned by R1, but a nested argument `Fx6.FromDouble(ParamSet.GetDouble(...))` is not obviously caught, so the headline guarantee that Core results do not depend on platform math is either false now or enforced by convention.
- [medium] Запрет не покрывает плавающие SIMD-типы (Vector<T>, Vector128/256<double>, System.Runtime.Intrinsics, Complex): R1/§8 enumerate float, Half, MathF, System.Random, Math.*, generic math and the r8/r4 opcode set. Explicit SIMD code (`Vector256<double>`, `Avx.Multiply`, `Vector.Dot`) compiles without any of those opcodes and without System.Math, so a Core or Kernel system could compute in SIMD double and pass every listed test. RR-0002 §5.2 names SIMD horizontal-reduction order as a determinism source, so this is a scope gap, not a hypothetical one.
- [medium] §7 R4: «только пространства имён … без прав у вложенных пространств», но первая запись — тип ToyFunnel: `Singularity.Core.Science.ToyFunnel` reads as a type inside `Singularity.Core.Science` (the parenthetical calls it "модель EXP-0001"), whereas `Singularity.Core.Simulation` is a namespace containing several types (ParamSet, MetricFormat). The ADR does not state the matching unit used by `CoreArchitectureTests.DoubleExceptions`/`R4Exceptions_AreNotStale`, so "новое исключение — только через ADR" has no defined granularity, and a namespace-level exception silently permits new double code anywhere in that namespace without a new ADR.
- [medium] Критерий единиц (§3) задан только для суммируемых запасов; для цен, коэффициентов и ставок единицы и точность не определены: §3 requires each unit to be chosen so that the world-wide sum over 1910–2100 fits 9.22e12 units with ≥10× headroom. That criterion is meaningless for non-summable quantities: prices, unit costs, rates and coefficients are neither summed nor bounded by it, so the DRAFT gives them no unit and no required precision. With the proposed money unit (millions of 1990 dollars) the quantization step is exactly $1, so a price or flow below $1 (e.g. $0.35 per unit) floors to zero, and floor keeps the bias one-directional. These are exactly the values ADR-0012 curves and market models feed into state.
- [medium] Утверждение «правило проверяется автоматически» неверно для внутреннего ограничения R3 «без a*b ± c над double»: The listed tests verify allowlist membership and the R1/R2 bans. Nothing verifies that the 13 allowlisted members avoid `a*b ± c` over double: alternative E's IL analyzer was rejected, and FmaContractionCanaryTests proves JIT behaviour on its own fixtures, not the absence of the pattern in product code. §Последствия nevertheless claims "правило проверяется автоматически", and R3's "Новый член списка проходит ревью по этому правилу" is then human review only.
- [medium] ARM64 помечен [Факт], но OPEN_QUESTIONS #1 говорит «ARM64 — не проверено», а ci.yml не фиксирует архитектуру runner'а: The ADR records as [Факт, TASK-0009] that the canary is green on "macos-latest ARM64 (CI b0b95cf)". The linked OPEN_QUESTIONS entry 1 still contains "ARM64 — не проверено: нужен контрольный тест"; the ADR notes the line is stale but records no owner, task or acceptance condition to fix it. Separately, ci.yml uses the moving label `macos-latest` with no assertion of process architecture, so the ARM64 leg depends silently on GitHub's label-to-image mapping: if the label resolves to an x64 image or is repointed, the canary still passes and the [Факт] becomes false while OPEN_QUESTIONS keeps saying "не проверено".
- [low] Округление floor выбрано без рассмотрения round_half_even, хотя RR-0002 §5.3 его рекомендует: The ADR cites RR-0002 and adopts floor "везде" for `Fx6`, listing the downward bias as a known minus, but the alternatives table never considers round-half-even (the rule RR-0002 §5.3 recommends for f64→i64 conversions) or truncation. A deviation from the linked research on a rule that touches every arithmetic operation is not traced or argued.
- [low] `related:` во frontmatter не содержит ADR-0005, на который опирается п. 1 решения: §1 states "Колонки таблиц — только LongColumn/IntColumn (ADR-0005); Fx6 хранится как Raw", and the ADR also cross-references ADR-0006/ADR-0013 implicitly, but `related` lists only RR-0002, ADR-0002, ADR-0012, ADR-0017, TASK-0009. Registry traceability for the table-storage rule (which the state representation depends on) is missing.
- [low] «Падение канарейки — блокер релиза» не согласовано с «политика на этот факт не опирается»: §9 asserts both that the policy does not rely on the JIT fact and that a canary failure after a runtime update is a release blocker. If no allowlisted member contains `a*b ± c` (as §9 asserts), a contracting JIT changes no result, so the blocker is a different commitment than the stated non-dependence, and the ADR does not say which governs. The ADR also does not say whether the canary is a proxy for other JIT semantic changes (reassociation, vectorized reductions), which it would not detect.
