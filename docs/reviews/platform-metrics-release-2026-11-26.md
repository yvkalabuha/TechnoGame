## 2. Релизная модель
- [Факт] Сейчас: каждая задача вливается в main через land.py (сборка и тесты на слитом дереве, второе ревью Codex); пакет изменений, меняющих эталоны, — раз в день; CI Linux на каждый push, Windows/macOS раз в сутки. Релизов и тегов нет; клиент запускается из ветки или main.
- [Предл.] Лёгкая релизная модель поверх нынешней (main остаётся местом интеграции, история не переписывается):
  1. **Кандидат (RC).** `release.py rc` отмечает текущий main тегом `rc-YYYY-MM-DD-N`, собирает список задач DONE с прошлого релиза (из реестра) и долгов, открытых за период.
  2. **Целостная проверка RC:** verify.py --full; CI на трёх ОС; регрессия Lab (pace_check, ворота slot_core: GAP36, полосы G2–G4, простой); L2-детерминизм; сборка клиента Godot; общая пачка кадров (с вашего разрешения); при желании — ваша короткая партия.
  3. **Отчёт RC** docs/releases/rc-….md: что вошло, результаты каждой проверки, найденные дефекты (каждый — в каталог ошибок), метрики периода.
  4. **Одобрение** — вашим ответом в окне вопросов.
  5. **Релиз:** тег `v0.N`, сборка клиента (экспорт Godot для Linux, при необходимости Windows) в папку релизов вне git, заметки к релизу простым языком.
  6. **Откат:** дефект в RC — RC отклонён, на main исправление (или `git revert` влитых задач, без переписывания истории), новый RC. Дефект после релиза — запуск предыдущего тега, исправление, новый релиз. Каждый откат — запись в каталог ошибок с причиной.
- Частота [Предл.]: перед каждой вашей партией и не реже раза в неделю.
- Плюсы: вы играете в проверенную сборку, а не в «что сейчас в main»; видно, что именно поменялось; откат на прошлый релиз за минуту; отчёты копятся для анализа.
- Минусы: проверка RC — 30–60 минут машины плюс пачка кадров; для одного владельца лишний шаг, если партий мало.
- Цена: около дня работы (release.py, шаблон отчёта, skill /release, сборка клиента).
