# Дневной режим: параллельные Inputs (F4), переиспользование view (F7), StateHash в дневном режиме

> Автор: systems-architect, 2026-11-17. Основа: `docs/simulation/tick-profile-m0.md` (§4 F4, F7, F8), ADR-0002, ADR-0006, ADR-0013, ADR-0014, ADR-0016, DECISIONS_LOG #228.
> Статус: записка с предложениями. Код не менялся. Пункт 3 — набросок ADR уровня gate+research; файл ADR создаёт Orchestrator через `/new`.

## Краткий вывод
- **F4.** [Предл.] Брать **вариант A**: `ViewBuilder.Inputs` параллельно по акторам, каждый поток пишет только слот `rows[a]` локального массива. Это та же схема, что `_failures[chunk]` в `TickRunner`. Правило «compute пишет только свои колонки» не задето: это фаза чтения на потоке симуляции, состояние не пишется. **Вариант B (Interlocked-мемо) отклонить**: общий изменяемый кэш пишут потоки разных чанков, а ключ «тик снимка» даёт устаревшее значение (команды, `ApplyDeals` и `WhyNot` работают внутри одного тика). Точная спецификация — §1.
- **F7.** [Предл.] Переиспользовать `Actors` прошлого снимка **только** на тике, где не было месячного шага и команд, а из систем работал лишь view-нейтральный `DailyProbeSystem`. **Ловушка:** `Decisions.Closes[].Reason` зависит от флага `stepped`. Дневной снимок, построенный заново, даёт `LineCloseReason.None`, а снимок месячного тика — настоящие причины. Наивное переиспользование меняет view, и предложенный в профиле ассерт «снимок дня == построенный заново» упадёт. Решение — §2. Замечание ревьюера (`Inputs`/`Step` == null в середине месяца) — **по контракту** (`SliceViews.cs`: «null if this tick ran no monthly step»). Но при #228 клиент, который опрашивает view, их почти не увидит. Предлагаю отдельное light-изменение поверхности (F7b).
- **Хеш.** [Предл.] SHA-256 остаётся каноническим, байтовый формат не меняется, все golden-хеши остаются в силе. Меняется **расписание**:
  - `LastHash` считается лениво, по запросу, и кэшируется до следующего непустого тика;
  - обязательная контрольная точка — тик месячного шага и тик с внешней командой;
  - ежедневный хеш включает execution-only флаг для тестов и Lab.
  Инкрементальный хеш (Merkle) и XXH3 сейчас отклонить: они меняют формат и golden, а при #228 грязными будут почти все колонки каждый день.
- **Важная находка.** [Факт: `hash-copy.txt` в профиле] `CopyCurrentToNext` стоит 1,88 мс × 30 = **≈ 56 мс/мес**. Это **больше всей доли `K_d ≤ 50` мс** ещё до хеша и снимка. С любой схемой хеша `K_d` останется выше 50 мс (исход WARN по ADR-0016), пока копирование не станет дешевле. Без смены расписания хеша `K_d` ≈ 30 × (8–10 + 1,9) ≈ 0,3 с > 150 мс: срабатывает флаг действия ADR-0016 §4, и Kernel-ADR обязателен до кода #228.

## 1. F4 — параллельные `ViewBuilder.Inputs`

**Почему не B.** [Факт: код]
1. Мемо `EffortAllocation?[]` по актору пишут рабочие потоки `Parallel.For` из **разных** чанков. Сайт актора может лежать в чанке, который не владеет строкой актора. Это общий изменяемый буфер, то есть прямое нарушение правила `csharp-core.md` («writes only to its own columns or per-chunk buffers»).
2. Ключ «тик снимка» недостаточен. Внутри одного тика `Current` меняют `ApplyPending` (колонки `cmd.*`) и `Policy.ApplyDeals` (`SliceSession.StepOne`). Публичные `WhyNot`/`CurrentRequirement` можно вызвать между тиками, и они заполнят мемо **до** команд следующего тика. Нужен счётчик версии, который поднимают все пути записи (`Load`, команды, сделки, загрузка сохранения). Это хрупко и не проверяется архитектурным тестом.
3. Ещё одно исключение из ADR-0013 п. 4 (данные вне таблиц), сброс при save/load и replay.
4. Выигрыш B над A — один лишний `Allocate` на актора в месяц. После F3 [Предп.] это ≈ 1 мс CPU × 200 ≈ 25–40 мс стены при t8. Если новый профиль покажет, что это важно, есть **вариант C** без общего кэша: compute Industry пишет нужные поля плана в след-слоты своего сайта (как `_lastRest`, ADR-0013 п. 4), а tooling-часть `Inputs` собирается после `RunTick` из следов. Это раунд 2, не сейчас.

**Спецификация A (для developer).**
- Тело цикла по `a` выносится без изменений в `private static ActorInputsView ActorInputs(SliceWorld w, int a, long month)`.
- `Inputs`:
  - `var rows = new ActorInputsView[n]; var errors = new Exception?[n];`
  - при `w.Config.Threads == 1` — последовательный цикл;
  - иначе `Parallel.For(0, n, new ParallelOptions { MaxDegreeOfParallelism = w.Config.Threads }, a => { try { rows[a] = ActorInputs(w, a, month); } catch (Exception e) { errors[a] = e; } })`;
  - затем бросается исключение с **наименьшим** индексом (`ExceptionDispatchInfo`), как в `TickRunner`;
  - `ImmutableArray.Create(rows)`;
  - `GFront(month − 1)` считается один раз вне цикла.
- **Предусловия.** Ревьюер проверяет каждое по списку вызовов тела. Каждая вызываемая функция — чистое чтение `Current` и неизменяемых layout/параметров, без записи в поля систем и адаптеров. Список: `IndustryInputs.Plan`, `Industry.RestActor`/`Allocation`, `Industry.Alloy`, `Industry.Profile`, `Policy.Budget`/`AlloyDeficit`/`RequirementVariants`/`ClassifyGiveUp`, `SharesOf` (`CommandState.SharesOverride` — колонки, ок), `ProcurementBudget`, `Products.PrcSet`/`IdleMonths`/`GateOpen`/`DefectsHidden`, `ProductsInputs.AdmittedYield`.
- **Запрет для F2.** Кэш `prc_set`/«процесс в плане» строится в merge/post или при применении команды и **никогда** не заполняется лениво при чтении. Иначе A получает гонку. [Факт: grep] Сейчас в Core и Session нет полей-кэшей с ленивым заполнением (`??=` только локальные).
- **Потоки (ADR-0014 п. 5).** Таблицы читает поток симуляции и рабочие, которых он запускает на время синхронного вызова, — так же, как `TickRunner.RunTick`. Внешние потоки таблиц не касаются. Публикация view не меняется.
- **`TrainingBudget`.** `Plan`/`RestActor` считаются один раз на актора: это локальная переменная цикла по линиям внутри `Purchases`. Работает в compute и пишет только в локальную переменную.
- **Тесты:**
  - `View.Inputs` структурно равен при Threads 1/4/8/16 и ChunkSize 1/8/32. Сравнивать сериализацией в JSON: у `record` с полями `ImmutableArray` равенство ссылочное;
  - `StateHash` не меняется (golden);
  - стресс-тест: 20 повторов на (24, 180) при t16.

## 2. F7 — view в дни без месячного шага

**Что требуют ADR-0014 и Session.** [Факт]
- Публикация после post **непустого** тика, одной атомарной записью ссылки (п. 5). После пустого тика view не публикуется заново (Проверка).
- `SliceView`: `Actors` — состояние после post месяца `Month`; `Inputs`/`Step` — входы и итоги шага, **null, если на этом тике не было месячного шага** (`SliceViews.cs`). Это же поведение уже есть после тика с командой в середине месяца (без зонда).
- `SliceObserver` (Lab) читает view сразу после месячного тика (`SliceObserver.cs:358`) и `StateHash` раз в год (`:396`). Зонд на него не влияет.

**F7a (без изменения поверхности).** [Предл.]
- Условие переиспользования: `!monthly && !applied`, и все системы, активные на тике, view-нейтральны. Сейчас это только `DailyProbeSystem`. Флаг задаётся явным списком в `SliceWorld`, а не «по умолчанию».
- Новый view = `prev with { Tick, Date, StateHash, Inputs = null, Step = null, Actors = actorsMid }`.
- `actorsMid` — `Actors` месячного снимка, где у `Decisions.Closes[i].Reason` стоит `LineCloseReason.None` (эквивалент `stepped == false` в `ViewBuilder.Decisions`). Он строится один раз за месяц, при первом таком дне. Остальные поля `ActorView` зависят только от колонок и `month` (`KeyOf`, `MaxFleetValue` по `month % 12`), а между месячными шагами без команд колонки не меняются.
- Тест: в прогоне с зондом на каждом дне JSON переиспользованного view == JSON `ViewBuilder.Snapshot(w, tick, hash, month, null, null)`. Плюс тест «тик с командой строит view заново».
- Ограничение [Предп.]: при #228 системы пишут каждый день, условие не выполняется никогда, и F7a — выигрыш только замера M0. Для #228 нужны дешёвый снимок (F1 + `bool[]` грантов по актору) и, возможно, публикация не чаще кадра клиента. Это изменение ADR-0014 п. 5, оно входит в ADR #228.

**F7b (изменение поверхности, light, `TestApiVersion` 9).** [Предл.] `Inputs`/`Step` означают «шага месяца `Month`» и переносятся в дневные view до следующего шага. Флаг `StepTick` (или `StepJustRan`) говорит, что шаг был на этом тике. Тогда клиент, который опрашивает view с частотой кадров, не теряет итоги месяца. Затрагивает `ViewTests` (утверждения о null после немесячного тика) и `SliceObserver` (проверка по `Month`). По ADR-0014 п. 6 это не gate, но решает Orchestrator.

## 3. StateHash в дневном режиме

**Что действительно требуется.** [Факт]
- ADR-0002, «Последствия»: «хеш… считается каждый тик **(или по расписанию)**». Расписание уже разрешено.
- ADR-0006: post включает хеш. Тест «дневной = месячный» сравнивает хеши на месячных шагах.
- ADR-0013 п. 2, 8: `state_hash` в заголовке сохранения пересчитывается при save и load.
- ADR-0014 п. 4: `LastHash` — хеш таблиц после последнего post. Между тиками таблицы **и есть** это состояние, поэтому ленивый пересчёт даёт то же значение.
- ADR-0016 §2: дневной режим определён как «каждый день … хеш, снимок», и `T` включает `StateHash`. **Это единственное место, которое расписание прямо противоречит.**
- [Факт: grep] Golden SHA-256 состояния есть в ~15 тестовых файлах, в `SelfTest.cs`, `SliceChecks.cs` и манифестах EXP-0002 (опубликованные результаты; их не переписывать).

**Оценка вариантов** (200, 2000; таблица ≈ 14 МБ):

| Вариант | Цена хеша в `K_d`/мес | Формат и golden | Сложность и риск |
|---|---|---|---|
| 0. SHA-256 каждый день + F8 | [Предп.] 30 × 8–10 мс ≈ 0,25–0,3 с | без изменений | нет; > 150 мс — флаг ADR-0016 |
| 1. Расписание: ленивый `LastHash` + контрольная точка на месячном шаге и тике команды; ежедневно — только флаг тестов/Lab | ≈ 1–2 × 9 мс ≈ 10–20 мс | без изменений | `View.StateHash` в дневных view → `string?` (`TestApiVersion` +1) |
| 2. XXH3/XXH128 (`System.IO.Hashing`, MIT) каждый день + SHA-256 на месяц | [Предп.] 30 × ~1 мс + 9 ≈ 40 мс | второй хеш, новые поля; golden SHA целы, если SHA остаётся каноническим | два хеша в API, путаница «какой сверять» |
| 3. Merkle по колонкам или чанкам, грязные — по объявленному write-set систем | при #228 ≈ вариант 0 (грязны почти все колонки) | **новый корень ⇒ все golden и EXP-0002 недействительны** | write-set надо объявлять и проверять; необъявленная запись ⇒ L1/L2 слепы |
| 3'. Параллельный SHA-256 по колонкам + корень | [Предп.] 30 × ~1,5 мс ≈ 45 мс | новый корень ⇒ все golden | средняя |

[Факт] `System.IO.Hashing` даёт `XxHash3` (64 бит) и `XxHash128`, это NuGet-пакет вне BCL. README пакета: «not suitable for security purposes» ([learn.microsoft.com/dotnet/api/system.io.hashing](https://learn.microsoft.com/dotnet/api/system.io.hashing), [nuget.org/packages/system.io.hashing](https://www.nuget.org/packages/system.io.hashing/), обращение 2026-11-17). Цифры скорости — [Предп.], нужен замер на i7.

**Рекомендация:** вариант 1 сейчас. Вариант 2 держать для lockstep-мультиплеера (проверка рассинхрона каждый тик, L3). Варианты 3/3' — только если ежедневный канонический хеш станет обязательным в игре.

### Набросок ADR (gate+research) — «Расписание StateHash и дневной режим»
- **Контекст:** профиль #283; `K_d ≤ 50` мс и флаг `K_d > 150` (ADR-0016 §4); #228 делает каждый день непустым.
- **Решение [Предл.]:**
  1. Канонический `StateHash` — SHA-256 с байтовым форматом ADR-0013/`StateHash.cs` (после F8 те же байты). Golden не меняются.
  2. `SliceSession.LastHash` — ленивый: считается при первом чтении после непустого тика и кэшируется. Счётчик `HashComputations` считает реальные вычисления.
  3. Обязательные точки: тик месячного шага (при #228 — граница календарного месяца), тик с применённой внешней командой, save, load, конец replay.
  4. Execution-only флаг `SliceRunConfig.HashEveryTick` (не хешируется) включает хеш на каждом непустом тике. В тестах L1/L2 и в Lab-аудитах он по умолчанию включён.
  5. `SliceView.StateHash` → `string?`: null, если на этом тике хеш не считался. `TestApiVersion` +1.
  6. **Частично заменяет ADR-0016 §2**: в определении дневного режима «хеш каждый день» → «хеш по расписанию п. 3». В `K_d` входит хеш по расписанию.
- **Альтернативы:** варианты 0, 2, 3, 3' (таблица выше), с причинами отказа.
- **Влияние на golden:** нет. Байты и алгоритм те же, меняется только частота. Тест «дневной = месячный» сравнивает на тех же точках.
- **Миграция:**
  - сохранения: не нужна, `state_hash` в заголовке тот же;
  - код: `LastHash` → свойство с кэшем; `ViewTests` (`v.StateHash == s.LastHash` на немесячных тиках) переводятся на флаг п. 4; `DailyTickProbeTests.FlagOn_HashesAndSnapshotsEveryDay` проверяет флаг п. 4;
  - EXP-0007 пере-регистрируется: какое расписание замеряется.
- **Проверка:**
  - тест «ленивый `LastHash` == принудительный SHA» на каждом дне;
  - L2 с флагом п. 4;
  - архитектурный тест: в Session нет вызова `StateHash.Compute` вне кэша;
  - замер `K_d` по ADR-0016.
- **Research до принятия:** замер F8 на i7 (SHA-256 с sha_ni); замер XXH3 и `CopyCurrentToNext` (с параллелью по колонкам и без), чтобы зафиксировать запасной вариант 2 и решить вопрос копии.
- **Отдельно (в этот же ADR или следом):** копия 56 мс/мес. Варианты: параллельная копия по диапазонам колонок (формат не меняется, light) или копия только write-set активных систем (нужны объявления, при #228 выигрыш мал).

## 4. Что требует одобрения владельца
1. ADR «Расписание StateHash» (gate+research), частично заменяющий ADR-0016 §2: в игре хеш не каждый день.
2. Принять, что при полной копии таблиц `K_d ≤ 50` мс недостижим (только копия ≈ 56 мс). Выбор: оптимизировать копию в том же ADR или пересмотреть долю `K_d` (ADR-0016 §3 — диагностическая).

Без владельца (Orchestrator, light): F4-A, F7a; F7b — по ADR-0014 п. 6 с повышением `TestApiVersion`.
