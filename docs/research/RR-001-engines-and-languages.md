## 1. Вопрос исследования

Какой язык выбрать для ядра симуляции и какой движок/фреймворк для визуализации, чтобы:
- ядро работало без GUI (headless Simulation Lab: batch, sweeps, Monte Carlo, регрессии, бенчмарки) — уже в M0;
- была обязательная многопоточность и детерминизм по seed (с заделом под lockstep);
- моддинг через данные был с самого начала, а скриптинг — по желанию;
- поддерживались Windows/Linux/macOS;
- код, который почти целиком пишет AI, мог надёжно проверять и сопровождать владелец с опытом PHP/web и без опыта в геймдеве.

## 2. Краткий вывод

1. **PROPOSED:** гибридная архитектура: ядро симуляции в виде **чистой библиотеки на C# / .NET 10 LTS** без зависимостей от движка. Headless CLI (Simulation Lab) строится на том же ядре. Фронтенд появится позже, **предпочтительно Godot 4 (.NET)**, и подключает ядро как обычную .NET-сборку в том же процессе.
2. C# лучше всего совмещает четыре вещи: читаемость для PHP-разработчика (синтаксис и ООП близки к PHP 8), надёжную генерацию кода LLM (меньше ошибок компиляции, чем у Rust/C++ [F12, F13]), приличную производительность и простой параллелизм (`Parallel.For`, `Task`, `System.Threading.Channels`).
3. Godot бесплатен (MIT), без роялти и отчётов о выручке. C# в нём поддерживается на всех desktop-платформах [F1]. Web-экспорт для C# не поддерживается [F1], но проекту он не нужен.
4. Unity технически подходит (Terra Invicta [F9]), но лицензия проприетарная, история с Runtime Fee [F4] подорвала доверие, а сам RimWorld в 1.7 ушёл с Unity на свой движок [F10]. Unreal избыточен для map/UI-heavy 2D-стратегии.
5. Rust/Bevy — сильная альтернатива по безопасности и параллелизму. Но у LLM в Rust самая высокая доля некомпилирующегося кода [F12], ревьюить его PHP-разработчику труднее всего, а Bevy пока на 0.x с ломающими релизами [F11].
6. C++ — отраслевой стандарт для этого жанра (Clausewitz/Jomini [F6, F7], Dwarf Fortress [F14], Factorio [F15]). Но для одиночного разработчика без опыта C++ это главный источник трудноуловимых багов (UB, память, гонки).
7. Детерминизм в любом языке обеспечивается дисциплиной архитектуры (fixed-point/целые числа в состоянии, собственный RNG, детерминированный порядок редукций), а не выбором языка [F15, F16].

## 4. Анализ гибридного подхода

**Схема (PROPOSED):**

```
Singularity.Core        (netstandard-free, net10.0 class library; без ссылок на движок)
  ├─ Model (state: countries, provinces, pops, tech graph) — плоские массивы/struct-of-arrays
  ├─ Systems (economy, science, politics…) — чистые функции tick(state, inputs) → state'
  ├─ Data (загрузка модов: JSON/YAML/TOML + JSON Schema валидация)
  └─ Determinism (seeded RNG per-system, fixed-point тип, порядок итерации)
Singularity.Lab         (console app: batch, sweeps, Monte Carlo, regressions, BenchmarkDotNet)
Singularity.Core.Tests  (xUnit/NUnit; golden-тесты по seed + hash состояния)
Singularity.Client.Godot(позже: Godot 4 .NET, ссылается на Core.dll, только читает снапшоты и шлёт команды)
```

**Плюсы:**
- M0 вообще не зависит от выбора движка: Lab и ядро — обычные .NET-приложения, которые CI собирает на 3 ОС бесплатно.
- Тестируемость: golden-тесты вида «seed 42, 100 лет → hash состояния X» запускаются в CI без GPU.
- Движок можно сменить (Godot → MonoGame/Avalonia/Unity), не трогая ядро. Пример цены переезда — RimWorld [F10].
- Lockstep-задел: клиент шлёт только команды, ядро — детерминированный автомат (модель Factorio [F15]).
- Параллелизм ядра не конфликтует с main thread движка: симуляция идёт в своём потоке/пуле, клиент получает неизменяемые снапшоты.

**Минусы / цена:**
- Нужен слой «снапшот → визуализация» и протокол команд, это дополнительный код [A].
- Нельзя пользоваться удобствами движка (сигналы, ноды) в логике: это дисциплина, которую нужно закрепить в правилах ревью.
- При in-process связке Godot требует совместимой версии .NET. Сейчас пакеты GodotSharp таргетят `net8.0` [F17], и .NET 10-сборка ядра должна грузиться в тот рантайм, который поднимает Godot. **Это нужно проверить прототипом** (открытый вопрос, см. риски). Обход: таргетить ядро на `net8.0`/multi-target или вынести ядро в отдельный процесс (IPC).

**Варианты связи ядра и клиента:**

| Вариант | Когда |
|---|---|
| In-process (Core.dll внутри Godot .NET) | По умолчанию: проще всего, нулевая сериализация |
| Out-of-process (ядро — сервер, клиент по IPC/socket, MessagePack) | Если клиент не на .NET, при несовместимости рантаймов или как прообраз multiplayer |
| Native (ядро через NativeAOT как C ABI `.so/.dll`) | Для клиента на C++/Rust/GDExtension; NativeAOT это позволяет [A], но экспорт API через C ABI трудоёмок |

**Детерминизм — практические правила (PROPOSED, применимы к любому языку):**
- Состояние симуляции хранить в целых/fixed-point (например, `long` с масштабом 10⁴ для денег и населения). `float`/`double` — только в презентации и в изолированных местах, где детерминизм не нужен.
- Не использовать `Math.Sin/Exp/Pow` в state-критичном коде (результат зависит от libm платформы [F16]), а при необходимости брать свою табличную/полиномиальную реализацию.
- Собственный PRNG (например, PCG/xoshiro) с отдельным потоком на систему или сущность; запретить `System.Random` без seed, `DateTime.Now` и итерацию по `Dictionary`/`HashSet` в логике.
- Параллелизм: разбивать работу на независимые партиции (например, по провинциям), писать результаты в предвыделенные слоты, а редукции выполнять в фиксированном порядке. Factorio прямо называет детерминированную многопоточность сложной [F15].
- CI-тест: одинаковый hash состояния на Win/Linux/macOS при одном seed.

## 5. Рекомендация (PROPOSED)

**Основная:**
- **Язык ядра:** C# на .NET 10 LTS. При необходимости — multi-target `net8.0;net10.0` ради совместимости с Godot; это проверить в M0.
- **Архитектура:** гибрид. `Singularity.Core` (библиотека) + `Singularity.Lab` (CLI) в M0, движок в M0 не ставим.
- **Фронтенд (после M0):** Godot 4.x .NET (MIT). На время разработки ImGui-подобный дебаг-UI (например, ImGui.NET) можно встроить в Lab для визуальной отладки без движка.
- **Моддинг:** данные в текстовых файлах (JSON/YAML) с JSON Schema с M0. Скриптинг откладывается: кандидаты — Lua (MoonSharp/NLua, проверенная практика в жанре) или WASM (песочница). Произвольные C#-сборки как моды — только с осознанием отсутствия песочницы.
- **Почему:** лучшее соотношение «LLM пишет корректно + PHP-разработчик читает + достаточно быстро + кросс-платформенная сборка тривиальна + бесплатная лицензия без роялти».

**Альтернатива A — Rust-ядро + Godot (gdext) или Bevy/egui.** Выбирать, если владельцу важнее, чтобы компилятор гарантировал отсутствие гонок данных, и он готов осваивать ownership/lifetimes. Цена: медленнее итерации с LLM [F12], сложнее ревью, Bevy нестабилен [F11].

**Альтернатива B — C++20-ядро + Godot GDExtension** (путь Paradox/Factorio). Выбирать, только если прототип покажет, что C# не тянет целевой масштаб (например, ≥100k pop-групп × ежедневный тик) даже после оптимизации структур данных. Цена: максимальная сложность и риск UB при слабом ревью.

**Когда рекомендация меняется:**
- Бенчмарк M0 показывает, что C#-ядро в 3+ раза медленнее целевого бюджета тика и профилирование не помогает → рассмотреть Rust для горячих систем (через C ABI) или полный переход.
- Совместимость Godot .NET и .NET-версии ядра окажется хрупкой → out-of-process клиент или MonoGame/Avalonia-фронт.
- Понадобятся мобильные платформы или web → C# в Godot на web не поддерживается [F1], а на Android/iOS он экспериментальный [F1]. Тогда пересмотреть фронт; ядро при этом остаётся.
- Владелец решит, что Unity-экосистема (ассеты, UI Toolkit) важнее лицензионных рисков → Unity как клиент; ядро на C# переносится без изменений.

## 7. Открытые вопросы для владельца

1. Готовы ли вы установить .NET 10 SDK и пользоваться VS Code + C# Dev Kit или JetBrains Rider (для некоммерческого использования бесплатен; условия уточнить при коммерциализации)?
2. Целевой масштаб в M0 и в v1: сколько стран, провинций и pop-групп, какой шаг тика (день/неделя/месяц)? От этого зависит, нужен ли fixed-point везде или достаточно частичного детерминизма.
3. Насколько строг детерминизм в v1: «бит-в-бит на одной ОС» или «бит-в-бит на Win/Linux/macOS» (второе дороже)?
4. Мобильные платформы и web точно вне scope? Это влияет на допустимость C# в Godot.

## 8. Что НЕ проверено (ограничения исследования)
