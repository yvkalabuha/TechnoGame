## (a) «FND RNG»: к каким типам узлов применяется случайное открытие
- **RR-0008** («Разногласия» п. 1, §12 A): hazard-открытие распространяется на ключевые ENG/CMP/PRC среза. Альтернатива — случайны только FND/PRN-предки.
- **Контракт.** §9.2 требует «RNG знания с заметной дисперсией времени открытия *самих ключевых узлов* (#32): ТРД, жаропрочный сплав, точная ковка лопаток». Но строка §9.2 (a) говорит «RNG открытий знания (FND, RR-0008)», §10 — «FND RNG», §12 п. 7 — «Дисперсия FND по ключевым узлам среза». Это остатки текста v2, не исправленные в v2.1.
- **Код и данные уже следуют #32** [Факт: `mods/core/nodes.yaml`, `node.schema.json` `hazard: none|hz|key`; `KnowledgeGraph.IsHazard`]. Случайность — атрибут узла `hazard`, а не его типа. В срезе `key` стоит у 4 ENG, 1 CMP и 5 PRC, `hz` — у 4 FND и 5 PRN. У APP везде `none`.
- **Рекомендация** [Предл.]: правило «право на hazard задаёт поле данных `hazard`, а не тип» закрепить в грамматике графа RR-0008. Допустимо для FND, PRN, ENG, CMP, PRC. Для APP — только `none`: APP собирается из ENG + CMP + PRC и своей случайности не имеет. Нарушение — громкая ошибка загрузки (валидатор, см. ниже). Альтернатива «только FND/PRN» отвергнута решением #32: она даёт меньший разброс, а это риск для ориентира #24 (§9.2).
- **Erratum контракта** [Предл.], без изменения смысла:
  - §9.2, строка (a): было «RNG открытий знания (FND, RR-0008);» → стало «RNG открытий знания: hazard-узлы любого типа, кроме APP (поле данных `hazard`; #32, RR-0008);».
  - §10, строка «Знание», колонка «В срезе»: «FND RNG» → «RNG знания на hazard-узлах (ключевые ENG/CMP/PRC, FND/PRN; #32)».
  - §12 п. 7: «Дисперсия FND по ключевым узлам среза (§9.2).» → «Дисперсия времени открытия ключевых hazard-узлов среза (§9.2, #32).».
- **Детерминизм.** L1/L2 не затронуты. Выборка — `CounterRng(seed, month, SystemKnow, entity(actor, node), 0)` без состояния (ADR-0004, #60), вне зависимости от типа узла. Поле `hazard` входит в `data_hash` (ADR-0010). Состояние сохранения не меняется (ADR-0013): у RNG нет состояния, `prog` уже есть в колонках. Erratum меняет только текст, хеши остаются прежними.

## (b) Деление на `K_d = 0` в §4.3
- **RR-0008** («Разногласия» п. 2): предлагает правило `K_d = 0 → ΔK_ind = 0` как новую правку контракта.
- **Контракт.** Правило уже есть: §4.3, «При `K_d = 0` — `ΔK_ind = 0` (защита от деления на ноль; v2.1)».
- **Остаточная дыра** [Факт: §4.0 п. 2 — каждое `·` округляется вниз в `Fx6`]. Знаменатель `θ_ind·K_d` равен 0 и при `K_d > 0`: если `K_d.Raw ≤ 3` при `θ_ind = 0.25`, то floor(raw·250000/10⁶) = 0. Тогда по букве контракта деление на ноль → исключение. Код уже защищён [Факт: `KnowledgeMath.KIndStep`, условие `kd == 0 || cap == 0`, ссылка на спеку §3.5 A16]. Текст контракта — нет.
- **Erratum §4.3** [Предл.]: было «При `K_d = 0` — `ΔK_ind = 0` (защита от деления на ноль; v2.1).» → стало «Если `V_d > 0` и `θ_ind·K_d = 0` (после округления `Fx6`, §4.0 п. 2; в том числе при `K_d = 0`), то `ΔK_ind = 0`, `K_ind` не меняется (защита от деления на ноль; v2.1, уточнено по спеке среза §3.5 A16).» Смысл тот же («мост не работает без науки»), поведение кода не меняется.
- **Детерминизм.** Без изменений: ветка уже исполняется в Core, хеши и эталон те же. Тест [Предл., test-engineer]: unit-тест `KIndStep` с `K_d.Raw ∈ {0, 1, 3, 4}` при `V_d > 0` — первые три дают `K_ind` без изменений, исключения нет.

## Вопрос 8: формат графа, валидация, масштаб 2000 узлов (#25)
**Источник истины** [Факт: ADR-0010, #53]. Мод `core`, YAML строгого подмножества + JSON Schema 2020-12, операции define/override/patch/delete по `id`. Предложения [Предл.]:
1. **Файлы** (обновлено 2026-11-14, принята позиция RR-0008; прежний вариант «файл на макросектор S1–S8» снят). `mods/core/knowledge/<discipline>.yaml` (по одному на дисциплину, ~34, `kind: node`) вместо одного `nodes.yaml`. В моде `core` поле `discipline` каждого `define` равно имени файла (громкая ошибка). Загрузчик собирает все файлы `kind: node` в порядке манифеста; строки графа упорядочены по `number`, порядок файлов на результат не влияет. Причина выбора: дисциплина — обязательное поле узла и единица `K_d`, а каталог секторов не зафиксирован.
2. **Идентичность** (обновлено 2026-11-14, `contract-proposals-wave1.md` A1). `id` = `<type>.<name>` (например `eng.turbojet_g1`): тип совпадает с полем `type`, сектор не хранится, а выводится из каталога дисциплин. Прежний формат `<sector>.<type>.<name>` снят: смена каталога секторов переименовала бы узлы. `id` — для людей и модов; `number` — постоянный целый ключ RNG и журналов: не переиспользуется после удаления узла, коллизия — громкая ошибка загрузки (ADR-0010). Диапазоны номеров для сторонних модов — когда появится второй мод (ADR-0010: скриптинг и моды — позже).
3. **Статика и состояние в Core.** Статика — `KnowledgeGraph` (неизменяемые массивы, рёбра `requires`/`informs` в CSR, строки по возрастанию `number`); в сохранение она не входит, её фиксирует `data_hash`. Состояние актора — SoA-колонки `(actor, node)` в таблицах Kernel (`known`, `prog`, `known_since`) плюс `(actor, discipline)` (`K_d`, `K_ind`). Новые колонки повышают `schema_version` (ADR-0013 п. 7).
4. **Валидация** в три слоя, всё в CI (ADR-0010 «Проверка»):
   - JSON Schema — структура, перечисления (`type`, `hazard`, `cluster`), обязательные поля PRC (уже есть `if type = PRC`);
   - семантика в загрузчике (`NodeTable.Validation`) — ссылки, самоссылка, порядок поколений, цикл `requires` (есть). Добавить из грамматики RR-0008: APP не может быть `requires`-предком FND; `speculative` не может быть hard-предком `historical`; `hazard ≠ none` запрещён у APP; у каждого `hidden` есть `reveal`; правило функции (≥1 эффект за пределами графа, исключение FND/PRN); `cluster`/`discipline` у PRC по каталогу RR-0006. Ошибка — громкая; «соседний сектор» — предупреждение;
   - отчёт Lab (не блокирует) — доли типов и уровней, доля узлов с `synergy`, недостижимые узлы, экспорт GraphML для просмотра. GraphML — производный артефакт, не источник.
5. **Масштаб 2000 узлов** [Предп.; оценки, не замеры]:
   - память: 2000 узлов × 30 акторов × ~3 колонки по 8 байт ≈ 1.4 МБ — пренебрежимо;
   - тик: hazard и `prog` считать только по фронту (узлы с выполненными `requires`, ещё не известные), а не по всем 2000; фронт — производная снимка, в сохранение не входит;
   - загрузка: проверка циклов — топологическая сортировка O(V+E); парсинг YAML на 2000 узлов (~1–2 МБ) — меньше секунды; замерить бенчмарком загрузчика при MVP ~180 узлов и на синтетическом графе из 2000.
6. **Блокеры масштаба (найдено в коде)** [Факт]:
   - **Закрыт (2026-11-14, #197):** ключ расширен до T12 вместе с TASK-0050 [Факт: код `KnowledgeRng.NodeKeyBits = 16`, `MaxActorNumber = 32767`, `checked`; `KnowledgeSchedule.DeltaIndex = actor·(MaxNodeNumber + 1) + node` по фактическому графу; golden пересчитан один раз]. Вопрос срока (RR-0008 Q6) снят; статус — `contract-proposals-wave1.md` A2. Ниже — исходный текст, история. Было: `KnowledgeRng.MaxNodeNumber = 63`, ключ `entity = actor·64 + node` (спека среза §9.1). Графы больше 63 узлов не загрузятся. [Предл.] Ключ `entity = actor·2¹⁶ + node` (номер узла до 65 535, актор до 32 767 в `int`). Нулевой узел остаётся за L_K. Меняет выборки всех акторов, кроме актора 0 → golden-хеши и эталон EXP-0002 обновить один раз. L1/L2 сохраняются: ключ — чистая функция стабильных id (ADR-0004). Сохранений игрока нет (ADR-0013), миграция не нужна. Сделать до того, как граф вырастет за 63 узла, и до первого сохранения игрока. Альтернатива — `entity = node`, а актор в счётчике `n`; хуже: `n` уже занят L_K-выборками. (2026-11-14) Второе место с `·64` — `KnowledgeSchedule.Delta` (`actorCount·64`): размер — `actorCount·(maxNumber + 1)` по фактическому графу. Срок — вопрос владельцу (RR-0008 Q6), варианты — `contract-proposals-wave1.md` A2.
   - `KnowledgeGraph.RowOf` и `IndustryLayout.RowOf` — линейный поиск, а вызываются в циклах (`WhyNotAnalyzer`, адаптеры Session). При 2000 узлах это O(n²) на вызов `why_not`. [Предл.] Плотный массив `number → row`, строится один раз в `Create`. Поведение и хеши не меняются.
7. **Проверка решения.** Тест загрузчика на синтетическом графе из 2000 узлов (время, отсутствие ошибок); архитектурный тест «нет линейного `RowOf` в compute»; тест ADR-0004 «перестановка строк не меняет выборки» — на новом ключе; golden-хеши — один раз с причиной «RNG key widening».
