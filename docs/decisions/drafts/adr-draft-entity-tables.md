# ADR-NNNN — Таблицы сущностей при переходе на ADR-0020: что уходит из таблицы акторов, дочерние таблицы с чанками по родителю

> Черновик systems-architect, 2026-11-24. Лежит в `docs/architecture/drafts/` (зона записи архитектора); место назначения — `docs/decisions/drafts/`, переносит Orchestrator. Уровень: gate (этап 3.7 `development/PLAN.md`, находка A5 ревью 2026-11-19). После ACCEPTED текст не меняется.

## Краткий вывод
- [Факт] Проекты, когорты, решения ИИ по слотам, очереди команд и лицензия хранятся семействами колонок на таблице «строка = актор»; ёмкость (`max_designs`, годы когорт) входит в **число колонок**, поэтому её правка меняет схему. ADR-0005 п. 1 оставил выбор «группы колонок или своя таблица» ADR слоя — это он.
- [Предл.] Свои таблицы получают сущности со слотами или со своим числом строк на актора: `designs` (проекты, строка = (актор, слот)), `licences` (TASK-0152), `institutes` (TASK-0151, строка = институт из данных). Матрицы «актор × данные» (узлы знаний, кластеры Industry) остаются семействами колонок, но узлы уходят в свою таблицу `knowledge` (строка = актор).
- [Предл.] Новое в Kernel — **дочерняя таблица**: строки сгруппированы по строке родителя, диапазоны постоянны с t0; система с `ChunkTable` = родитель пишет строки детей своего чанка напрямую через срез `Span`, выдаваемый Kernel только на свой диапазон. L2 сохраняется по построению.
- [Предл.] Перенос — **тем же поездом, что #228** (одна смена эталонов). Рычаги (институты, лицензии) пишутся сейчас на текущем Kernel через объект раскладки со строками, сгруппированными по актору, чтобы перенос был механическим.

## Контекст
- [Факт: ревью проекта 2026-11-19, A5] «Проекты, когорты и очереди команд хранятся семействами колонок на таблице акторов. Отсюда смена схемы при каждой правке ёмкости и голые номера слотов (DEBT-0052, DEBT-0053). При переходе на несколько таблиц вынести сущности в свои таблицы со строкой `(actor, generation)`. Это gate.»
- [Факт: ADR-0005 п. 1, п. 3] Таблица на тип сущности; подсущности с ёмкостью — группы колонок или своя таблица, «выбор — в ADR слоя по бюджету `K_d`»; слоты переиспользуются со счётчиком поколения, ссылка — handle `(slot, generation)`.
- [Факт: ADR-0020 п. 1–3] `World` — список таблиц; система объявляет `ChunkTable`; compute пишет только строки своего чанка своей `ChunkTable`, в строки других таблиц — через буферы чанков в merge. Строки `actors` создаются в t0, число постоянно.
- [Факт: код `ProductsSystem.cs:188–227`] На слот проекта ≈ 34 колонки + `alt.{s}` + маски `q` + `cohort.{год}` (по колонке на год, до `MaxCohortYears`); `max_designs` = 12. [Факт: `CommandState.cs:38–86`, `PolicySystem.Products.cs:73–105`, `PolicySystem.Fleet.cs:28–45`] Очереди `cmd.dsn/flt/series/close.{k}` и решения ИИ `pol.dsn/start/close/flt.{k}` — семейства по слоту. [Факт: `PolicySystem.Events.cs:37–55`] Одна лицензия на актора (`pol.lic.*`). [Факт: `KnowledgeSystem.cs:109–124`] Узлы — `know.known/prog/since.{N}`.
- [Факт: `docs/architecture/notes/multi-table-api.md`] API: `World`, `Table.Name/SchemaVersion`, `ITickSystem.ChunkTable`, `ChunkCountOf(s)`; оценка 1,5–2,5 дня developer.
- [Факт: ADR-0017 «Контекст»] Полный масштаб ≈ 8800 колонок × 200 строк ≈ 14 МБ; CoW открывает колонку целиком при первом касании.
- [Факт: `research-institutes-priorities.md` §1.3, разд. 10; `production-lines-and-licence-market.md` разд. 2, 5] Институт — строка данных `{country}:{slug}`, 3–10 на страну, растут по данным; рынок — несколько лицензий на страну с ключом (seller, gen); оба добавляют состояние ядра в пакете рычагов.

## Решение
1. **Своя таблица** — если у сущности число экземпляров на актора задаётся ёмкостью или данными и у неё есть время жизни или ≥ 5 полей:
   - `designs`: строка = (актор, слот), `max_designs` строк на актора; колонки проекта, `occupied`, `generation` (ADR-0005 п. 3), решения ИИ по проекту (пишет `PolicyDecision`, читает `ProductsFlow` — разные колонки одной таблицы, один писатель на колонку), постоянные приказы игрока (`rateCmd` и т. п.). Годы когорт остаются семейством колонок **внутри** `designs` (в день открывается одна колонка текущего года).
   - `licences`: строка = (актор, слот), ёмкость `max_licences` из данных; handle `(slot, generation)`.
   - `institutes`: строка = институт из данных сценария (все, включая будущие кандидаты), отсортированы по (актор-владелец, id); колонки `built`, уровни, опыт, приоритетный узел. Как `actors` в ADR-0020 п. 3: строки с t0, активность — колонкой.
2. **Остаются семействами колонок**: матрицы «актор × объект данных» без времени жизни — узлы знаний, кластеры и площадки Industry, скалярные поля актора. Узлы переносятся в таблицу `knowledge` (строка = актор): правка числа узлов меняет `schema_version` только этой таблицы.
3. **Очереди команд `cmd.*`**: [Предл.] в #228 команда действует в тике своего штампа (ADR-0019 п. 13), поэтому очередь «до следующего месяца» исчезает; постоянный приказ хранится в колонке своей сущности (`designs`), разовый — только в журнале команд (ADR-0014). Опись колонок `cmd.*` — шаг developer в #228 [Предп.: часть колонок окажется постоянными приказами].
4. **Дочерняя таблица (Kernel).** `Table` может объявить родителя и постоянные смещения `offset[parentRow]` (ёмкость: `a·cap`; данные: префиксные суммы при сборке). Для системы с `ChunkTable` = родитель Kernel даёт `column.NextRange(in ctx)` — `Span` только на строки детей текущего чанка; запись вне диапазона невозможна по построению. Границы — функция `(RowCount родителя, chunkSize, offset)`, от потоков не зависят (L2). Merge и буферы ADR-0020 п. 2 остаются для записи в чужие таблицы.
5. **Время.** Kernel `World` + дочерние таблицы — один шаг (TASK по наброску TASK-0090 + п. 4). Перенос `designs`, `knowledge`, `licences`, `institutes` — в поезде #228, по системам в порядке описи (Policy → Knowledge → Industry → Products), golden один раз.
6. **Рычаги до переноса** (TASK-0151, TASK-0152): состояние институтов и лицензий — через объект раскладки (как `ProductsLayout`) со строками, сгруппированными по актору, и handle; голых индексов в командах и видах нет. [Предл., D2 Orchestrator] Если Kernel `World` вольётся раньше шага «состояние» TASK-0151, институты сразу создаются таблицей.

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| Оставить всё семействами на `actors` | Ёмкость в схеме, ≈ 1,5 тыс. колонок проектов на актора [Предп.: 12 × (34 + когорты)], голые номера слотов; A5 остаётся |
| Таблица «актор × узел» для знаний (400 тыс. строк при 2000 узлах) | CoW открывает 3,2 МБ на колонку каждый день [Предп.: ≈ 10–20 мс/мес. копий]; семейства открывают только тронутые узлы |
| Дочерние строки только через буферы merge (ADR-0020 п. 2 как есть) | Каждый день все записи `ProductsFlow` шли бы через буфер: аллокации и цена merge на тике |
| `ChunkTable` = `designs`, суммы актору через журнал | Работает, но решения ИИ и правила проекта читают состояние актора построчно; чанки по родителю проще и дешевле |
| Перенос сейчас, до рычагов | Задерживает пакет рычагов (#474) на Kernel и gate |
| ECS / динамические строки | Отклонено ADR-0005 (фиксированные строки, L2, сейв) |

## Последствия
- **Плюсы:** ёмкость меняет `n_rows`, а не схему; handle естественно = строка + поколение (закрывает остаток DEBT-0052 по пути данных); новые сущности (институты, лицензии, будущие изделия других классов) получают общий образец; схема актора стабильна.
- **Минусы:** новый механизм Kernel (`NextRange`, смещения); сейв меняет формат (`save_format_version`; сейвов игрока нет, ADR-0013 п. 7); код рычагов переносится второй раз [Предп.: ≈ 1–2 дня в поезде #228].
- **Цена тика** [Предп.]: `designs` 200 × 12 = 2400 строк, ≈ 40 колонок × 19 КБ ≈ 0,8 МБ копий в день при полном открытии → ≈ 3–6 мс/мес. в `K_d`; хеш — те же байты плюс заголовки таблиц. Цена записывается в реестр бюджета M1 (черновик `adr-draft-province-budget.md` п. 3).
- **Обязательно:** запись в дочерние строки — только через `NextRange`; handle во всех ссылках.

## Проверка
1. Kernel: L2 на мире с дочерней таблицей — threads 1/4/8/16 × ChunkSize 1/8/32 × ёмкость 1/12 и переменные смещения из данных; хеш каждого дня равен.
2. Kernel: `NextRange` возвращает ровно диапазон чанка (property по случайным смещениям); пустой родитель — пустой `Span`.
3. Архитектурный тест: в Core нет обращения к `Next` дочерней колонки из системы с `ChunkTable` = родитель (только `NextRange`); один писатель на колонку (TASK-0086) по всем таблицам.
4. Save/load: таблицы `designs`, `licences`, `institutes` — тот же хеш после загрузки; смена `max_designs` меняет `n_rows` и не меняет `SchemaFingerprint` колонок.
5. Ревью TASK-0151/0152: раскладка по актору, handle, нет голых индексов (п. 6).

## Вопросы владельцу (простыми словами)
1. **Когда наводить порядок в хранении.** Сейчас всё о стране — проекты, лицензии, будущие институты — лежит в одной большой «строке страны»; из-за этого любое изменение лимитов (например, 12 проектов) меняет формат данных и путает ссылки. Предлагаю разложить это по отдельным таблицам вместе с переходом на ежедневный расчёт: все контрольные числа игры поменяются один раз, а не дважды. Согласны? Альтернатива — сделать это раньше, до рычагов (рычаги задержатся примерно на неделю), или не делать (дешевле сейчас, дороже с каждой новой механикой).
