- [high] RNG entity `e` is the domain row ordinal, not a stable entity id (p. 6).: ADR-0004 is ACCEPTED and explicitly says entity_id is a stable id from data, never a row index, and its test says permuting rows with the same stable ids must not change draws. ADR-0021 uses the sparse-table row ordinal for (o,t) and `e` for every domain. RR-0017's Net[o,t] is sparse and changes as networks are created/lost; RR-0019 links are planned/built/opened and can change controller. Any insertion/removal or reordering shifts `e`, so subsequent u values, the `e mod period_days` schedule, `stoch_last_tick`/cooldown, and golden/save reproducibility change. The ADR has no partial-supersession section for ADR-0004.
- [high] `stoch_today` capacity C and constant n_rows assume a static domain (p. 9).: C = sum ceil(|domain|/period_days) is computed at world build and overflow is called impossible. But intel.expose's domain is the sparse Net[o,t] from RR-0017, which grows and shrinks, and link.failure's domain is links that can be planned, built, opened or transferred with a controller change (RR-0019). A new row can exceed C and cannot be added because n_rows is constant; inserting it also changes ordinals (finding 1). There is no rule for domain growth, row creation/deletion, or the required save_format_version change.
- [high] Controller change is treated as target_gone for every target, including links; the owner of a cross-controller link hazard is undefined.: The RR-0019 critic high requires a link to belong to and be paid by the controller of its source region; cross-country means different controllers; a controller change transfers the network and invalidates the Phi cache, not deletes the link. ADR-0021 p. 3 says a case is discarded with target_gone if 'сменился контролёр', which is wrong for a link. The ADR never says which controller writes `hazard_<stream>` for a cross-controller link, so the one-writer rule is not satisfied for link.failure.
- [high] The #342 seed-independence claim is unqualified; at_war/war_over in M2 connect stochastic consequences to the events table.: scripted-events-conditions §1 makes at_war/war_over false in M1 and live in M2. If a stochastic link.failure changes war progression, a scenario event conditioned on war_over makes events.status/effective_tick seed-dependent. ADR-0021 p. 13 analyses only the metric path. Проверка 7 (M2 package on/off, 20 seeds, same events columns) would fail once war-related events exist.
- [medium] `pending`/`pending_choice` state is undefined while stoch_today is overwritten every merge.: p. 4 says a case can wait for expose/turn as a Decision in the owner's column (pending), but p. 10 says StochasticEventSystem writes only stoch_last_tick_* and stoch_count_*. No owner pending column, writer, lifetime, decision slot, or save/hash rule is defined. If the owner's consequence code is a Decision system (ADR-0019 p. 3) and the actor is not in today's slot, the case can be lost when the next merge overwrites stoch_today.
- [medium] Cooldown rule is wrong for the last_tick = -1 sentinel (p. 8).: The rule is `D < last_tick + cooldown_days`; with last_tick = -1 it suppresses rolls for early D < cooldown_days - 1 even though no previous case exists. The ADR states -1 means none but does not guard the comparison. It also does not say whether last_tick updates on success, target_gone or pending_choice.
- [medium] `tick = D` and `system = stream_id` for a 7-day stream deviate from ADR-0004 without partial supersession.: ADR-0004 defines tick as the firing index at the system's frequency (monthly index, yearly index, daily tick) and separates system_id by frequency. ADR-0021 computes in D-1 but keys with D, and uses one daily StochasticEventSystem with period_days = 7; this is not the ADR-0004 firing-index rule. The ADR does not list this as a partial replacement.
- [medium] The annual-probability test p. 5 is not exact for period_days = 7 because a year has 52 or 53 scheduled rolls, not 365/7.: The formula assumes Y/period_days rolls per year. For period_days = 7 a calendar year has 52 or 53 rolls, not 52.14. For hazard 0.1 the actual annual probability is about 0.095-0.097, 3-5% below 0.1; with 1e5 rows the stated ±3σ band can be exceeded, so the property test will fail. Leap-year and year-boundary phase are undefined.
- [medium] RR-0017 monthly p_expose/intel.turn probabilities are treated as annual hazards; intel.turn stays in M2 contrary to the critic's staging.: RR-0017 defines p_expose = clamp(a*activity*eff*f(ci_eff),0,p_max) as a monthly risk and p_detect_turn = 0.05 monthly. ADR-0021 p. 1 says 'p_expose RR-0017 is hazard' without a conversion; weekly period_days=7 materially changes the risk. The critic medium recommended deferring dis/turned to later and changing #260, but ADR-0021 includes intel.turn and the expose/turn choice in M2 with no owner decision cited.
- [medium] Column semantics for stoch_count_<stream>, count in row 0 and the m extra columns are undefined.: stoch_count_<stream> is never given a meaning or consumer. p. 9 says count in row 0 but does not say whether it is a column, how it coexists with a case in row 0, or what m is (max n_extra?). These are schema/hash/save ambiguities.
- [medium] No claimed daily cost for the new system and for the full stoch_today rewrite, contrary to ADR-0019 p. 27.: ADR-0019 p. 27 requires a per-day price before code and ADR-0016 gates. ADR-0021 Проверка 11 only repeats the requirement; no number is stated. stoch_today is fully rewritten every merge, with C rows and all extra columns, so the cost is not negligible; CoW opens all its columns daily.
- [medium] R3 is under 'Research до ACCEPTED' but is due 'до gate M2', after acceptance; source RR-0017/RR-0019 remain contradictory.: The ADR's 'Обязательно' says RR-0017/RR-0019 are rewritten, but the R3 deadline is gate M2. If ADR-0021 is ACCEPTED now, the linked RRs still describe monthly p_expose, RR-0019's controller rule and the support book; the decision would be accepted on documents that contradict it.
- [low] The one-writer architecture test is assumed to exist, but ADR-0017 says it is not included.: ADR-0021 p. 10 says the architecture test covers the new columns. ADR-0017 'Разногласия' says the one-writer test was not included and is a separate test-engineer task; ADR-0019 p. 4 is still PROPOSED. The ADR therefore relies on a test that may not exist.
- [low] The validator sentence preempts open question 2 and conflicts with RR-0019's link_open condition.: p. 13 says access of #299 branches to stream results is question 2, but the same paragraph says the validator forbids the atoms only outside `branch: counterfactual`, which already permits them. RR-0019 p. 5 proposes `link_open` as an M2+ scenario condition, while ADR-0021 bans `link_open` outside counterfactual branches. The ADR does not distinguish a stochastic-result atom from a link-state atom.
