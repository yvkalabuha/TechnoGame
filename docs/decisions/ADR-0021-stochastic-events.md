# ADR-0021 — Stochastic event system next to scripted events (scandals, link failures)

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Уровень: gate+research (детерминизм, формат сейва). Цель — M2. Причина: gate RR-0017/0019 (`docs/reviews/rr-0017-0019-critic.md` RR-0017 high #2, `rr-0017-0019-advocate.md` RR-0017 п. 4): у случайных событий нет места в архитектуре.

## Краткий вывод
- [Предл.] Новая система `StochasticEventSystem` (роль `Event`) **только бросает кости**: читает годовой риск `hazard`, который пишет владелец предметной области, и выдаёт «случаи дня». Последствия (потеря сети, падение `support`, отказ звена) применяет **владелец колонок** в тике `D` по маркеру — как E1 по `events.effective_tick` (ADR-0019 п. 19). Один писатель на колонку сохранён.
- [Предл.] Ключ RNG — `(seed, D, stream_id, entity, n)`, `D` — индекс дня действия; `stream_id` — из реестра потоков P05 (RR-0011), только добавление.
- [Предл.] Граница #342: сценарные условия в базовом сценарии результаты потоков **не читают**; доступ — только веткам #299 и только после решения владельца (вопрос 2).
- [Предл.] Абляция Lab: флаг потоков в манифесте прогона; выключенный поток даёт `hazard_eff = 0` без смены схемы.

## Контекст
- [Факт: DECISIONS_LOG #256, #260; RR-0017 §2] Раскрытие сети — вероятность от активности и `ci_eff`, поток `intel.expose`, ключ `(o,t)`; исход — событие `scandal`; RR-0017 предлагает писать `support` прямо из слоя событий.
- [Факт: RR-0019 §2] Случайные срывы звеньев (бомбёжка, шторм) — «только из слоя событий (#256, P05)». [Факт: RR-0016 §1] Внезапность и погода войны — тоже из P05.
- [Факт: #342; `docs/game-design/scripted-events-conditions.md` §4] У `ScenarioEventSystem` нет RNG ни в условиях, ни в исходах; базовый M1 не зависит от seed (#329).
- [Факт: ADR-0019 п. 3, 4, 9, 15, 16, 19] Решения ИИ — раз в 7 дней со сдвигом (#344); один писатель на колонку; переводы — журнал; ключ RNG `Flow`/`Decision` — индекс дня; событие даты `D` — в merge `D−1` (#347).
- [Факт: ADR-0020 п. 2, 3, 10, 11] Мир — именованные таблицы; строки `actors` заранее; экономика региона — контролёру (#349); регионы строго по линиям событий (#350).
- [Факт: `src/Singularity.Kernel/CounterRng.cs`] `NextU64(tick, system, entity, n)` без состояния; `Chance(u, Fx6 p)` — порог с шагом `p` 1e-6.
- [Факт] Формулировка задачи «Decision RNG — по месяцу» расходится с ADR-0019 п. 15 (по дню). Здесь принят текст ADR-0019 (OPEN для Orchestrator).

## Решение

### 1. Разделение обязанностей
1. **Владелец области** (Intelligence, Logistics, позже War, Politics) пишет в своей таблице колонку `hazard_<stream>` — годовая вероятность, `Fx6` ∈ [0; 1], детерминированно из своего состояния (`p_expose` RR-0017 — это `hazard`). Владелец же задаёт «домен» потока: строки таблицы (сети, звенья), по которым бросают.
2. **`StochasticEventSystem`** (Core, `Singularity.Core.Events`) не содержит формул области: для каждого потока читает `hazard`, бросает, пишет случаи. Колонки области не пишет.
3. **Последствия** применяет владелец колонки в тике `D`, читая случаи дня `D` из `Current` (п. 9): Intelligence — `N`, `A`, `mode`; книга `support` (RR-0021) — `support`; Logistics — `q`/`cap` звена. Если цель за ночь исчезла (событие сценария деактивировало актора, сменился контролёр), владелец случай отбрасывает с причиной `target_gone` (п. 14).
4. Выбор ответа на случай (RR-0017: «разоблачить / обратить») — `Decision` владельца в слоте актора (#344), без RNG; случай ждёт решения в колонке владельца (`pending`), не здесь.

### 2. Потоки и ключи
5. **Реестр потоков** `StochasticStreams` (Core, таблица-константа; это и есть P05 RR-0011): `stream_id` (`int`, только добавление, повторно не выдаётся), имя (`intel.expose`, `intel.turn`, `link.failure`; позже `war.surprise`, `war.weather`, `politics.*`), таблица-домен, колонка `hazard`, `period_days`, `cooldown_days`, число вторичных бросков `n_extra`. `stream_id` не пересекается с `system` id систем `Flow`/`Decision` (диапазон `0x5000_0000+`).
6. **Ключ:** `u_k = CounterRng.NextU64(tick = D, system = stream_id, entity = e, n = k)`, где `D` — индекс дня, с утра которого случай действует (бросок считается в тике `D−1`); `e` — порядковый номер строки домена (для пар `(o,t)` — строка разреженной таблицы сетей, а не `o·M+t`); `k = 0` — бросок «случилось ли», `k = 1..n_extra` — тяжесть, вариант. Число бросков на случай фиксировано, иначе ключи следующих смещаются.
7. **Расписание:** строка `e` бросается в дни `D`, где `D mod period_days = e mod period_days` (сдвиг как #344, без RNG). Вероятность броска `p_roll = 1 − (1 − hazard)^(period_days / Y)`, `Y ∈ {365, 366}` — обобщение `Fx6.DayRate` ADR-0019 п. 12 (таблица при загрузке не нужна: `period_days` — константа потока). [Предл.] `intel.expose`, `intel.turn` — `period_days = 7`; `link.failure` — `1`.
8. Не бросается: строка неактивна (актор или звено), поток выключен (п. 16), действует `cooldown` (`D < last_tick + cooldown_days`). Решение «бросать или нет» — только из `Current` и констант.

### 3. Место в дне и колонки
9. **Таблица `stoch_today`** (владелец — `StochasticEventSystem`): фиксированная ёмкость `C = Σ_stream ⌈|домен|/period_days⌉` (вычисляется при сборке мира → переполнение невозможно; `n_rows` постоянно), колонки `stream`, `entity`, `day`, `extra_0..extra_{m−1}` (`long`), `count` в строке 0. Перезаписывается в каждом merge целиком: в `Current` тика `D` лежат ровно случаи дня `D`.
10. **Колонки состояния** в таблице-домене, писатель — `StochasticEventSystem`: `stoch_last_tick_<stream>` (`int`, −1 = нет), `stoch_count_<stream>` (`int`). Других колонок система не пишет. Архитектурный тест «один писатель» (ADR-0019 п. 4) охватывает их.
11. **compute** (тик `D−1`, чанки по строкам домена): бросок по `Current`, запись в буфер чанка. **merge** — порядок `(stream_id, entity)`: чанки 0..N−1 потоков по возрастанию `stream_id`. Место в списке систем — **сразу после `ScenarioEventSystem`**. Ни одна система не читает чужой `Next` в merge, поэтому порядок двух событийных систем на состояние не влияет; фиксируется ради журнала и валидатора.
12. Сценарное событие и случай одного дня `D` не видят друг друга: оба посчитаны по состоянию конца `D−1`; последствия обоих — с утра `D`. Конфликт (событие убрало цель) разрешает владелец по п. 3.

### 4. Граница #342
13. **Сценарные условия базового сценария не читают** `stoch_*`, `stoch_today` и колонки, изменённые последствиями случаев, через новые атомы; атомов `scandal_fired`, `net_eff`, `link_open` в словаре нет. Валидатор запрещает их во всех пакетах без `branch: counterfactual`. Итог: таблица `events` (статусы, даты) не зависит от seed. [Предп.] Косвенная связь через экономику (скандал → `support` → …) в M2 невозможна, пока атом `metric` запрещён (#340); снятие запрета `metric` — отдельное решение M2, проверить заново.
   - Обратное разрешено: поток читает `actors.active`, контролёров, `events.status` (например, `hazard = 0` до `fired(E_FRG)`).
   - Доступ веток #299 к результатам потоков — вопрос 2.

### 5. Журнал, why_not, UI
14. **Журнал случаев** (производный, не хешируется; Lab — JSONL, UI — кольцевой буфер): на каждый случай `stream`, `entity`, `day`, `hazard`, `p_roll`, `u_k` (как `r = u>>11`), `extra[]`, `outcome ∈ applied | target_gone | pending_choice`, `factors[]` — до 3 вкладов в `hazard`, которые владелец области выдаёт функцией `ExplainHazard` (id фактора, значение Fx6).
15. **why_not** «почему не случилось»: UI не хранит неслучившиеся броски. Ответ строится из состояния: `hazard` сейчас, `p_roll`, ближайший день броска (п. 7), `cooldown`, флаг выключенного потока; шаблоны i18n как у сценарных событий («Сеть в ГБР не раскрыта: риск ~4 %/год, проверка 21.03»). Полная трасса бросков — только Lab `--trace-stochastic`. Как подавать вероятность игроку — вопрос 4.

### 6. Сейв и хеш
16. В `StateHash` и сейв входят `stoch_today`, `stoch_last_tick_*`, `stoch_count_*` и колонки `hazard` (их владельцы). Генератор не имеет состояния — сохранять нечего. Реестр потоков (id, параметры) — в `scenario_hash`; маска включённых потоков — в манифесте сейва и прогона; загрузка с другой маской или неизвестным `stream_id` — ошибка `save_format`. Новый поток = рост версии реестра (как атомы, `scripted-events-conditions.md` §6); `save_format_version` ADR-0013 растёт при добавлении таблицы.

### 7. Абляции Lab
17. `--stochastic off | on | streams=intel.expose,link.failure` — маска в манифесте. Выключенный поток: строки не бросаются (п. 8), схема и хеш-формат прежние, `stoch_today.count = 0`. `--stochastic force=<stream>:<entity>:<day>` — принудительный случай для тестов и контрфактов (только Lab, в манифесте, `u` в журнале = `forced`).
18. С включёнными потоками исход зависит от seed: отчёты Lab по потокам — распределение по ≥ 100 seeds (доля прогонов, медиана дня первого случая), сравнение с `off`. Golden M1 — с `off` (в M1 потоков нет, #329 не меняется).

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| RNG в `ScenarioEventSystem` | Нарушает #342; seed влияет на таблицу владения |
| Поток пишет `N`, `A`, `support` сам (RR-0017 §2) | Два писателя колонки; ломает ADR-0019 п. 4 |
| Последствия журналом переводов | Журнал — для сохраняемых величин; `N`, `q` — не переводы; лишний механизм |
| Бросок внутри каждой системы области (без общей системы) | Ключи и расписание расходятся, P05 «нет RNG вне потоков» не проверить, why_not и абляция в N местах |
| Ключ по месяцу, бросок в день 1 | Противоречит ADR-0019 п. 15; пик нагрузки |
| Ежедневный бросок всех потоков | Шаг Fx6 1e-6 огрубляет редкие риски (п. R1); ×7 цены для сетей |
| Растущая таблица истории случаев | `n_rows` растёт, сейв растёт; истории хватает `last_tick`/`count` и журнала |
| Альтернатива advocate: исторические раскрытия — сценарные события, RNG только для неисторических | Не отклонена: вопрос 1 |

## Последствия
- **Плюсы:** один писатель сохранён; формулы риска остаются у владельцев; одна точка для абляции, журнала и проверки P05; таблица `events` не зависит от seed.
- **Минусы:** у каждой области — колонка `hazard` и код применения последствий; случай действует только с `D` при броске в `D−1`; появляется seed-зависимость результатов M2 (нужны отчёты по многим seeds).
- **Обязательно:** RNG Core только через реестр `StochasticStreams` или `Flow`/`Decision` по ADR-0019; RR-0017 и RR-0019 переписываются под `hazard` + последствия у владельца.

## Проверка
1. **Архитектура:** `CounterRng` в Core вызывается только из `StochasticEventSystem` и систем, перечисленных в реестре ролей; `stream_id` уникальны и не пересекаются с id систем; атомы `stoch_*` отсутствуют в словаре базовых пакетов (валидатор).
2. **Один писатель:** колонки п. 9–10 — только `StochasticEventSystem`; `hazard_*` и последствия — только владельцы.
3. **L1/L2:** threads 1/4/8/16 × ChunkSize 1/8/32, `HashEveryTick`, 2 года, все потоки с завышенным `hazard` (случаи каждый день) — хеш каждого дня равен; повтор с тем же seed — побитно.
4. **Ключи:** golden-вектор `u_k` для 3 потоков; смена `period_days` одного потока не меняет броски других.
5. **Распределение (Lab, property):** при постоянном `hazard` доля строк со случаем за год = `hazard` ± 3σ на 10⁵ строк; для `period_days ∈ {1, 7}`; для `Y = 366`.
6. **Расписание:** строка бросается ровно раз за `period_days`; `cooldown` соблюдается; неактивная строка не бросается.
7. **Граница #342:** прогон M2-пакета с потоками `on` и `off` и 20 seeds — столбцы `events.status`, `effective_tick` одинаковы.
8. **Порядок дня:** сценарное событие деактивирует цель в merge `D−1`, случай на ту же цель — `target_gone`, состояние цели не меняется.
9. **Сейв:** save/load в любой день, в том числе между броском и применением, — тот же хеш; загрузка с иной маской — ошибка.
10. **Абляция:** `off` = все `stoch_*` по умолчанию, хеш-формат прежний; `force` даёт случай ровно в указанный день.
11. **Бюджет:** цена системы на день заявлена до кода (ADR-0019 п. 27); K4 M2 с потоками `on`.

## Research до ACCEPTED
- **R1. Точность вероятности.** `Chance` берёт `Fx6`: при `period_days = 1` годовой риск 0,1 % даёт `p_roll` ≈ 2,7 raw (ошибка до ~30 %). Варианты: `p_roll` в ppb (новый `ChanceRaw(u, num, den)` в Kernel) или нижняя граница `period_days`. Решение и property-тест п. 5 — до ACCEPTED.
- **R2. `Fx6` степень** `(1−h)^(period/Y)` — переиспользовать бисекцию `DayRate` или таблицу по `period_days`; эталонные значения.
- **R3. Переписать RR-0017 §2 и RR-0019 §2** под п. 1–4 (владельцы `hazard`, `pending`, последствия), включая книгу `support` (RR-0021) — до gate M2.
- **R4. Прототип Lab:** 600 сетей + 1000 звеньев, 30 лет, мс/день и тест п. 5.

## Вопросы владельцу
1. **Исторические раскрытия.** (а) [Предл. advocate] Гузенко 1945, Фукс/Венона 1950 — детерминированные сценарные события с эффектом на сеть; RNG только для неисторических сетей и после исторических дат; (б) всё случайно, история — только калибровка `hazard`; (в) (а) в базовом сценарии, (б) в режиме «свободная история».
2. **Ветки #299 и случайность.** Может ли ветка (`branch: counterfactual`) иметь условие на результат потока (например, «советская бомба раньше, если Фукс не раскрыт»)? (а) нет, никогда; (б) да, только в ветках, базовый сценарий — нет; (в) отложить до M3.
3. **Зависимость от seed в M2.** С потоками итог прогона зависит от seed. Принять, что проверки M2 (гипотезы, баланс) идут по распределению ≥ 100 seeds, а golden — с выключенными потоками? Или требовать, чтобы базовый M2 тоже был seed-независим (потоки только в режимах)?
4. **Показ риска игроку.** RR-0017: «полоса, не число». Показывать ли после случая «риск был ~4 %/год» и в why_not — проценты или только слова-шкалу?
