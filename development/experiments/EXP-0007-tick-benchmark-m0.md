# EXP-0007 — tick benchmark M0 (ADR-0016)

## Вопрос
Укладывается ли ядро в бюджет тика ADR-0016 п. 1 (p95 ≤ 500 мс и медиана ≤ 400 мс на игровой месяц, t8, i7-11800H) на синтетическом мире полного масштаба M0, и каков раздел `S` / `K_d`. Исход — одна строка таблицы ADR-0016 §4 (ниже, §П7). Основание: ADR-0016 (ACCEPTED, #276), `docs/architecture/notes/tick-benchmark-m0.md` §2, §4, §5.

## Пре-регистрация (TASK-0065, 2026-11-17; до любого замера)

Этот раздел замораживается до первого замера. Менять его после замера нельзя; отступление записывается в «Ошибки и аномалии» с причиной и решением Orchestrator. Манифест `lab bench` (TASK-0064) обязан воспроизвести значения ниже; его `manifest_hash` записывается во frontmatter перед прогоном. Где ADR-0016 молчит, решение помечено [Предл.] — оно в силе, пока Orchestrator не отменит его до прогона.

### П1. Мир
- [Факт: `src/Singularity.Lab/Bench/SynthWorld.cs`] Синтетический мир — Lab-only оверлей-мод `synth_bench` поверх `mods/core` (ADR-0010), сценарий `synth_bench`. Ни Core, ни Session не меняются; оверлей загружается `ModLoader` и проходит все проверки загрузки и старта (S-2, L-C1…L-C3a).
- Акторы: 5 акторов ядра первыми и без изменений (USA, GBR, SUN, FRA, SWE); затем клоны по кругу от них, id `XAA`, `XAB`, …; у клона GDP, GDP на душу и `budget_index` умножены на `1 + u`, `u ∈ [−0,1; +0,1]` из `CounterRng(generator_seed)`.
- Узлы: копия 0 — граф ядра (61 узел); копии 1… — клоны с id `<id>_kC` и номером `100·C + n`; последняя копия может быть неполной — префикс топологического порядка (Kahn, при равенстве — меньший номер), замкнутый по `requires`. Каждый актор знает и освоил клон каждого узла, который знает и освоил его источник, во всех копиях.
- Варианты графа: `Clones` — непересекающиеся копии; `CrossEdges` — те же копии плюс случайные рёбра между копиями: каждый FND-клон даёт 2 `informs` (вес 0,3) на ENG/PRC своей дисциплины в других копиях; каждый клон поколения ≥ 1 с вероятностью 1/4 получает 1 `requires` на узел строго более раннего поколения в другой копии, который знает каждый актор-источник, знающий потомка (граф ацикличен, стартовое знание замкнуто).
- `generator_seed` = 85621515 (`0x51A7B0B`, `SynthWorldSpec.DefaultGeneratorSeed`) во всех точках.
- [Предп.] Замечание к записке §1: в `mods/core` 61 узел, а не ~180. Поэтому точка «180 узлов» тоже синтетическая (≈ 3 копии), а не «реальный срез».

| B | (200, 2000, CrossEdges) | t1 | 15 = seed {1, 2, 3} × 5 | Обязательная записываемая; исход не определяет |
| C1 | (200, 2000, CrossEdges) | t4, t16 | по 3 (seed 1, 2, 3) | Справка |

| D | сетка акторы 6/24/96/200 × узлы 180/500/2000 × {Clones, CrossEdges} (24 точки) | t8 | по 3 (seed 1, 2, 3) | Наклоны log-log |

- [Предл.] Точка исхода — вариант `CrossEdges`: клоны занижают ветвление (ADR-0016 «Минусы»), перекрёстные рёбра — более консервативная оценка. `Clones` в той же точке — справка C3.
- [Предл.] Сетка D шире ADR («Проверка»: N 6/24/200 × узлы 180/2000) по TASK-0065: добавлены N = 96 и 500 узлов.
- **Процессы последовательны**, по одному на машине. Порядок всех процессов блоков A–D перемешан один раз до прогона: Fisher–Yates с `CounterRng(20261117)` над списком в порядке таблицы; список записывается в план прогона до первого замера.
- **Внутри процесса** — одна точка, один seed, два прогона с новой `SliceSession`: месячный (`DailyTickProbe = false`) и дневной (`DailyTickProbe = true`, TASK-0063). Порядок: нечётная реплика — M, затем D; чётная — D, затем M (сглаживает дрейф внутри процесса).
- Команды [Предл., записка §4]: в начале каждого месяца каждому актору одна `SetBudgetShares` с его текущими долями (по состоянию не меняет ничего); одинаково в обоих режимах.

### П3. Прогрев и замер
- Прогрев 24 месяца, затем замер 120 месяцев, в каждом прогоне каждого процесса (ADR п. 5).
- `M_i` — время Stopwatch хоста на месяц `i` месячного прогона; `T_i` — на месяц `i` дневного прогона (все тики месяца: системный и дневные пустые с копией, хешем и снимком). Всё, что ядро делает за месяц (ADR п. 1 «Что входит»); загрузка, сборка, CSV — нет.
- Прямой путь (TASK-0063 принят). Запасной путь ADR п. 2 (`M^cmd + 29·k_copy,p95`) не применяется; если TASK-0063 откатят, этот раздел пересматривается до прогона.

### П4. Статистика
- **Бюджет** (точка A): медиана `T` = медиана 15 медиан процессов; p95 `T` = по всем 1800 месяцам (15 × 120). То же для `M` (запись).
- **Составляющие** по парам месяцев одного процесса (ADR п. 2): `k_i = (T_i − M_i)/29`, `K_d,i = 30·k_i`, `S_i = M_i − k_i`. `S` и `K_d` в исходе — **p95 по 1800 месяцам**; медианы записываются.
- [Предл.] Для справки записываются и `k_i` с числом дней месяца `d_i`: `(T_i − M_i)/(d_i − 1)`; исход считается по формуле ADR (29/30).
- Проверка формулы (запись): расхождение `T_p95` и `M_p95 + 29·k_p95`.
- **Удельные цены** (запись, ADR п. 7): `S_p50/N` и `S_p95/N` — мкс на актор-месяц, `S/узлы` — на узел, всего и по каждой системе по доле inclusive-профиля (П6); `k / число колонок Table` — `k` на колонку; `P` = доля Products × `S` (p95 — для правила `19·P`).
- **Наклоны** (запись): МНК `log T_p50` и `log S_p50` по `log N` при 2000 узлах (4 точки D, отдельно по варианту) и по `log узлы` при N = 200 (3 точки).
- **Шум** (точки A и B) = (p90 − p10)/медиана по 15 медианам процессов; порог ≤ 10 %.
- Правило раздела (ADR п. 3, critic M4): если `S_p95 + K_d,p95 + 19·P_p95 > 500` мс — до кода E1 обязателен ADR пересмотра раздела (запись, исход не меняет).

### П5. Условия, частота, троттлинг
- Сборка и среда (ADR п. 5): Release; одна точная версия .NET 10 (SDK и runtime записываются); `DOTNET_gcServer=0`, concurrent GC; TieredPGO по умолчанию; ОС записывается; питание от сети, профиль «производительность»; один процесс замера на машине; `ChunkSize = 8`.
- **Эталон частоты** до прогона: 8 потоков целочисленной нагрузки, 5 мин, `f_ref` = медиана средней по логическим CPU частоты за последние 3 мин. `f_ref` записывается сюда.
- **Сэмплирование**: раз в 1 с среднее `scaling_cur_freq` по `/sys/devices/system/cpu/cpu*/cpufreq/` (иначе `/proc/cpuinfo` «cpu MHz»; источник записывается).
- **Правило**: процесс троттлит, если медиана частоты за его окна замера < 0,9·`f_ref`. Такой процесс повторяется один раз (в конце очереди); записываются оба, в статистику идёт первый валидный. Если повтор снова троттлит — исход INCONCLUSIVE.

### П6. Валидность и профиль (без замера времени)
- **V1 (ADR (а))**: для seed 1, 2, 3 в точке A — дневной прогон 144 месяца при threads 1/4/8/16 (`ChunkSize` 8) и при t8 с `ChunkSize` 1/32: финальный `StateHash` одинаков, иначе INVALID.
- **V2** [Предл.]: для тех же seed финальный `StateHash` месячного и дневного прогона одинаков. Разложение `k_i` опирается на «одни и те же состояния» (ADR п. 2); при расхождении `S` и `K_d` недействительны → INVALID.
- **V3**: финальный хеш каждого замерного прогона равен хешу V1 того же seed и режима.
- **Профиль**: отдельный процесс, точка A, seed 1, дневной режим, прогрев 24 + 60 месяцев под `dotnet-trace` (CPU sampling): top-10 методов по exclusive CPU и inclusive-доли систем Knowledge, Industry, Products, Policy и Kernel/Session. Время этого процесса в статистику не входит.

### П7. Исходы (копия ADR-0016 §4)
`S` и `K_d` читаются по p95 месяцев. PASS означает: бюджет **не опровергнут** в масштабе M0 (нижняя граница цены полной игры), повторный замер — в E1.

| Исход | Условие | M0 (#272) | Действие |
|---|---|---|---|
| INVALID | (а) Для одного seed `StateHash` в конце прогона различается между threads 1/4/8/16 или между `ChunkSize` 1/8/32 (ADR-0002). (б) Нарушено одно из перечисленных условий: не Release; разные версии .NET между точками; server GC; другой процесс замера на машине; `ChunkSize` ≠ 8 в обязательной точке; работа от батареи. Троттлинг — не INVALID, а повтор (п. 5) | блокирует | Исправить, повторить |
| INCONCLUSIVE | Шум > 10% на прогоне без троттлинга (п. 5), или после повтора прогон снова троттлит | блокирует | Исправить харнесс или условия |
| PASS | Бюджет п. 1 выполнен; `S ≤ 100` и `K_d ≤ 50` | закрывает | ADR-0001 не опровергнут в масштабе M0; повторный замер — в E1 |

- Маршрут языка (тест Rust-порта) пре-регистрирован в ADR-0016 §4 и здесь не повторяется; в M0 не выполняется (#272).

### П8. Записываемая диагностика (исход не определяет)
- доля пауз GC: `GC.GetTotalPauseDuration()` за окно замера / время окна;
- наклоны log-log `T` и `S` по N и по узлам (П4);
- `S(t1)/S(t8)` (блоки B и A, по p50 и p95);
- `K_d` (p50, p95) и флаг `> 150`;
- top-10 методов по exclusive CPU (П6);
- удельные цены (П4), `P`, правило `19·P`;
- аллокации (ADR п. 6): `GC.GetTotalAllocatedBytes(true)` за окно / 120 — порог ≤ 1 МБ на месяц; сборки gen2 за окно — порог 0 (отметка «выполнено/нет»);
- пиковая память процесса (peak working set);
- дневной тик p99 (дневной прогон точки A, по всем тикам окна);
- пропускная способность Lab: `M_p50(t1) × 1872` месяцев; если > 10 мин — правило ADR п. 7 (N ≤ 24 по умолчанию, ≤ 100 прогонов полного масштаба);
- справка: t4, t16, фон, Clones (блок C); provenance: `core_commit`, SDK/runtime, ОС, `f_ref`, `data_hash` оверлея, `OverlaySha256` каждой точки, `generator_seed`.
