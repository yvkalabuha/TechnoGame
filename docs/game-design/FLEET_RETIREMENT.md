## 2. Что есть в модели (на чём строятся варианты)

- [Факт, спека A41/§4.2] Закупки ИИ: `r_AI = ⌊B_proc/unit_cost_floor⌋`; доли P1/P3/P2 закупок — 0,40 / 0,42 / 0,50. У P2 пресет `producible` держит парк в 8 600–9 900 машин, `upkeep/B_proc` 0,75–0,82 (`d1-output-diagnosis.md` §5). Равновесие: `N* = B_proc/upkeep`.
- [Факт] Слова `u = Σ upkeep / B_proc`: лёгкое < 0,25 · заметное [0,25; 0,5) · тяжёлое [0,5; 0,8) · съедает закупки ≥ 0,8 (STATE_WORDS §4, [Предп.] пороги).
- [Факт, ревью] Возраст на `readiness` и `upkeep` не влияет. Значит, внутри проекта когорты различаются только сроком списания: выгодно снимать самую старую (ближайшую к `service_life`) — тогда выигрыш минимален, и самую раннюю по возрасту снимать «не жалко». Между проектами разница есть: `perf_rel`, `upkeep`, `readiness`.
- [Факт, контракт §9.1] `fielded` = в строю ≥ 50 единиц когорт проекта, выпущенных на site актора, и освоены все `prc_set`. Списанные единицы в «в строю» не входят автоматически.
- [Факт, спека §3.4, #118] Бюджет — поток, не запас: денег «от продажи» нет; неизрасходованный остаток пропадает. Любой доход от списания — новый приток в бюджет (нарушает инвариант `spent ≤ budget` без правки).

## 3. Варианты

### Вариант A. Команда `retire_cohort(design_id, n)` — выход из строя без остатка
**Состояние.** Новых колонок на когорту нет: `count` уменьшается. Одна колонка проекта `retired[design]` (кумулятивно, шт., `Fx6` целое) — для печати и теста сохранения. Колонка `cancelled` не трогается.
**Команда.** Вычисляется по снимку t, применяется в начале t+1 (ADR-0006), порядок `(apply_tick, source_class, source_id, local_n)` (ADR-0014). Валидатор в шаге 2 §4.4d, после `close_line`, до `start_series`: свой проект в стадии С или В; `1 ≤ n ≤ ⌊units_in_service⌋` по состоянию на шаг 2; не больше одной `retire_cohort` на проект в месяц (как слот `close_line`, SLICE_COMPOSITION §7.3). Иначе отказ `BAD_RETIRE` (счётчик, журнал). Выбор когорт — **старшие по году первыми** (год возрастает; ничьей нет, год уникален внутри проекта). Выбора когорты игроком нет: нет и причины (возраст на готовность не влияет, п. 2).
**Эффекты.**
- Содержание: единицы удалены в шаге 2, до шагов 3–4 месяца t+1; `need` уменьшается на `n·upkeep`. Задержки нет.
- Аварии и выявление (шаг 3, 6): считаются по оставшимся `units_in_service` — снимаются и риск, и вклад в `fleet_hours`.
- Деньги за списанное: нет (σ = 0). Расхода тоже нет. [Предл.] Вариант A+ (возврат доли σ·`unit_cost_floor` в `left` месяца) отклонён для этой версии: меняет инвариант бюджета (§2) и открывает цикл «выпустить — списать — вернуть деньги».
- Стадия: проект в В, у которого `count` стал 0, переходит в «снят» по существующему правилу (все когорты нулевые). Проект в С может терять парк, пока линия выпускает; ИИ так не делает.
- `FV` (§5.5): не меняется — это гипотетический парк при B (П-11). `FV_fleet` (Σ по когортам; контракт §9.1 v2.3, П-11 «вернётся при нескольких классах») предлагается печатать как диагностику, не метрику исхода.
- `tech_lead`: только через `fielded` (G, T, N, P). Опасный случай — списание ниже 50 машин проекта, который был лучшим `fielded`: актор теряет G. Защита — в прогнозе (UI) и в правиле ИИ; сама команда игрока такое разрешает (его решение, видимое предупреждение).
**`why_not` и рычаг.** Корень цели «больше выпуска / новая серия» часто — `ECONOMY` и слово содержания «съедает закупки» (■, STATE_WORDS §4). Рычаг: `retire_cohort`, видимый в звене. Прогноз `retire_forecast(design_id, n)` — чистая функция снимка (как `force_forecast`): Δcontent/мес., новая `u` и её слово, новый `limiter` линии, `fielded` до/после, остаток службы списываемых единиц. Честность: если `limiter` линии не деньги (сплав, `H`, культура), прогноз пишет «высвобожденные деньги не будут потрачены» (#118) — это ответ на «почему мера не помогла».
**Читаемость для игрока.** Одно действие с одним числом; результат виден в следующем месяце в слове `u`. Риск «таблицы»: решение по строке отчёта без компромисса (см. краткий вывод). Противовес — прогноз `fielded` и запрет скрытых бонусов.
**Правило ИИ (A41-R) [Предл.] — ЗАМЕНЕНО в v0.2 на A41-R′ (§9); числа и пре-регистрация ниже сняты (#141).** Месячное решение по снимку, после `close_line` и до `start_series` (A41 шаг 3); RNG нет.
1. `u = Σ upkeep / B_proc`, где `B_proc` — статья закупок месяца. Если `u < u_hi(P)` — ничего. Гистерезис: при превышении снимаем до `u_lo(P)`.
2. Кандидаты: проекты в В или С (серия — только если не лучший по ключу); ключ списания: возрастание `κ_d = (readiness_d·perf_rel_d)/upkeep_d` («ценность за деньги содержания»), сравнение перекрёстным умножением в `Int128`, ничья — по `design_id`. `perf_rel^γ` в ключ не входит (чтобы `FV` не становился входом ИИ, зависимость от ADR-0003 ARM64 не расширяется, контракт §9.1 reviewer 11).
3. Из проекта с наименьшим `κ` снимаем `n = min(count_d − keep_d, ⌈(Σ − u_lo·B_proc)/upkeep_d⌉)` старшей по году части; когорты младше `a_prot` не берём. `keep_d` = 0 у всех, кроме проекта с наибольшим `κ` (лучшего «ценность за деньги»): ему `keep` = `n_service_min` = 50, чтобы не терять `fielded`. Повтор по следующему `κ`, пока `u ≤ u_lo` или кандидаты кончились; не больше одной команды на проект в месяц.
**Числа по профилям [Предп.], объявлены до прогона, привязаны к границам слов STATE_WORDS §4 (не подбираются).**
| | P1 «качество» | P3 «адаптивный» | P2 «массовость» |
|---|---|---|---|
| `u_hi` (запуск) | 0,25 («заметное») | 0,50 («тяжёлое») | 0,80 («съедает закупки») |
| `u_lo` (цель) | 0,10 | 0,35 | 0,65 |
| смысл | малый современный парк; не терпит содержания | терпит среднее | терпит почти всё; чистит только когда содержание съедает закупки |
`u_lo = u_hi − 0,15` для всех (одно число гистерезиса). `a_prot` = 60 мес. (треть `service_life`): свежие когорты не снимаются, чтобы ИИ не «выпускал и сразу списывал». Все три числа — по словам и доле срока, а не по `FV`/исходу.
[Факт, прогон D1] P2 сейчас 0,74–0,82; порог 0,80 сработает лишь у части seeds — это сознательное следствие доктрины «массовость терпит». Альтернативная проверка (одна абляция, не подбор): все профили 0,50 → 0,35 (`RET_UNI`).
**Детерминизм.** Чистая функция снимка и целочисленной арифметики (`Int128`, `⌈·⌉` как целочисленное деление вверх), порядок по `design_id`, RNG не используется (#28). Команда ИИ-источника — в журнале с `source_class` ИИ. Новая колонка `retired` и новые отказы — `schema_version`↑, `save_format_version`↑ (ADR-0013 п. 7); фикстуры пересоздаются из сценария и журнала (миграция до первого сохранения не нужна, контракт §3.1). Параметры A41-R — в манифесте HYP-0002, не в данных мода: `data_hash` не меняется.
**Пре-регистрация (#48) и калибровка.**
- До первого прогона main правка манифеста: правило A41-R + контроль `NO_RETIRE` (1…1000 seeds, +1000 прогонов ≈ + 1 мин, §10 спеки) + `RET_UNI` (1…400). ## 8. Команда `retire_cohort(design_id, n)` — уточнения v0.2 [Предл.]
Имена семейства: `retire_cohort`, `sell_cohort` (§10), позже `mothball_cohort`, `reactivate_cohort`; все `(design_id, n)`, один порядок выбора, одна форма отказа `BAD_<CMD>`.
1. **Ключ когорты.** `(design_id, год_выпуска)`; порядок выбора — `(год ↑, site_id ↑)`. [Предп.] Проект принадлежит одному актору и одному site, тогда `site_id` в порядке вырожден; если лицензионный выпуск даёт когорты одного проекта на разных site, порядок однозначен и без правки. Проверить в контракте §3.1 (systems-architect).
2. **Дробный хвост.** `count` — `Fx6`, `units_in_service = ⌊Σcount⌋`. Валидатор: `1 ≤ n ≤ ⌊Σcount⌋ − keep` (для игрока `keep` = 0, предупреждение, §9.3). Идём по когортам в порядке п. 1, снимаем `take = min(остаток n, count_i)` в `Fx6` (вычитание точное, округления нет): дробная часть самой старой когорты уходит первой, ровно `n` единиц суммарно. Если после снятия `Σcount < 1` (пыль), команда `n = ⌊Σcount⌋` снимает и пыль целиком; `retired += n + пыль` (`Fx6`); `loss_acc` при `Σcount = 0` обнуляется [Предл., проверить systems-architect: иначе фантомные потери без парка].
3. **Инварианты.** `cancelled` и `built_any` команда **не трогает** никогда (`cancelled` = «снят без выпуска», §3.1; списание парка — не отмена проекта). `Σ retired_month ≤ units_in_service` на шаге 2; `count ≥ 0`; `Σupkeep` падает ровно на `n·upkeep` (до пыли).
4. **Стадия и `Requirement`.** Проект в В с `count = 0` → «снят» (`Withdrawn`) с `cancelled = false`, `built_any = true` — то же состояние, что после списания по возрасту. `Requirement` (A41) и повтор A40 различают только `cancelled`; списание парка их **не запускает** и не гасит: цепочка «снять → Requirement» остаётся только через потребность поколения, как и без команды. Проект в С: парк может стать 0, стадия остаётся С (линия работает). Одна линия на актора (#125) команды не касается; проект на линии ИИ не списывает (§9). Условие F17 (#138) и A40 — без изменений: команда не меняет допуск процессов. Тест: после `retire_cohort` полного парка проекта в В `Requirement` не вызывается в тот же месяц сам по себе.

## 9. Правило ИИ A41-R′ (#141) [Предл.]
Месячное решение по снимку, после `close_line`, до `start_series` (A41 шаг 3). RNG нет, `Int128`.
1. **Линия** `L` — проект на единственной линии актора (#125). Если линии нет — правило не работает.
2. **`κ`.** `κ_d = perf_rel_d / upkeep_d`, где `perf_rel_d` — `Fx6` raw, `upkeep_d` — целые raw в месяц (> 0). `readiness` в `κ` **не входит** (v0.1 включал): она зависит от `paid/need`, которое сама команда меняет — получилась бы обратная связь; `κ` — свойство проекта. Строго лучше: `κ_L > κ_d ⇔ perf_L · upkeep_d > perf_d · upkeep_L` (`Int128`, оба произведения положительны). Равенство — «не строго лучше»: списания нет. Порядок кандидатов: `κ ↑`, при равенстве `design_id ↑`.
3. **`keep_d`.** `n_service_min` для каждого `d ∈ Def(K)`, где `Def(K)` — проекты `fielded` актора, определяющие текущий `K = (G, T, N, P)`: по каждой компоненте (контракт §9.1) проекты, достигающие её значения, объединением. Остальным `keep = 0`. `keep` считается по единицам, учитываемым в `fielded` (когорты на site актора). [Предл.] Точное определение `Def(K)` по §9.1 — simulation-engineer.
4. **Условия.** Кандидат `d ≠ L`, `d` в В (не в С), `κ_L > κ_d` строго, `limiter(L)` = деньги (именование — по спеке A41), `u ≥ U_HI(P)`. Тогда `n = min(count_d − keep_d, ⌈(Σupkeep − U_LO(P)·B_proc)/upkeep_d⌉)`; когорты моложе `A_PROT` не берутся. Если `limiter(L)` — не деньги, освобождённые деньги не будут потрачены (#118): правило молчит. Проект, который сам на линии, не списывается никогда.
5. **Выбор «списать или продать»** — §10.6. Не больше одной команды на проект в месяц.
6. **Плейсхолдеры, объявляются после печати T6c2 и до первого прогона main:** `U_HI(P)`, `U_LO(P)` (по профилям P1/P3/P2; привязка к словам STATE_WORDS §4 — только как правило выбора, не как значения), `A_PROT`. Значений здесь нет намеренно (#141). [Предл.] Объявленные числа вносятся в манифест HYP-0002 одним коммитом до прогона.
7. **Абляция `PURCHASE_CAP` (для сравнения, критик).** Команд нет; закупки ограничены: `r = min(r_AI, max(0, ⌊(U_LO·B_proc − Σupkeep)/upkeep_L⌋))`. Остаток денег пропадает (#118). Те же `U_LO`, что в main — иначе сравнение нечестное.

## 10. Продажа на внешний рынок `sell_cohort(design_id, n)` (#142) [Предл.]

**10.2 Команда.** Те же правила, что у `retire_cohort` (§8): снимок t → применение в начале t+1, шаг 2 после `close_line`; старшие когорты первыми; один вызов `sell_cohort` или `retire_cohort` на проект в месяц (общий слот); отказы `BAD_SELL`: `NOT_SURPLUS`, `QUOTA`, `STAGE`, `COUNT`.
**10.3 Кто может купить (допуск).** Продаётся только проект с `gen(d) ≤ G_front(t) − 1`, где `G_front(t)` — наибольшее поколение, которое стоит `fielded` хотя бы у одного актора среза. Смысл [Предп.]: самую передовую машину на рынок не отдают, и рынок не «подпитывает» лидера. Машины текущего фронта (`gap = 0`) — только `retire`.
**10.4 Цена.** Общая сумма: `Σ_i take_i · price_i`, `price_i = ⌊ σ0 · φ_gen(gap) · rem_i/service_life · unit_cost_floor(d) ⌋` (целочисленно, `Fx6`/`Int128`; `rem_i = service_life − возраст_i` в месяцах на шаге 2, ≥ 0). `gap = G_front − gen(d) ≥ 1`. Значения по умолчанию [Предп., без источника]: `σ0` = 0,50; `φ_gen` = 1,0 / 0,6 / 0,3 для `gap` = 1 / 2 / ≥3; `ς` (годовая квота) = 0,10 парка проекта-продавца. Цена не растёт ни от чего другого: потерять на «купил — продал» нельзя меньше половины стоимости (`σ0` ≤ 0,5), цикла выигрыша нет.
   *Исторические данные (поиск 2026-11-04).* Годовых цен вторичного рынка для F-86, Meteor, Vampire, MiG за 1950–70-е не найдено. Найдено: Hansard подтверждает продажи излишков иностранным государствам (Бельгия, Нидерланды, Франция и др.) без цен — [HC Deb 12 May 1947](https://api.parliament.uk/historic-hansard/written-answers/1947/may/12/surplus-military-aircraft-foreign-sales), [HC Deb 21 March 1950](https://api.parliament.uk/historic-hansard/written_answers/1950/mar/21/aircraft-foreign-sale) («не в общественных интересах раскрывать количества»); новые Meteor T.7 для Нидерландов ≈ £29 975 за штуку [Факт, вторичный, выдача поиска, не проверено по первоисточнику]; стоимость F-86A 1950 ≈ $178 408 [Факт, низкое качество источника]. Доля «цена б/у / новая» не восстанавливается. **10.5 Поступление денег и инвариант бюджета.** Единицы снимаются на шаге 2 месяца t+1; выручка `sale_income(t+1) = Σ price_i` (целое, `Int128`) входит в статью закупок `B_proc(t+1)` до шага 4 — то есть работает как «деньги месяца t+1». Контракт: инвариант `spent ≤ budget` переформулируется в `spent ≤ budget + sale_income`; вводится накопительный счётчик `sale_income_total[actor]` для теста сохранения («внешний приток = Σ цен проданного»; других притоков нет). Неизрасходованная выручка пропадает, как и бюджет (#118). Внешний приток — единственный в срезе; он **не** копится и не переносится.
**10.6 Лимит и правило ИИ.** Квота: `sold_year(актор, проект) ≤ ⌈ς·N_проект⌉` на календарный год (N — `Σcount` на 1 января); общий рынок между продавцами [Предл.] не вводится (иначе скрытая связь акторов). ИИ в рамках A41-R′ (§9, условия те же): для выбранных `d, n` сначала `sell_cohort` на `min(n, квота, допуск)`, если средняя цена за единицу ≥ `π_MIN(P)·unit_cost_floor` (профильный минимум, «не отдавать за бесценок»); остаток — `retire_cohort`. Плейсхолдеры (после T6c2): `ς(P)`, `π_MIN(P)`, `sell_first(P)` ∈ {да, нет} — P1 «качество» разумно «да», P2 «массовость» — решается данными, не здесь.
**10.7 Честно про баланс.** Продажа не хуже списания пока есть квота и допуск, значит `retire` в main для ИИ — редкий случай (машины фронта `gap = 0`, превышение квоты, цена ниже `π_MIN`). Для игрока `retire` остаётся (быстро, без квоты, без реформ). Риск: продажа превращается в «печатный станок» (выручка → закупки → выпуск → `line_E`). Ограничено: `σ0` ≤ 0,5, возраст, квота `ς`; контроль — печать §11 и `NO_SALE`.
**10.8 Влияние на метрики (#143).** `FV` и `tech_lead` — без ценности проданного: проданные единицы выходят из «в строю» ровно как списанные, `keep` тот же. Покупатель вне среза: утечки технологий в срезе нет (`mastered` соперников не растёт). `volume_lead` считает выпуск, а не продажи.
**10.9 `why_not` и читаемость.** Звено `ECONOMY` / слово содержания: два рычага рядом — `retire_cohort` и `sell_cohort`. `sell_forecast(design_id, n)` — чистая функция снимка: выручка с разложением на три множителя (база · возраст · поколение), Δcontent/мес., новая `u` и слово, `limiter` линии, `fielded` до/после, квота остатка, причина отказа (`NOT_SURPLUS` показывает `gap`). Если `limiter` — не деньги: «выручка не будет потрачена». Одно действие — одно число выручки; результат виден в слове `u` и в строке «внешний приток» отчёта месяца.
