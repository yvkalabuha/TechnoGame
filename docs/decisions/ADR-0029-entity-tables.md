# ADR-0029 — Таблицы сущностей при переходе на ADR-0020: что уходит из таблицы акторов, дочерние таблицы с чанками по родителю

> Ред. 3 от 2026-11-25, systems-architect: из черновика `docs/decisions/drafts/adr-draft-entity-tables.md` ред. 2 (ред. 1 — 2026-11-24); по существу не менялся, ответы #512–#514 его не касаются. Учтены gate-ревью `docs/reviews/m1-adr-drafts-critic.md`, `docs/reviews/m1-adr-drafts-advocate.md`, DeepSeek `tools/llm_worker/runs/gate-adr-draft-entity-tables-c7caca75-third.json`, решение #504. Уровень: gate (этап 3.7 `development/PLAN.md`, находка A5 ревью 2026-11-19). Пара: ADR-0027, ADR-0028. После ACCEPTED текст не меняется.

## Краткий вывод
- Что меняется: это внутреннее устройство данных, игрок его прямо не видит. Проекты изделий, лицензии и институты получают свои таблицы вместо длинных наборов полей у каждой страны.
- Что это даёт игре: число одновременных проектов и лицензий страны задаётся в данных и меняется без переделки формата; на рынке лицензий страна держит несколько лицензий; ссылки на проект или лицензию из команд, подсказок «почему нет» и сохранений не путаются после закрытия и повторного открытия слота.
- Ограничение M1: институт не переходит к другой стране сам; передача (например, при смене владельца территории) должна быть заранее подготовлена в данных сценария, иначе загрузка сообщит об ошибке. Переименование внутри страны (NACA→NASA) работает.
- Цена: новый механизм ядра — ≈ 3–4 дня разработчика; перенос в ветке дневного тика одним влитием; расчёт месяца дороже на ≈ 3–6 мс [Предп.], это мерится прототипом.
- Если код рычагов институтов и лицензий ещё не начат, когда механизм ядра готов, они сразу пишутся таблицами (решение Orchestrator, п. 7) — без второго переноса.
- Вопросов владельцу нет.

## Контекст
- [Факт: ревью проекта 2026-11-19, A5] Вынести сущности в свои таблицы со строкой `(actor, generation)`; это gate.
- [Факт: ADR-0005 п. 1, п. 3] Подсущности с ёмкостью — группы колонок или своя таблица; слоты со счётчиком поколения, ссылка — handle.
- [Факт: ADR-0020 п. 2–3] compute пишет только строки своего чанка своей `ChunkTable`; в строки других таблиц — только через буферы чанков в merge. Строки `actors` создаются в t0.
- [Факт: `docs/architecture/notes/multi-table-api.md` §1.3] `Compute(in TickContext, int chunk, int rowStart, int rowEnd)`; `TickContext` — `World`, `ChunkTable`, RNG, тик, календарь; оценка `World` 1,5–2,5 дня developer.
- [Факт: код `ProductsSystem.cs:188–227`, `CommandState.cs:38–86`, `PolicySystem.*`, `KnowledgeSystem.cs:109–124`] Раскладка семейств по слоту, очереди `cmd.*`, одна лицензия `pol.lic.*`, узлы `know.*.{N}` (ред. 1, не перепроверялось).
- [Факт: TASK-0152; `production-lines-and-licence-market.md` разд. 2] Несколько лицензий на страну с ключом `(seller, gen)`.
- [Факт: RR-0012; #325] Смена `owner` института внутри одной страны (NACA→NASA) и события смены владения территорией.
- [Факт: TASK-0151…0153 IN_PROGRESS, 2026-11-25] Код рычагов пишется сейчас; #504 — параллельные ветки.

## Решение
1. **Своя таблица** — если число экземпляров на актора задаётся ёмкостью или данными и у сущности есть время жизни или ≥ 5 полей:
   - `designs`: строка = (актор, слот), `max_designs` строк на актора; колонки проекта, `occupied`, `generation`, решения ИИ по проекту (пишет `PolicyDecision`, читает `ProductsFlow`; один писатель на колонку), постоянные приказы игрока. Годы когорт остаются семейством колонок внутри `designs`.
   - `licences`: строка = (покупатель, слот), ёмкость `max_licences` из данных; колонки `seller`, `design_gen` (ключ рынка `(seller, gen)`), `occupied`, `generation`. Инвариант: у одного покупателя не больше одной занятой строки с данным `(seller, design_gen)`. `entity_id` лицензионных событий ADR-0021 — глобальная строка `licences` (строки постоянны, id стабилен).
   - `institutes`: строка = институт из данных сценария (все, включая будущих кандидатов), сортировка (актор-владелец, id); колонки `built` (0/1, может переключаться), уровни, опыт, приоритетный узел. Строки с t0, активность — колонкой. **Инвариант M1: актор-владелец строки не меняется.** Смена страны-владельца — закрытие строки (`built = 0`) и открытие заранее подготовленной в данных строки нового владельца; переименование внутри страны (NACA→NASA) — колонка, не владелец. Валидатор загрузки: событие сценария, передающее институт другому актору без подготовленной строки, — ошибка.
2. **Handle** — один для всех дочерних таблиц: `(row, generation)`, где `row` — глобальная строка таблицы (`offset[actor] + slot`). Команды, виды, `why_not` и сейв ссылаются только так; устаревший handle (другое `generation`) — отказ команды с причиной.
3. **Остаются семействами колонок**: матрицы «актор × объект данных» без времени жизни — узлы знаний, кластеры Industry, скалярные поля актора. Узлы переносятся в таблицу `knowledge` (строка = актор).
4. **Очереди `cmd.*`**: в #228 команда действует в тике своего штампа (ADR-0019 п. 13); разовая команда живёт только в журнале команд (ADR-0014), постоянный приказ — колонка своей сущности. **То же правило уже для пакета рычагов:** новых семейств `cmd.*` нет (чек-лист ревью, ADR-0027 п. 15).
5. **Дочерняя таблица (Kernel).** `Table` объявляет родителя и постоянные смещения `offset[parentRow]` (ёмкость: `a·cap`; данные: префиксные суммы при сборке).
   - API: `Span<T> NextRange(in TickContext ctx, int chunk)` у дочерней колонки; диапазон — функция `(chunk, RowCount родителя, chunkSize, offset)`; потоковых и `[ThreadStatic]` данных нет (L2). Пустой родитель — пустой `Span`.
   - `Next` дочерней колонки в compute системы с `ChunkTable` = родитель бросает исключение (одна проверка bool, как ADR-0017 п. 14) — запись вне диапазона закрыта проверкой Kernel и архитектурным тестом, не «по построению».
   - **Открытие CoW** дочерних колонок — однопоточное, в планировщике до compute системы, по списку колонок записи системы (тот же, что проверяет тест «один писатель») [Предп.: список доступен Kernel; иначе — объявление при регистрации системы].
   - Merge и буферы ADR-0020 п. 2 остаются для записи в чужие таблицы и в дочерние строки чужого чанка.
6. **Время и ветка.** Kernel `World` + дочерние таблицы — один шаг developer [Предп.: 1,5–2,5 дня `World` + 1–1,5 дня дочерних таблиц и тестов]. Перенос `designs`, `knowledge`, `licences`, `institutes` — в ветке `m1-228` по системам (Policy → Knowledge → Industry → Products), **одним влитием на `main`**, без промежуточного состояния и двойной записи; эталоны — один раз в ветке.
7. **Рычаги до переноса** (TASK-0151, TASK-0152): состояние институтов и лицензий — объект раскладки (как `ProductsLayout`), строки сгруппированы по актору, ключи и handle п. 1–2; голых индексов в командах и видах нет. [Предл., D2 Orchestrator] Если на момент начала кода состояния TASK-0151/0152 шаг Kernel п. 6 может влиться раньше рычагов, институты и лицензии сразу создаются таблицами в пакете рычагов (второй перенос не нужен); решение и дата — в ORCH_DECISIONS.

### Частично заменяет
- **ADR-0020 п. 2** (запись в строки других таблиц только через буферы): исключение — система с `ChunkTable` = родитель пишет строки дочерней таблицы **своего** чанка напрямую через `NextRange` (п. 5). Остальная запись между таблицами — через буферы, как было. Утверждается владельцем вместе с этим ADR.
- **ADR-0005 п. 1** — дополняется (выбор «своя таблица» для перечисленных сущностей).

## Рассмотренные альтернативы
| Альтернатива | Причина отказа |
|---|---|
| Оставить всё семействами на `actors` | Ёмкость в схеме, ≈ 1,5 тыс. колонок проектов на актора [Предп.], голые номера слотов; A5 остаётся |
| Таблица «актор × узел» для знаний (400 тыс. строк) | CoW открывает 3,2 МБ на колонку каждый день [Предп.: ≈ 10–20 мс/мес.] |
| Дочерние строки только через буферы merge | Каждый день все записи `ProductsFlow` шли бы через буфер: аллокации и цена merge на тике |
| `ChunkTable` = `institutes` с колонкой `owner`, суммы актору через журнал | Работает при смене владельца, но дороже; запасной путь, если M2 потребует передач без подготовленных строк |
| Годы когорт как строки (третий уровень) | См. «Разногласия» |
| ECS / динамические строки | Отклонено ADR-0005 |

## Последствия
- **Плюсы:** `max_designs` и `max_licences` меняют `n_rows`, а не колонки; один handle; общий образец для новых сущностей; схема актора стабильна.
- **Минусы:** новый механизм Kernel; `MaxCohortYears` по-прежнему меняет `designs.schema_version` и формат сейва; сейв меняет `save_format_version` (сейвов игрока нет, ADR-0013 п. 7); код рычагов переносится второй раз, если D2 п. 7 не сработает [Предп.: ≈ 1–2 дня в `m1-228`].
- **Цена тика** [Предп.]: `designs` 2400 строк, ≈ 40 колонок × 19 КБ ≈ 0,8 МБ копий в день → ≈ 3–6 мс/мес. в `K_d`. Мерится прототипом этапа 3.5 (ADR-0027 п. 1) и пишется в реестр цен (ADR-0028 п. 6).
- **Обязательно:** запись в дочерние строки — только через `NextRange`; handle п. 2 во всех ссылках; инвариант владельца института.

## Проверка
1. L2 на мире с дочерней таблицей — threads 1/4/8/16 × ChunkSize 1/8/32 × ёмкость 1/12 и переменные смещения; хеш каждого дня равен.
2. `NextRange` возвращает ровно диапазон чанка (property по случайным смещениям); пустой родитель — пустой `Span`; `Next` дочерней колонки в compute системы-родителя — исключение (отрицательный тест).
3. CoW: дочерняя колонка, которую пишут 8 чанков в одном тике, открывается один раз до compute; L2-тест с открытием в первый день.
4. Архитектурный тест: один писатель на колонку (TASK-0086) по всем таблицам, включая Core, Session, Lab.
5. Save/load: тот же хеш; смена `max_designs` меняет `n_rows`, хеш мира и `save_format_version` и не меняет `designs.schema_version`; смена `MaxCohortYears` меняет `designs.schema_version`.
6. Валидатор данных: институт, переданный событием другому актору без подготовленной строки, — ошибка загрузки; дубль `(seller, design_gen)` у покупателя — исключение команды `BuyLicence`.
7. Ревью TASK-0151/0152: раскладка, handle п. 2, нет голых индексов и новых `cmd.*`.
