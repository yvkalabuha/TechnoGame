### 3a. Ось «надёжность» (#89, G-6) [Предл.]
**Почему v0.1 не работал.** В v0.10 выявление и штраф нормированы на `D0`, а в правке A35 v0.1 `D_ref = d0·complexity` — сложность сокращалась, оставалась только `novelty`; срок до серии от `D0` не зависел. Слово «доводка» на экране было ложным (G-6).

**Эталон.** `D_ref = d0·c_ref`, `c_ref` = `complexity` эталонного «превосходящего» G2 = 37 (`product_class.md` §2) → `D_ref` = 740. Смысл: `D_ref` — это `D0` полностью нового проекта эталонной сложности у КБ без опыта. Почему G2: по нему калиброван `λ_D` в A31 («60% `D0` за 24 мес.» ≈ исторические «первый полёт → строй» 12–31 мес., `product_inputs.md` §10) [Предп.: случаи §10 — в основном машины G2-эпохи, research-scientist подтверждает]. `c_ref` берётся из данных и не калибруется.

**Механизм 1 — допуск к серии (для всех, валидатор команды `start_series`):** `D_hidden ≤ k_gate·D_ref` и испытаний ≥ `t_test_min`. `D_hidden = D0 − detected` (A31). Решение в закрытой форме: доля, которую нужно выявить, `f* = 1 − k·D_ref/D0`; если `f* ≤ 0` — только `t_test_min`; иначе `T* = (f*/λ_D)^(1/β)` часов испытаний.
- `k_gate` = 0,7 = самая смелая доктрина v0.10 (P2, «≥ 30% `D0`») на эталонном проекте: никто не запускает серию раньше, чем самый смелый ИИ v0.10 на эталоне.
- `t_test_min` = 6 мес. = срок P2 v0.10 на эталоне (30% `D0` за 6 мес., A31). Нужен, иначе знакомая сборка шла бы в серию без испытаний.

**Механизм 2 — A35 (готовность):** `readiness = min(1, оплачено/нужно)·q·(1 − ψ_D·D/D_ref)`, `D` = скрытые + выявленные неисправленные. **Смысл `ψ_D`:** доля готовности, которую теряет парк с `D_ref` открытых дефектов (т. е. эталонный новый проект до любых испытаний). Значение 0,5 сохраняется: на эталоне оно совпадает с v0.10. Ограничение (валидатор манифеста): `ψ_D·c_max/c_ref < 1`, где `c_max` — наибольшая `complexity` среди всех сборок класса (из `pareto_audit`); тогда готовность не уходит ниже 0 без зажима. Сейчас `c_max` ≈ 49–55, предел — 74.

**Доктрины ИИ (вместо «выявлено ≥ x_P·D0»):** запуск при `D_hidden ≤ k_P·D_ref` и допуске механизма 1, `k_P = 1 − x_P`: P1 0,40 · P3 0,55 · P2 0,70 (= `k_gate`). Смысл через готовность: доля готовности, которую теряет парк из-за скрытых дефектов при запуске, `ε_P = ψ_D·k_P` = 0,20 / 0,275 / 0,35. Для эталонного проекта сроки совпадают с v0.10 точно. Для остальных сроки растут с `novelty·complexity/(1 + bureau_exp/E_B)`.
- Пример (P1, `λ_D` 0,0087, `β` 0,5, 200 ч/мес.): новая G3-сборка (`cx` 48, `novelty` 1, опыт 0, `D0` 960) — 32 мес. (v0.10: 24); сборка C §5 при опыте 0 (`D0` 164) — 6 мес. Честно: разброс задаёт прежде всего `novelty` и опыт КБ (×5), сложность — до ×1,9.
- Это меняет пре-регистрированное правило ИИ §4 — входит в пакет G-7 (§10).

### 3b. Досрочный запуск серии (#94) [Предл.]
**Команда.** `start_series(design_id, rate, force)`. Валидатор: стадия О (работа `W` выполнена) — для всех. Если допуск механизма 1 не выполнен: `force = false` → отказ со звеном `why_not` (§4); `force = true` → принято. Компьют по снимку t, применение в t+1 (ADR-0006). Решение необратимо: «отменить досрочность» нельзя, темп меняется обычными командами. ИИ `force = true` не подаёт никогда (#94); инвариант для test-engineer: в журнале команд ИИ нет `force = true`. RNG нет.

**Уровень допуска проекта.** `D_gate = min(k_gate·D_ref, D0 − detected(t_test_min·test_rate))` — сколько скрытых дефектов осталось бы в момент, когда допуск открылся бы при одних испытаниях (обе части условия #89). Считается один раз при входе в стадию О (Fx6, поле проекта). Пример: новая G3-сборка §3a (`D0` 960) — `D_gate` = 518, допуск через ≈ 15 мес. испытаний.

**Избыток.** `X(t) = max(0, D_hidden(t) − D_gate)`. Скрытые дефекты только убывают, поэтому у всякого, кто запустил серию по допуску, `X ≡ 0`: все штрафы ниже нулевые, отдельного флага «досрочный» в формулах нет. Прогоны ИИ (main) от §3b не меняются — сравнимость с v0.10 и HYP-0002 сохраняется.

**Плата (три части, одна причина — дефекты, которые нашёл строй, а не испытатели):**
1. **Аварии** (#94). В compute t: `loss_acc += (((units_in_service·fleet_hours)·a_acc)·X(t−1))/D_ref`, floor на каждом `·` и `/`. В merge списывается `⌊loss_acc⌋` машин, остаток копится (Fx6, без RNG). Машины снимаются с когорты проекта с наибольшим числом машин, ничья — более ранний год выпуска. Потеря уменьшает `n_v` и содержание. `a_acc` — вероятность потери на лётный час при `X = D_ref` (смысл как у `ψ_D`). [Предп.] 1·10⁻³ 1/ч, З. Порядок: ранние годы службы F-100 — ≈ 75 потерь на 100 000 ч (1956), за всю службу ≈ 16; F-104 USAF за всю службу ≈ 25 [Факт по выдаче поиска: AFSC https://www.safety.af.mil/Portals/71/documents/Aviation/Aircraft%20Statistics/F-100.pdf (колонку таблицы я не сверил); https://hushkit.net/2013/06/13/aviation-mythbuster-1-why-everything-you-thought-you-knew-about-the-f-104g-starfighter-is-wrong/, 2026-11-03]. Избыток ранних лет над зрелым уровнем ≈ 6·10⁻⁴ 1/ч. research-scientist проверяет таблицу AFSC.
2. **Доработка построенных** (моё добавление сверх #94, нужно решение владельца). Дефект, найденный в строю, исправляют и на уже построенных машинах. Пул `retro_pool` = `X` в месяц запуска. Каждый исправленный дефект (A32), пока пул > 0, расходует одну единицу пула и стоит `c_retro·units_in_service`, `c_retro = (unit_cost_floor·ρ_retro)/D_ref`. `ρ_retro` — доля цены машины, которую стоит доработка на `D_ref` дефектов. [Предп.] 0,5, З, источника нет (research-scientist: доработка F-100A в 1955 г.). Платится из бюджета закупок после содержания и до закупок. Если денег нет — исправляется столько, сколько оплачено; дефект остаётся открытым и бьёт по готовности.
3. **Готовность** — A35 без изменений: `D = скрытые + открытые`. Досрочный парк стартует с низкой готовностью, потому что `D` ≈ `D0`.

**Почему без доработки механика пуста (ручной расчёт, ≈; точно — плечо `FORCE`, §8).** По A31 выявление идёт и в строю (`k` = 1, 20 ч на машину в месяц). Новая G3-сборка (`D0` 960, `X` при запуске 442 = 0,6·`D_ref`, исправление 58 деф./мес. при КБ 674):
| | Большой парк, 20 шт./мес. | Малый парк, 3 шт./мес. |
|---|---|---|
| Ждать допуска | серия с мес. 15, готовность 0,65, «боеготов» ≈ мес. 26 | серия с мес. 15, готовность 0,65 |
| Досрочно с мес. 0: `X` → 0 | ≈ 3 мес. | ≈ 7 мес. |
| Готовность мес. 1 / 6 / 15 | 0,35 / 0,55 / 0,90 | 0,35 / 0,55 / 0,92 |
| Аварии при `a_acc` 10⁻³ | ≈ 0,7 машины | ≈ 0,2 |
| Доработка при `ρ_retro` 0,5 | ≈ 32 цены машины ≈ 18% закупок первых 9 мес. | ≈ 3 цены ≈ 14% закупок первых 7 мес. |
Строй находит дефекты в 2–4 раза быстрее испытаний. Поэтому без доработки досрочный запуск стоил бы < 1 машины и был бы доминирующим ходом. Доработка делает цену заметной: это деньги закупок, то есть меньше машин в поле `N`.

**Почему это решение, а не очевидный ход** [Предп.; проверка — плечо `FORCE`]:
- Ранний парк при готовности 0,35–0,55 мало добавляет к `FV` (это max по проектам): старый парк G2 в 300 машин при 0,95 перекрывается досрочным G3 только с ≈ 13-го месяца. Если соперник не впереди и старый парк ещё годен, досрочность — деньги без выигрыша.
- Бюджет закупок: 14–18% ранних закупок уходят на доработку. При бюджетном потолке это минус в поле `N`.
- Темп — второе решение внутри досрочности. Малая «предсерия» (низкий темп) дешевле в доработке, потому что меньше машин, но строй ищет дефекты медленнее, и низкая готовность держится дольше.
- Досрочность выгодна, когда соперник уходит вперёд по `T`/`P` или старый парк уходит в списание. Это исторический случай: F-100A посадили на землю в ноябре 1954 г. после серии катастроф и дорабатывали [Предп.: дата и обстоятельства из памяти, research-scientist сверяет].
- Риск: у богатого актора в гонке досрочность может выигрывать почти всегда. Критерий проверки и что делать — §8.

**Зависимость от A31.** Если simulation-engineer снизит вес лётных часов строя `k` (лётные часы без приборов дают меньше сведений, чем испытательные) [Предп.], избыток держится дольше, аварии и доработка растут. Это затрагивает и ИИ, поэтому решать надо в пакете G-7, а не здесь (§12).

### 3c. Компромисс в слоте двигателя (F-PC5) [Предл.]
**Проблема.** У всех рангов двигателя PRC 54 и 44. При R-PS2m шаги ранга 1→2 и 3→4 не меняют ни ΣPU, ни множитель. Значит, более новый двигатель того же блока стоит 0 по цене, сплаву, часам и освоению и только поднимает `perf`. Пример §5: B с `eng_g4` вместо `eng_g3` — та же цена, `perf` ×1,29. Слот двигателя — мёртвое решение: «бери новейший». Это противоречит #82.

### 3d. Планер M2 (F-PC4) [Предл.]
**Нужен ли PRC tier 5 «конструкция M2» — да.** Сейчас у `af_mach2` и `af_titanium` один `prc_set`. Актор, освоивший титан, делает планер M2 сразу с тем же `yield`, а вход в G4 закрыт только знанием (узел 29). Для игры это плохо по трём причинам:
- платформа G4 — главный скачок среза, а «уметь» на нём не проверяется. Это единственная точка, где «знать» сразу означает «делать»;
- у `af_mach2` разница с `af_titanium` — только цена ×3,4 и `perf` ×1,125. Пока G4 не нужен, это мёртвая альтернатива; когда нужен — безальтернативная, и без PRC в ней нет решения «когда браться»;
- `complexity` не растёт, поэтому ось «надёжность» G4-планер не замечает.
С PRC tier 5 (+5 к `complexity`, эталон G4 49 → 54): освоение M2 становится отдельным путём (оснастка, культура), `D0` и `W` растут, `c_max` ≈ 60 остаётся ниже предела 74 (§3a). Цена эталона G4 воспроизводится тем же правилом R-PS2m (остаток в блоке планера), меняются только множители. Решает Orchestrator (граф, `data_hash`); пересчёт — research-scientist.

## 6. Пресеты и политика ИИ (HYP-0002)
[Предл.] `compose(preset, a, snapshot t)` считается в compute месяца t, применяется в t+1 (G-8). Детерминирован, без RNG; ничья — ранг, затем `alt_id` (ordinal). Цель `g*` = новейшее известное APP (правило `Requirement` §4 спеки), планер — не ниже `platform_min_rank[g*]`.
1. **`superior`** (P1): в каждом слоте — наибольший ранг из `avail` (сплав и `yield` не учитываются: доктрина «качество»).
2. **`producible`** (P2): в каждом слоте — наибольший ранг из `avail`, у которого узкий PRC на своём site даёт `yield ≥ y_prod` (0,5). Для горячей части дополнительно `alloy_ok(h)`: `supply_a / alloy_kg[h] ≥ n_service_min / T_field`, `T_field` = 24 мес. (З). Нет подходящих — самая лёгкая альтернатива (для планера — порог). Правило совпадения §1.4 и F-PC2/F-PC3 сохраняются.
3. **`adaptive`** (P3): из `superior` и `producible` — больший `FV`.
4. **`adaptive_local`** (P4, **только диагностика**, G-9): от сборки P3 перебираются все замены **одного** слота (доступные, планер не ниже порога); берётся лучший `FV`, если он строго больше, ничья — `alt_id`. Печатается доля `Requirement`, где P4 ≠ P3, и прирост `FV`. Это прокси «стоит ли игроку править 1–2 слота»; в main не действует.

**`FV` для ИИ и метрики** [Предл.; #91; G-5; меняет спеку §5.5 и контракт §9.1]:
- `FV_a = max_v n_v·readiness_v·PowFrac(perf_rel_v, q10_γ)`, `γ` = 0,5 (`q10_γ` = 512 — тот же, что у `q10_β`), З.
- **Обоснование `γ`** без подгонки: по квадратичному закону Ланчестера сила стороны пропорциональна средней эффективности единицы, умноженной на квадрат числа единиц [Факт: F. W. Lanchester, «Aircraft in Warfare», 1916, https://www.math.fsu.edu/~mesterto/NewCourses/MAP5932/2016/PDF/PDF02/Lanchester1916aAircraftInWarfare.pdf; https://en.wikipedia.org/wiki/Lanchester%27s_laws, 2026-11-03]. `n·√perf` = `√(perf·n²)` — монотонное преобразование этой силы, поэтому проекты упорядочиваются так же. `γ` = 1 соответствует линейному закону. [Предп.] `perf` читается как эффективность единицы; это допущение, а не данные. Альтернативы, которые я отклонил: `log` (не определён при сравнении через ноль, нет механического обоснования), подбор `γ` по `pareto_audit` (запрещён #91).
- `n_v = min(n_budget, ⌊(supply_a/alloy_kg_v)·H_build⌋)` с шагом 10 вниз; `n_budget` — как в §5.5; `H_build` = `T_field` = 24 мес. (одна величина: «за сколько надо поставить парк»), З. G-5.
- `tech_lead` поле `P` остаётся линейным `perf` (порядок от вогнутости не зависит).

**Сколько проектов.** Не больше одного на пару (`g_p`, пресет), как слоты `(g, вариант)` v0.10. Производные — только в плече `DERIV` (§7).

**Не под результат.** `y_prod`, `n_service_min`, `T_field`, `γ`, `k_P`, `k_gate`, `t_test_min`, `c_ref` фиксируются в манифесте до калибровки и меняются только новым EXP.
