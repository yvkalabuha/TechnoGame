# ADR-0005 — Модель данных ядра: таблицы struct-of-arrays

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.
> Ревизия 2 (systems-architect, 2026-11-18): текст приведён к коду M0 и к ACCEPTED ADR-0013, ADR-0017. Многотабличный мир — предмет ADR-0020 (PROPOSED), здесь только ссылка.

## Краткий вывод
- Состояние мира — колонки `Table` из Kernel: плотные массивы `long`/`int`, двойной буфер `Current`/`Next` с copy-on-write (ADR-0017). ECS нет.
- Число строк таблицы фиксировано при сборке мира. Сущности, которые появляются по ходу игры (проекты, приказы), занимают заранее выделенные слоты; слоты не переиспользуются.
- В M0 мир — одна таблица «строка = актор», подсущности лежат группами колонок. Это расходится с ревизией 1 («таблица на тип сущности»); переход к нескольким таблицам описывает ADR-0020.
- Строковые ID живут в данных и в загрузчике; в тике — только плотные индексы.

## Контекст
- [Факт] В grand strategy мало типов сущностей и много связей. RR-0002.
- [Факт, код] `src/Singularity.Kernel/Table.cs`, `Column.cs`: `Table(rowCount)` с фиксированным `RowCount`; колонки `LongColumn`/`IntColumn` в порядке регистрации, этот порядок задаёт `StateHash`. `Current` — `ReadOnlySpan`, `Next` открывается на первое касание в тике (COW, ADR-0017 п. 10–13). `Load` вне тика для начального состояния и загрузки.
- [Факт, код] `TickRunner` и `TickContext` работают с одной `Table`. `SliceWorld` (Session) создаёт `new Table(scenario.ActorCount)`; Core-системы регистрируют группы колонок (`cmd.dsn.{k}.kind`, `ProductsLayout`: `max_designs` слотов на актора, «наименьший свободный, никогда не переиспользуется»).
- [Факт, код] Загрузчик модов (`Singularity.Core.Data.ObjectStore`): объекты по ID в `SortedDictionary` с ordinal-сравнением; `ScenarioData`/`ProductsLayout` разрешают ID в номера один раз при сборке (`ImmutableArray`).
- [Факт] ADR-0013 (ACCEPTED): сохранение — бинарный снимок колонок; порядок строк сохраняется байт в байт; состояния вне таблиц нет, кроме буферов `[Scratch]`; миграции — по стабильным строковым ID.
- [Факт, код] `ScratchTests` проверяет ADR-0013 п. 4: у систем нет изменяемых полей вне таблиц, кроме `[Scratch]` и явного списка `PrecomputedFields`. `CoreProject_PackageReferences_AreExactlyApproved` — в Core только `YamlDotNet`.
- [Факт] ADR-0020 (PROPOSED) вводит `World` — список именованных таблиц, один писатель на колонку, общий формат хеша.

## Решение
1. **Таблица на группу сущностей с общим числом строк.** Поле — плотный массив (`Column<T>`, `T` ∈ {`long`, `int`}; `Fx6` — как `Raw`, ADR-0003). Строка — плотный индекс `0..RowCount−1`.
2. **Фиксированное число строк.** `RowCount` задаётся при сборке мира из сценария и данных и в игре не меняется. Сущности с динамическим временем жизни получают ёмкость (`max_*`) и слоты; слот после освобождения не переиспользуется (стабильный id = индекс слота). Превышение ёмкости — состояние отказа команды (`DesignCapacity`), не рост таблицы.
3. **Связи** — индексы в колонках (`int`); обратные индексы и смежность графов — неизменяемые массивы, собранные при загрузке, либо колонки, если меняются в игре.
4. **Только Kernel-колонки хранят состояние.** Системы не держат изменяемого состояния вне таблиц, кроме `[Scratch]` (ADR-0013 п. 4).
5. **Стабильные строковые ID** — в данных модов, сохранениях (ADR-0013) и миграциях. Отображение ID → индекс строится один раз при загрузке в ordinal-порядке ID; в тике строки не ищутся по ID.
6. **Двойной буфер.** Системы читают `Current` (состояние t) и пишут `Next` (t+1); `Next` открывается copy-on-write (ADR-0017). Запись вне тика — только `Load`.
7. **ECS-фреймворк не используется.**
8. **Несколько таблиц** (провинции, регионы, акторы) — по ADR-0020 после его ACCEPTED. До этого в мире одна таблица.

## Рассмотренные альтернативы
| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **A** | **SoA-таблицы Kernel, фиксированные строки, слоты (выбран)** | плотная память, простой хеш и снимок (ADR-0013), детерминированный порядок | ёмкость надо задавать заранее; «широкая» таблица акторов в M0 |
| B | ECS (Arch, DefaultEcs, Friflo) | сильнее при множестве однородных сущностей | слабее на связях; порядок архетипов и хеш сложнее держать детерминированными; внешний пакет в Core |
| C | Динамический `RowCount` (добавление/удаление строк) | нет потолков ёмкости | меняет индексы и порядок merge; противоречит ADR-0013 п. 3 |
| D | Объекты-классы (AoS) | привычно | GC, нет простого снимка и хеша, легко спрятать состояние вне таблиц |

## Последствия
- Плюсы: хеш, снимок и COW делаются на уровне Kernel без знания домена; правило «нет состояния вне таблиц» проверяется тестом.
- Минусы: потолки ёмкости — параметры данных, их надо калибровать; пока мир — одна таблица, число колонок растёт как `акторы × слоты × поля` (M0: сотни колонок).
- Обязательно: каждая ёмкость (`max_*`) записана в данных с проверкой на худший сценарий; добавление типа колонки (`short`, `byte`) — только в Kernel и с правкой формата хеша (ADR-0017/0020).

## Открыто перед ACCEPTED (вопросы владельцу)
1. Принимать ADR-0005 сейчас как базу (одна таблица, слоты) и расширять ADR-0020, или принять их одним gate? [Предл.] Одним gate с ADR-0020: п. 8 и «широкая» таблица иначе устареют сразу.
2. Потолки слотов (`max_designs` и будущие): [Предл.] при исчерпании — отказ команды с причиной в `why_not`, без роста таблицы. Альтернатива — пересборка мира с большей ёмкостью при загрузке сохранения.
