# ADR-0016 — Бюджет тика

> После ACCEPTED текст не меняется. Изменение решения — новый ADR с `supersedes`.

Ревизия 3 (2026-11-17): после gate (`docs/reviews/adr-0016-critic.md`, `adr-0016-advocate.md`, `adr-0016-deepseek.md`) и решений владельца #270–#272. Вывод чисел и метод — `docs/architecture/notes/tick-benchmark-m0.md`.

## Контекст

- MS-M0 закрывается после замера тика (#267).
- Замер питает триггер языка RR-0001 §5. ADR-0001 пересматривается, только если производительности не хватает, но бюджета до сих пор не было.
- Владелец задал рамку (#269):
  - максимальная скорость — 1 игровой месяц/с;
  - ядру — половина этого времени, ≈ 500 мс на месяц;
  - полный масштаб — ~200 стран, ~200 регионов;
  - базовое железо — i7-11800H (8C/16T, 31 ГБ).
- Решения #270–#272 задают триггер языка, статистику бюджета и правило закрытия M0.

## Решение

### 1. Бюджет (обязательный)
- [Факт #269, #271] Время ядра на игровой месяц `T`: **p95 ≤ 500 мс и медиана ≤ 400 мс**.
- Условия: threads = 8, i7-11800H, условия замера по п. 5.
- t4 и прогон под синтетической фоновой нагрузкой клиента (2 потока) — справочные точки «слабая машина», они не обязательны.
- [Предп.] Насколько слабее машины укладываются в бюджет, этот ADR не утверждает.

**Полный масштаб.** ~200 акторов (стран), ~200 регионов, ~2000 узлов знания. **Провинции (#195, волна 3) сюда не входят.** Для них бюджет пересматривается новым ADR.

**Что входит в `T`.** Всё, что ядро делает за месяц в полном `ViewMode`:
- `Compute`/`Merge`/`Post` систем, включая инварианты и метрики фазы post (ADR-0006);
- копия и swap таблиц, планировщик, `StateHash`;
- снимок видов и применение команд.

Не входят: загрузка данных, сборка мира и метрические CSV-синки Lab.

### 2. Составляющие `T`
- `M_i` — прямой замер месяца `i` в точке (N = 200, узлы 2000, t8, полный `ViewMode`). Режим месячный: в срезе один непустой тик на месяц.
- `k` — цена одного дополнительного непустого тика по семантике #228: копия и хеш таблицы той же формы плюс снимок видов (разность `ViewMode` полный − Calibration).
- **Обязательный режим — дневной (#228):** `T_i = M_i + 29·k`. Месячный режим `M_i` записывается для справки.
- `K_d = 30·k` — Kernel + Session на месяц в дневном режиме.
- `S_i = M_i − k` — системы. **`S` — прямой замер, не экстраполяция.** Наклоны по сетке N и узлов только диагностируют.
- [Предп.] Месячный `S` — нижняя граница для #228: фиксированная цена вызова систем там умножится на 30.

### 3. Раздел бюджета (диагностический) [Предл.]
- Системы типа среза — **≤ 100 мс**;
- Kernel + Session (`K_d`) — **≤ 50 мс**;
- резерв — **350 мс**. Из резерва явно выделяется доля на классы изделий 2…20: `19 × (цена Products на один класс)` из профиля.

Раздел предварительный до E1. Его превышение — повод оптимизировать или пересмотреть раздел, **но не язык** (#270).

### 4. Чтение результата
`S` читается по p95 месяцев, `K_d` — по медиане.

| Исход | Условие | Действие |
|---|---|---|
| INVALID | `StateHash` в конце прогона различается для одного seed между threads 1/4/8/16 или между `ChunkSize` 1/8/32 (ADR-0002); или нарушены условия п. 5 | Исправить, повторить. M0 заблокирован (#272) |
| INCONCLUSIVE | Шум (п. 5) > 10% после одного повтора | Исправить харнесс или условия. M0 заблокирован |
| PASS | Бюджет п. 1 выполнен, `S ≤ 100`, `K_d ≤ 50` | M0 закрыт, ADR-0001 в силе |
| WARN | Бюджет п. 1 выполнен, но `S > 100` или `K_d > 50` | M0 закрыт (#272). Правило выхода ниже |
| WARN-K | Дополнительно `K_d > 150` | Kernel-ADR к #228 до кода #228: инкрементальный хеш, копия изменённых колонок, хеш не каждый день. M0 закрыт |
| FAIL-pending | Бюджет п. 1 нарушен | Один раунд оптимизации, затем повторный замер |
| FAIL | После раунда бюджет п. 1 всё ещё нарушен | M0 закрыт (#272). Маршрут — по тесту причины |

**Ожидаемый риск.** [Предп.] По собственному прогнозу записки PASS при `S ≤ 100` маловероятен. Ожидаемый исход — WARN.

**Один раунд оптимизации.** Одна TASK (developer) на top-3 горячих места по inclusive CPU из `dotnet-trace`. Timebox — [Предл.] 3 рабочие сессии. Golden-хеши не меняются. Затем повторный замер по тому же манифесту и протоколу.

**Выход из WARN и эскалация.** WARN открывает в следующей вехе раунд оптимизации.
- Если после него `S ≤ 100` и `K_d ≤ 50`, исход — PASS.
- Иначе до кода первой системы резерва (E1) обязателен ADR пересмотра раздела. В нём — оценки цены систем резерва по удельным ценам из EXP. Новый раздел обязан сохранить бюджет п. 1.
- Резерв не расходуется молча: каждая новая система заявляет удельную цену. Если измеренные `S + K_d` плюс заявленное больше 500, назначается gate.

**Тест причины** (пре-регистрируется; проверяется по порядку, первое совпадение задаёт маршрут FAIL):
1. Доля пауз GC (`GC.GetTotalPauseDuration()`) > 10% времени — **аллокации**: ADR переделки.
2. Наклон log-log по N или по узлам > 1,2 — **алгоритм**: ADR переделки.
3. `S(t1)/S(t8) < 4` — **параллелизм**: вопрос Kernel/ADR-0006.
4. `K_d > 150` — **Kernel** по #228: Kernel-ADR.
5. Иначе — **вычисления**: проверка языка ниже.

**Триггер языка (#270).** Пересмотр RR-0001 открывается (gate+research), только если выполнены оба условия:
- после раунда оптимизации `T` > 500 мс;
- Rust-порт горячего места (≤ 200 строк, тот же вход) по замеру быстрее в **≥ 2 раза**.

Если порт быстрее меньше чем в 2 раза, маршрут — ADR переделки.

### 5. Условия замера и шум
- Сборка Release; одна точная версия .NET 10 (runtime и SDK записываются); workstation concurrent GC (`DOTNET_gcServer=0`); TieredPGO по умолчанию.
- ОС — как установлена на i7, записывается.
- Питание от сети, профиль «производительность»; частота и температура записываются; один процесс на машине.
- `ChunkSize = 8` (25 чанков при N = 200).
- Прогрев — 24 месяца; замер — 120 месяцев; 5 процессов × 3 seed.
- Медиана — медиана 15 медиан процессов; p95 — по всем 1800 месяцам.
- **Шум** = (p90 − p10) / медиана по 15 медианам процессов; порог ≤ 10%. При троттлинге — один повтор.
- [Предп.] Числа .NET 10 для работы внутри Godot (`net8.0`, ADR-0001) оптимистичны. Точка `net8.0` снимается в Godot-spike после M0.

### 6. Аллокации
- В установившемся режиме (после прогрева) на полном масштабе: **≤ 1 МБ на месяц**, снимок видов включён [Предл.]; **0 сборок gen2 за 120 месяцев**.
- 0 Б в `Compute` каждой системы — цель для BDN `MemoryDiagnoser` (single-thread), если BDN появится. Правило переносится в `.claude/rules/csharp-core.md` отдельно.

### 7. Запись и вторичные ограничения
- EXP `kind: benchmark`. Правило п. 4 пре-регистрируется до прогона.
- Provenance — по `Provenance.cs` плюс условия п. 5.
- Записываются **удельные цены**: мкс на актор-месяц и на узел по каждой системе, `k` на колонку.
- Записываются пиковая память и дневной тик p99 (для справки).
- **Пропускная способность Lab** — второе, записываемое ограничение. Если кампания 1945–2100 (1860 месяцев) при `S(t1)` идёт дольше 10 мин [Предл.], массовые эксперименты Lab по умолчанию идут на уменьшенном масштабе (N ≤ 24), а прогонов полного масштаба — не больше 100 на эксперимент.

## Рассмотренные альтернативы
- 40 мс на месяц при скорости «год/с» — отклонено решением #269.
- Только 500 мс целиком, без раздела. Отклонено: тогда не видно, сколько остаётся системам резерва. Раздел оставлен, но диагностический (#270).
- FAIL по доле среза (`S > 300`) включает Rust — отклонено решением #270.
- Бюджет по среднему, без p95 — отклонено решением #271.
- Обязательная точка t4 или фоновая нагрузка — отклонено #271, только справка.
- Экстраполяция `S` по наклонам как основное чтение. Отклонено: точку (200, 2000) можно замерить прямо.
- Отложить бюджет до E1 — отклонено решением #267.

## Последствия
- Плюсы:
  - исход однозначен и пре-регистрирован;
  - смена языка требует замеренного выигрыша Rust;
  - любой валидный исход закрывает M0.
- Минусы:
  - [Предп.] замер среза — нижняя граница полной игры: нет систем резерва, парных O(N²) взаимодействий, `net8.0`;
  - клоны подграфа занижают ветвление и промахи кэша.
- Обязательно:
  - новые системы заявляют удельную цену;
  - Kernel-ADR к #228 укладывает `K_d` в 50 мс;
  - пропускная способность Lab записывается в каждом EXP полного масштаба.

## Проверка
- `lab bench` (Stopwatch в хосте, ADR-0008): прямой замер в точке (200, 2000, t8); сетка N 6/24/200 × узлы 180/2000 для наклонов; вариант со случайными перекрёстными рёбрами; потоки 1/4/8/16. Результат — EXP `kind: benchmark`.
- Проект BenchmarkDotNet создаётся, только если по Stopwatch `K_d > 5` мс (10% доли).
- CI: per-PR проверка аллокаций на тик при N = 24 и отсутствия gen2. Сравнение base/head на одном раннере в одном job; порог [Предл.] +25%, при превышении — повтор. Абсолютный бюджет проверяется только на i7: на каждой вехе вручную, записью EXP.
- Бюджет пустых тиков ADR-0006 в силе.

## Разногласия
Отклонено или изменено в этой ревизии, с причинами:
- **Critic 2 (вторая часть)**: судить о языке по `S(t1)` против 8 × 100 мс. Отклонено: решение #270 судит язык замеренным Rust-портом. Тест ускорения оставлен только для выбора маршрута.
- **Critic 5**: триггер против доли среза (300 мс). Снято решением #270: читается вся `S + K` против 500.
- **Critic 6**: ось классов изделий 1/5/20. Отклонено: класс зашит в `SliceWorld.ProductClass`, а ось требует правки Session. Вместо оси — явная доля резерва (п. 3).
- **Critic 10, Advocate 4**: обязательные t4 или фоновая нагрузка. Отклонено решением #271, это справка.
- **Critic 13**: точка `net8.0` в M0. Отклонено: нужен multi-target сборки. Вместо неё оговорка (п. 5) и замер в Godot-spike.
- **Critic 9**: «0 Б на систему» как правило ADR. Оставлено целью BDN, правило — в `csharp-core.md`.
- **Advocate 2**: обязательный дневной тик p99 ≤ 25 мс. Не обязателен: #271 задаёт только статистики месяца. p99 записывается.
- **Advocate 3**: основное чтение и при t1. Отклонено: t1 — справка и тест причины (#271).
- **Advocate 10**: порог памяти. Отложен до волны провинций, пока только запись.
- **DeepSeek**: бюджет кадра клиента — вне рамок ADR, клиента нет до конца M0. Доверительный интервал на экстраполяцию снят: `S` замеряется прямо.
