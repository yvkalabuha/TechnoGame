## Вопрос исследования

Как устроить пространство в 60 → 400–600 → 2000 узлов (#25; исходная постановка «1000–5000» устарела) поверх модели C из RR-0003 (дисциплины как запасы, узлы-открытия, слой применений)? Что нужно решить: секторы, типы узлов и рёбер, специализация институтов, ценность фундаментальной науки, «открытие ≠ производство» (интерфейс к RR-0006), бюджет узлов (лестница: срез ~60 → первая версия 400–600 → потолок 2000, #25), правило «у каждого узла есть функция», авторинг и валидатор, UI, стоимость тика, первая ступень после среза. Входы: CONCEPT_EXPANSION §7.1–7.5, 8.1, 9, 9.11; ANALYSIS §2, T8; урок пилота EXP-0001.

### 3. Типы узлов
| Тип | Что это | Вклад и цена | Допустимые эффекты (функция) |
|---|---|---|---|
| FND | фундаментальное открытие | вклад от `K_d`, финансирования, приборов (ускоритель, лаборатория) | рост `K_d` и φ дисциплины; новая дисциплина или клин; престиж; приток учёных; ≥2 исходящих `informs` |
| PRN | технологический принцип («можно сделать X на основе Y») | вклад; часто через `hidden` | открывает ENG; повышает веса направления |
| ENG | инженерное решение (схема, архитектура) | проект КБ/института (RR-0007), стоимость в инженеро-годах | параметр или компонент для конструкторов; `retrofit` (зависит от RR-0007) |
| PRC | производственный процесс | изучение = знание; **освоение** — в слое способности (RR-0006, ключ `site`) | право вести процесс (`known_processes`); выход годных считает `production_profile` (контракт §4.2); `complexity_tier` — метка |
| CMP | компонент/материал | нужен PRC | вход для ENG/APP и конструкторов; модификаторы параметров |
| APP | применение (класс изделий/инфраструктуры) | нужны ENG + CMP + PRC | новые категории в конструкторах, экономике, армии, обществе |

**Момент открытия задаёт поле `hazard`, а не тип** (#32; контракт §9.2; `mods/schemas/node.schema.json`) [Факт для набора значений; семантика — по спеке среза §3, сверять там]:
- `none` — детерминированно: узел открывается, когда накопленный вклад `prog` достиг порога.
- `hz` — после порога открывается с месячной вероятностью (hazard); разброс времени между seeds. В срезе: FND/PRN поколений G2–G4.
- `key` — то же, но для ключевых узлов цепочки (ТРД, сплав, ковка; метка ★ спеки), чья дисперсия калибруется по ориентиру #24.

[Предл.] FND/PRN **могут** иметь `none` (давно устоявшиеся основы; предоткрытые на старте узлы), но FND/PRN без `hz` — предупреждение валидатора: фундаментальные открытия по смыслу случайны. APP — только `none`; ENG/CMP/PRC — `none`, `hz` или `key`.

[Предл.] Цепочка CE §8.1 ложится на типы так: открытие = FND, принцип = PRN, инженерное решение = ENG, затем проектирование и испытания — это **процессы над изделием** (RR-0007, не узлы графа), производство = PRC + CMP, эксплуатация — это парк изделий (RR-0007, vintage capital). Значит, граф знаний кончается на APP. Изделия и парк — отдельные сущности, граф лишь их подпитывает.

### 4. Типы рёбер и грамматика
| Ребро | Семантика | Механика | Ограничения валидатора |
|---|---|---|---|
| `requires` | без A узел B невозможен | логическое И; для ИЛИ — `alt_group` | без циклов; ≤3 на узел [Предл.]; FND→FND только для явной логики |
| `informs(w)` | A облегчает B | −стоимость / +вероятность, сумма весов с убыванием отдачи | циклы допустимы; w ∈ (0,1] |
| `synergy` | B требует сочетания секторов | бонус к вероятности, только если `K` в каждом из ≥2 секторов выше порогов | у ≥30% узлов ENG/APP есть synergy или inputs из ≥2 макросекторов [Предл.] |
| `hidden(cond)` | ребро (или узел) не видно, пока не выполнено условие | 4 вида: *concealed* (порог K: «не знаешь, чего не знаешь»), *classified* (чужая секретная программа; раскрывает разведка), *conditional* (условие мира: дефицит нефти → веса синтетического топлива растут), *serendipity* (малый случайный шанс) | у каждого `hidden` есть `reveal`; serendipity — с детерминированным RNG |
| `alt_group` | альтернативные пути к одной функции | достаточно одного; другие узлы группы дешевеют | ≥2 члена; общая цель |
| `retrofit` | ENG/CMP/PRC улучшает уже выпускаемые изделия | модернизация без нового проекта (CE §8.1; детали — RR-0007) | цель — параметр изделия, а не узел |

Грамматика [Предл.]: APP не может быть `requires`-предком FND; `speculative` не может быть hard-предком `historical` (RR-0003); у PRC обязательны `complexity_tier`, `capability_req`, `cluster` и `discipline` (§5). Рёбра `uses_material` / `uses_energy` из RR-0003 сводятся к входам CMP/PRC.

[Предл.] Правило `hazard`: случайность открытия задаёт поле данных узла `hazard: none|hz|key`, а не тип. `hazard ≠ none` допустимо для FND, PRN, ENG, CMP, PRC; у APP только `none` (она собирается из ENG + CMP + PRC). Нарушение — ошибка загрузки валидатора. Основание: #32, контракт §9.2; код и `mods/core/nodes.yaml` уже так устроены (note, спор (a)).

### 5. «Открытие ≠ производство»: интерфейс к слою способности
Слои, ключи и API заданы контрактом (`LAYER_CONTRACT.md` §1, §5); здесь — только то, что относится к графу. Граф отвечает за **знание** (ключ `actor`), слой способности — за **умение** (ключ `site`).

```
# статические данные узла PRC (граф -> способность)
ProcessDef { id, complexity_tier: int,            # шкала RR-0006 §4.3; только метка
  cluster: ClusterId,                             # ОБЯЗАТЕЛЬНО: MET|CHEM|MECH|ELEC|AERO|NUC|ENER|BASE
  discipline: DisciplineId,                       # ОБЯЗАТЕЛЬНО: одна из ~34 дисциплин графа (для K_ind)
  capability_req: { dim -> tier },                # разреженно, в единицах tier; имена измерений — RR-0006
  key_dims, learning_half, energy_per_unit,       # поля способности, контракт §2
  inputs: [cmp_id | resource_id | energy], workforce: { category: amount },
  outputs: [cmp_id | app_id], test_infra_req? }
known_processes(actor) -> bitset<prc>             # пишет граф
```
Граф читает из слоя способности только (контракт §5): `production_profile(site, prc_set)` и `capability_tier(site, cluster)` — для режима цели и UI (§10); `discipline_volume(actor, d)` (для `K_ind`) и `world_lead(prc, actor)` — **чистые функции снимка в compute** (контракт §4.0, §4.3 A10), не post-фаза. Прежние `capability(actor|enterprise, dim)`, `operable(actor, prc)` и `cumulative_output` **удалены**: их заменяют `capability_tier`, `production_profile` и `proc_X[site,p]` (контракт §2).

- [Предл.] Знать PRC без нужной возможности = «есть чертежи, нет фабрики». Пути — рычаги контракта §6–7: учебная серия, оснастка, лицензия, `simplified_variant` (более лёгкий `prc_set`, в т.ч. старый процесс из той же `alt_group`).
- [Предл.] **Промышленность → наука (CE §14) — только через `K_ind[actor,d]`** (контракт §3, §4.3). Растёт от объёма выпуска PRC своей дисциплины при `yield ≥ 0.3` с убывающей отдачей и потолком `θ_ind·K_d` (≈ четверть научного запаса). Действует **только** как добавка к `K_d` в цене узлов ENG/PRC; на вероятность FND/PRN не влияет. Без выпуска в d забывается (`δ_ind`, за месяц). `K_d` от производства напрямую не растёт.
- **Валидатор `cluster`/`discipline`** [Предл.]: у каждого PRC оба поля заданы; `cluster` ∈ 8 кластеров RR-0006; `discipline` есть в списке дисциплин и принадлежит сектору узла или соседнему (иначе — предупреждение); каждое измерение в `capability_req` известно для этого `cluster` (каталог RR-0006); `complexity_tier` в шкале RR-0006 §4.3. Узел без `cluster` не компилируется.

### 6. Фундаментальная наука как самостоятельная ценность
[Предл.] FND даёт ценность четырьмя путями, и ни один не требует немедленного применения:
1. **Запас и скорость:** открытие поднимает `K_d` и показатель φ в `dA/dt = δ·L^λ·A^φ` (RR-0003 §5.2), то есть ускоряет всю дисциплину.
2. **Опцион:** раскрывает `concealed`-узлы и целые клинья (например, физика ядра → сектор S4). Пока они не раскрыты, игрок не видит, что может потерять.
3. **Люди:** престиж науки привлекает учёных и студентов (миграция знаний, связь с RR-0010) и улучшает качество институтов.
4. **Сотрудничество и диффузия:** открытые публикации ускоряют всех, но первооткрыватель получает лаг-преимущество и престиж. Засекречивание (RESTRICTED/CLOSED, ANALYSIS T6) замедляет и себя.

Приборы (ускоритель, большой телескоп, химическая лаборатория) — это объекты-институты, а не узлы графа. Они открывают доступ к классам FND и умножают вероятность их открытия.

### 7. Специализация институтов и школы
[Предл.] У института есть вектор специализации `s_d` (сумма 1) и **накапливаемый** запас школы `school_H[inst,d]` (контракт §2–3; с производственной культурой `culture_H` не обменивается). Выход по дисциплине `d`: `out_d = base · (s_d + ε) · (1 + k_school·school_H[inst,d])`, где `ε > 0` — «не закрывает другие области» (CE §7.5). Перелив: `0.1–0.3 · out` идёт в соседние по кругу дисциплины, а по `synergy`-хордам — в связанные дальние. `school_H` растёт только от вклада института (наука, не производство), убывает на `δ_s` за месяц при недофинансировании и переносится с людьми (эмиграция школ). В первом срезе `school_H` — FUTURE (контракт §10). Вся схема — **условная, после вердикта EXP-0002**.
- Против доминирования старта [Предп.]: (а) у `school_H` убывающая отдача и потолок; (б) скидка догоняющему — уже в спеке среза (`k_diff`, #190; отсылка к «преимуществам отсталости» по Гершенкрону в этой сессии не проверена), к `school_H` отношения не имеет; (в) сдвиг парадигмы (keystone) обнуляет часть преимущества старых школ в секторе.
- [Факт] Решение #192: собственный запас `school_H` у института — **решается после EXP-0002**. Новая гипотеза по `school_H` **не регистрируется**: вердикт по медленным запасам (HYP-0002/EXP-0002) определит, нужен ли `school_H` или хватит `bureau_exp`. До вердикта §7 — условная схема, P10a — EXPERIMENTAL, условно. Проверка перелива на абстрактном графе ~50 узлов (метрики EXP-0001) — возможный эксперимент **после** вердикта, а не до контента; скидка догоняющему (P10b) проверяется отдельно, без `school_H`.

- Экспорт в GraphML/DOT для ревью в Gephi/Cytoscape (RR-0003).

### 10. UI-навигация (высокий уровень)
- Масштабирование по смыслу: круг секторов (заливка — % освоения, полосы `K_d`) → клин дисциплины (кластеры-семейства) → узел.
- Поиск по имени, эффекту («что улучшает дальность самолёта»), тегу, году. Фильтры: тип, уровень, состояние (известно / доступно / изучается / освоено в производстве / известно о чужом), источник (своё / лицензия / разведка).
- **Режим цели**: игрок выбирает APP — граф показывает минимальный набор недостающих узлов и узкие места, включая PRC-разрыв («знание есть, возможностей нет»). Цепочку причин строит `why_not` (контракт §6); уровень кластера на site показывает `capability_tier(site, cluster)`. Это ответ на «альтернативные пути» и «автоматический анализ связей» (CE §7.2).
- Скрытые связи: «?»-заглушки с подсказкой о классе условия (порог дисциплины / разведка / событие) — без раскрытия содержимого.
- Управление: [Факт, #19] игрок задаёт требования, приоритеты, бюджет и выбирает варианты; может вмешиваться во флагманские проекты. [Предл.] Для графа это значит: игрок выбирает **направления и приоритеты** институтам (как в Alpha Centauri), узлы-цели — только для флагманских проектов; «режим цели» показывает путь, но не ставит узлы в очередь по одному. Рекомендация, а не решение: уровень детализации выбора в графе владелец не утверждал.

### 11. Производительность
[Предп.] Для первой версии: **≤ 30 акторов** × 400–600 узлов (сценарий 1945, #23) — нагрузка на порядок ниже расчёта ниже. Расчёт для **потолка**: 200 акторов × 2000 узлов (#25) → состояние в bitset (~50 КБ на все узлы) плюс Fx-прогресс только по фронтиру (50–150 узлов у актора). Наука идёт на месячной частоте (мультичастотность, RR-0002). В месяц: 200 × 150 × ~8 рёбер ≈ 2,4·10⁵ операций, плюс `K_d` 200 × 34 и диффузия 200² × 34 ≈ 1,4·10⁶ (или по сети контактов). Итого ≪ 1 мс на ядро в месяц, против бюджета 8–45 мс на день (ANALYSIS T4). Пересчёт фронтира — инкрементально при открытии узла. Скрытые условия проверяются событиями, а не каждый тик. Счётный RNG (CounterRng) — детерминизм и параллельность; ключ `entity(actor, node)` и его расширение (сейчас `actor·64 + node`) — по note (вопрос 8, п. 6). Счётчик `n` зарезервирован под serendipity (P6) и не занимается другими выборками.

[Факт, один вторичный источник migflug.com] патент Уиттла — январь 1930; He 178 — 27.08.1939; Gloster E.28/39 — май 1941. [Предп., не сверено] стендовые запуски 1937: Уиттл — апрель, фон Охайн — сентябрь по migflug.com; по памяти агента первый стенд фон Охайна (HeS 1, водородный) работал в марте 1937, а сентябрь — HeS 3 на жидком топливе. Источники расходятся, нужна сверка с первичными или энциклопедическим источником. Вывод для механики: между PRN и APP прошло ~10 лет. Узкие места были в материалах и финансировании, а не в идее — это хорошо ложится на PRC/CMP и `capability_req`. [Предп.] Названия конкретных сплавов не проверены.

**Дисперсия открытий в срезе (контракт §9.2, #32, #40).** [Предл.] В слоях способности и изделия случайности нет (#28), поэтому разброс между seeds даёт RNG знания. **На старте 1945 великие державы уже знают ТРД, сплав и ковку (#40)**: сами эти узлы (`s8.eng.turbojet`, `s5.cmp.heat_resistant_alloy`, `s6.prc.precision_blade_forging`) в игре не открываются. Случайное открытие распространяется на их **аналоги в поколениях G2–G4** (спека среза §1.3: область hazard — 11 ключевых ★ + 9 FND/PRN, `hazard: key|hz`).
- Узел с `hazard ≠ none` открывается с месячной вероятностью после накопления порога, а не детерминированно по сумме. Hazard — рациональная функция от вклада и `K_d` (без `exp`, контракт §4.5); RNG — CounterRng на отдельном потоке знания (ADR-0004/0005).
- Цель [Предп., калибрует Lab]: коэффициент вариации времени открытия hazard-узла G2–G4 при равных вложениях ≈ 0,3–0,5. Окно — **после 1945**, по поколениям спеки (G2 1947–55, G3 1955–65, G4 1965–75, окна [Предп.]), то есть порядка 3–5 лет на узел внутри окна поколения. Предки по цепочке тоже случайны, разброс складывается.
- Иллюстрация, не ориентир калибровки: [Предп., не сверено] одновременные открытия у соперников бывают — Уиттл и фон Охайн независимо подошли к стендовому ТРД в 1937 г. (даты расходятся, см. выше). Значит, одновременные открытия у соперников должны быть возможны, а не исключены; к окну 1947–1975 эти даты отношения не имеют.
- Lab: абляция «фиксированный seed потока знания» показывает вклад этого источника в разброс `tech_lead` (контракт §9.2).

## Риски
- Контент: даже 2000 узлов с источниками — это месяцы работы. Нужны семейства и AI-черновики, а валидатор обязателен (RISK-0001).
- Доминирование старта повторится, если специализация — множитель к капиталу без убывающей отдачи (урок EXP-0001).
- Историческая предопределённость: жёсткие окна превратят игру в «рельсы», слабые — дадут анахронизмы. Исторический прогон — только мягкое ограничение.
- Эксплойты: прямой «рывок» к цели через сумму `informs`, накопление бонусов специализации, фарм serendipity. Нужны убывающая отдача и потолки.
- UI-перегрузка при ~2000 узлах. Без режима цели и масштабирования по смыслу граф нечитаем.
- Интерфейс с RR-0006/0007 согласован контрактом (сейчас v2.4 r9). Остаётся риск, что RNG знания на hazard-узлах не даст разброса для ориентира #24 (контракт §9.2, #32).
- **Блокеры масштаба** (note `docs/architecture/notes/rr-0008-contract-disputes.md`, вопрос 8, п. 6) [Факт, по коду]: (1) ключ RNG `actor·64 + node`, `KnowledgeRng.MaxNodeNumber = 63` — ограничение на **номер** узла `number` (постоянный, не переиспользуется), а не на число узлов; номер больше 63 не загрузится; предложено `actor·2¹⁶ + node`. Смена ключа меняет выборки всех акторов кроме 0, то есть **эталон EXP-0002**. Срок — решение владельца: «до финального прогона EXP-0002 или сразу после с переснятием эталона». (2) линейный `RowOf` (`KnowledgeGraph`, `IndustryLayout`) — O(n²) на `why_not`; предложен плотный массив, хеши не меняются. Решение — задачи Orchestrator, не RR.
- Формат `id` (префикс-тип `s5.prc.name` или чистое имя + поля `type`/`sector`) — задача systems-architect до роста графа выше 63 узлов: от неё зависят переименования и ссылки модов.
- Каталог дисциплин (~34) и размер файлов (по дисциплинам) — не зафиксированы; влияет на загрузчик и конфликты при параллельной работе.

## Открытые вопросы

**Настоящие вопросы дизайна (владельцу):**
- Q3. Уровень выбора игрока в графе. [Факт, #19] гибрид задан. Варианты [Предл.]: **A** — только направления и приоритеты институтам, узлы-цели лишь для флагманских проектов; **B** — «закрепить узел»: игрок помечает целевой узел, и вес приоритетов вдоль пути растёт без жёсткой очереди (совместимо с #19, режим цели §10 остаётся подсказкой).
